# SOLID Design Principles in Python — A Hands-On Guide

---

## Why This Matters

Real-world projects have thousands of classes. Without structure, they become a tangled mess — tightly coupled, hard to debug, impossible to extend. A single bug takes days to find. A new feature breaks three existing ones.

SOLID design principles exist to prevent this. Follow them and your code stays clean, readable, and maintainable. They were introduced by computer scientist Robert C. Martin in 2000.

**SOLID** is an acronym:

- **S** — Single Responsibility Principle (SRP)
- **O** — Open/Closed Principle (OCP)
- **L** — Liskov Substitution Principle (LSP)
- **I** — Interface Segregation Principle (ISP)
- **D** — Dependency Inversion Principle (DIP)

This guide covers S, O, and L — with code examples and assignments after each.

---

## S — Single Responsibility Principle (SRP)

**Definition:** A class should have only one reason to change. It should do only one thing.

One class, one responsibility. All its methods and attributes should serve that single purpose.

A TV remote controls the TV. It doesn't also control the fridge and AC. The moment it does, it becomes complicated and a nightmare to maintain.

### The Problem

Consider an e-commerce `ShoppingCart` class:

### UML Diagram

                 ┌───────────────────────┐
                 │        Product        │
                 ├───────────────────────┤
                 │ + name : str          │
                 │ + price : float       │
                 ├───────────────────────┤
                 │ + __init__()          │
                 └──────────▲────────────┘
                            │
                            │ contains
                            │
                 ┌──────────┴────────────┐
                 │     ShoppingCart      │
                 ├───────────────────────┤
                 │ + products            │
                 ├───────────────────────┤
                 │ + add_product()       │
                 │ + get_products()      │
                 │ + calculate_total()   │
                 │ + print_invoice()     │
                 │ + save_to_db()        │
                 └───────────────────────┘

```python
class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price


class ShoppingCart:
    def __init__(self):
        self.products = []

    def add_product(self, product):
        self.products.append(product)

    def get_products(self):
        return self.products

    def calculate_total_price(self):
        total = 0
        for product in self.products:
            total += product.price
        return total

    def print_invoice(self):
        for product in self.products:
            print(f"{product.name}: {product.price}")
        print(f"Total: {self.calculate_total_price()}")

    def save_to_db(self):
        print("Saving shopping cart to database...")


# Usage
cart = ShoppingCart()
cart.add_product(Product("Laptop", 1500))
cart.add_product(Product("Mouse", 50))
cart.print_invoice()
cart.save_to_db()
```

This `ShoppingCart` class is doing three different things:
- Calculating total price
- Printing invoices
- Saving to database

This violates SRP. If the database logic changes, you must touch this class. If invoice formatting changes, same class. Multiple reasons to change = SRP violation.

### The Fix

Break it into focused classes, each with a single responsibility:

### UML Diagram

                 ┌───────────────────────┐
                 │        Product        │
                 ├───────────────────────┤
                 │ + name : str          │
                 │ + price : float       │
                 └──────────▲────────────┘
                            │
                            │ contains
                            │
                 ┌──────────┴────────────┐
                 │     ShoppingCart      │
                 ├───────────────────────┤
                 │ + products            │
                 ├───────────────────────┤
                 │ + add_product()       │
                 │ + get_products()      │
                 │ + calculate_total()   │
                 └───────┬───────┬───────┘
                         │       │
                         │       │
                    uses │       │ uses
                         │       │
                         ▼       ▼

      ┌──────────────────────┐    ┌──────────────────────┐
      │ InvoicePrinter       │    │ DBStorage            │
      ├──────────────────────┤    ├──────────────────────┤
      │ + cart              │    │ + cart              │
      ├──────────────────────┤    ├──────────────────────┤
      │ + print_invoice()   │    │ + save_to_db()      │
      └──────────────────────┘    └──────────────────────┘

```python
class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price


class ShoppingCart:
    def __init__(self):
        self.products = []

    def add_product(self, product):
        self.products.append(product)

    def get_products(self):
        return self.products

    def calculate_total_price(self):
        total = 0
        for product in self.products:
            total += product.price
        return total


class ShoppingCartInvoicePrinter:
    def __init__(self, cart: ShoppingCart):
        self.cart = cart

    def print_invoice(self):
        for product in self.cart.get_products():
            print(f"{product.name}: {product.price}")
        print(f"Total: {self.cart.calculate_total_price()}")


class ShoppingCartDBStorage:
    def __init__(self, cart: ShoppingCart):
        self.cart = cart

    def save_to_db(self):
        print("Saving shopping cart to database...")


# Usage
cart = ShoppingCart()
cart.add_product(Product("Laptop", 1500))
cart.add_product(Product("Mouse", 50))

printer = ShoppingCartInvoicePrinter(cart)
printer.print_invoice()

storage = ShoppingCartDBStorage(cart)
storage.save_to_db()
```

Now each class has exactly one reason to change. Database logic changes → only `ShoppingCartDBStorage`. Invoice formatting changes → only `ShoppingCartInvoicePrinter`.

> **Note:** SRP does NOT mean one method per class. A class can have many methods — as long as all of them serve the same single responsibility. `ShoppingCartDBStorage` could have five helper methods, all serving the purpose of database storage.

## O — Open/Closed Principle (OCP)

**Definition:** A class should be open for extension but closed for modification.

**Modification** = changing existing code. **Extension** = adding new features.

When adding a new feature, you should not go into existing, working classes and change their code. Instead, you extend the system by adding new classes.

### The Problem

Building on the previous example — the `ShoppingCartDBStorage` currently saves to a SQL database. Now you need to also support MongoDB and file storage.

The naive approach:

```python
class ShoppingCartDBStorage:
    def __init__(self, cart):
        self.cart = cart

    def save_to_sql(self):
        print("Saving shopping cart to SQL database...")

    def save_to_mongo(self):
        print("Saving shopping cart to MongoDB...")

    def save_to_file(self):
        print("Saving shopping cart to file...")
```

This violates OCP. To add a new feature (MongoDB support), you went into an existing class and added new methods. Every new storage type means touching this class again.

### The Fix

Introduce an abstraction (abstract base class). Each storage type becomes its own class that extends the abstraction. Existing classes are never touched.

### UML Diagram

                          ┌──────────────────────┐
                          │     Persistence      │
                          │    <<abstract>>      │
                          ├──────────────────────┤
                          │ + cart              │
                          ├──────────────────────┤
                          │ + save()            │
                          └──────────────────────┘
                                     ▲
                                     │
          ┌──────────────────────────┼──────────────────────────┐
          │                          │                          │
          │                          │                          │
          │                          │                          │
          │                          │                          │
          │                          │                          │
          ▼                          ▼                          ▼

 ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
 │ SQLPersistence   │    │ MongoPersistence │    │ FilePersistence  │
 ├──────────────────┤    ├──────────────────┤    ├──────────────────┤
 │ + save()         │    │ + save()         │    │ + save()         │
 └──────────────────┘    └──────────────────┘    └──────────────────┘

```python
from abc import ABC, abstractmethod


class Product:
    def __init__(self, name, price):
        self.name = name
        self.price = price


class ShoppingCart:
    def __init__(self):
        self.products = []

    def add_product(self, product):
        self.products.append(product)

    def get_products(self):
        return self.products

    def calculate_total_price(self):
        return sum(p.price for p in self.products)


class ShoppingCartInvoicePrinter:
    def __init__(self, cart: ShoppingCart):
        self.cart = cart

    def print_invoice(self):
        for product in self.cart.get_products():
            print(f"{product.name}: {product.price}")
        print(f"Total: {self.cart.calculate_total_price()}")


# Abstract base class — the "contract"
class Persistence(ABC):
    def __init__(self, cart: ShoppingCart):
        self.cart = cart

    @abstractmethod
    def save(self):
        pass


# Concrete implementations — extend, never modify the above
class SQLPersistence(Persistence):
    def save(self):
        print("Saving shopping cart to SQL database...")


class MongoPersistence(Persistence):
    def save(self):
        print("Saving shopping cart to MongoDB...")


class FilePersistence(Persistence):
    def save(self):
        print("Saving shopping cart to file...")


# Usage
cart = ShoppingCart()
cart.add_product(Product("Laptop", 1500))
cart.add_product(Product("Mouse", 50))

printer = ShoppingCartInvoicePrinter(cart)
printer.print_invoice()

storages = [
    SQLPersistence(cart),
    MongoPersistence(cart),
    FilePersistence(cart),
]

for storage in storages:
    storage.save()
```

Now if you need Cassandra support tomorrow, you create `CassandraPersistence(Persistence)` and implement `save()`. You never touch `SQLPersistence`, `MongoPersistence`, or any other existing class.

## L — Liskov Substitution Principle (LSP)

## Simple Definition

A child class should be able to replace its parent class without breaking the program.

In other words:

> If a piece of code works with the parent class, it should also work with any child class.

The child class can add new features, but it should not change or break the behavior that users expect from the parent class.

---

## Simple Example

Imagine we have a `Vehicle` class.

Every vehicle can:

- Start
- Stop
- Move

Now we create a child class called `Car`.

A car can still:

- Start
- Stop
- Move

And it can also do extra things:

- Open trunk
- Turn on AC

Since a `Car` can do everything a `Vehicle` can do, we can safely use a `Car` wherever a `Vehicle` is expected.

This follows the **Liskov Substitution Principle**.

---

### UML Diagram

                ┌────────────────────┐
                │      Vehicle       │
                ├────────────────────┤
                ├────────────────────┤
                │ + start()          │
                │ + move()           │
                │ + stop()           │
                └─────────▲──────────┘
                          │
                          │ inherits
                          │
                ┌─────────┴──────────┐
                │        Car         │
                ├────────────────────┤
                ├────────────────────┤
                │ + open_trunk()     │
                │ + turn_on_ac()     │
                └────────────────────┘

## Python Implementation

```python
class Vehicle:
    def start(self):
        print("Vehicle started")

    def move(self):
        print("Vehicle is moving")

    def stop(self):
        print("Vehicle stopped")


class Car(Vehicle):
    def open_trunk(self):
        print("Trunk opened")

    def turn_on_ac(self):
        print("AC turned on")


def drive_vehicle(vehicle: Vehicle):
    vehicle.start()
    vehicle.move()
    vehicle.stop()


# Parent object
vehicle = Vehicle()
drive_vehicle(vehicle)

print()

# Child object replacing parent
car = Car()
drive_vehicle(car)
```

### Output

```text
Vehicle started
Vehicle is moving
Vehicle stopped

Vehicle started
Vehicle is moving
Vehicle stopped
```

Notice that `drive_vehicle()` expects a `Vehicle`,
but it works perfectly when we pass a `Car`.

This is LSP.

# Example of LSP Violation

Suppose we create a child class that breaks the expected behavior.

### UML Diagram

                ┌────────────────────┐
                │      Vehicle       │
                ├────────────────────┤
                ├────────────────────┤
                │ + move()           │
                └─────────▲──────────┘
                          │
                          │ inherits
                          │
                ┌─────────┴──────────┐
                │   BrokenVehicle    │
                ├────────────────────┤
                ├────────────────────┤
                │ + move()           │
                └────────────────────┘

```python
class Vehicle:
    def move(self):
        print("Vehicle is moving")


class BrokenVehicle(Vehicle):
    def move(self):
        raise Exception("This vehicle cannot move")
```

Now code that expects a `Vehicle` will fail:

```python
def start_journey(vehicle: Vehicle):
    vehicle.move()


broken = BrokenVehicle()
start_journey(broken)
```

### Result

```text
Exception: This vehicle cannot move
```

The child class cannot properly replace the parent class.

This breaks the **Liskov Substitution Principle**.

### The Problem

A banking system. All accounts can deposit and withdraw:

### UML Diagram

                     ┌──────────────────────┐
                     │       Account        │
                     │     <<abstract>>     │
                     ├──────────────────────┤
                     ├──────────────────────┤
                     │ + deposit()          │
                     │ + withdraw()         │
                     └──────────▲───────────┘
                                │
        ┌───────────────────────┼───────────────────────┐
        │                       │                       │
        ▼                       ▼                       ▼

┌──────────────────┐ ┌──────────────────┐ ┌────────────────────┐
│ SavingsAccount   │ │ CurrentAccount   │ │ FixedTermAccount   │
├──────────────────┤ ├──────────────────┤ ├────────────────────┤
│ + balance        │ │ + balance        │ │ + balance          │
├──────────────────┤ ├──────────────────┤ ├────────────────────┤
│ + deposit()      │ │ + deposit()      │ │ + deposit()        │
│ + withdraw()     │ │ + withdraw()     │ │ + withdraw() ❌    │
└──────────────────┘ └──────────────────┘ └────────────────────┘


                ┌──────────────────────┐
                │      BankClient      │
                ├──────────────────────┤
                │ + accounts           │
                ├──────────────────────┤
                │ + process_transactions() │
                └──────────┬───────────┘
                           │
                           │ uses
                           ▼

                      Account

```python
from abc import ABC, abstractmethod


class Account(ABC):
    @abstractmethod
    def deposit(self, amount):
        pass

    @abstractmethod
    def withdraw(self, amount):
        pass


class SavingsAccount(Account):
    def __init__(self, balance=0):
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        print(f"Deposited {amount}")

    def withdraw(self, amount):
        if self.balance - amount < 0:
            print("Insufficient funds")
        else:
            self.balance -= amount
            print(f"Withdrawn {amount}")


class CurrentAccount(Account):
    def __init__(self, balance=0):
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        print(f"Deposited {amount}")

    def withdraw(self, amount):
        if self.balance - amount < 0:
            print("Insufficient funds")
        else:
            self.balance -= amount
            print(f"Withdrawn {amount}")


# Fixed Deposit — you cannot withdraw from it
class FixedTermAccount(Account):
    def __init__(self, balance=0):
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        print(f"Deposited {amount}")

    def withdraw(self, amount):
        raise Exception("Withdrawal not allowed in Fixed Term Account")


class BankClient:
    def __init__(self, accounts):
        self.accounts = accounts

    def process_transactions(self):
        for account in self.accounts:
            account.deposit(100)
            account.withdraw(50)  # This will EXPLODE for FixedTermAccount


# This breaks
client = BankClient([SavingsAccount(), CurrentAccount(), FixedTermAccount()])
client.process_transactions()
```

`FixedTermAccount` is substituted in place of `Account`, but it explodes when `withdraw()` is called. LSP is broken.

The bad fix — adding an `isinstance` check in the client — just trades one problem for another. Now the client is tightly coupled to every account type, and adding a new account type means modifying the client (OCP violation).

### The Fix

Rethink the hierarchy. `FixedTermAccount` was never truly an `Account` with both capabilities. Split the abstraction:

### UML Diagram

                    ┌────────────────────────┐
                    │ DepositOnlyAccount     │
                    │    <<abstract>>        │
                    ├────────────────────────┤
                    ├────────────────────────┤
                    │ + deposit()            │
                    └──────────▲─────────────┘
                               │
                               │
                    ┌──────────┴──────────┐
                    │ WithdrawableAccount │
                    │   <<abstract>>      │
                    ├─────────────────────┤
                    ├─────────────────────┤
                    │ + withdraw()        │
                    └──────────▲──────────┘
                               │
              ┌────────────────┼────────────────┐
              │                                 │
              ▼                                 ▼

 ┌────────────────────┐           ┌────────────────────┐
 │  SavingsAccount    │           │  CurrentAccount    │
 ├────────────────────┤           ├────────────────────┤
 │ + balance          │           │ + balance          │
 ├────────────────────┤           ├────────────────────┤
 │ + deposit()        │           │ + deposit()        │
 │ + withdraw()       │           │ + withdraw()       │
 └────────────────────┘           └────────────────────┘


            ┌────────────────────┐
            │ FixedTermAccount   │
            ├────────────────────┤
            │ + balance          │
            ├────────────────────┤
            │ + deposit()        │
            └──────────▲─────────┘
                       │
                       │ inherits
                       │
                DepositOnlyAccount


           ┌─────────────────────────────┐
           │         BankClient          │
           ├─────────────────────────────┤
           │ + withdrawable_accounts     │
           │ + deposit_only_accounts     │
           ├─────────────────────────────┤
           │ + process_transactions()    │
           └─────────────┬───────────────┘
                         │
            ┌────────────┴────────────┐
            │                         │
            ▼                         ▼

  WithdrawableAccount      DepositOnlyAccount

```python
from abc import ABC, abstractmethod


class DepositOnlyAccount(ABC):
    @abstractmethod
    def deposit(self, amount):
        pass


class WithdrawableAccount(DepositOnlyAccount):
    @abstractmethod
    def withdraw(self, amount):
        pass


class SavingsAccount(WithdrawableAccount):
    def __init__(self, balance=0):
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        print(f"Deposited {amount}")

    def withdraw(self, amount):
        if self.balance - amount < 0:
            print("Insufficient funds")
        else:
            self.balance -= amount
            print(f"Withdrawn {amount}")


class CurrentAccount(WithdrawableAccount):
    def __init__(self, balance=0):
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        print(f"Deposited {amount}")

    def withdraw(self, amount):
        if self.balance - amount < 0:
            print("Insufficient funds")
        else:
            self.balance -= amount
            print(f"Withdrawn {amount}")


class FixedTermAccount(DepositOnlyAccount):
    def __init__(self, balance=0):
        self.balance = balance

    def deposit(self, amount):
        self.balance += amount
        print(f"Deposited {amount}")


class BankClient:
    def __init__(self, withdrawable_accounts, deposit_only_accounts):
        self.withdrawable_accounts = withdrawable_accounts
        self.deposit_only_accounts = deposit_only_accounts

    def process_transactions(self):
        for account in self.withdrawable_accounts:
            account.deposit(100)
            account.withdraw(50)

        for account in self.deposit_only_accounts:
            account.deposit(100)


# Clean, no exceptions
client = BankClient(
    withdrawable_accounts=[SavingsAccount(), CurrentAccount()],
    deposit_only_accounts=[FixedTermAccount()]
)
client.process_transactions()
```

The client now works with two clear interfaces. It never needs to know what specific account type it's dealing with. LSP holds — every subclass is fully substitutable for its parent without surprises.
