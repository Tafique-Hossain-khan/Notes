# Singleton Design Pattern in Python

Welcome back to the LLD series. Today's topic: the **Singleton Design Pattern** — the easiest design pattern to implement, the most basic one, and at the same time, one of the most heavily used patterns, whether in LLD interviews or real-world applications. It also has some disadvantages, which we'll cover.

We'll first implement it from scratch, then study its advantages, disadvantages, and real-world usage.

---

## 1. What is a Singleton?

A Singleton is a special kind of class. Imagine a class whose **only one object (instance)** can ever be created. If you try to create another instance, it returns the **same first instance** back to you.

In short: a class whose multiple objects cannot exist. Implementing such a class is called the Singleton Design Pattern.

---

## 2. Understanding Object Creation (Background Concepts)

Before implementing, let's understand what happens **under the hood** when an object is created.

### Two Types of Memory

- **Stack Memory**: Stores all primitive data types (int, char, bool, etc.) declared inside a class/function.
- **Heap Memory**: Stores all non-primitive data types — i.e., objects of custom classes.

So when you write:

```python
a = A()
```

An object of class `A` gets created in **heap memory**, and a reference (pointer/variable) `a` sits in **stack memory** pointing to that heap object.

### What Happens When You Call the Constructor

1. A space gets reserved in heap memory — the size depends on the class's size (sum of sizes of all its data types).
2. The constructor of the class is called. If you haven't written one yourself, the language (Python, C++, Java) provides a **default constructor**.
3. The constructor's job is to **instantiate** the object — i.e., assign initial/default values to its fields.

For example, if class `A` has `int x` and `char y`, the default constructor might initialize `x = 0` and `y = ''`.

4. Finally, the reference to this heap object is assigned to the variable in stack memory.

### The Core Problem

If we write:

```python
a1 = A()
a2 = A()
a3 = A()
```

Each line creates a **new object** in heap memory. So how do we **restrict** a class so that:
- Either no object can be created freely, OR
- Only **one** object can ever be created, and any further "creation attempts" just return that same first object?

## 4. The Problem: The Constructor is Public

The problem is: every time we use the class name followed by `()`, a new object gets created — because the **constructor is public**, anyone can call it.

### The Idea: Make the Constructor "Private"

We do something interesting: make this "constructor" inaccessible from outside the class, similar to how in encapsulation we make data variables private and provide **getters/setters** to access them.

> **Note on Python specifics:** In C++/Java, you can mark a constructor `private`, and trying to call `new Singleton()` from outside gives a compiler error: *"Singleton constructor is inaccessible"*. 
>
> Python does not have true "private" access modifiers enforced by the language — but we replicate this concept using **`__new__`** to control instance creation, and by convention using a single/double underscore prefix to signal "do not call this directly".

So:
- We control object creation so the constructor cannot be freely called from outside.
- But we **do want to allow ONE object** to be created. After that, further "creation attempts" should just return the first object.

## 5. Providing a Public "Get Instance" Method

Since the raw constructor call shouldn't be allowed to freely create new objects, we provide a **public method** — let's call it `get_instance` — which will:
- Return the instance of the Singleton class.
- Be the **only** sanctioned way to obtain the object.

### Why Must This Method Be Static (Class-Level)?

To call a normal method, you need an object first (e.g., `s1.get_instance()`). But we don't have an object yet — that's the whole problem! 

So this method must belong to the **class itself**, not to any object. In Python, this means using a **`classmethod`** (or in some designs, `staticmethod`).

- A classmethod/staticmethod belongs to the class.
- It's called using the class name: `Singleton.get_instance()`.
- It's the **same** for every "object" — i.e., shared behavior at the class level.

## 6. Introducing the Static Instance Variable

We still create multiple objects because `get_instance` is doing exactly what the constructor was doing — nothing has changed yet.

We need **one more variable** — let's call it `instance` — that:
- Holds the **single object** of the Singleton class once created.
- Is checked by `get_instance` every time it's called:
  - If `instance` is `None` (not yet created) → create a new object, store it in `instance`, return it.
  - If `instance` is **not** `None` (already created) → just return the existing `instance`.

This variable must also be at the **class level** (shared across all calls), so it's declared as a **class attribute**.

### Full Working Singleton (Basic Version)

```python
class Singleton:

    instance = None  # class-level variable holding the single instance

    def __init__(self):
        print("Singleton constructor called, new object created")

    @staticmethod
    def get_instance():
        if Singleton.instance is None:
            Singleton.instance = Singleton()
        return Singleton.instance
```

Usage:

```python
s1 = Singleton.get_instance()
s2 = Singleton.get_instance()

print(s1 is s2)
```

### Step-by-Step Trace

1. `s1 = Singleton.get_instance()` is called.
2. Checks: is `Singleton.instance` equal to `None`? **Yes** (no object created yet).
3. So it creates a new object: `Singleton.instance = Singleton()`. This calls `__init__`, printing the message **once**.
4. `Singleton.instance` is returned and assigned to `s1`.
5. `s2 = Singleton.get_instance()` is called.
6. Checks: is `Singleton.instance` equal to `None`? **No** (already created in step 3).
7. So it skips the creation step entirely — the constructor is **NOT** called this time.
8. The existing `Singleton.instance` is returned directly and assigned to `s2`.
9. `print(s1 is s2)` → prints `True`.

### Expected Output

```
Singleton constructor called, new object created
True
```

The constructor message prints **only once** (not twice), and `s1 is s2` is `True`.

2. Added a class-level `instance` variable that holds the single created instance (or `None` if not yet created).

   - Returns the existing instance if already created.

## 8. Making the Class Thread-Safe

The Singleton we built above works correctly in a **single-threaded** environment. But it is **NOT thread-safe**.

### The Problem in a Multi-Threaded Environment

Imagine multiple threads (`T1`, `T2`) running in parallel (e.g., on different CPU cores), and both call `get_instance()` at almost the same time:

- Both `T1` and `T2` check `if instance is None` **simultaneously**.
- Since `instance` is still `None` for both, **both** threads enter the `if` block.
- **Both** threads create their own new object.
- Result: **two different Singleton objects exist** — the entire point of Singleton is broken!

We want: no matter how many threads call `get_instance()`, they should all share **the same one** object.

### Solution: Locks

To fix this, we introduce a **lock** (similar to a mutex in C++). 

- **Locking** means: only **one thread at a time** can enter a particular section of code (called the **critical section**).
- That thread executes the section, and when it exits, it **unlocks**, allowing another thread to enter.

In Python, we use `threading.Lock`.

### Naive Thread-Safe Version (Lock the Whole Method)

```python
import threading

class Singleton:

    instance = None
    lock = threading.Lock()  # lock for thread safety

    def __init__(self):
        print("Singleton constructor called, new object created")

    @staticmethod
    def get_instance():
        with Singleton.lock:  # lock the entire critical section
            if Singleton.instance is None:
                Singleton.instance = Singleton()
            return Singleton.instance
```

### Trace

- `T1` calls `get_instance()`. It acquires the lock and enters.
- `T2` calls `get_instance()` at the same time, but it must **wait** because `T1` holds the lock.
- `T1` checks `instance is None` → True → creates a new object → assigns it to `instance` → returns it → releases the lock.
- `T2` now acquires the lock and enters.
- `T2` checks `instance is None` → **False** (because `T1` already created it) → skips creation → returns the existing `instance`.
- `T2` releases the lock.

This is **thread-safe**. Constructor only called once. `s1 is s2` → `True`.

## 9. The Problem With Always Locking

Locking/unlocking is an **expensive operation** — it consumes resources and holds up threads. We want to **avoid locking** as much as possible, and only lock when truly necessary.

### The Issue With the Naive Approach

In the version above, we lock **every single time** `get_instance()` is called — even after the instance has already been created and all future calls just need to return the existing instance. That's wasteful.

### Better Approach: Check Before Locking

- **First**, check (without a lock): is `instance` already `None`?
  - If **NOT** `None` → just return the existing `instance` immediately. No lock needed — this is completely safe because we're not creating anything new.
  - If `instance` **IS** `None` → only **then** acquire the lock, because we might need to create a new object, and we must prevent multiple threads from creating multiple objects.

## 10. Double-Checked Locking

If we naively just move the lock inside the `if instance is None:` check, we introduce a **new bug**. Let's understand why, step by step.

### The Buggy "Single Check" Version

```python
@staticmethod
def get_instance():
    if Singleton.instance is None:  # check 1 (no lock yet)
        with Singleton.lock:
            Singleton.instance = Singleton()  # BUG: created unconditionally inside lock
    return Singleton.instance
```

### Why This Is Still Broken

- Suppose `instance` is `None` (first time ever).
- `T1` and `T2` both execute the **first check** (`if instance is None`) at the same time.
- For **both** threads, this condition is **True** — so **both** enter this outer `if` block.
- Now both `T1` and `T2` want to acquire the lock.
- Say `T1` gets the lock first. It enters, creates a new object, assigns it to `instance`, returns it, and **releases the lock**.
- The moment the lock is released, `T2` acquires it.
- **But `T2` never re-checked whether `instance` is still `None`!** It only checked once, at the top, before either thread had created anything.
- So `T2` **also** creates a brand-new object and overwrites `instance`.

Result: **two objects were created** — the Singleton concept is broken again, even with a lock in place.

### The Fix: Check Again, Inside the Lock

We need to check the condition **twice**:
1. **Outside the lock** — to avoid acquiring the lock unnecessarily on every call (performance optimization).
2. **Inside the lock** — to ensure that, after acquiring the lock, the instance still wasn't created by another thread while we were waiting.

This technique is called **Double-Checked Locking**.

```python
import threading

class Singleton:

    instance = None
    lock = threading.Lock()

    def __init__(self):
        print("Singleton constructor called, new object created")

    @staticmethod
    def get_instance():
        if Singleton.instance is None:          # check 1: avoid locking if already created
            with Singleton.lock:
                if Singleton.instance is None:   # check 2: avoid double creation
                    Singleton.instance = Singleton()
        return Singleton.instance
```

### Why Check 2 Is Needed (Recap of Reasoning)

Multiple threads **can** enter past **check 1** simultaneously (since `instance` is `None` for all of them at that point). But they **cannot** all enter past **check 2**, because check 2 is **inside** the lock — only one thread can be inside the lock's block at a time, and by the time the second thread gets the lock, the first thread has already set `instance`, so check 2 will be `False` for it.

## 11. Eager Initialization

There's a much simpler approach that needs **no locks at all** — neither single nor double. It's called **Eager Initialization**.

### The Idea

Instead of creating the instance **lazily** (only when `get_instance` is first called), we create it **immediately**, at the time the class-level variable is declared/initialized.

```python
class Singleton:

    instance = Singleton()  # NOTE: this exact line won't work directly in Python — see assignment below

    def __init__(self):
        print("Singleton constructor called, new object created")

    @staticmethod
    def get_instance():
        return Singleton.instance
```

### What This Means

- Before `main` (or any function) even runs, a Singleton-type object is **already created** in heap memory.
- Now, no matter how many times `get_instance()` is called, it always returns the **same** instance that was created at class-definition time.

### Advantage

We don't need any `if/else` logic at all (`if instance is None: create else: return instance`). We **know** `instance` can never be `None`, because it was already given an object at initialization time. This makes `get_instance` extremely simple — it just returns `instance`.

### Disadvantage

Imagine the Singleton class is a very **expensive** object to create — it consumes a lot of memory/resources. With eager initialization, this object gets created **before the main function even runs** (i.e., before the application even starts properly) — regardless of whether it's ever actually used.

If that object's methods are **never called** during the program's execution, you've **wasted memory/resources** creating something that was never needed.

> **Eager** = "do it immediately, right away."

This approach is practical **only if** the Singleton object is **lightweight** — not very memory-intensive. It's not used very often in practice for this reason.

## 12. Conclusion (What We Built)

To build the Singleton Design Pattern, we did the following:

1. Conceptually restricted direct/free object creation (the "private constructor" idea).
2. Created a class-level **static instance** variable that holds the single instance (initially `None` in the lazy approach, or pre-created in the eager approach).
3. Provided a `get_instance` method that:
   - Returns the existing instance if one was already created.
   - Otherwise, creates it once, stores it, and returns it.
4. Optionally added **thread safety** using locks — either a simple lock, or better, **double-checked locking**, to avoid unnecessary locking overhead.
5. As an alternative, used **eager initialization** to avoid locks entirely — at the cost of creating the object upfront regardless of whether it's used.

## 13. Practical Use Cases of Singleton

Now let's talk about **where** Singleton is actually used in real life.

### 1. Logging System

In any application, we write **logs** — to track what's happening (which API call came in, what request/response looks like, etc.), similar to using `print` statements while debugging.

We want our **entire application** to print logs through a **single object/instance**.

**Why?** Imagine a banking system. If the logging system creates a **new object every time** some service needs to log something:

- A **Payment Service** asks the logger: "give me an object" → gets a new object → logs through it.
- A **Notification Service** asks the logger: "give me an object" → gets **another new** object → logs through it.

**Problems this causes:**
- Too many objects floating around in memory, all doing the same job — unnecessary memory usage.
- Logs from different objects writing to a file may get printed in a jumbled/out-of-order manner, because we don't know which object is writing where.

**Solution:** Have **one single instance** — say `log` — that holds the logger's instance. This **one instance** is shared across **all services**. Whatever method (e.g., `get_log` or `create_log`) is needed, it's called through this single shared object.

> *(Note: the video mentions that a Factory Design Pattern might be used inside the logger to "give an object" — that's a separate pattern, just mentioned as an aside here.)*

### 2. Database Connection

Establishing a database connection is a **very expensive operation** — it consumes a lot of memory and resources.

**Problem without Singleton:** If the Database Connection class is not a Singleton, every time the application needs a DB connection (e.g., for a new user request), it creates a **brand new instance**. Over time, this massively increases memory usage — and that memory is essentially **wasted**, because we don't need so many separate connection instances.

**Solution:** We need **one instance** that is **shared across the entire application**.

### 3. Configuration Manager

Applications have many **configuration files** that all services need to access — for example, an **API key** used for authentication, stored in some config file.

**Problem without Singleton:** If every service holds its **own separate object** of the Configuration Manager, then each service could potentially **modify** that object's data (like the API key) independently — leading to inconsistent configuration values across the application.

**Solution:** We want a **single source of truth**. To ensure all services see and use the **same** configuration data, the Configuration Manager must be a Singleton.

## 14. Where NOT to Use Singleton

Singleton has its own bottlenecks. Here's when to **avoid** it:

### 1. When You Already Know You Need Multiple Instances

If you already know a class needs **multiple instances by design**, never force it into a Singleton.

**Example:** A game with multiple players who interact with each other. Each player is a **separate object**. You would never want all players to share a single instance/session.

### 2. Thread-Safety Complications

Dealing with Singletons in a multi-threaded environment adds complexity to your multi-threading code. This makes:
- Writing the multi-threaded code itself more complicated.
- Writing **unit tests** for that code more complicated.

### General Guidance

Avoid Singleton **unless** you are clear that it actually helps — for example:
- It will **save memory** (one instance instead of many).
- It maintains a **single source of truth**.

In such cases, Singleton becomes very useful.
