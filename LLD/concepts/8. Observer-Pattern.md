# Observer Design Pattern in Python

Welcome back to the LLD series. Today we're starting a new design pattern called the **Observer Design Pattern**.

You've subscribed to a lot of YouTube channels. When those channels upload a new video, you get a notification. How does this system work? How does your YouTube account and the channel's account interact and communicate when this happens? This is exactly what the Observer Design Pattern is about.

This pattern solves a very specific problem: suppose there are two objects, and whenever **one object changes**, the **other objects want to know** when it changed, or what its value became after the change. And whenever that object changes, it wants to **communicate its new value** to all the objects that want to know about it.

We'll understand this through an example, UML diagrams, code, and then look at where else this pattern can be used.

---

## 1. Setting Up the Scenario

In the Observer Design Pattern, we have **one object**. Let's call it `OBJ1`. There are many other objects that want to know when the internal state of `OBJ1` changes.

Take the YouTube example: suppose `OBJ1` is a YouTube channel you've subscribed to. There are many accounts — Account 1, Account 2, Account 3, Account 4, and so on — that have subscribed to this channel. Let's say one of them is **your** account.

After subscribing, whenever this YouTube channel (i.e., `OBJ1`) uploads a new video, **you** get a notification. In fact, **everyone** who has subscribed gets a notification: "A new video is uploaded."

How does this happen? Whenever this object (`OBJ1`) changes its internal state — goes from State 1 → State 2 → State 3, and so on — its job is to **notify all the objects** that are waiting for the state change.

---

## 2. The Polling Technique (The Bad Approach)

Before understanding the Observer pattern's actual solution, let's understand the technique we'd use **without** it — the **Polling Technique**.

### Setting Up Terminology

We have `OBJ1` and (for now, just one) `OBJ2`, which wants to know about `OBJ1`'s state. (In reality, there could be many objects — `OBJ2`, `OBJ3`, `OBJ4`, `OBJ5` — that want to know `OBJ1`'s state.)

Calling them `OBJ1` and `OBJ2` repeatedly is confusing. So:
- The object whose state we want to know about → **Subject** → also called **Observable** ("something that can be observed").
- The object that wants to know → **Observer** ("the one that is actually observing").

There can be **many Observers** for **one Observable** — a **one-to-many** relationship between Observable and Observer.

### What Polling Means

In polling, the **Observer goes and asks the Observable**: "Has your value changed?"

But when would it ask this? We have **no idea** when a YouTube channel is going to upload a new video. So would you keep asking the channel: "Is there a new video? Is there a new video? Is there a new video?" — at what frequency? Every second? Every millisecond?

This means the Observer keeps sending repeated requests: "Have you changed? Have you changed?" — and every time the reply is "No, no, no, no" — until finally one time the reply is "Yes, my value has changed, you can read it now."

This concept is **terrible** — extremely time-consuming. The Observer is repeatedly asking "Have your value changed?" and we'd have to figure out at what frequency it should keep asking.

## 3. The Pushing Technique (The Real Solution)

Rather than polling, we shift to **pushing**. This is the entire Observer pattern: instead of the Observer repeatedly asking, the **Observable** should take the **responsibility** of telling the Observers whenever it changes.

So: whenever the Observable's state changes, the Observable will send a request to all the Observers saying: **"My state has changed. You can read the new value now."**

### How This Works Conceptually

Take the YouTube example again — one Observable (the channel), and multiple Observers (the subscriber accounts).

**Subscribing** means: the YouTube channel becomes **aware** of these subscribers — that they exist. Only then can it update them when its value changes.

So internally, this Observable (the channel/object) maintains some data structure — could be a list, a map, a set, whatever internal implementation we choose — that holds references to all the Observers (`O1`, `O2`, `O3`, `O4`) who have subscribed to it.

1. **Point 1**: Subscribers subscribe → the Observable becomes aware of all of them.
2. **Point 2**: Whenever the Observable's internal state changes (in our example, a new video is uploaded), the Observable will **update all of them** — telling each one "my value has changed."

This is the entire concept of the Observer Design Pattern.

## 4. A Note on Naming Convention: Interfaces vs Abstract Classes

Before drawing the UML, there's a naming convention to discuss.

So far in this series, whenever we had an abstract class (a class where all methods are virtual/abstract), we just wrote "Abstract" on top of it in diagrams. 

In C++, a "pure abstract class" (all methods virtual) is called an **interface** in other languages, and even in C++ we can refer to it as a **contract** — a contract that allows a client and a concrete class to interact with each other.

**The convention**: any pure abstract class (all methods virtual) gets prefixed with **`I`** — e.g., if the class is named `Channel`, the pure-abstract version is called `IChannel`. The `I` tells us: "this is a pure abstract class — a contract. Any concrete class that inherits/overrides this must implement all its methods."

> **Python note :** In Python, we represent this "interface" using **Abstract Base Classes** (`abc.ABC` with `@abstractmethod`). The naming convention `IObservable`, `IObserver`, `IChannel`, `ISubscriber` will be used as class names directly.

We'll use this `I` convention throughout — for `IObservable`, `IObserver`, `IChannel`, `ISubscriber`, etc.

## 5. UML Design — IObservable and IObserver

### IObservable (the thing being observed)

We create `IObservable` — a pure abstract class ("something that can be observed"). It has the following methods:

1. **`add`** — Corresponds to the "subscribe" action. Takes a parameter of type `IObserver` (let's call it `o`) and adds it to an internal list/map/whatever collection we choose.

2. **`remove`** — Same idea, but removes the given `IObserver` (`o`) from that list. This corresponds to "unsubscribe" in the YouTube analogy.

3. **`notify`** — The **most important method** an Observable must have. It loops through the entire collection of Observers and, one by one, calls each Observer's `update` method to tell it "my value has changed."

### IObserver (the thing observing)

We create `IObserver` — also a pure abstract class. It has:

1. **`update`** — Called by `notify`. This is how the Observer "updates itself" — i.e., whenever the Observable changes, the Observer updates itself saying "I've received a new value."

   For example: when a YouTube account (as a subscriber) learns a new video has been uploaded, it "updates itself" — meaning it can now go look at that video / its title / whatever it wants to do.

### Relationship

There's a **one-to-many** relationship: `IObservable` ←→ `IObserver` (many Observers can observe one Observable).

## 6. Concrete Classes — ConcreteObservable and ConcreteObserver

Now we create the concrete classes: `ConcreteObservable` and `ConcreteObserver`. Their job is to **override** all the methods defined in the interfaces (`IObservable` / `IObserver`).

### ConcreteObservable

- Overrides `add`, `remove`, and `notify`.
- It maintains a list of all `IObserver`s that have subscribed to it — say a `Vector<IObserver>` called `list` (could just as well be a map or a set; internal implementation choice).

**`add`**: Takes an observer `o` and adds it to this `list`.

**`remove`**: Takes an observer `o` and removes it from this `list`. (From the YouTube perspective, this is "unsubscribe" — once you unsubscribe, you stop getting recommendations/notifications for new videos.)

**`notify`**: Loops through `list`. For each Observer in the list, it gets every Observer and calls **that Observer's `update` method** — telling it "my value has changed."

### ConcreteObserver

When `notify` calls `update` on a Concrete Observer — **no parameter is needed** for this call. Why?

Because the Concrete Observer needs to know **whose** value changed — i.e., **which** Observable it's observing. So we pass a **`ConcreteObservable` instance** into the `ConcreteObserver` — it **holds a reference/instance** of the `ConcreteObservable` (let's call it `ob`).

### An Important Design Note: Concrete-to-Concrete Relationship

Normally in system design, relationships should be drawn between **abstract classes**, not concrete classes. But in the Observer pattern, we do something different: `ConcreteObserver` **has-a** `ConcreteObservable` — a relationship between two **concrete** classes.

**Why?** Because as soon as `update` is called, the Observer already knows: "I need to go read the value **from this specific Observable**." We'll see exactly how next.

### How `update` is Implemented

Whenever `notify` calls `update` on the Observer, inside `update` there's logic like: "go to the Observable I am observing, and call its `get_value` method to fetch whatever new value I need."

- This `get_value` method's name/behavior depends on the use case (it's not a fixed standard).
- In the YouTube example, this would be something like `get_new_video` or `get_video_data`.

The `ConcreteObserver`'s `update` method calls `concrete_observable.get_video_data()` (or similar), reads the new value, and does whatever it wants with it.

## 7. Standard Definition of Observer Design Pattern

> **Define a one-to-many relationship between objects so that when one object changes state, all of its dependents are notified.**

This is exactly what we did:
- A one-to-many relationship: one Observable, many Observers.
- Whenever the Observable changes its state, the Observers get to know — they are **notified**.
- The dependents are **notified and updated automatically**. We call their `update` method, and `update` reads the value and updates itself.

That's the whole Observer Design Pattern.

## 8. The YouTube Example — UML Design

Now let's build the full YouTube example.

### IObservable → IChannel

What are we observing? A **channel** that uploads new videos. So we call it `IChannel` — this is our Observable.

### IObserver → ISubscriber

What is `IChannel` being observed by? **Subscribers** — accounts that have subscribed to our YouTube channel. So we call it `ISubscriber` — this is our Observer.

There's a **one-to-many** relationship between `IChannel` and `ISubscriber`, drawn the same way as before.

### Methods on IChannel

`IChannel` has: `subscribe`, `unsubscribe`, `notify_subscribers`.

- **`subscribe`** ↔ corresponds to `add`.
- **`unsubscribe`** ↔ corresponds to `remove`.
- **`notify_subscribers`** ↔ corresponds to `notify` — stays the same.

### Methods on ISubscriber

`ISubscriber` has exactly one method: **`update`**.

### Why `IChannel` Doesn't Have `get_video` / `get_description` Methods

We **don't** put a `get_video` or `get_description` method on `IChannel` itself. Why? Because `IChannel` is an **interface** — and we want **scalability** and **reusability**. We don't want to lock this interface into being specifically a "video channel." 

We want to be able to:
- Override/inherit this with a `Channel` for videos this time.
- Inherit it some other way next time (different concrete implementation, different "get" methods).

So those use-case-specific methods (`get_video`, `get_description`, etc.) belong only on the **concrete classes**, not on the interface.

## 12. Observer Pattern Breaks SRP (Single Responsibility Principle)

If you noticed — our Observer Design Pattern implementation **breaks a SOLID design principle**: the **Single Responsibility Principle (SRP)**.

### Why?

Look at `ConcreteChannel` — it is doing **two jobs**:

1. **Job 1 — Observer pattern logic**: `subscribe`, `unsubscribe`, `notify_subscribers` — basically telling every subscriber "I've uploaded a new video, go read it."

2. **Job 2 — Business logic**: `upload_video`, `get_video_data` — i.e., handling what happens when a new video is uploaded, and how to get it.

So `ConcreteChannel` is handling **both** the Observer pattern's bookkeeping **and** the business logic. This is, in some sense, breaking SRP.

### How to Fix It (Optional Improvement)

If you want the Observer pattern implemented **without** breaking SRP, here's what you can do:

Instead of making `IChannel` a **pure abstract class** (interface with all virtual methods), you can write the `subscribe`, `unsubscribe`, and `notify_subscribers` code **directly inside `IChannel`** itself (i.e., make it a concrete/partially-concrete base class that holds the `subscribers` list and implements these three methods).

This way:
- **`IChannel`** handles **all** the Observable-pattern functionality (the part that "never changes").
- **`ConcreteChannel`** handles **only** its own business logic (`upload_video`, `get_video_data` — the part that "can change").

### The Trade-off

This breaks SRP, but: there are only **two** functionalities being handled — implementing the Observable pattern, and implementing business logic. In this case, **only the business logic can change**; the Observable pattern's functionality (`subscribe`, `unsubscribe`, `notify`) will **never** change.

Recall from earlier in the series: whatever in your code is **changing**, separate it from what is **not changing**. So here, it's assumed: the Observable pattern functionality (subscribe/unsubscribe/notify) is fixed and will remain "as is" — that's why it's reasonable to bundle it together.

If you Google standard Observer Design Pattern UML diagrams, you'll find that **most of them also break SRP** in this same way. You *could* avoid breaking it and make things more complicated — but there's no real benefit. **The simpler you keep this pattern, the better.**

## 13. Real-World Use Cases of Observer Pattern

Before finishing, think about where else this Observable Design Pattern can be used.

### 1. Notification Service

For any kind of notification system — there will be a **notification server**. Whenever a new notification arrives, it tells everyone: "I have changed — I have a new notification, go read it."

### 2. News Feed Service

Same idea as a notification service — think of Facebook or Instagram. Whenever a new post (video, photo, anything) is uploaded to someone's news feed, it tells **every account that follows/is friends with** that account about the new post.

### 3. Event Handling (Programming Term)

In **event handling**, whenever an **event** occurs (i.e., a task happens), we **trigger** that event. There are many objects that want to **listen** to that event — they want to "listen" for it.

If you've done a bit of front-end development, you've created **event listeners**. These are, internally, also using the Observable Design Pattern.
