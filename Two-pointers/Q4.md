# Triplets with Smaller Sum

**Pattern:** Two Pointer (3Sum variant — counting, not listing) · **Difficulty:** Medium · **LeetCode:** 3Sum Smaller

---

## Problem
Given an array (all elements distinct) and a `target` sum, count the **number of triplets** `(i, j, k)` such that `arr[i] + arr[j] + arr[k] < target`. Return the count, not the triplets themselves.

---

## Recognition Signals
- [x] Array? → Yes
- [x] Sorted / sortable? → Sort first (same as 3Sum family)
- [x] Keyword match? → "triplets" → 3Sum-family, Two Pointer
- [x] No duplicates in input → dedup logic from 3Sum is NOT needed here

---

## Core Idea
Same `i` + `left` + `right` skeleton as 3Sum, but simplified to **two branches instead of three** (`sum < target` vs `sum >= target`, merged from the original `==`/`<`/`>`), and instead of storing one triplet per match, **count multiple triplets in bulk** using `right - left` whenever a valid smaller-sum combination is found — because if `arr[i]+arr[left]+arr[right] < target`, then swapping `right` for *any* index between `left+1` and `right` also produces a smaller sum (array is sorted).

---

## Key Notes
- **Why only 2 branches, not 3:** the goal only cares about "smaller than target" vs "not smaller." An exact match (`sum == target`) is *not* what we want, so it gets grouped with `sum > target` — both cases shrink `right`.
- **The key insight — batch counting:** if `arr[i] + arr[left] + arr[right] < target`, then because the array is sorted, replacing `right` with **any** index between `left+1` and `right` still gives a sum smaller than target (since all those values are ≤ `arr[right]`). So instead of moving `right` one step and rechecking, add `right - left` directly to the count — this represents all valid triplets `(i, left, x)` for `x` from `left+1` to `right`.
- **Why `left++` happens even after counting:** once `left`'s best possible pairing is fully counted (every valid `right` accounted for via the batch add), `left`'s job is done — same reasoning as standard Two Pointer, just with a bulk-count step inserted before advancing.
- **Complexity flips to worse than 3Sum's O(n²)** in the video's derivation: outer loop O(n) × inner Two Pointer O(n) = O(n²) is the *intended* complexity — same order as 3Sum, since the counting itself is O(1) per step (not proportional to how many elements are skipped).

## Approach Comparison

| Approach | Time | Space | Verdict |
|---|---|---|---|
| Brute force (3 nested loops, check `< target`) | O(n³) | O(1) | Too slow |
| Two Pointer (3Sum skeleton + batch count) ⭐ | O(n²) | O(1) | Optimal |

---

## Algorithm Steps
1. Sort the array.
2. `count = 0`.
3. For `i = 0` to `n - 3`:
   - `left = i + 1`, `right = n - 1`.
   - While `left < right`:
     - `sum = arr[i] + arr[left] + arr[right]`
     - **sum < target:** `count += (right - left)`; then `left++` (every triplet from `left+1` to `right` paired with current `left` is valid — count them all at once)
     - **sum >= target:** `right--`
4. Return `count`.

---

## Pseudocode
```
function triplesSmallerSum(arr, target):
    sort(arr)
    n = length(arr)
    count = 0

    for i = 0 to n - 3:
        left, right = i + 1, n - 1
        while left < right:
            sum = arr[i] + arr[left] + arr[right]
            if sum < target:
                count += (right - left)
                left++
            else:
                right--

    return count
```

## Dry Run
`arr = [-2, 0, 1, 3]` (sorted), `target = 2`

| i | left,right | sum | Action | count |
|---|---|---|---|---|
| -2 | left=1(0),right=3(3) | -2+0+3=1 | 1<2 → count += (3-1)=2, left++ | 2 |
| -2 | left=2(1),right=3(3) | -2+1+3=2 | 2>=2 → right-- | 2 |
| -2 | left=2,right=2 | — | left==right → stop | 2 |

**Result:** `2` — the triplets `(-2,0,1)` and `(-2,0,3)` both have sums < 2.

---

## Gotchas / Edge Cases
- Don't increment `count` by 1 per match — the whole point of the optimization is the batch add `right - left`.
- No duplicate-handling needed — problem guarantees distinct elements, unlike standard 3Sum.
- Easy to mix up with 3Sum's three-branch structure — this problem only needs two branches since "equal" behaves like "not smaller."
- Still bound the outer loop to `i < n - 2` to leave room for `left` and `right`.
