# Bridge Design Pattern

## The Problem: Class Explosion

Imagine you are building a car system. Every car can be driven, so every car has a `drive` method. Cars can be of different types:

- Sedan
- Hatchback
- SUV

And cars can have different engines:

- Petrol Engine
- Diesel Engine
- Electric Engine

Now here is the problem. A Sedan can have a petrol engine, a diesel engine, or an electric engine. Same for a Hatchback. Same for an SUV. Every car type can be paired with every engine type.

If you try to model this using inheritance, you end up creating a class for every combination:

```
SedanWithPetrol
SedanWithDiesel
SedanWithElectric
HatchbackWithPetrol
HatchbackWithDiesel
HatchbackWithElectric
SUVWithPetrol
SUVWithDiesel
SUVWithElectric
```

With 3 car types and 3 engine types, you already need **3 × 3 = 9 classes**.

Now if tomorrow you introduce a CNG engine, you need 3 more classes — one for each car type. Add a new car type like a Convertible, and you need 3 more — one for each engine. The number of classes grows as **m × n** where m is the number of car types and n is the number of engine types. This is called **class explosion**.

**Class explosion** means: you have created far too many classes to implement a single feature, and every small change forces you to create even more. The system becomes complicated, code reuse drops to nearly zero, SOLID principles break down, and the relationships between classes become very hard to understand.

---

## How the Bridge Pattern Solves It

The Bridge pattern says: if you have a concept to implement, **break it into two parts**:

- A **high-level part** (also called Abstraction)
- A **low-level part** (also called Implementation)

> A note on terminology: "Abstraction" here does not mean abstract classes and "Implementation" does not mean concrete classes in the OOP sense. In the Bridge pattern, "Abstraction" means looking at something from the outside — what it looks like at a high level. "Implementation" means looking at something from the inside — how it actually works. Use "high-level part" and "low-level part" in your own thinking. Use "Abstraction" and "Implementation" when you want to sound impressive in an interview.

For the car example:

- **High-level part (Abstraction)** = Car type (Sedan, SUV, Hatchback) — this is what the car looks like from the outside
- **Low-level part (Implementation)** = Engine (Petrol, Diesel, Electric) — this is what is actually happening inside the car

Instead of combining them into m × n classes, you keep two **separate hierarchies**:

```
High-level hierarchy:   Car → Sedan, SUV, Hatchback
Low-level hierarchy:    Engine → PetrolEngine, DieselEngine, ElectricEngine
```

The **high-level part holds a reference to the low-level part**. That reference is the bridge.

Now instead of m × n = 9 classes, you only need **m + n = 3 + 3 = 6 classes**. And both hierarchies can grow independently. Add a new engine? Add one class to the engine hierarchy — done. Add a new car type? Add one class to the car hierarchy — done. Neither side needs to know about the other.

## UML Diagram

```
HIGH-LEVEL HIERARCHY (Abstraction)          LOW-LEVEL HIERARCHY (Implementation)

┌──────────────────────────────────┐        ┌──────────────────────────────────┐
│         <<abstract>>             │        │         <<abstract>>             │
│              Car                 │        │             Engine               │
├──────────────────────────────────┤        ├──────────────────────────────────┤
│ # _engine: Engine                │◆───────│ + start()  ← abstract           │
├──────────────────────────────────┤  has-a └──────────────────────────────────┘
│ + drive()  ← abstract            │                    △
└──────────────────────────────────┘        ┌───────────┼────────────┐
              △                             │           │            │
    ┌─────────┴──────────┐        ┌─────────────┐ ┌──────────┐ ┌───────────────┐
    │                    │        │PetrolEngine │ │DieselEng.│ │ElectricEngine │
┌────────┐          ┌────────┐   ├─────────────┤ ├──────────┤ ├───────────────┤
│ Sedan  │          │  SUV   │   │ + start()   │ │+ start() │ │ + start()     │
├────────┤          ├────────┤   └─────────────┘ └──────────┘ └───────────────┘
│drive() │          │drive() │
└────────┘          └────────┘

┌──────────────────────────────────────────────────┐
│                    Client                        │
├──────────────────────────────────────────────────┤
│ car = Sedan(engine=PetrolEngine())               │
│ car.drive()   → calls self._engine.start()       │
│                                                  │
│ # Car does not know which engine is inside.      │
│ # Engine does not know which car contains it.    │
└──────────────────────────────────────────────────┘
```

**The bridge** is the `has-a` arrow from `Car` to `Engine`. That single reference connects the two otherwise independent hierarchies. The `drive()` method in any car subclass simply calls `self._engine.start()` — the car does not know or care whether the engine is petrol, diesel, or electric.

## Standard UML (Generic Form)

```
┌───────────────────────────────┐     ┌───────────────────────────────┐
│       <<abstract>>            │     │       <<abstract>>            │
│        Abstraction            │     │        Implementor            │
│     (High-level layer)        │     │      (Low-level layer)        │
├───────────────────────────────┤     ├───────────────────────────────┤
│ # _imp: Implementor           │◆────│ + implement()                 │
├───────────────────────────────┤     └───────────────────────────────┘
│ + execute()                   │                  △
└───────────────────────────────┘     ┌────────────┼──────────────┐
              △                  ┌────────────┐ ┌────────────┐ ┌────────────┐
    ┌─────────┴──────────┐       │ConcreteImp1│ │ConcreteImp2│ │ConcreteImp3│
┌──────────┐  ┌──────────┐      ├────────────┤ ├────────────┤ ├────────────┤

│execute() │  │execute() │   execute() calls self._imp.implement()
└──────────┘  └──────────┘
```

## Python Implementation

```python
from abc import ABC, abstractmethod


# -----------------------------------------------------------------------
# LOW-LEVEL HIERARCHY (Implementation / Engine)
# -----------------------------------------------------------------------

class Engine(ABC):
    """Abstract low-level layer. Defines how a car is powered internally."""

    @abstractmethod
    def start(self) -> None:
        pass


class PetrolEngine(Engine):
    def start(self) -> None:
        print("Petrol engine starting with ignition")


class DieselEngine(Engine):
    def start(self) -> None:
        print("Diesel engine starting with compression")


class ElectricEngine(Engine):
    def start(self) -> None:
        print("Electric engine powering up silently")


# -----------------------------------------------------------------------
# HIGH-LEVEL HIERARCHY (Abstraction / Car type)
# -----------------------------------------------------------------------

class Car(ABC):
    """
    Abstract high-level layer. Holds a reference to an Engine.
    This reference IS the bridge connecting the two hierarchies.
    """

    def __init__(self, engine: Engine):
        self._engine = engine  # has-a relationship with the low-level layer

    @abstractmethod
    def drive(self) -> None:
        pass


class Sedan(Car):
    def drive(self) -> None:
        self._engine.start()
        print("Driving a Sedan on the highway")


class SUV(Car):
    def drive(self) -> None:
        self._engine.start()
        print("Driving an SUV off-road")


# -----------------------------------------------------------------------
# Client
# -----------------------------------------------------------------------
if __name__ == "__main__":
    # Pair any car type with any engine — freely
    petrol_engine   = PetrolEngine()
    diesel_engine   = DieselEngine()
    electric_engine = ElectricEngine()

    sedan_petrol   = Sedan(engine=petrol_engine)
    suv_electric   = SUV(engine=electric_engine)
    suv_diesel     = SUV(engine=diesel_engine)

    print("=== Sedan with Petrol Engine ===")
    sedan_petrol.drive()

    print()
    print("=== SUV with Electric Engine ===")
    suv_electric.drive()

    print()
    print("=== SUV with Diesel Engine ===")
    suv_diesel.drive()
```

**Expected Output:**

```
=== Sedan with Petrol Engine ===
Petrol engine starting with ignition
Driving a Sedan on the highway

=== SUV with Electric Engine ===
Electric engine powering up silently
Driving an SUV off-road

=== SUV with Diesel Engine ===
Diesel engine starting with compression
Driving an SUV off-road
```

Notice what is happening:

- `Sedan` does not know which engine is inside it. It just calls `self._engine.start()`.
- `ElectricEngine` does not know it is inside an SUV. It has no reference to the car at all.
- The two hierarchies are completely independent of each other. You can freely pair any car with any engine at the time of construction.
- To add a `CNG` engine tomorrow: create one new class `CNGEngine(Engine)`. Nothing else changes.
- To add a `Hatchback` car tomorrow: create one new class `Hatchback(Car)`. Nothing else changes.

## The Standard Definition

> Bridge decouples an abstraction (high-level layer) from its implementation (low-level layer) so that both can vary independently.

That is the entire pattern. Separate the high-level from the low-level. Give the high-level a reference to the low-level. Let both grow independently.

---

## Bridge vs Strategy — What Is the Difference?

This is a very common point of confusion because the UML diagrams of Bridge and Strategy look almost identical. Both have a class holding a reference to an interface with multiple concrete implementations. So why are they two different patterns?

The difference is **intent**.

**Strategy pattern:** You have a client and a family of interchangeable algorithms. The goal is to allow the client to **dynamically switch** between algorithms at runtime. Today the car uses a petrol engine; tomorrow you dynamically swap it for a diesel engine on the same object. The focus is on the interchangeability.

**Bridge pattern:** You have two dimensions that need to grow independently. The goal is not primarily dynamic swapping — it is to allow **both the high-level layer and the low-level layer to be extended independently** without class explosion. Once a Sedan is paired with a petrol engine, you generally do not swap it at runtime. The focus is on independent variation and preventing m × n classes.

In Strategy, you typically have one "client" class and multiple algorithms. In Bridge, you explicitly have **two hierarchies** — both of which grow with multiple classes — and you want to pair any member of one hierarchy with any member of the other.

Think of it this way: a car with a petrol engine does not become a diesel car at runtime. Once paired, that is its identity. But you wanted the freedom to create any combination — SUV+Electric, Sedan+Diesel, Hatchback+Petrol — without writing 9 classes. That freedom is what Bridge gives you.

When UML alone does not tell you which pattern to use, ask yourself: "What is my intent?" If you want to swap algorithms dynamically on one object, use Strategy. If you want two independent hierarchies that can each grow freely and be combined in any pairing, use Bridge.

## Real-World Use Cases

**Remote control system:** A Sony TV (low-level) can be paired with a Sony remote (high-level). You might have LCD TVs, LED TVs, and OLED TVs — these are your low-level implementations. You might have a standard button remote, a touch screen remote, a voice remote — these are your high-level abstractions. Both should grow independently. A new remote should work with any TV. A new TV should work with any remote.

**GUI components across operating systems:** A TextBox, a Dropdown, and a RadioButton are the high-level layer. Windows, macOS, and Linux are the low-level layer. The same TextBox looks slightly different on Windows vs macOS — different font, different border style. You want to define the GUI components once (high-level) and implement their rendering per operating system (low-level) without creating a TextBoxOnWindows, TextBoxOnMac, TextBoxOnLinux class for every single component.
