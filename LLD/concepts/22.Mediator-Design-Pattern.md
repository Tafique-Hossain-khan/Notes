# Mediator Design Pattern

## The Problem: Tight Coupling Between Objects

Consider two objects, OB1 and OB2, that need to communicate with each other. In object-oriented terms, communicating means calling each other's methods. For OB1 to call a method on OB2, OB1 needs to hold a reference to OB2. And for OB2 to reply back, it needs a reference to OB1.

```
OB1 <──────────────────> OB2
(holds ref to OB2)       (holds ref to OB1)
```

Now introduce a third object OB3. All three need to interact. You add OB3's reference to OB1's list, OB3's reference to OB2's list, and both OB1 and OB2's references to OB3's list.

```
OB1 ◄──► OB2
 ▲         ▲
 └────┬────┘
      ▼
     OB3
```

Keep going. Add OB4, OB5, OB6. Every time you add a new object, you must update every existing object's reference list. Each object must know about n-1 other objects if there are n objects total in the network.

**This is the problem.** As objects increase, every object's list keeps growing. Every time you add a new object, you change every existing object. Everything is tightly coupled. Objects that just need to talk to each other end up knowing too much about each other.

---

## The Solution: Mediator

Instead of objects talking directly to each other, introduce a single **Mediator** object in the middle.

```
OB1 ──► Mediator ◄── OB2
             │
            OB3
             │
            OB4
```

Now none of OB1, OB2, OB3, OB4 hold references to each other. Every object only knows about the Mediator. Every object only holds a reference to the Mediator.

If OB1 wants to send a message to OB4, OB1 tells the Mediator: "Send this message to OB4." The Mediator has references to everyone, so it delivers the message. OB4 doesn't need to know OB1 exists. OB1 doesn't need to know OB4 exists.

The entire reference list — that grew with every new object — now lives in exactly one place: the Mediator.

Two problems solved:
1. **n² connections reduced** — each object now has just one reference (to the Mediator)
2. **Tight coupling eliminated** — objects are now loosely coupled

## Chat Room Example

A chat room is a perfect real-world scenario. Multiple users need to interact with each other. Let's build it first **without** the Mediator pattern to see the pain, then rebuild it **with** the Mediator.

---

## Without Mediator: The Bad Design

Each user needs a list of all other users. A user can:
- Send a broadcast message to everyone (`send_all`)
- Send a private message to one person (`send_to`)
- Mute another user so their messages are blocked

```
┌──────────────────────────────────────┐
│                 User                 │
│──────────────────────────────────────│
│ - name: str                          │
│ - peers: List[User]    ← grows with  │
│ - muted: List[str]       every user  │
│──────────────────────────────────────│
│ + add_peer(user: User)               │
│ + mute(user: User)                   │
│ + send_all(message: str)             │
│ + send_to(to: str, message: str)     │
│ + is_muted(name: str) -> bool        │
│ + receive(from_user: str, msg: str)  │
└──────────────────────────────────────┘
```

The `send_all` method must loop through all peers, check for each peer whether the sender is in that peer's muted list, and only then deliver the message. Every new feature (mute, block, admin-only) means opening this class and adding yet another list or condition.

If you have n users, each user stores n-1 references. That's n × (n-1) total connections in the system.

### Python Code — Bad Design

```python
class User:
    def __init__(self, name: str):
        self.name = name
        self.peers: list['User'] = []     # every other user in the network
        self.muted: list[str] = []        # names of users this user has muted

    def add_peer(self, user: 'User'):
        self.peers.append(user)

    def mute(self, user: 'User'):
        self.muted.append(user.name)

    def is_muted(self, name: str) -> bool:
        return name in self.muted

    def send_all(self, message: str):
        print(f"\n[BROADCAST] {self.name}: {message}")
        for peer in self.peers:
            # Check if the receiver has muted the sender
            if peer.is_muted(self.name):
                continue
            peer.receive(self.name, message)

    def send_to(self, to: str, message: str):
        print(f"\n[PRIVATE] {self.name} → {to}: {message}")
        for peer in self.peers:
            if peer.name == to:
                if peer.is_muted(self.name):
                    print(f"  [blocked] {to} has muted {self.name}")
                    return
                peer.receive(self.name, message)
                return

    def receive(self, from_user: str, message: str):
        print(f"  {self.name} got from {from_user}: {message}")


# ── Main ───────────────────────────────────────────────────────────────────────

if __name__ == "__main__":
    rohan = User("Rohan")
    neha  = User("Neha")
    mohan = User("Mohan")

    # Every pair must be wired manually — this grows as n²
    rohan.add_peer(neha);  neha.add_peer(rohan)
    rohan.add_peer(mohan); mohan.add_peer(rohan)
    neha.add_peer(mohan);  mohan.add_peer(neha)

    # Rohan mutes Mohan
    rohan.mute(mohan)

    # Mohan broadcasts — Rohan won't receive it because he muted Mohan
    mohan.send_all("Hello everyone!")

    # Mohan sends a private message to Neha
    mohan.send_to("Neha", "Hey Neha!")
```

**Expected output:**
```
[BROADCAST] Mohan: Hello everyone!
  Neha got from Mohan: Hello everyone!
  (Rohan blocked — muted Mohan)

[PRIVATE] Mohan → Neha: Hey Neha!
  Neha got from Mohan: Hey Neha!
```

**Why this is painful:**
- Three users required 6 manual `add_peer` calls. Ten users would require 90.
- Every new feature (mute, block, admin role) adds another list inside `User`.
- `User` knows too much — it stores all peers AND manages mute logic AND handles delivery.
- Adding a new user means touching every existing user's setup code.

## Introducing the Mediator

Two users who want to talk don't talk directly. They talk through the Mediator. The Mediator holds the list of everyone. The users hold only a reference to the Mediator.

```
User1 ──sends to Mediator──► Mediator ──delivers to──► User2
User2 ──sends to Mediator──► Mediator ──delivers to──► User1
```

The objects being mediated are called **Colleagues** in this pattern. The term is deliberate — colleagues work together but don't need to know each other's home addresses.

---

## UML Diagram

```
┌───────────────────────────────────────┐
│           IMediator  (Abstract)       │
│───────────────────────────────────────│
│ + register_colleague(c: IColleague)   │
│ + send(from: str, message: str)       │
│ + send_private(from,to,message: str)  │
└──────────────────┬────────────────────┘
                   │ inherits
                   ▼
┌───────────────────────────────────────┐
│        ChatMediator  (Concrete)       │
│───────────────────────────────────────│
│ - colleagues: List[IColleague]        │
│ - mutes: List[Tuple[str, str]]        │
│   (who muted whom)                    │
│───────────────────────────────────────│
│ + register_colleague(c: IColleague)   │
│ + mute(who: str, whom: str)           │
│ + send(from: str, message: str)       │
│ + send_private(from,to,message: str)  │
└───────────────────────────────────────┘


┌───────────────────────────────────────┐
│          IColleague  (Abstract)       │
│───────────────────────────────────────│
│ - mediator: IMediator                 │
│───────────────────────────────────────│
│ + get_name() -> str                   │
│ + send(message: str)                  │
│ + send_private(to: str, msg: str)     │
│ + receive(from: str, message: str)    │
└──────────────────┬────────────────────┘
                   │ inherits
                   ▼
┌───────────────────────────────────────┐
│            User  (Concrete)           │
│───────────────────────────────────────│
│ - name: str                           │
│───────────────────────────────────────│
│ + get_name() -> str                   │
│ + send(message: str)                  │
│ + send_private(to: str, msg: str)     │
│ + receive(from: str, message: str)    │
└───────────────────────────────────────┘

Relationships:
ChatMediator ──has many──► IColleague   (1 to many)
IColleague   ──has one───► IMediator    (many to 1)
```

**Key design decisions:**

- `IColleague` holds a reference to `IMediator`. When a colleague is constructed, it immediately calls `mediator.register_colleague(self)` so the Mediator's list is populated automatically.
- `ChatMediator` stores a flat list of all colleagues plus a list of `(who, whom)` tuples for mutes. The entire mute logic lives here, not inside each user.
- When a user calls `send(message)`, the user passes itself (via `self.name`) and the message to the Mediator. The Mediator handles routing. The user doesn't touch anyone else's reference.

## Python Code — With Mediator

```python
from __future__ import annotations
from abc import ABC, abstractmethod


# ─── Abstract Mediator ─────────────────────────────────────────────────────────

class IMediator(ABC):

    @abstractmethod
    def register_colleague(self, colleague: IColleague) -> None:
        pass

    @abstractmethod
    def send(self, from_name: str, message: str) -> None:
        pass

    @abstractmethod
    def send_private(self, from_name: str, to_name: str, message: str) -> None:
        pass


# ─── Abstract Colleague ────────────────────────────────────────────────────────

class IColleague(ABC):

    def __init__(self, mediator: IMediator):
        self._mediator = mediator
        mediator.register_colleague(self)   # registers itself on construction

    @abstractmethod
    def get_name(self) -> str:
        pass

    @abstractmethod
    def send(self, message: str) -> None:
        pass

    @abstractmethod
    def send_private(self, to: str, message: str) -> None:
        pass

    @abstractmethod
    def receive(self, from_name: str, message: str) -> None:
        pass


# ─── Concrete Mediator ─────────────────────────────────────────────────────────

class ChatMediator(IMediator):

    def __init__(self):
        self._colleagues: list[IColleague] = []
        # Each tuple is (who_muted, whom_was_muted)
        self._mutes: list[tuple[str, str]] = []

    def register_colleague(self, colleague: IColleague) -> None:
        self._colleagues.append(colleague)

    def mute(self, who: str, whom: str) -> None:
        """Record that `who` has muted `whom`."""
        self._mutes.append((who, whom))
        print(f"  [MUTE] {who} muted {whom}")

    def send(self, from_name: str, message: str) -> None:
        """Broadcast message to all colleagues except sender and those who muted sender."""
        print(f"\n[BROADCAST] {from_name}: {message}")
        for colleague in self._colleagues:
            # Don't send to self
            if colleague.get_name() == from_name:
                continue
            # Check if this colleague has muted the sender
            is_muted = False
            for (who_muted, whom_muted) in self._mutes:
                if who_muted == colleague.get_name() and whom_muted == from_name:
                    is_muted = True
                    break
            if not is_muted:
                colleague.receive(from_name, message)

    def send_private(self, from_name: str, to_name: str, message: str) -> None:
        """Send message to one specific colleague, unless they muted the sender."""
        print(f"\n[PRIVATE] {from_name} → {to_name}: {message}")
        for colleague in self._colleagues:
            if colleague.get_name() == to_name:
                # Check if recipient muted the sender
                is_muted = False
                for (who_muted, whom_muted) in self._mutes:
                    if who_muted == to_name and whom_muted == from_name:
                        is_muted = True
                        break
                if is_muted:
                    print(f"  [blocked] {to_name} has muted {from_name}")
                else:
                    colleague.receive(from_name, message)
                return


# ─── Concrete Colleague ────────────────────────────────────────────────────────

class User(IColleague):

    def __init__(self, name: str, mediator: IMediator):
        self._name = name
        super().__init__(mediator)   # registers with mediator immediately

    def get_name(self) -> str:
        return self._name

    def send(self, message: str) -> None:
        """Broadcast to everyone via mediator."""
        self._mediator.send(self._name, message)

    def send_private(self, to: str, message: str) -> None:
        """Send privately to one user via mediator."""
        self._mediator.send_private(self._name, to, message)

    def receive(self, from_name: str, message: str) -> None:
        print(f"  {self._name} got from {from_name}: {message}")


# ─── Main ──────────────────────────────────────────────────────────────────────

if __name__ == "__main__":
    chat_room = ChatMediator()

    # Users register themselves with the mediator automatically on construction
    rohan = User("Rohan", chat_room)
    neha  = User("Neha",  chat_room)
    mohan = User("Mohan", chat_room)

    # No manual peer wiring needed — zero n² connections

    # Rohan mutes Mohan (Rohan won't receive Mohan's messages)
    chat_room.mute("Rohan", "Mohan")

    # Mohan broadcasts — Rohan won't receive it
    mohan.send("Hello everyone!")

    # Mohan sends a private message to Neha
    mohan.send_private("Neha", "Hey Neha!")
```

**Expected output:**
```
  [MUTE] Rohan muted Mohan

[BROADCAST] Mohan: Hello everyone!
  Neha got from Mohan: Hello everyone!

[PRIVATE] Mohan → Neha: Hey Neha!
  Neha got from Mohan: Hey Neha!
```

Notice what changed compared to the bad design:
- No `add_peer` calls anywhere in main
- No reference from any User to any other User
- Mute logic lives entirely inside `ChatMediator`, not inside `User`
- Adding a new user is one line: `User("someone", chat_room)`

## Standard UML (Generic Pattern)

```
┌──────────────────────────────┐
│        IMediator             │  ← Abstract
│──────────────────────────────│
│ + add(colleague: IColleague) │
│ + send(from, message)        │
└──────────────┬───────────────┘
               │ inherits
               ▼
┌──────────────────────────────┐
│      ConcreteMediator        │
│──────────────────────────────│
│ - colleagues: List           │  ◄── holds references to ALL colleagues
│──────────────────────────────│
│ + add(colleague: IColleague) │
│ + send(from, message)        │  ← loops through list, delivers message
└──────────────────────────────┘


┌──────────────────────────────┐
│        IColleague            │  ← Abstract
│──────────────────────────────│
│ - mediator: IMediator        │  ◄── holds reference to mediator ONLY
│──────────────────────────────│
│ + set_mediator(m: IMediator) │
│ + send(message)              │
│ + receive(from, message)     │
└──────────────┬───────────────┘
        ┌──────┴──────┐
        ▼             ▼
┌────────────┐  ┌────────────┐
│ Concrete   │  │ Concrete   │
│ Colleague A│  │ Colleague B│
│────────────│  │────────────│
│send()      │  │send()      │
│receive()   │  │receive()   │
└────────────┘  └────────────┘

Concrete Colleague A ──calls──► mediator.send()  ──routes to──► Concrete Colleague B
Concrete Colleague B ──calls──► mediator.send()  ──routes to──► Concrete Colleague A
```

Each colleague calls `mediator.send()` when it wants to communicate. The Mediator handles routing. Neither colleague holds a reference to the other.

## Standard Definition

> **Mediator Design Pattern** defines an object that encapsulates how a set of objects interact, and promotes loose coupling by preventing objects from referring to each other explicitly.

Instead of a group of objects all knowing about each other, they all know only about the Mediator. The Mediator becomes the single point that manages all communication. The objects themselves stay simple and focused on their own behavior.

---

## Mediator vs Observer

The UML diagrams look almost identical. Both have:
- One central object holding a list of many objects
- A `register` method to add to the list
- A method to push a message to list members

But the **intent is completely different**:

| | Observer | Mediator |
|---|---|---|
| **Central object** | Observable (Subject) | Mediator |
| **Registered objects** | Observers | Colleagues |
| **Intent** | When my state changes, notify all observers | Allow two colleagues to talk without knowing each other |
| **Communication direction** | One-way: Observable → Observers | Two-way: Any colleague ↔ Any colleague via Mediator |
| **Who triggers** | State change in Observable triggers notification | Any colleague can initiate communication at any time |
| **Real use** | Notification systems, event listeners | Chat rooms, multiplayer games, matchmaking platforms |

**Observer example:** A news publisher (Observable) pushes updates to all subscribers (Observers) when a new article is published. The subscribers don't talk to each other. They just receive.

**Mediator example:** A chat room where any user can send a message to any other user. Users communicate in both directions. The Mediator routes messages between them.

If you need to notify many objects that something changed → **Observer**.
If you need multiple objects to communicate with each other without coupling → **Mediator**.

---

## Real World Use Cases

- **Chat rooms** — exactly what we built. Any user messaging any other user through a server (the Mediator).
- **Online multiplayer games** — chess.com, online card games, any match where multiple players interact in real time. The game server acts as the Mediator. Players don't hold each other's connections directly.
- **Any matchmaking platform** — whenever multiple users need to interact and you don't want them referencing each other directly, route communication through a central Mediator.
