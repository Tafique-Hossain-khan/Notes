# Error Handling and Fault-Tolerant Backends: A Mindset Guide

This video has **no tools, no frameworks, and no code**. It teaches a **mindset**: how a backend engineer should think about errors. This post follows it in order: the kinds of errors you will meet, how to detect them early, how to react when they happen, how to centralize error handling, and how to avoid leaking secrets through errors.

---

## 1. Errors Are Normal

Errors are not just problems to solve. They are a **normal part of building applications**. Every developer must accept that errors *will* happen. The key is being ready to **detect** them and **fix** them.

These are facts of life:

- Your **database queries** will sometimes fail.
- Your **external APIs** will sometimes time out.
- Your **users** will sometimes send bad data that breaks your API if you aren't expecting it.
- Your **business logic** will sometimes hit unexpected edge cases.

> The question is not *whether* errors will happen, but *how you handle them when they do*.

If you are responsible for core business logic, and for making sure every transaction and every user action goes smoothly, you need a **fault-tolerant mindset**: prepare for the worst and know how bad it can get.

---

## 2. The Types of Errors You Will Meet

### 2.1 Logic Errors

The most common type, and in the author's experience **the most dangerous**. They don't crash your app. They make it **do the wrong thing**. The code runs fine, but the results are incorrect or unexpected.

**Example:** an e-commerce store accidentally applies a discount **twice**, which produces **negative shipping costs**. Nothing crashes, but the business **loses money on every single order**. Such errors can go unnoticed for **weeks or months** unless you monitor for them or users report them.

**Why they happen:**

| Cause | Example |
|---|---|
| **Misunderstanding requirements** | A confusing conversation with the client or product manager leaves you with the wrong notes. You implement the wrong thing, it ships with too little testing, and it reaches users. |
| **Implementing algorithms incorrectly** | A complicated discount algorithm that depends on user behavior and purchase history has one slight miscalculation. |
| **Not thinking about edge cases** | You didn't expect a particular user behavior in a payment or discount workflow. |

Logic errors are especially dangerous around **payments, money, and security**, because they can corrupt data and produce wrong business results over time without being detected.

### 2.2 Database Errors

Most backends rely heavily on their database, so database errors **can bring the whole system down**. They range from a simple connection problem to deadlocks and transaction issues.

**a) Connection errors**

Your app cannot talk to the database. The backend throws `500` errors and the front end shows empty screens. Causes:

- the network is down,
- the database server is overloaded,
- you ran out of **connection pool** slots.

*Connection pooling* means the backend keeps a few TCP connections to the database open, so it doesn't repeat the TCP handshake and setup for every request. It's an optimization, but the pool itself can run out and cause errors.

**b) Constraint violations**

You try something that breaks a database rule:

- **Unique constraint:** creating a user with an email that already exists.
- **Foreign key constraint:** the `orders` table has a non-nullable `customer_id` that references `customers`. You insert an order with a customer ID that doesn't exist.

If you don't handle these properly and don't send a well-formatted message to the front end, the error bubbles up and becomes a **`500`**.

How to deal with them:

- Part of the cause is a weak **validation layer**. Handle edge cases in both front end and back end.
- But **some can't be avoided**. Only the database knows whether an email is unique. For those, focus on **error formatting**: return a user-friendly message so the front end can show "this email already exists, try a different one".

**c) Query errors**

Your SQL is **malformed**, for example a **typo in the table name** (`select * from customrs`), or the query is so complex that it **times out**.

**d) Deadlocks**

Multiple database operations **wait on each other**, forming a circular dependency, so none can proceed. They are particularly tricky.

### 2.3 External Service Errors

Modern apps (especially SaaS) depend on external services: payment processors, email providers, cloud/object storage like S3, Redis, and authentication providers like Auth0 or Clerk. Each one is a **point of failure you don't control**.

You can't avoid them, because you can't build every complex system from scratch. So **expect them to fail** and be ready with a plan.

**a) Network problems**

Your backend reaches services over HTTP, TCP, or WebSocket, and the internet isn't perfect. Expect **connection timeouts, DNS failures, and network partitions** (affected by routing).

**b) Authentication errors**

External services reject your request because of **bad credentials, expired tokens, or insufficient permissions**.

A related warning: using an external auth provider does not make you secure by itself. It's an integration, and your own backend can still cause security problems, for example by **exposing sensitive user information in your logs**.

**c) Rate limiting**

Services like OpenAI or Resend limit how many requests you can send in a time window. This protects them from abuse and from malicious users. If a burst of user activity (or a logic error) makes you hit their API too often, they block you and return **`429 Too Many Requests`**.

Prepare with **exponential backoff**: on a `429`, wait 1 minute and retry. If it still fails, wait **double** (2 minutes), then 4 minutes, and so on until you get a successful response.

**d) Service outages**

Even major cloud providers (GCP, parts of AWS) have incidents or maintenance windows, and many of their customers go down with them. You can't control this, but your app must handle it **gracefully with fallbacks**.

Example: if your Redis service goes down, have a second layer, such as **in-memory caching** or a **second Redis node**, so critical functions like payments and order processing aren't affected.

### 2.4 Input Validation Errors

These come from **users sending bad data** that doesn't meet your rules. The validation layer is your **first line of defense** against bad or malicious input, since it checks data at the entry point of your backend. (The author has a separate validation video in this playlist.)

| Rule type | What it checks | Examples |
|---|---|---|
| **Format** | Is the data in the expected shape? | Valid email, phone number, date. For custom data, be clear about the exact format you expect and accept only that (for security and fault tolerance). |
| **Range** | Are values within limits? | Maximum amount too high, minimum too low; string too long or too short; array with fewer than 3 or more than 100 items |
| **Required field** | Is a mandatory field present? | Missing a field needed for the operation |

You typically return **`400 Bad Request`**. These are the **easiest errors to expect and handle**, because you already know your data requirements and just enforce them at the door. (Compare logic errors, which are hard to detect, and external failures, which you can't control.) Build a robust validation layer in every backend.

### 2.4 Configuration Errors

These can **prevent your app from starting**, or make production behave unexpectedly. They usually appear when moving between **development, staging, and production**.

**Example:** in development you add `OPENAI_API_KEY` to your `.env` file and merge the PR, but you **forget to add it in production** (manually, or via something like AWS Parameter Store). The deployment succeeds. Now two things can happen:

| Setup | Result |
|---|---|
| **You validate required configuration at startup** | The app **fails to start**. This is the **best-case scenario**. With setups like **blue-green deployment**, the previous deployment keeps running until the new one starts successfully, so users never see downtime. |
| **You don't validate at startup** | The app starts fine. Later, when a user hits an API that needs the OpenAI key, the service can't find it and errors out. The user gets a **`500` at runtime**. This is the **worst case**. |

**Rule:** **crash at startup, before serving real users**. Validate all required configuration (from environment variables or remote stores) before the server starts. If anything is missing or corrupt, fail right there. (The next video in the series covers configuration management in depth.)

## 3. Prevention: Find Errors Before They Spread

> **The best error handling starts before errors happen.**

Detect problems the moment they occur, before they cause real damage. That is the best strategy in any system (front end, back end, or infrastructure).

### 3.1 Health Checks

Expose an endpoint such as `/health` or `/status` that returns a generic OK response. What matters is the **status code**:

- `200` means it's running.
- `400`/`500` means something is wrong.

External tools can keep pinging it to confirm the service is alive and error-free.

But "the server is running" isn't enough. **Also check that it is actually doing its job.**

**Database health checks**

- **Connectivity:** can we connect?
- **Query performance:** a query that used to take 500 ms now takes 4 to 5 seconds means something is wrong.
- **Data integrity.**
- A simple ping isn't enough. Run a **representative query**, check the result, and measure how long it takes (and the average).

**External service health checks**

| Service | Check |
|---|---|
| Payment processor | Run **test transactions**. If the last one 5 minutes ago succeeded, you have confidence going into real ones. |
| Email service | **Send test messages** to internal addresses to confirm delivery and connectivity. |
| Authentication service | **Generate test tokens** and verify them against the provider's validation endpoint. |

**Core functionality checks**

- **Configuration** is properly loaded. If required variables are missing, stop and show a **meaningful message** so the infrastructure operator can fix them and restart.
- **Caches** needed for production workloads are populated.
- **Internal data structures** (configuration, external-service state) are consistent.

Together these are **proactive error detection**: being prepared for worst-case scenarios ahead of time, with ways to prevent them and fix them if they occur.

### 3.2 Monitoring and Observability

This is a huge topic with its own video later in the series, so here is the short version. Monitoring **detects errors quickly, while they are happening**, and gives you **context to debug**.

- **Don't only track error rates. Track performance too.** Performance degradation is often an early warning that a service is about to fail. Monitor **response times, resource usage, and throughput**.
- **Cover every error source:** HTTP errors, database errors, external service failures, and business logic errors.
- **Monitor business metrics.** A sudden drop in successful transactions or successful authentications can indicate a technical problem **even when error rates look normal**.
- **Log well.** Use **structured logs** (for example JSON, which is easy to parse and extend with metadata). Tools like **Grafana** and **Loki** aggregate logs so you can search, store, and explore error rates on a dashboard.

## 4. Philosophies for Reacting to Errors

### 4.1 Immediate Error Response

Your immediate reaction decides whether an error stays **minor or becomes a major failure**. The right strategy depends on the error type and context.

| Error kind | Strategy | Notes |
|---|---|---|
| **Recoverable** (network errors, temporary resource problems, running out of database connections, a failed email send, since email can tolerate delay) | **Retry** with **exponential backoff** | Be careful **not to overwhelm an already stressed system**. Your retry logic must not add more stress. |
| **Non-recoverable** | **Containment and graceful degradation** | Serve **cached data**, **disable non-essential features**, provide **alternative functionality** or a fallback, and **contain the scope of the damage**. |

### 4.2 Error Recovery Strategies

The right approach depends on the nature of the error and how critical the functionality is.

**Automatic recovery** can handle many errors without human intervention:

- **Restart** a service that has stopped responding (with a tool or setup that does it automatically).
- Run **cleanup** (for example, clearing corrupted caches).
- **Switch to backup systems**.

But **design these carefully**, because they can sometimes make a problem worse. Be ready for trial and error: test how your services behave near their error thresholds and learn which strategy works for which service.

**Manual recovery** is necessary for some errors because it needs human judgment and decisions. For those, **document the process** so your team and new hires know what to do during an incident or failure, and **test it** so you know it works and can be executed quickly under stress.

**Data recovery:** protect your data above all.

> Code and services are replaceable. **The data you hold** (users, transactions, orders) is the one tangible, irreplaceable thing. Data integrity should be a top priority.

Data recovery strategies include **backups at key moments, restoring from backups, replaying transaction logs, and specialized recovery tools**.

### 4.3 Propagation Control

Not every error should be handled at the moment it occurs. Sometimes errors should **propagate up to higher levels, where there is more context** (the stack trace is part of this idea). But **keep the bubbling in your control**, or it may spread to other services or shut down your main service.

Most languages use **exception handling** (`try/catch` in JavaScript, `try/except` in Python). Exception hierarchies give structure to propagation: catch **low-level exceptions**, **wrap them with context**, and bubble them up to higher-level exceptions that have **business context**. At that point you can log the right data, return a meaningful error to the front end, or trigger a recovery strategy. This is so common that it has its own name: **global error handling** (next section).

### 4.4 Error Boundaries

Error boundaries are the **last point where you stop errors from spreading**. In a service architecture they **prevent an error in one service from affecting others**:

- Use **separate processes**.
- Set **timeouts** to protect service boundaries.
- Use **message queues** (such as RabbitMQ) to decouple services and communicate **asynchronously**, so **a bug in one service doesn't cause another to fail**.

## 5. Global Error Handling: The Final Safety Net

The author calls this one of his favorite mechanisms and pays attention to it in every backend he builds. It takes effort **once**, when you set up the platform, and after that you only tweak it or add conditions. It **pays off immediately**.

### 5.1 The Architecture Refresher

A typical request flows through these layers:

```
Request
  ↓
Routing layer      → decides which handler takes the request
  ↓
Handler            → extracts data from the payload; deserialization, validation, binding
  ↓
Service method     → orchestrates one or more repository methods
  ↓
Repository method  → leaf node; does ONE thing, usually one database query
```

Example: `GetUserByID` is a repository method. A service method that returns a user **and** their posts calls two repository methods. Repositories stay small and unit-level, and the service decides which to call and how many.

### 5.2 The Pattern

Errors can arise in **any layer**. Instead of every layer deciding how to respond to the user, **bubble the error up to a global error handler**, usually a **middleware**, because middleware has access to all incoming requests and outgoing responses.

- In languages with **exceptions** (JavaScript, Python): **throw** the error and **catch** it in the middleware.
- In languages like **Go**, where errors are **returned**: keep returning the error from repository to service to handler until it reaches the middleware.

Every language lets you define **custom errors**. Repositories can throw **database errors**, services can throw **internal errors**, and handlers can throw **validation errors**. The middleware reads the error, **decides what kind it is**, and returns the right response.

### 5.3 Worked Example: A Book Management Platform

Imagine a simplified Goodreads. The `create book` endpoint takes `name` (required) and `description` (optional). Here is how the global handler treats different failures.

| # | What happened | Where | Global handler's response |
|---|---|---|---|
| 1 | Book name is **700 characters**, but the rule says **max 500** | **Handler** (validation) | `400 Bad Request` plus the validation messages so the user can fix the data |
| 2 | A book with this name **already exists** (the repository's `INSERT` hit a **unique constraint violation**) | **Repository** | `400` (bad request, since it's caused by the user's data) with the message "book already exists" |
| 3 | `GET /books/123`, but **no book with that ID exists** (a `SELECT` returned **no rows**; most relational database drivers have a "no rows" error for this) | **Repository** | The middleware sees a database "no rows" error on a route that asked for one specific resource, so it concludes the resource doesn't exist and returns `404`: "book with ID 123 does not exist" |
| 4 | Creating a book with an **author ID that doesn't exist** (**foreign key violation**) | **Repository** | `404`: this author ID doesn't exist |

A typical HTTP error body has a **code** (the status code), a **message**, and optionally a list of **form-field errors** (an array of objects).

For case 1, notice that the error is created in the handler but responded to in the middleware. It's the same pattern for every layer.

### 5.4 Why It's Worth It

1. **More robust and secure.** It doesn't matter *where* an error occurs, because it is handled at the final gateway. You can't forget a condition in one place.
   - Without it, each repository method would have to turn its own unique-constraint error into a proper `400`. If one method forgets, the error isn't recognized, and most backends convert unrecognized errors into a **`500`**, so the user sees "something went wrong" instead of "this book already exists".
2. **Less redundancy.** Without a central place, the "is it a unique violation? a foreign key violation? no rows?" checks would be repeated around **every** query in every repository method. That means more code and more bugs.

## 6. Security in Error Handling

### 6.1 Don't Leak Internal Details in Error Messages

Be mindful of what leaves your backend. Leaking details can compromise **your platform and your users**. Compromising users is arguably worse, because it damages your **goodwill and trust in the market**.

**The danger:** a database error can contain **table names, index names, and constraint names**. If your global handler simply forwards whatever bubbled up from the repository into the `message` field, malicious users can use those details to plan **more advanced attacks, including more advanced forms of SQL injection**, and keep adapting to bypass your security.

**The rules:**

- **Control your messages.** Work out what kind of error came from which layer, and generate a message **meant for a user**.
- In your **default (fallback) handler**, return `500` with a **generic message** such as "Something went wrong" or "Internal server error". If you got to the default case, it means you've already checked for validation errors, unique-constraint errors, business errors, and so on, and you **don't know** what this error is. It most likely holds internal details, so the user must not see it.

### 6.2 Login Endpoints and User Enumeration

Authentication is **one of the most targeted modules**. A naive login flow does this:

1. Look up the user by email. If missing, return "user with this email does not exist".
2. Check the password. If wrong, return "incorrect password".

That seems natural, but it lets an attacker work **step by step**:

1. Try many emails with one password. For each one that doesn't exist, they see "user does not exist".
2. When they finally see "your password is incorrect", they **know that email belongs to a real user**.
3. Now they try common passwords against that known account.

**Fix:** return the **same message for both cases**: **"Invalid email or password."**

For this kind of thing, the author recommends the **OWASP Cheat Sheet Series**, which has practical dos and don'ts for authentication and many other workflows. Follow whatever is relevant to your use case.

### 6.3 Don't Put Sensitive Data in Logs

Logs feel internal, but they often aren't. A company with significant traffic produces **hundreds of GB of logs per day** and uses **multiple external services** for storage, analysis, and observability. In many major data breaches, the **logs got leaked**, and if they contained credit card numbers, emails, passwords, or API keys, all of that was exposed to many malicious users.

So **don't log** sensitive information such as:

- emails,
- passwords,
- API keys,
- credit card numbers.

For example, when an authentication error occurs, log the **user ID** (not the email) and a **correlation ID**, so you have enough context to debug without exposing secrets.

## 7. Cheat Sheet

**Error types**

| Type | Typical examples | Typical response |
|---|---|---|
| Logic | Double discount, wrong algorithm, missed edge case | Business-metric monitoring, tests, clear requirements |
| Database | Connection/pool exhaustion, unique/foreign key violation, bad SQL, deadlock | Validation, formatted errors, retries for transient issues |
| External service | Network, auth, rate limit (`429`), outage | Timeouts, exponential backoff, fallbacks |
| Input validation | Format, range, missing fields | `400` plus clear messages |
| Configuration | Missing env var in production | Validate at startup and **crash early** |

**Prevention**
- Health checks that test actual work (database, external services, config, caches), not just "is the process up".
- Monitor performance, business metrics, and every error source. Use structured JSON logs.

**Reaction**
- Recoverable → retry with backoff (without overloading the system).
- Non-recoverable → contain and degrade gracefully.
- Automate recovery where safe. Document and test manual recovery. Protect the data first.
- Wrap low-level errors with context as they bubble up. Use boundaries (processes, timeouts, queues).

**Global error handler (one middleware)**

| Error | Response |
|---|---|
| Validation | `400` plus field messages |
| Unique constraint | `400`, "already exists" |
| No rows | `404` |
| Foreign key violation | `404` |
| Anything unknown | `500`, generic message |

**Security**
- Never forward raw internal error text.
- Use "Invalid email or password" for login failures.
- Never log passwords, API keys, emails, or card numbers. Log user ID and correlation ID instead.

## 8. Notes Beyond the Transcript

Everything above follows the video. These are my additions or clarifications:

- **Status code choices.** The video uses `400` for unique-constraint violations and `404` for foreign-key violations. Many teams prefer **`409 Conflict`** for duplicates and **`422`** or `400` for a bad reference, which I covered in REST Part 3. What matters is that the mapping is **consistent**, and the global handler is where you enforce it.
- **Transcript artifacts.** The speech-to-text wrote "4 to 9" for `429`, "OAS" for OWASP, and "dreadlock" and "wagon operator" for deadlock and (probably) the ops engineer. The video also numbers two sections "2.4" in effect, since validation and configuration errors both follow external service errors; I've kept the order the video uses.
- **A tiny illustration of the global handler** (the video has no code; this is only to make the idea concrete, in framework-free Python):

```python
class AppError(Exception):
    def __init__(self, status, message, details=None):
        self.status, self.message, self.details = status, message, details or []

class ValidationFailed(AppError):
    def __init__(self, details): super().__init__(400, "Invalid request", details)

class NotFound(AppError):
    def __init__(self, what): super().__init__(404, f"{what} does not exist")

def to_http_error(err: Exception) -> dict:
    """The one place that decides what the client sees."""
    if isinstance(err, AppError):                       # known, safe-to-show errors
        return {"status": err.status, "body": {"message": err.message, "details": err.details}}
    # Unknown error: log the real one internally, show only a generic message.
    log_internally(err)                                 # includes user ID + correlation ID, never secrets
    return {"status": 500, "body": {"message": "Something went wrong"}}
```
