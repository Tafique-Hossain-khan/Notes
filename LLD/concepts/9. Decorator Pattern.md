# Decorator Design Pattern in Python

Welcome back to the LLD series. Today we're starting a new design pattern called the **Decorator Pattern**. This pattern is very interesting and you'll definitely learn something new. Let's see how we can use this pattern and how it makes building LLD applications better.

---

## 1. The Aim of This Pattern

Suppose we have an object — call it `OBJ1`. I want to give this object **additional responsibilities at runtime**. "Additional responsibilities" means additional functionalities — that whatever `OBJ1` is currently doing, it should be able to do **something more**, and I should be able to change this at **runtime, not compile time**.

### Example

Suppose `OBJ1` has a method called `do_something`. When I call this method, the object returns: `"I did something"`.

Now I want to **dynamically change** this output. For example, sometimes when I call `do_something`, I want it to reply with something else — say, `"I did something great"`.

How can I do this?

---

## 2. The Obvious (Bad) Approach: Inheritance

The first thing you'd think of is **inheritance** — that's what we usually use to dynamically change or enhance an object's properties/functionalities.

### How Inheritance Works (Recap)

- We have a **base class**.
- We have a **child class**.
- The child class **overrides** the base class.

Suppose the base class has a method `run`, and it's not just declared but also **defined** — say its definition returns `"Running"`.

Now, the child class **overrides** this `run` method and changes its output — say it returns `"Running with skates"`.

### Runtime Determination via Reference Type

To determine behavior at runtime:

```python
b = Base()  # or b = Child()
b.run()
```

Whichever class I instantiate (`Base` or `Child`) determines which `run` method gets called:
- If `b` refers to a `Base` object → `"Running"` is printed.
- If `b` refers to a `Child` object → `"Running with skates"` is printed.

This is how I "determine at runtime" which `run` method should be called — I could even wrap this in an `if/else` based on some condition: if a condition is true, create a `Base` object; otherwise, create a `Child` object.

### So Why Do We Need a New "Decorator" Pattern?

The reason is very clear — something we already established in the **first** design pattern lecture of this series: **inheritance is bad**.

Why is inheritance bad?
- It creates **multiple hierarchies**.
- It creates **class explosion**.
- And many other problems — one of which we'll see in the example below, and then see how the Decorator pattern solves it.

## 3. The Mario Game Example (Using Inheritance) — The Problem

You've all played the Mario game as kids. We have a character named **Mario**.

When the game starts, Mario is very small and running. As he gets **power-ups**:
- He gets a **mushroom** → Mario's **height** goes up.
- He gets a **flower** → Mario gets the **gun shooting** ability.
- He gets a **star** → Mario gets the **star ability** — he runs faster and destroys everything he touches. The star ability lasts only for a **limited time**.

These are Mario's power-ups. If I'm designing a game with a Mario character, and I want Mario to keep getting power-ups as he progresses — basically I'm **enhancing the functionalities of the Mario character over time**. I want to **dynamically change/enhance** an object's behavior or functionality — **adding additional responsibilities** to this object.

### If We Used Inheritance...

I'd create a class `Mario`, with a method `get_abilities`. Suppose `get_abilities` simply returns something like `"Simple Mario Character"` — the basic character we get at the start of the game.

To enhance its properties/functionalities, I'd create **child classes**:
- `MarioWithHeightUp` — overrides `get_abilities`.
- `MarioWithGunAbilities` — another class.
- `MarioWithStarAbilities` — another class.

Right now it looks like just 3 classes. But suppose we want this design to be **scalable** — we want to keep adding new characteristics. To complicate things further, suppose the new design says: Mario can have **gun abilities WITH height-up**, and Mario can have **gun abilities WITHOUT height-up** too.

In the actual Mario game, this isn't how it works — if he has gun abilities, he should already have height abilities (he's always tall first, then gets gun abilities). But suppose **our** design wants to be scalable enough that: if Mario gets a flower **without** first getting a mushroom, he simply has gun abilities but **not** height abilities. So there's **no fixed order**.

This means we can have:
- A class `MarioWithGunAbilities`
- A class `MarioWithHeightUp`
- **Another** class `MarioWithGunAndHeightAbilities`

See how complicated this is getting? Now, every new characteristic that gets added to Mario — say the next characteristic is a **flying ability** — we'd need to create:
- `MarioWithFlyAbilities`
- `MarioWithFlyAndHeightUp`
- `MarioWithFlyAndGunUp`
- `MarioWithHeightUp_FlyUp_GunUp`

### This Is Called "Class Explosion"

Class explosion means: we end up with **so many child classes**, and with **every change**, a **new child class** gets created. Managing so many classes in your application becomes very difficult.

This class explosion happens **because of inheritance**. We saw a similar problem in the Strategy Design Pattern lecture — inheritance keeps making the hierarchy longer and bigger, and with every new change, we have to modify the hierarchy.

This is why we generally say **"inheritance is bad"**, and we always say: **favor composition over inheritance**.

So in this Decorator Pattern, what changes do we need so that we can change functionalities at runtime **without** running into problems like class explosion (or other inheritance problems)? The Decorator Pattern solves exactly this, in a very interesting way.

## 4. The Mario Game Example (Using Decorators) — The Solution

Going back to our original example: we have `OBJ1`, and we call `do_something` on it, and it replies `"I did something"`.

Now I want to **dynamically enhance/change** its functionalities/characteristics. I want that when I call `do_something`, I can also get `"I did something amazingly"`.

### What the Decorator Pattern Says

**Decorate** (or **wrap**) `OBJ1` with another new object — call it `Decorator1`.

- Now, whenever you call `do_something`, you call it on **`Decorator1`** first.
- `Decorator1` will call `do_something` on `OBJ1`.
- `OBJ1` replies with what it always replies: `"I did something"`.
- `OBJ1` replies this to `Decorator1`.
- `Decorator1` can **enhance** this reply and give back something else to the client — e.g., `"I did something amazingly"`.

So: `Decorator1` took `"I did something"` and attached `"amazingly"` to it, returning `"I did something amazingly"` to the client. This is how we **dynamically changed the property**.

### Stacking Decorators Infinitely

We can stack this decorator **infinitely**. I can attach a new decorator — `Decorator2` — onto `Decorator1`.

- Now you call `do_something` on `Decorator2`.
- `Decorator2` calls `do_something` on `Decorator1`.
- `Decorator1` calls `do_something` on the object (`OBJ1`).
- `OBJ1` replies `"I did something"` → to `Decorator1`.
- `Decorator1` replies `"I did something amazing"` → to `Decorator2`.
- `Decorator2` finally replies to the client: `"I did something amazing today"`.

So basically, we're **dynamically enhancing** its property — **without using inheritance**. We're using the **Decorator Pattern**.

### What Is the Decorator Actually Doing?

If I say "I'm decorating this base object with another object" — setting color aside — I'm decorating this base object with another object, and I can send the same `do_something` request to it too.

So one thing is clear: this **decorator is also an object**. So there's an **"is-a" relationship** between the decorator and the base object — the **inheritance relationship still exists between both**.

**Why is the inheritance relationship needed here?** So that any request I can send to the base object (`do_something`), I can also send to the decorator — **so that the decorator can behave like the object**. So it **is** an object → **is-a** relationship.

### The Second Relationship: Composition (Has-A)

There's **another** relationship here — a **composition** relationship, which is "has-a". The Decorator **also has-a** object.

Why does it additionally use "has-a"? To **dynamically change** any property/behavior. Meaning: it's **not** using inheritance to dynamically change things — it uses inheritance to **behave like** the object, and it uses **composition** to dynamically **change/extend** its behavior.

This might feel a bit complicated right now, but once you see the UML properly, everything will become clear. For now, just understand this much.

## 5. Understanding Decorator Relationships (General UML)

We have a **base class**, and we have a **Decorator**.

The Decorator has **two types of relationships** with the base class:
1. **Has-a**
2. **Is-a**

So we say: **Decorator IS-A base class**, AND **Decorator HAS-A base class**.

- **Decorator IS-A base class**: so that the Decorator **can behave like** a base class. To behave like something, you have to **become** it (i.e., inherit it). If you inherit a base class, you will behave like the base class. That's why Decorator is-a base class.

- **Decorator HAS-A base class**: meaning the Decorator holds a **reference** to a base class — call it `c` (for "character", as we'll see). Now the Decorator can **call methods on `c`**.

For example, if both the base class and the decorator have a method `run`:
- `run` exists on the Decorator (because it **overrides** it).
- The Decorator can call `c`'s `run`, **and then** call its own `run` — i.e., it can call `c.run()` and **add to** that result with its own logic.

This is exactly what we saw in the "I did something" example. If it's still not clear, the Mario example will make it crystal clear.

## 6. UML for the Mario Example

We have a Mario character, and it can have additional power-ups — e.g., gun ability, height-up characteristic, etc.

### Step 1: ICharacter (the base interface)

At the most basic level: we have a **Mario character**. But what actually IS a Mario character? It's **a character**. So first we create an interface (pure abstract class) for it: **`ICharacter`**.

Following our naming convention (pure abstract class = prefix `I`, and we can also write "Abstract" on top for clarity): `ICharacter` has **one method**: **`get_abilities`**.

This is just a **declaration** — it's a pure abstract class.

### Step 2: MarioCharacter (concrete implementation)

We create a concrete implementation: **`MarioCharacter`**. It also has `get_abilities`. Suppose its `get_abilities` returns: `"Normal Mario Character"`.

### Step 3: CharacterDecorator (the abstract Decorator)

To enhance `MarioCharacter`'s functionalities at runtime, we need a **Decorator** that will decorate this Mario object.

We create a Decorator class: **`CharacterDecorator`**. This Decorator is **itself an abstract class** — meaning we can have **different types** of decorators.

The relationship:
- **`CharacterDecorator` HAS-A `ICharacter`**
- **`CharacterDecorator` IS-A `ICharacter`**

This is interesting — maybe the first time you're seeing **both** "is-a" and "has-a" relationships together in a UML diagram.

Since `CharacterDecorator` **is-a** `ICharacter` (via inheritance), it also gets the `get_abilities` method. But since `CharacterDecorator` is **itself** an abstract class, it **doesn't define** `get_abilities` either — it just **declares it** (keeps it abstract). That's its child classes' responsibility to define.

### Step 4: Concrete Decorators

We now build different types of decorators:

1. **`HeightUpDecorator`**
2. **`GunPowerDecorator`**
3. **`StarPowerDecorator`**

Each of these:
- Gets the `get_abilities` method (because `CharacterDecorator` inherits `ICharacter`).
- Has a **reference to `ICharacter`** — call this reference `c` (for "character"). This is the "has-a" part.

## 7. How Each Concrete Decorator Enhances Abilities

How do these decorators provide additional responsibilities to the Mario character?

### HeightUpDecorator

`HeightUpDecorator` has a reference `c` to a character (basically `MarioCharacter` in our case). Inside its **own** `get_abilities` method:

1. It first calls `c.get_abilities()` — i.e., **the referenced character's** `get_abilities`. This will call Mario's characteristic. Mario returns whatever it wants to return — say `"Simple Mario Character"`.
2. This decorator then **appends its own characteristic** in front of/after that result. E.g., returns `"Simple Mario Character with Height Up"`.

### GunPowerDecorator

Same idea — it also has a reference `c` (`ICharacter`). Inside its `get_abilities`:
1. First calls `c.get_abilities()` (Mario's, or whatever it's wrapping).
2. Enhances that result with its own ability — appends something about gun power.

### Why This Is Interesting

I can connect these three decorators (`HeightUpDecorator`, `GunPowerDecorator`, `StarPowerDecorator`) with each other in **any order**, and **any number of times**.

### Example: Building a New Character

```python
mario = HeightUpDecorator(MarioCharacter())
```

Here, when I `new` (instantiate) `HeightUpDecorator`, I give it **decorators to wrap** — finally wrapping the base object. First, I want `HeightUpDecorator`. Since its constructor takes an `ICharacter`, I pass it a `MarioCharacter` object: `HeightUpDecorator(MarioCharacter())`.

I've created a Mario character that **also has height-up abilities**. Because whenever I call `mario.get_abilities()`, it calls `HeightUpDecorator`'s `get_abilities` — which internally calls `MarioCharacter`'s `get_abilities` (returns something), and then `HeightUpDecorator` appends to that and returns the final result.

### Stacking Further

```python
gun_pavor = GunPowerDecorator(HeightUpDecorator(MarioCharacter()))
```

You can think about how long a chain you can build — multiple permutations and combinations are possible.

### Adding a New Decorator Doesn't Require Many New Classes

If a new requirement comes — say we need a **`FlyPowerDecorator`** — we **don't** need to create lots of new classes. We just create **one** new class: `FlyPowerDecorator`. Then we can use it at runtime in any combination:

```python
character = FlyPowerDecorator(GunPowerDecorator(MarioCharacter()))
```

You can use it in **any combination** you want.

### Recursion Insight

If you think carefully — we're using **recursion** here. `get_abilities` calls `get_abilities`. If we build a triple hierarchy, we're going **inward recursively**. It's a recursive call, just happening across **different classes**.

### Visualizing the Stack

If we built: `StarPowerDecorator(GunPowerDecorator(HeightUpDecorator(MarioCharacter())))`

We'd have:
- A `MarioCharacter` at the base.
- Wrapped by a `HeightUpDecorator`.
- Wrapped by a `GunPowerDecorator`.
- Wrapped by a `StarPowerDecorator`.

These are decorating each other — each is being passed as an object **into the constructor** of the next.

**How is this possible?** Because, from the UML: **every Decorator IS-A `ICharacter`**. So `HeightUpDecorator` can take a reference to `ICharacter` in its constructor — and `GunPowerDecorator` is **also** an `ICharacter`, so `HeightUpDecorator` can take a `GunPowerDecorator` in its constructor too! That's exactly why we used the **is-a** relationship.

The **has-a** relationship is used to **delegate**: `get_abilities` first says "call the abilities of the character I'm holding" — but to behave like that character (so I can pass different decorators into the constructor), it needs the **is-a** relationship. So whatever I pass into the constructor must **be-a `ICharacter`** — giving us a long hierarchy tree.

### Call Flow (Tracing `get_abilities`)

When we call `get_abilities` on the outermost wrapper (e.g., `StarPowerDecorator`):

1. `StarPowerDecorator`'s `get_abilities` is called first.
2. It says: "call the `get_abilities` of the `ICharacter` reference I'm holding" → calls `GunPowerDecorator`'s `get_abilities`.
3. `GunPowerDecorator`'s `get_abilities` says the same thing: "call the `get_abilities` of my reference first" → calls `HeightUpDecorator`'s `get_abilities`.
4. `HeightUpDecorator` does the same → calls `MarioCharacter`'s `get_abilities`.
5. `MarioCharacter` returns something (e.g., `"Simple Mario Character"`).
6. `HeightUpDecorator` adds onto that and returns (e.g., `"Simple Mario Character with Height Up"`).
7. `GunPowerDecorator` adds onto **that** and returns (e.g., `"... with Gun"`).
8. `StarPowerDecorator` adds onto **that** and returns the final result (e.g., `"... with Star Power"`).

This is, in a sense, like inheritance — basically a **recursive relationship** where you go all the way down the ladder, and once a base case is hit, you come back up adding to the result at each level. **This is pure Decorator Pattern.**

## 8. Standard UML Diagram

The standard UML diagram for the Decorator pattern:

- We have an abstract class **`IComponent`**.
- There can be many **`ConcreteComponent`**s. (In our Mario example, we only had one — `MarioCharacter`. But tomorrow we could introduce a `SonicCharacter` too, mixing games — so there can be many concrete components.)

To dynamically add responsibilities to these concrete components, we need a **Decorator**.

- **`Decorator` HAS-A `IComponent`**, **AND `Decorator` IS-A `IComponent`** — both relationships are followed.
- Since "has-a", the Decorator holds a **reference to `IComponent`**.

We can have multiple types of decorators — **`ConcreteDecoratorA`**, **`ConcreteDecoratorB`**, etc.

- If `IComponent` has `methodA` and `methodB`, then `Decorator` (inheriting `IComponent`) also gets `methodA` and `methodB`.
- `ConcreteDecoratorA` and `ConcreteDecoratorB` (inheriting `Decorator`) also get `methodA` and `methodB`.
- Additionally, they have the `IComponent` reference.
- They can call `methodA`/`methodB` on this `IComponent` reference, **and then** call their own `methodA`/`methodB` logic.

## 9. Standard Definition of Decorator Pattern

> **The Decorator Pattern attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality.**

Now this should make much more sense: we're providing additional responsibilities to an object, **dynamically**.

The next part is very interesting: it provides a **flexible alternative to inheritance** — i.e., we should **avoid subclassing** / avoid relying only on inheritance, because we know inheritance has many cons/disadvantages. We use an **alternative** — the Decorator Pattern — which is: **decorate**, i.e., **wrap** the object with additional decorators.

## 12. Real-World Use Cases

### 1. Text Editor (e.g., Google Docs)

In a text editor, we have **text**, and we can enhance its properties — i.e., **decorate** it — using **Bold**, **Italics**, etc.

- When you write text and make it **bold**, you're decorating it using **Bold**.
- If you then make that bold text **italic**, you're further decorating that bold text using **Italics**.

So **Bold** and **Italics** act as **decorators**, and the **Text** class is our **base class**.

UML sketch:
- A base `Text` class — an abstract class.
- Many decorators: `BoldDecorator`, `ItalicsDecorator`, and you can keep decorating further — e.g., `UnderlineDecorator`, or a font-change decorator.

The Decorator Pattern fits **very well** in these scenarios.

### 2. Form Validation (Backend)

Imagine a frontend form that a user fills and submits to the backend. On the backend, you need to apply **many validations**:
- Check if the email ID entered is valid or not.
- Check whether the request contains an **attack** — e.g., a **SQL injection attack**, a **CSS/XSS injection attack**, etc.

All of these are essentially **decorations** on top of the form:
- First, you look at a **basic form** and its validations.
- Then you apply an **EmailCheckDecorator**.
- On top of that, a **CSSCheckDecorator**.
- On top of that, a **SQLInjectionCheckDecorator**.

This is another use case where the Decorator Design Pattern fits well.
