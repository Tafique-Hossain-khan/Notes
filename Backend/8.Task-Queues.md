# Background Jobs and Task Queues for Backend Engineers

This post covers background tasks from first principles: what they are, why you need them, how a task queue works internally (producers, brokers, consumers, acknowledgements, visibility timeouts), the four kinds of tasks you'll meet, and the design considerations and best practices for running them at scale. The ideas apply to any language or framework. The few code snippets are short, framework-free Python that illustrate the mechanics, and they don't use Celery or any other library.

---

## 1. What Is a Background Task?

A **background task** (or background job) is any piece of code or workflow that runs **outside the request-response life cycle**.

```
Client ──request──▶ Server ──response──▶ Client
                      │
                      └── (work handed off here, runs elsewhere, later)
```

Anything that runs outside this client-server interaction is a background job. That implies three properties:

- It does **not need to happen immediately**.
- It is **not mission-critical to the response**: the client doesn't need its result right now.
- It is **not synchronous**, so it can be offloaded to a separate process and finish however you've programmed it to finish.

If you understand background jobs, you can build backends that are **scalable and responsive**.

## 2. Why Do We Need Them? The Signup Email Example

Imagine a SaaS platform. A user signs up with an email, a name, and a password. The front end calls your backend API, and the backend validates the email, the password length, and the password complexity.

After that succeeds, the backend must **send a verification email**, a step you've seen on many platforms. It proves the user owns the address, and the email contains either:

- a **link** that redirects to the front end, or
- a **6- or 8-digit code** (a one-time password) the user types into the UI.

### 2.1 How the email actually gets sent

Your backend doesn't deliver email itself. You use a third-party email provider (the transcript names Resend, Mailgun, and Brevo). Your backend:

1. Fills an HTML template with the verification link or code.
2. Provides the recipient address, subject, and sender address.
3. Makes an **API call to the provider's server**.
4. The provider checks that your API key is valid and so on, sends the email, and responds with success or failure.

### 2.2 The problem with doing it synchronously

That provider's server is **not under your control**. A traffic spike or an outage can make it slow or unavailable. Suppose you send the email inside the signup request and the provider is down. There are two bad outcomes:

| Scenario | What happens |
|---|---|
| **No error handling around the email call** | The email API call fails, so your whole signup API call fails. The user's signup fails because of a third party. |
| **Error handling exists, but the signup still returns success** | The signup succeeds and the UI says "we've sent you a verification email", but it was never sent. The user has to come back, click "resend email", and hope the provider is up by then. If it is still down, the same lie repeats. |

Both are poor experiences, and both come from doing everything in the same request-response cycle.

### 2.3 The background-job version

1. The user submits the signup form and the front end calls your server.
2. The server does the initial processing: validation, saving the user, generating the verification code, constructing the email content.
3. Instead of calling the email provider now, the server **packages everything needed to send the email**, serializes it (for example to JSON), and **pushes it into a queue**.
4. The server immediately returns a success status (`200` or `201`, depending on your semantics).
5. The front end immediately shows "we've sent a verification email".

On the other side of the queue, a **consumer** (also called a **worker**) does the sending:

1. A consumer, running as a **separate process** from your main backend application, takes the task out of the queue.
2. It **deserializes** the data into the language's native form (a dictionary in Python, an object in JavaScript, a struct in Go).
3. It runs a **handler** you registered, which is the same function you would have run synchronously: build the email from the template, sender, receiver, subject, and user info, then call the provider's API.
4. The provider sends the email and the user receives it.

```
            ┌──────────────┐
 Client ──▶ │  API server  │ ──▶ validate, save user ──▶ push task ─┐
   ▲        └──────┬───────┘                                        ▼
   └── 201 ───────┘                                         ┌───────────────┐
        (immediately)                                       │  Task queue   │
                                                            └───────┬───────┘
                                                                    ▼
                                                  ┌──────────────────────────┐
                                                  │ Worker (separate process)│
                                                  │ pop → deserialize →      │
                                                  │ handler → email provider │
                                                  └──────────────────────────┘
```

Latency is not a problem here. Processing normally takes milliseconds, or at worst 5 to 10 seconds under heavy queue traffic. Verification links and codes usually expire after 15 to 20 minutes, so a few seconds of delay is irrelevant.

### 2.4 When the provider is down

The email API call fails, so the handler fails, so the task fails. In the synchronous world this would break the request and return a `500`. In the background world, the task library puts the task **back into the queue to be retried**.

Libraries differ by language: **Celery** (Python), **BullMQ** (Node.js), **Asynq** (Go). They all implement retries. A popular strategy is **exponential backoff**: wait longer after each failure, up to a configured maximum number of retries (say five).

| Attempt | Waits before retry |
|---|---|
| 1st failure | 1 minute |
| 2nd failure | 2 minutes |
| 3rd failure | 4 minutes |
| 4th failure | 8 minutes |
| ... | stops at the configured maximum (e.g., 5 retries) |

A big provider such as Resend or Mailgun rarely stays down for minutes. Downtime is usually seconds or milliseconds, so the task fails once or twice and then succeeds. The user still gets the email, and nobody saw an error.

### 2.5 The advantages

1. **Responsiveness:** your API isn't blocked by an external service or heavy processing.
2. **Retry and failure detection:** tasks that are prone to failing get automatic retries.
3. **No timeouts caused by dependencies:** a slow third party can't stall your API.
4. **A better overall user experience.**

In summary, background tasks let you offload **time-consuming and non-critical operations**, which keeps your API fast.

## 3. What Typically Goes to the Background

| Task | Why it's offloaded |
|---|---|
| **Sending emails** | Depends on an external service (the example above). |
| **Processing images or videos** | A user uploads an image and you must resize or convert it into multiple formats and sizes. Phones need small images; desktop apps need large ones (2XL, XL, ...). Heavy work, not needed for the response. |
| **Generating reports** | In an enterprise app (say project management) you send daily, weekly, or monthly reports as PDFs or HTML emails (all completed tasks, pending tasks, sprint status). They run on a schedule, for example every midnight or every Sunday at 12:00. Libraries like Celery and BullMQ have **scheduled task** features (cron-style) for exactly this. |
| **Sending push notifications** | The notifications on your phone's notification bar (Swiggy, Zomato: "your delivery partner has reached the restaurant"). The flow is below. |

### 3.1 How push notifications work

1. When the user installs the app, the **device is registered** with the push service of its operating system: **Google's** for Android, **Apple's** for iOS.
2. Your backend stores that device's token in its database.
3. To notify a device, your backend makes a **service call to Google or Apple**, depending on the user's OS.
4. **The OS vendor's service delivers the notification.** Your backend cannot send it to the phone directly.

Because this involves an API call to an external service, it's offloaded to a background task as well.

## 4. Task Queue Internals

A **task queue** is a system for **managing and distributing background jobs**. It is the engine behind the scenes that reliably hands work off to a separate process. A useful mental model: **a to-do list for your backend**. Your application adds items; workers pick them off one by one and execute them.

### 4.1 The Three Roles

| Role | What it does |
|---|---|
| **Producer** | Your application code (Node, Python, Go, ...). It **creates the task**, including every piece of information the worker will need, **serializes** it (JSON or another serializable format your library uses), and **pushes it into the queue**. That's all a producer does. |
| **Broker (the queue)** | Stores tasks until a worker is ready. A temporary holding area. |
| **Consumer / Worker** | Runs in a **different process** (or thread). It monitors the queue for new items, takes one, and executes it with the handler you registered. It can live in the same codebase as the API or in a separate one. |

A task might contain the user ID, the user's name and email, an image to process, or all the data for a report.

**Terminology** (from data structures):

- **Enqueue:** adding an item to the queue (the producer's action).
- **Dequeue:** taking an item out of the queue (the consumer's action).

### 4.2 Technologies Behind the Broker

The "queue" in diagrams is usually backed by real technology:

- **RabbitMQ**
- **Redis** (the transcript mentions its Pub/Sub module for implementing task queues; see the note in section 9)
- **Amazon SQS**, a managed queue service from AWS. It's deployed in multiple regions, so it's a good choice when you scale task processing across nodes around the world.

### 4.3 Acknowledgements

When a worker finishes a task, it sends an **acknowledgement (ack)** back to the queue. That tells the queue the task was processed successfully and **can be removed**.

If no acknowledgement arrives, the queue decides from its parameters what happened. Maybe the task was unresponsive, maybe it failed, and then it applies a retry mechanism. Frameworks like Celery, BullMQ, and Asynq already handle these edge cases.

### 4.4 Visibility Timeout

There is a subtle problem. The queue **removes** a task when a worker takes it, so what if the worker crashes midway, or the external service hangs? The task would be lost.

The solution is the **visibility timeout**: the period during which a task is considered **in progress** with a particular worker.

- If the worker acknowledges within the timeout, the task is done.
- If **no acknowledgement arrives within the timeout** (the worker crashed, the external service hung, or anything else), the queue **makes the task available to other workers again**, so it is never lost.

Someone must always send an acknowledgement to mark a task as a success or a failure.

### 4.5 A Tiny Illustration

This is a minimal in-process model of the producer, queue, worker, serialization, and retry with exponential backoff. It is not production code, but it shows the moving parts:

```python
import json, queue, threading, time

broker = queue.Queue()             # stands in for RabbitMQ / Redis / SQS
MAX_RETRIES = 5

# ---------- PRODUCER (inside your API request handler) ----------
def enqueue(task_name, payload, attempt=0):
    broker.put(json.dumps({"task": task_name, "payload": payload, "attempt": attempt}))

def signup(email, name):
    # ...validate, save user, generate code...
    enqueue("send_verification_email", {"email": email, "name": name, "code": "482913"})
    return 201                      # respond immediately; email is NOT sent yet

# ---------- HANDLERS (registered on the consumer side) ----------
def send_verification_email(payload):
    email_provider_api(payload["email"], payload["code"])   # may raise if provider is down

HANDLERS = {"send_verification_email": send_verification_email}

# ---------- CONSUMER / WORKER (separate process in real life) ----------
def worker():
    while True:
        raw = broker.get()                       # dequeue (blocks until a task arrives)
        task = json.loads(raw)                   # deserialize to a native dict
        try:
            HANDLERS[task["task"]](task["payload"])
            # success → "acknowledge": the task is simply not re-enqueued
        except Exception:
            attempt = task["attempt"] + 1
            if attempt > MAX_RETRIES:
                print("giving up:", task)        # in real systems: dead-letter queue + alert
            else:
                delay = 60 * (2 ** (attempt - 1))   # 60s, 120s, 240s, 480s, 960s
                threading.Timer(delay, enqueue,
                                args=(task["task"], task["payload"], attempt)).start()

threading.Thread(target=worker, daemon=True).start()
```

## 5. The Four Kinds of Tasks

### 5.1 One-Off Tasks

Triggered by something that happened in the request-response cycle, executed once in the background. This is the most common kind. Examples:

- A user registered, so send a verification email.
- Verification succeeded, so send a welcome email.
- Someone requested a password reset, so send the reset link.
- In a social app, someone texted you, so send a notification.

### 5.2 Recurring Tasks

Executed **periodically at specific intervals**.

- **Reports:** daily, monthly, or annual stats sent to users.
- **Cleanup and maintenance jobs.** Example: with **stateful authentication**, every login creates a session row. Over time users accumulate many abandoned (orphan) sessions that are no longer active but were never deleted. A recurring job (monthly, every two months, quarterly) deletes them to free storage.

### 5.3 Chain Tasks

Tasks with a **parent-child relationship**. A task can be triggered only after its parent has been triggered and **completed successfully**.

**Example: an LMS (Udemy-style) video upload.** The instructor uploads a video (for example straight to S3 with a pre-signed URL). The backend acknowledges immediately so the request isn't blocked. Then:

```
Video uploaded
   └─▶ Task 1: encode video into multiple formats/resolutions
          ├─▶ Task 2: generate thumbnails
          │      └─▶ Task 3: process thumbnails into multiple sizes
          └─▶ Task 4: generate audio transcription (subtitles)
```

- Tasks 2 and 4 both depend on Task 1 but **not on each other**, so they can run **in parallel**.
- Task 3 depends on Task 2.

### 5.4 Batch Tasks

A single task, or a single trigger, that fans out into **many tasks**.

**Example 1: Delete account.** A big platform can't delete a user's data inside one request. The data may be spread across databases, shards, and regions, and deletion could take 40 to 60 seconds or more, and you can't block an API call that long. Instead:

1. The API call creates a `delete_account` task, pushes it to the queue, and **responds immediately** with success. The front end logs the user out.
2. Optionally, a **grace period** (3 or 7 days) lets the user log back in and cancel. Otherwise the account is considered deleted immediately.
3. The worker runs the deletion in the background: go through the user's resources (for example, projects they own in a project-management app), remove their entities, delete their profile and assets (logos, cover images), delete the account itself, and send a "your account has been deleted" email.

The `delete_account` task can itself spawn many tasks (delete entities, delete assets, ...), which is why it's a batch task.

**Example 2: Report sending at midnight.** At 12:00 or at the end of the week, a big platform triggers thousands of identical "generate report and send to user" tasks at once, one per user.

## 6. Design Considerations at Scale

### 6.1 Idempotency

Design tasks so they can be **executed multiple times safely, without side effects**. This ties directly to the idempotency concept from the REST series.

In the transcript's example, the delete-account task goes through the user's entities and removes or nulls them. If something fails midway (a database error or an external API call), you want a **transaction** and a (possibly manual) **rollback**, so that when the queue retries the task, it starts again **from scratch, at 0% completion**, as if the failed attempt never happened.

(The next section's note explains why this matters even more than it seems.)

### 6.2 Robust Error Handling

Everything happens in a different process, so no one is looking at it live. Cover every edge case and bottleneck. Catch errors, **log them**, and let the task be retried.

### 6.3 Monitoring

Track at all times:

- how many tasks are in the queue,
- how many succeeded,
- how many failed,
- the **major reasons for failure** (an external service or an internal error).

Tools like **Prometheus** and **Grafana** support this through **metrics**: every time something happens (a task created, completed, failed), you record a metric, and a dashboard shows the current state. (Metrics, logs, traces, and the ELK stack are covered in a separate video.)

### 6.4 Scalability

If the user base doubles, add more **consumers**. Design the system so you can **scale consumers horizontally** (add more nodes) and keep processing responsive.

### 6.5 Ordering

If tasks must run in a particular order, make sure your **library or framework supports ordered delivery**.

### 6.6 Rate Limiting

If tasks call external services, **rate-limit them** to avoid overloading those services. External services charge per API call and enforce their own rate limits. A burst of thousands of queued tasks could blow through both.

## 7. Best Practices

1. **Keep tasks small and focused.** One task, one processing unit.
   - If one fails, the others are unaffected.
   - If one step depends on another, use a **chain** (parent-child) so a failing child can be retried on its own (with exponential backoff) without redoing the parent.
   - A big task that fails near the end forces the whole thing to repeat, wasting worker CPU.
   - Small tasks are easier to scale, debug, and monitor, and the queue can apply retries more easily.
2. **Avoid long-running tasks.** If a task takes a long time, it's doing too much. Break it into smaller chunks, either concurrent tasks or parent-child tasks, depending on the requirements.
3. **Use proper error handling and logging.** This gives the queue the chance to retry, and gives you the information to debug whether it was an external service or an internal error.
4. **Monitor queue length and worker health.** Set up **alerting**. If the queue length exceeds a limit, scale up. If workers keep going down, investigate why. You should always know that the background system is running smoothly.

## 8. Cheat Sheet

**Concept**
- Background task = code that runs outside the request-response cycle, so the API can answer immediately.
- Flow: **producer → serialize → enqueue → broker → dequeue → deserialize → handler (worker) → ack**.

**Reliability machinery**

| Mechanism | Purpose |
|---|---|
| Retries with exponential backoff | Survive temporary failures (1 → 2 → 4 → 8 min, capped at N tries) |
| Acknowledgement | Tells the queue the task is done and can be removed |
| Visibility timeout | A task from a crashed or hung worker is made available to others, so it's never lost |

**Task types**

| Type | Description | Example |
|---|---|---|
| One-off | Triggered once by an event | Verification, welcome, or reset email |
| Recurring | Runs on a schedule | Daily reports, orphan-session cleanup |
| Chain | Child runs only after parent succeeds | Encode video → thumbnails → thumbnail sizes; plus transcription in parallel |
| Batch | One trigger spawns many tasks | Delete account; thousands of reports at midnight |

**Typical use cases:** emails, image and video processing, report generation, push notifications.

**Technologies:** brokers: RabbitMQ, Redis, Amazon SQS. Libraries: Celery (Python), BullMQ (Node.js), Asynq (Go).

**Design checklist:** idempotency, robust error handling, monitoring, horizontal scalability, ordering, rate limiting.

**Best practices:** small and focused tasks, no long-running tasks, good logging, alert on queue length and worker health.

## 9. Notes Beyond the Transcript

Everything above follows the video except these additions and clarifications, which I'm flagging so you can tell them apart:

- **The code snippet** is mine. It's a single-process toy and not how production systems are built.
- **Redis Pub/Sub vs. task queues.** The video mentions Redis Pub/Sub as a way to implement task queues. In practice, Pub/Sub is fire-and-forget (messages are lost if no subscriber is listening), so reliable task queues on Redis use **lists or streams** instead. This is how Celery, BullMQ, and similar libraries do it internally. When you pick a broker, check that it gives you durability and acknowledgements.
- **Delivery is typically "at least once".** Because of visibility timeouts and retries, a task may occasionally run **more than once** (for example, the worker finished but crashed before sending the ack). That's the deeper reason idempotency matters: an email task should not email the user twice, so design handlers to check "was this already done?" (for instance with an idempotency key, as in the REST series, Part 3).
- **Dead-letter queues.** After the maximum retries, failed tasks usually move to a **dead-letter queue** for inspection instead of vanishing. The video doesn't mention it, but it's standard and goes naturally with the alerting advice.
- The video places this topic after caching. It also links to a few topics it says are covered in other videos (metrics, logs, traces, stateful authentication).
