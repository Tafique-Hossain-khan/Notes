# Full-Text Search for Backend Engineers: Why `LIKE` Fails and How Elasticsearch Fixes It

Search looks easy until your data grows. This post explains, in simple terms, why a normal database query becomes slow and "dumb" for search, how the **inverted index** changes the problem, how **Elasticsearch** ranks results, and what a real benchmark between **PostgreSQL** and **Elasticsearch** looks like.

You do not need to know search theory to follow this. The goal is the intuition: *when should I reach for a search engine, and why does it work?*

## 1. The Story: A Search Feature in 2005

Imagine it is **2005**. You are a software engineer at an e-commerce company. The company is growing fast (the dot-com era), and you have a task: build an API that takes a user's search text, looks through your products, and returns relevant results.

You have about **5,000 products**. In a typical relational database you write:

```sql
SELECT *
FROM products
WHERE name LIKE '%laptop%'
   OR description LIKE '%laptop%';
```

The `%` symbols mean "any characters can come before or after". So if the word `laptop` appears anywhere in the name or the description, the row is returned.

A customer searches for "laptop", gets a few results, and life is simple.

### Then the company grows

Within a short time you have **millions of products**. The same simple query that used to return in **50 milliseconds** now takes **30 seconds**. Customers are frustrated. Your manager is frustrated. Everyone asks you to fix it, and you are clueless.

And the requirements grow, too. It is not just "make it faster":

| Requirement | What it means |
|---|---|
| **Fast** | Results in milliseconds, not seconds |
| **Relevant** | Search "laptop" and show a *MacBook Pro* first, not a *laptop bag* |
| **Typo-proof** | During a sale, customers type in a hurry. "lpatop" should still find laptops |

This is the story of why search engines like **Elasticsearch** exist.

## 2. The Librarian Analogy

To get the intuition, think of your relational database (PostgreSQL, MySQL) as a **librarian**. You ask the librarian where a book is, and the librarian knows how to find it. But the librarian has **one fatal flaw**.

### Flaw 1: The librarian checks every book, one by one

You say: *"I'm looking for books about machine learning."*

The librarian starts:

1. Book 1: *Harry Potter and the Philosopher's Stone*. No "machine learning". Next.
2. Book 2: *Game of Thrones*. No. Next.
3. Book 3: *Introduction to Machine Learning*. Match! Return it.
4. ...and keeps going through **every book on every shelf**, to the very end.

For a small library that is fine. For a library with 10 million or 1 billion books, it could take minutes, hours, or even days.

### Flaw 2: The librarian has no idea what "relevant" means

Suppose two books match:

- Book A is titled **"Introduction to Machine Learning"**.
- Book B is about something else entirely, but the phrase "machine learning" appears once on its last page.

The librarian may return Book B first. Both "match", and the librarian does not know that A is far more useful to you. You might not even want Book B at all.

### How this maps to your database

The query `WHERE review ILIKE '%machine learning%'` is exactly this librarian:

- The database **scans every row**.
- It **examines every text field** and does **character-by-character pattern matching**.
- It is thorough (it will find all matches) but **painfully slow**.
- It returns results in **no meaningful order**. The best result could be at position 1,000 or 10,000.

> **Side note:** `ILIKE` (Postgres) is the case-insensitive version of `LIKE`. The transcript says "I like" because that is how it sounds out loud.

## 3. Why the Industry Needed Something Better

Around the same time (2005), there was an **information explosion**:

- **Google** was crawling and indexing billions of web pages.
- **Amazon** was cataloging millions of products.
- **LinkedIn** was indexing millions of profiles.

These companies **cannot wait 30 seconds** for search results. Even **2 seconds** of delay is considered huge today. Search has to respond in **milliseconds**, because slow search directly hurts conversion and user retention, and these companies make a great deal of money every second.

The solution did not appear out of nowhere. Text search and **information retrieval** had been studied by computer scientists since the **1960s**. The big breakthrough came from flipping the problem upside down.

## 4. The Big Idea: The Inverted Index

> Instead of searching through every document for a word, **what if we record, in advance, which documents each word appears in?**

Back to the library. Instead of the librarian walking every shelf, imagine that **when each book arrives**, someone reads all its words and builds an index:

> "For each word, which books contain it, and on which pages?"

Here is a small example (using the transcript's numbers):

**Index for the word `machine`**

| Book | Pages where "machine" appears |
|---|---|
| Introduction to Machine Learning | 1, 15, 23 |
| The Machine Age | 5, 89 |
| Coffee Machine Manual | 1 |

**Index for the word `learning`**

| Book | Pages where "learning" appears |
|---|---|
| Introduction to Machine Learning | 1, 16, 24 |
| Learning to Cook | 2 places |
| Deep Learning Fundamentals | 3 places |

(In real life, a book called *Introduction to Machine Learning* would use these words hundreds of times. The example uses 3 just to keep it simple.)

Now the search works the other way around:

- **Before (normal scan):** go through the *content* to find the *terms*.
- **Now (inverted index):** look up the *term* and instantly get the *content*.

That is why it is called an **inverted** index: we inverted the direction of the search.

### The same idea in code (tiny Python demo)

```python
from collections import defaultdict

docs = {
    1: "Introduction to Machine Learning",
    2: "The Machine Age",
    3: "Coffee Machine Manual",
    4: "Learning to Cook",
    5: "Deep Learning Fundamentals",
}

# Build the inverted index ONCE, when documents are added
index = defaultdict(set)
for doc_id, text in docs.items():
    for word in text.lower().split():
        index[word].add(doc_id)

# Search = a dictionary lookup, not a scan of every document
print(index["machine"])                       # {1, 2, 3}
print(index["machine"] & index["learning"])   # {1}  -> docs with BOTH words
```

Searching is now a lookup in a dictionary instead of a loop over every document. That is the whole secret behind fast text search. (Real engines add much more, but this is the core.)

## 5. Lucene and Elasticsearch

The inverted index is what powers **Elasticsearch**, one of the most famous full-text search tools.

Elasticsearch is not a brand-new invention. It is built on **Apache Lucene**, the key inverted-index-based text search library. Lucene is the engine, and many other tools use it too.

Elasticsearch is **not the only option**:

- Many tools use Lucene underneath.
- Even relational databases like **PostgreSQL** now have built-in **full-text search** support.

### What is a "document" in Elasticsearch?

In Elasticsearch, a single record (like one book, one product, or one review) is called a **document**. It is stored as **JSON**, similar to MongoDB.

```json
{
  "title": "Introduction to Machine Learning",
  "description": "A beginner-friendly guide...",
  "content": "..."
}
```

## 6. Relevance Scoring (and BM25)

The inverted index makes search **fast**. But Elasticsearch also gives you something the librarian never had: **relevance**.

Looking at our `machine` example:

- **Introduction to Machine Learning**: the word is in the **title** *and* appears **many times**. Two strong signals, so it ranks **first**.
- **The Machine Age**: in the title, but used less often. Ranks **second**.
- **Coffee Machine Manual**: in the title, but used very rarely. Ranks **third**.

So instead of "anything that matches", you get "the most meaningful matches first". This is called **relevance scoring**.

### Do you need to understand the math?

The transcript's advice: **no, not at first.** Understanding the architecture is nice, but if you just want to build a feature:

1. Recognize that your use case needs full-text search.
2. Read the docs, copy the example, and implement it.
3. Move on.

You only need deep knowledge if you are building a search library yourself or an alternative to Elasticsearch. Knowing the best practices is enough. If you are curious, the Elasticsearch docs are a good place to learn more.

### BM25: the scoring algorithm

Elasticsearch uses an algorithm called **BM25** to score results. It looks at four main things:

| Factor | Plain-English meaning | Example |
|---|---|---|
| **Term frequency (TF)** | How often does the word appear **in this one document**? | "machine" appears 3 times in this book |
| **Document frequency (DF)** | How common is the word **across all documents**? | If "the" is in every book, it tells you little. A rare word is more meaningful |
| **Document length** | How long is the document? | A word in a short document usually matters more than the same word in a huge one |
| **Field boosting** | *Where* does the word appear? | Title is more important than description, which is more important than content |

### Field boosting, explained

If the term appears in the **title**, that is a stronger signal than appearing in the **description**, which is stronger than appearing in the **content**.

And this is **not fixed**. When you write a search query you can decide your own boosts. For example, you can say "the content matters most for my use case".

Elasticsearch queries are written in a **JSON-based query language** (the Query DSL), which offers many parameters for different kinds of search.

Here is what field boosting looks like (this example is mine, not from the video):

```json
{
  "query": {
    "multi_match": {
      "query": "machine learning",
      "fields": ["title^3", "description^2", "content"]
    }
  }
}
```

`^3` means "a match in the title counts three times as much".

## 7. Typo Tolerance and Type-Ahead

Besides plain text matching, search engines handle **typos** very well.

The transcript uses Google as the example (we do not know whether Google uses Elasticsearch or something proprietary built on Lucene, but it is a similar technology):

1. Start typing "what is..." and you instantly get suggestions. This is called a **type-ahead** interface. You see the same on Amazon.
2. Now type **"what is treading today"** with an intentional typo (instead of *trending*).
3. Google still understands that **"what is trending today"** is the most likely intended query.

Full-text search tools can infer this from context. For experiences like **typos and type-ahead**, they are a major advantage.

Elasticsearch handles typos with **fuzzy matching** (this snippet is my addition):

```json
{
  "query": {
    "match": {
      "review": {
        "query": "lpatop",
        "fuzziness": "AUTO"
      }
    }
  }
}
```

This still finds documents containing "laptop". A `LIKE '%lpatop%'` query would find nothing.

## 8. Your Options: Postgres Full-Text Search vs Elasticsearch

If you need to build a search-like feature in a backend, you have two main choices.

| Option | When it makes sense |
|---|---|
| **PostgreSQL full-text search** | You already use Postgres and want to keep your stack simple. Modern Postgres has built-in full-text search. |
| **Elasticsearch** | Your company **already runs Elasticsearch** (for example as part of the ELK stack, below), or you need advanced search features. |

A small Postgres full-text example (my addition, not from the video):

```sql
-- Add a searchable column and index it
ALTER TABLE reviews
  ADD COLUMN search_vec tsvector
  GENERATED ALWAYS AS (to_tsvector('english', review)) STORED;

CREATE INDEX reviews_search_idx ON reviews USING GIN (search_vec);

-- Search + rank by relevance
SELECT id, review, ts_rank(search_vec, query) AS score
FROM reviews, plainto_tsquery('english', 'laptop') AS query
WHERE search_vec @@ query
ORDER BY score DESC
LIMIT 20;
```

The `GIN` index is Postgres's version of an inverted index, the same core idea.

## 9. The ELK Stack

Elasticsearch is not only used for search boxes and type-ahead. It is also very famous for **log management**, through the **ELK stack**:

- **E**lasticsearch: stores and searches the data
- **L**ogstash: collects and processes logs
- **K**ibana: visualizes data

(The transcript says "Elastic Search, Kibana and Lock stacks", meaning Logstash.)

Because Elasticsearch is very fast at searching logs, deriving statistics, and visualizing data, many companies already run it. If your company already has Elasticsearch as part of the ELK stack, using it for your full-text search needs also makes a lot of sense, instead of adding Postgres full-text search.

## 10. Hands-On Benchmark: Postgres `LIKE` vs Elasticsearch

To make this real, the video builds a small side-by-side comparison. Here is the setup.

### 10.1 Setup

- **App:** a Next.js project (chosen only because LLMs generate Next.js prototypes well; there is no special reason to use it).
- **UI:** one search box that runs the same query on **both** a PostgreSQL database and an Elasticsearch instance and shows the time each one took.
- **Postgres:** a **Neon** serverless cloud Postgres instance.
- **Elasticsearch:** an **Elastic Cloud** instance.
- **Fairness:** both are hosted in **US-West**, so network distance should not skew the result.

### 10.2 The data

A big CSV file of about **50,000 reviews**, each with:

| Field | Meaning |
|---|---|
| `review` | The review text |
| `sentiment` | `positive` or `negative` |

In Postgres, a `reviews` table has three columns: `id`, `review` (text), and `sentiment`.

### 10.3 The populate script (Node.js)

This script loads the same 50,000 rows into both systems.

**Step 1: Configuration and clients**

- Read the database URL, the Elasticsearch address, and the Elasticsearch API key from environment variables.
- If any is missing, throw an error.
- Create a Neon client and an Elasticsearch client.

**Step 2: Read the CSV**

- Read the file synchronously and store it in a variable.

**Step 3: Populate Postgres**

1. Create the `reviews` table **if it does not exist** (it already existed, so this step was skipped).
2. Reset the ID field so we start fresh.
3. Filter out rows that do not have **both** `review` and `sentiment`.
4. Insert in **batches of 1,000**, because inserting everything at once hits a limit on the Neon instance. Each batch is a normal `INSERT INTO reviews (review, sentiment) VALUES ...`.

**Step 4: Populate Elasticsearch**

1. Check whether the `reviews` index exists. If it does, **delete it** and start fresh.
2. Create the index with a **mapping** (the schema), with two fields:
   - `review` of type **`text`**
   - `sentiment` of type **`keyword`**
3. Filter out invalid rows again (both fields must be present).
4. **Bulk insert** all 50,000 records.

**Verification:**

- Elastic Cloud shows **50,000 documents**.
- In the Neon SQL editor, `SELECT count(*) FROM reviews;` returns **50,000**.

Both systems now hold identical data.

#### `text` vs `keyword`: the difference in simple terms

The transcript's explanation of these types is a little loose, so here is the clean version:

| Type | What Elasticsearch does | Use it for |
|---|---|---|
| **`text`** | **Analyzes** the value: splits it into words (tokens), lowercases them, and builds an inverted index. This is what enables full-text search. | Free text: reviews, descriptions, titles |
| **`keyword`** | Stores the value as **one exact string**. Only exact matches work. | Fixed values: status, sentiment, IDs, tags |

So `review` is `text` (searchable word by word), and `sentiment` is `keyword` (it is only ever exactly "positive" or "negative").

Here is the equivalent in the Python client (a rough sketch of the Node script's logic):

```python
from elasticsearch import Elasticsearch, helpers

es = Elasticsearch("https://<your-deployment>.es.cloud", api_key="<key>")

if es.indices.exists(index="reviews"):
    es.indices.delete(index="reviews")          # start fresh

es.indices.create(index="reviews", mappings={
    "properties": {
        "review":    {"type": "text"},          # analyzed, full-text searchable
        "sentiment": {"type": "keyword"},       # exact match only
    }
})

helpers.bulk(es, (
    {"_index": "reviews", "_source": {"review": r, "sentiment": s}}
    for r, s in rows if r and s                 # skip incomplete rows
))
```

### 10.4 The search API route

The UI is generic. The interesting part is the API endpoint that runs when the user types something and presses enter.

**What it does:**

1. Take the **search term** from the request JSON. If something is wrong, return **bad request** (`400`).
2. Start a **stream** to the front end. The two systems finish at different times, and we do not want one to delay the other. As each result is ready, it is streamed to the UI, so you can *see* which one wins and how long each took.
3. Run both searches and time them.

**Postgres search:**

- Start a timer.
- Run:

```sql
SELECT id, review, sentiment
FROM reviews
WHERE review ILIKE '%' || $1 || '%';
```

- `ILIKE` makes the search **case-insensitive** for wider coverage. The `%` on both sides means "any characters before or after, as long as the term is present".
- Stop the timer and stream the result.

**Elasticsearch search:**

- Query the `reviews` index with a query string.
- **Lowercase** the search term to cover as many matches as possible.
- Allow any characters before and after it (wildcard-style matching).
- Add some default fields to enhance the search.
- Stop the timer and stream the result.

**Fairness:** the criteria were deliberately kept the same: lowercase, with anything allowed before and after, so both return the same number of results. The demo is about **speed**, not about showing off relevance or typo tolerance.

**Front end:** it simply reads the streamed responses as they arrive.

## 11. Results

| Search term | Elasticsearch | Postgres (`ILIKE`) | Notes |
|---|---|---|---|
| `laptop` | about **1 second** | about **3 seconds** (almost 4) | |
| `something` | about **500 ms** | about **7.5 seconds** | Both found about **8,000** results |

Even with the **same number of results**, the time difference is huge: Elasticsearch finishes while Postgres is still scanning.

And this is with only **50,000 rows**. Remember the 2005 story: with millions of rows, a scan-based `LIKE` gets dramatically worse, while an inverted index stays fast.

> Note that this is a simple benchmark. Postgres `LIKE '%term%'` is one of the worst-case approaches. Postgres **full-text search with a GIN index** (section 8) would perform much better than the numbers above. The video's point is that a *scan* loses to an *index*.

## 12. How Much Should You Learn?

The transcript gives a clear priority:

- **Databases:** you must **master** them: how to work with them, how to optimize them, how indexes work, every part of it. As a backend engineer, databases touch about **99% of your codebase**.
- **Elasticsearch / full-text search:** you should have it **in your arsenal**, but you do **not** need to master it. For most use cases, adapting snippets from the docs (or an LLM) is more than enough. If you need to optimize later, read more then.

When a requirement says "search", "type-ahead", or "typo-tolerant", the right reaction is: *this is a full-text search problem*, so use Postgres full-text search or Elasticsearch instead of `LIKE`.

## 13. Cheat Sheet

**The problem with `LIKE '%term%'`**
- Scans **every row** and checks every character, so it is slow and gets slower as data grows.
- Has **no concept of relevance**, so the best result can be at position 10,000.
- Cannot handle **typos**.

**The solution**
- **Inverted index:** map each **word to the documents (and positions) that contain it**. Search becomes a lookup.
- Powered by **Apache Lucene**, which Elasticsearch is built on.

**Relevance (BM25) looks at**
1. Term frequency (how often in this document)
2. Document frequency (how common across all documents)
3. Document length
4. Field boosting (title > description > content, and you can tune it)

**Elasticsearch basics**
- A record is a **document** (JSON).
- Queries use the **JSON Query DSL**.
- `text` = analyzed for full-text search. `keyword` = exact match.

**Choosing a tool**
- Postgres full-text search: simple stack, already using Postgres.
- Elasticsearch: already in your company (for example ELK), or you need advanced search.

**ELK** = Elasticsearch + Logstash + Kibana, a famous log-management stack.

**Benchmark (50,000 rows):** Elasticsearch ~0.5 to 1 s vs Postgres `ILIKE` ~3 to 7.5 s.
