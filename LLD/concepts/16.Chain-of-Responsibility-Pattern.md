# Chain of Responsibility Design Pattern

## The Core Idea

Imagine you have a **Client** that sends a **request**. But instead of sending that request to one single object, it sends it along a **chain of objects**.

Here is what the chain looks like:

```
Client → Request → R1 → R2 → R3 → ...
```

- `R1`, `R2`, `R3` are separate objects linked together — `R1` holds a reference to `R2`, `R2` holds a reference to `R3`, and so on.
- The Client sends the request to `R1` first.
- `R1` checks: can I handle this request? If yes, it responds. If no, it passes the request to `R2`.
- `R2` does the same. If it cannot handle it, it passes to `R3`. And so on.
- The response travels back through the chain to the Client.

When you look at this, it reminds you of a **linked list**. One object pointing to the next, traversal happening through a `next` pointer. That similarity is intentional — but the intent is very different. We will come back to that distinction.

---

## The ATM Example

This is the standard example for Chain of Responsibility. There is no better way to understand it.

When you go to an ATM to withdraw money, the machine has **separate compartments for different denominations** — one for ₹1000 notes, one for ₹500, one for ₹200, one for ₹100, and so on. Each compartment is a **handler**.

Why separate? Because each denomination has a different physical size, a different way to validate authenticity, and a different count available at any given time.

When you request ₹5000:
1. The ₹1000 handler checks: can I fulfil ₹5000? It has 5 notes → yes. Done.

When you request ₹6000 and the ₹1000 handler only has 5 notes (₹5000):
1. ₹1000 handler dispenses 5 notes (₹5000), then passes the remaining ₹1000 to the ₹500 handler.
2. ₹500 handler has 10 notes, needs 2 → dispenses 2 × ₹500. Done.

When you request ₹150 but only ₹1000, ₹500, ₹200, ₹100 handlers exist (no ₹50 handler):
1. ₹1000 → cannot handle → passes to ₹500.
2. ₹500 → cannot handle → passes to ₹200.
3. ₹200 → cannot handle → passes to ₹100.
4. ₹100 → can give ₹100, but ₹50 still remains → either partial fulfilment or fail the transaction. This depends on the use case.

The chain keeps passing the request forward until either the request is fully handled or the chain ends.

## UML Diagram

```
┌──────────────────────────────────────────────────────────┐
│               <<abstract>>                               │
│              MoneyHandler                                │
├──────────────────────────────────────────────────────────┤
│ # _next_handler: MoneyHandler | None                     │
├──────────────────────────────────────────────────────────┤
│ + set_next_handler(handler: MoneyHandler)  ← defined here│
│ + dispense(amount: int)                   ← abstract    │
└──────────────────────────────────────────────────────────┘
         △                      △                    △
         │ (inherits)           │ (inherits)         │ (inherits)
         │                      │                    │
┌──────────────────┐  ┌──────────────────┐  ┌──────────────────┐
│  Handler1000     │  │  Handler500      │  │  Handler100      │
├──────────────────┤  ├──────────────────┤  ├──────────────────┤
│ - _num_notes:int │  │ - _num_notes:int │  │ - _num_notes:int │
│ + dispense(amt)  │  │ + dispense(amt)  │  │ + dispense(amt)  │
└──────────────────┘  └──────────────────┘  └──────────────────┘

┌───────────────────────────────────────────────────────────┐
│                       Client                              │
├───────────────────────────────────────────────────────────┤
│ - handler: MoneyHandler   ← holds ref to the first handler│
│ + withdraw(amount)        ← calls handler.dispense(amt)  │
└───────────────────────────────────────────────────────────┘

Chain setup (done in client / main):

  Handler1000 → Handler500 → Handler200 → Handler100 → None
  (set via set_next_handler calls)
```

**Critical design decision:** The `_next_handler` reference lives in the **abstract parent class** (`MoneyHandler`), not in the concrete classes. This way:

- `Handler1000` does not hard-code "my next is `Handler500`". 
- `Handler500` does not hard-code "my next is `Handler200`".
- The chain is assembled dynamically in the client/main code using `set_next_handler()`.

If tomorrow ₹500 notes are demonetised, you just change the chain setup — not the handler classes themselves. The concrete handlers are completely decoupled from each other.

This also follows:
- **Open/Closed Principle** — to add a ₹50 handler tomorrow, just create a new class. No existing code changes.
- **Single Responsibility Principle** — `Handler1000` only knows about ₹1000 notes. `Handler500` only knows about ₹500 notes. If the physical structure of a ₹500 note changes, only `Handler500` needs updating.

---

## Why Not Just Use If-Else?

You could put all this logic in one class with nested `if-elif-else` blocks. But:

- Adding a new denomination (₹50) means modifying existing code → violates Open/Closed Principle.
- One class handles everything → violates Single Responsibility Principle.
- If the ₹100 note changes shape/security features, you must hunt through one big class to find the relevant part.

With the Chain of Responsibility pattern, each handler owns its own logic completely. The chain is assembled separately. Everything stays independent.

## Python Implementation

```python
from abc import ABC, abstractmethod


class MoneyHandler(ABC):
    """Abstract base class for all denomination handlers."""

    def __init__(self):
        self._next_handler: 'MoneyHandler | None' = None

    def set_next_handler(self, handler: 'MoneyHandler') -> None:
        """Link the next handler in the chain."""
        self._next_handler = handler

    @abstractmethod
    def dispense(self, amount: int) -> None:
        """Try to dispense the requested amount. Pass remainder to next handler."""
        pass


class Handler1000(MoneyHandler):
    """Handles ₹1000 notes."""

    def __init__(self, num_notes: int):
        super().__init__()
        self._num_notes = num_notes

    def dispense(self, amount: int) -> None:
        notes_needed = amount // 1000

        if notes_needed > self._num_notes:
            notes_needed = self._num_notes
            self._num_notes = 0
        else:
            self._num_notes -= notes_needed

        if notes_needed > 0:
            print(f"Dispensing {notes_needed} x ₹1000 note(s)")

        remaining = amount - (notes_needed * 1000)

        if remaining > 0:
            if self._next_handler is not None:
                self._next_handler.dispense(remaining)
            else:
                print(f"Cannot fulfil remaining ₹{remaining} — insufficient funds in ATM")


class Handler500(MoneyHandler):
    """Handles ₹500 notes."""

    def __init__(self, num_notes: int):
        super().__init__()
        self._num_notes = num_notes

    def dispense(self, amount: int) -> None:
        notes_needed = amount // 500

        if notes_needed > self._num_notes:
            notes_needed = self._num_notes
            self._num_notes = 0
        else:
            self._num_notes -= notes_needed

        if notes_needed > 0:
            print(f"Dispensing {notes_needed} x ₹500 note(s)")

        remaining = amount - (notes_needed * 500)

        if remaining > 0:
            if self._next_handler is not None:
                self._next_handler.dispense(remaining)
            else:
                print(f"Cannot fulfil remaining ₹{remaining} — insufficient funds in ATM")


class Handler200(MoneyHandler):
    """Handles ₹200 notes."""

    def __init__(self, num_notes: int):
        super().__init__()
        self._num_notes = num_notes

    def dispense(self, amount: int) -> None:
        notes_needed = amount // 200

        if notes_needed > self._num_notes:
            notes_needed = self._num_notes
            self._num_notes = 0
        else:
            self._num_notes -= notes_needed

        if notes_needed > 0:
            print(f"Dispensing {notes_needed} x ₹200 note(s)")

        remaining = amount - (notes_needed * 200)

        if remaining > 0:
            if self._next_handler is not None:
                self._next_handler.dispense(remaining)
            else:
                print(f"Cannot fulfil remaining ₹{remaining} — insufficient funds in ATM")


class Handler100(MoneyHandler):
    """Handles ₹100 notes. Acts as the last handler in this chain."""

    def __init__(self, num_notes: int):
        super().__init__()
        self._num_notes = num_notes

    def dispense(self, amount: int) -> None:
        notes_needed = amount // 100

        if notes_needed > self._num_notes:
            notes_needed = self._num_notes
            self._num_notes = 0
        else:
            self._num_notes -= notes_needed

        if notes_needed > 0:
            print(f"Dispensing {notes_needed} x ₹100 note(s)")

        remaining = amount - (notes_needed * 100)

        if remaining > 0:
            # Last handler — no next_handler available
            print(f"Cannot fulfil remaining ₹{remaining} — no smaller denomination available")


# -----------------------------------------------------------------------
# Client / Main
# -----------------------------------------------------------------------
if __name__ == "__main__":
    # Create handlers with available note counts
    h1000 = Handler1000(num_notes=3)   # 3 × ₹1000 = ₹3000 available
    h500  = Handler500(num_notes=5)    # 5 × ₹500  = ₹2500 available
    h200  = Handler200(num_notes=10)   # 10 × ₹200 = ₹2000 available
    h100  = Handler100(num_notes=20)   # 20 × ₹100 = ₹2000 available

    # Build the chain
    h1000.set_next_handler(h500)
    h500.set_next_handler(h200)
    h200.set_next_handler(h100)
    # h100 has no next — it is the last handler

    print("=== Withdraw ₹300 ===")
    h1000.dispense(300)

    print()
    print("=== Withdraw ₹3000 ===")
    h1000.dispense(3000)

    print()
    print("=== Withdraw ₹4000 ===")
    h1000.dispense(4000)

    print()
    print("=== Withdraw ₹150 (no ₹50 handler exists) ===")
    h1000.dispense(150)
```

Walk through ₹300 manually:
- `Handler1000`: `300 // 1000 = 0` notes needed. Nothing to dispense. Remaining = 300. Pass to `Handler500`.
- `Handler500`: `300 // 500 = 0` notes needed. Nothing to dispense. Remaining = 300. Pass to `Handler200`.
- `Handler200`: `300 // 200 = 1` note needed. Dispense 1 × ₹200. Remaining = 100. Pass to `Handler100`.
- `Handler100`: `100 // 100 = 1` note needed. Dispense 1 × ₹100. Remaining = 0. Done.

Walk through ₹4000 with only 3 × ₹1000 notes available:
- `Handler1000`: needs 4 notes, only has 3. Dispenses 3 × ₹1000. Remaining = ₹1000. Passes to `Handler500`.
- `Handler500`: needs 2 notes, has 5. Dispenses 2 × ₹500. Remaining = 0. Done.

## The Standard UML Diagram

```
┌──────────────────────────────────────────────────┐
│            <<abstract>>                          │
│              IHandler                            │
├──────────────────────────────────────────────────┤
│ # _next: IHandler | None  ← self-referential     │
├──────────────────────────────────────────────────┤
│ + set_next(handler: IHandler)  ← defined here    │
│ + handle_request(request)      ← abstract        │
└──────────────────────────────────────────────────┘
     △              △
     │              │  (both inherit from IHandler)
     │              │
┌──────────────┐  ┌──────────────┐
│ ConcreteH1   │  │ ConcreteH2   │
├──────────────┤  ├──────────────┤
│ handle_req() │  │ handle_req() │
└──────────────┘  └──────────────┘

┌──────────────────────────────────────────────────┐
│                   Client                         │
├──────────────────────────────────────────────────┤
│ - handler: IHandler                              │
│ + handler.handle_request(req)                    │
└──────────────────────────────────────────────────┘
```

The key structural insight: `IHandler` has a **self-referential** `_next` field — it holds a reference to another `IHandler`. This is what forms the chain. But the concrete classes (`ConcreteH1`, `ConcreteH2`) are completely different classes — they just share the same interface/abstract parent.

---

## Linked List vs Chain of Responsibility

These two look structurally similar — objects pointing to the next — but they are fundamentally different.

| | Linked List | Chain of Responsibility |
|---|---|---|
| **Purpose** | Store data | Handle a request |
| **What each node holds** | Data + pointer to next same-type node | Business logic + pointer to next handler |
| **Node types** | All nodes are the same class | Each handler can be a different class |
| **Traversal result** | Always traverses all nodes | Stops as soon as the request is handled |
| **Pattern category** | Data Structure | Behavioural Design Pattern |

In a linked list, all nodes are instances of the **same class**. In Chain of Responsibility, each handler is a **different class** (e.g., `Handler1000`, `Handler500`) — they just share a common abstract parent. That is the biggest structural difference.

---

## The Standard Definition

> Chain of Responsibility allows an object to pass a request along a chain of potential handlers. Each handler decides either to process the request or to pass it along to the next handler in the chain.

---

## Real-World Use Cases

Any problem where a **hierarchy of handlers** exists — where each level can either handle the request fully or escalate it to the next level — is a Chain of Responsibility problem.

**Logger System** — a very common interview question. Loggers have levels: `INFO`, `DEBUG`, `ERROR`. Each is a different handler. An `INFO` message is handled by the INFO handler. A `DEBUG` message passes through INFO and is handled at DEBUG level. An `ERROR` message passes through all and is handled at ERROR level.

```
INFO (Level 1) → DEBUG (Level 2) → ERROR (Level 3)
```

**Leave Request System (Interview Question)** — An employee requests leave.
- ≤ 2 days → Team Lead approves directly.
- 2–5 days → goes to Manager.
- > 5 days → goes to Director.
- If Director also cannot approve → request fails.

This is a direct Chain of Responsibility implementation. The request travels up the chain until someone handles it or it reaches the end.
