# Caching for Backend Engineers: CDNs, DNS, CPU Caches, Redis, and Real-World Patterns

This post covers caching from first principles: what it is, why high-performance systems depend on it, the levels where you'll meet it as a backend engineer (network, hardware, software), why in-memory databases like Redis are fast, the strategies and eviction policies they use, and the typical use cases. As you asked, it stays about concepts. The few code snippets are short, framework-free Python using the Redis client, and they only illustrate the patterns.

---

## 1. What Is Caching?

**One-sentence version:** caching is a mechanism for decreasing the time and effort needed to perform some work.

**Technical definition:** caching means keeping a *subset* of some primary data in a location that is faster and easier to access than the primary storage. Which subset you keep depends on how often the data is used, how likely it is to be needed again soon, and similar parameters.

Three words in that definition matter:

- **Subset**: a cache is not a copy of everything. Keeping everything defeats the purpose.
- **Faster**: less time to retrieve.
- **Easier**: less effort (CPU, memory, disk work, network distance) to retrieve.

This single technique is a huge factor in high-performance applications, especially ones that track latency in the tens of microseconds or milliseconds.

**Terminology you'll need:**

| Term | Meaning |
|---|---|
| **Cache hit** | The data you want is found in the cache |
| **Cache miss** | The data is not in the cache; you must go to the primary source |
| **TTL (time to live)** | How long a cached item is kept before it expires |
| **Eviction** | Removing items from a full cache to make room for new ones |

---

## 2. Three Real-World Examples

### 2.1 Google Search

When you search, the query goes through a complex pipeline that involves crawling, indexing, and ranking billions of web pages. That is **computationally expensive**: lots of CPU, lots of memory.

Take a query like "what is the weather today", searched millions of times a day. Without caching, Google would recompute everything for every query, which means:

- very high latency,
- very high server load,
- every query going through the index and every ranking algorithm.

**With caching**, Google uses a **distributed in-memory caching system**. "Distributed" means the cache servers are spread across the world, not concentrated in one place. The flow:

1. User searches. The system checks whether results for this query are cached.
2. **Cache hit:** return the results instantly. Retrieval from a cache is very fast (section 7 explains why).
3. **Cache miss:** run the full ranking workflow, then **store the result in the cache**, so the next user (or the same user) who types that query gets it from the cache.

### 2.2 Netflix and CDNs

Netflix delivers movies and series to millions of users worldwide. A single title can be many gigabytes, and the whole catalog is hundreds or thousands of terabytes.

**Encoding:** for each movie, Netflix prepares multiple resolutions (say 1080p, 720p, 480p) for different devices and network speeds. It dynamically sends the version that fits your network and device, so you don't waste bandwidth and Netflix's servers carry less load.

**Delivery:** how do you serve that much data globally with minimal buffering and without crashing your servers? With a **CDN (Content Delivery Network)**:

- Netflix has its own **origin servers** (say, in data centers in the US) that hold the actual movies.
- It also places servers at many **edge locations** around the world, chosen based on available infrastructure and network connectivity.
- They're called "edge" because they're strategically placed near end users, so latency is minimal.
- Users in the US get low buffering because they're geographically close to servers. Without edge locations, a user in India would be served from the US origin, with much higher latency, and the origin would carry every request from the whole planet.

CDNs aren't just for Netflix. Many companies use them for videos, images, and web pages with static assets (JavaScript, HTML, CSS). Platforms like **Vercel** have an edge network too: a request to a front-end app deployed there is served from the region closest to you instead of the origin.

This is the caching definition again. Netflix caches only a **subset** of its catalog at each edge location. It can't put everything everywhere, because that would cost too much, and caching storage is more expensive than disk storage. Deciding which subset to cache involves a lot of computation: machine-learning models, trend analysis, and real-time data about what people in each region watch.

### 2.3 X (Twitter) Trending Topics

Twitter identifies trending topics by analyzing millions of tweets in real time, extracting patterns and trends. That is extremely expensive: ML algorithms, GPUs, big infrastructure, terabytes of data.

If it ran that calculation every time a user opened the trending section, the servers would crash within minutes, since billions of people use the platform. So Twitter **caches** the result.

Trends don't change by the second. A trending topic like an election stays for hours or days, so it's safe to cache. Roughly (the exact algorithm and interval aren't public), every few minutes Twitter recomputes trends from data across regions and stores the result in an **in-memory key-value store like Redis**. When users request it, they get the cached data instantly, with no loading time (on a decent connection).

The same pattern applies to Facebook, LinkedIn, YouTube, and other social platforms.

### 2.4 The Pattern

Caching comes into play in two situations:

1. **You want to avoid repeating heavy computation** (Google ranking, Twitter trend detection).
2. **You want to avoid sending large amounts of data to many users** (Netflix video).

## 3. Three Levels of Caching a Backend Engineer Meets

Caching exists everywhere, from hardware to software to browsers, and covering it all would take too long. These are the three levels you'll notice most as a backend engineer:

1. **Network-level**: CDN and DNS
2. **Hardware-level**: CPU caches and RAM
3. **Software-level**: Redis, Memcached, and similar

Software-level caching isn't purely software, because it runs on hardware-level caches. It's called "software-based" because you interact with it through a library or software tool.

## 4. Network-Level Caching

### 4.1 CDN in Detail

A CDN caches content on servers geographically closer to end users. These are called **edge servers** or **edge nodes**. "Edge" always means "closest to you" instead of "the origin server".

**How a request flows:**

1. A user enters a URL (for an image, video, or web page) in the browser.
2. The browser sends a **DNS query** to resolve the domain into an IP address (DNS converts domain names to IP addresses so browsers can reach the server).
3. The **CDN's DNS system routes the request to the nearest PoP (Point of Presence)**. A PoP is a fancy term for a region with a collection of edge servers. Routing considers:
   - **the user's geographic location** (a user in New York gets routed to a PoP near New York), and
   - **network conditions.** A user with a poor connection might be routed to a PoP holding lower-quality versions of the video, so they get minimal buffering. (The transcript gives this as a rough example.)
4. The edge server checks whether it has the requested content cached.
   - **Cache hit:** it sends the content to the user. This is the happy path.
   - **Cache miss:** the edge server fetches the content from the **origin server** (say in the US, when the user is in India). The origin has all the resources. The edge server then serves it (and keeps a copy).
5. **TTL:** CDNs keep content only for a set duration. Companies pick a reasonable window, say a few hours, because the content might have a new version or regional changes. After the TTL expires, the next request fetches fresh content from the origin and gets a new TTL.

```
User ──DNS──▶ CDN DNS ──▶ nearest PoP (edge servers)
                               │ hit  → serve from edge
                               │ miss → fetch from origin → cache (with TTL) → serve
```

### 4.2 DNS Caching

DNS is used constantly and unnoticed, and caching is critical to it because resolving a name from scratch is a lot of work.

**The full DNS lookup (no caching), for `example.com`:**

1. The user's device (laptop or phone) sends a DNS query to a **recursive resolver**. It's usually provided by your **ISP** (Jio, ACT, Airtel in India), or by a public DNS provider like **Google** or **Cloudflare**.
2. The resolver first checks **its own local cache**. On a hit, it returns the IP right away.
3. On a miss, it queries the **root servers**. There are multiple root servers spread around the world (the instructor wasn't sure of the exact count; it's 13 root server identities, each with many instances). They don't have the IP of `example.com`, but they know the addresses of the **top-level domain (TLD) servers** (`.com`, `.org`, `.in`, ...). They return a referral to the `.com` TLD server.
4. The **TLD server** doesn't have the IP either, but it returns the address of the **authoritative name server** for `example.com`.
5. The **authoritative name server** has the actual IP and returns it.
6. The resolver is called "recursive" because it keeps going deeper through different servers until it finds the answer.

**Where caching happens (several layers):**

| Layer | What it does |
|---|---|
| **Operating system** (Windows, macOS, Linux) | Keeps a local DNS cache and checks it **first**, before ever contacting the resolver |
| **Browser** (Chrome, Firefox, ...) | Keeps its own DNS cache, the next level after the OS |
| **Recursive resolver** (ISP, Google, Cloudflare) | Caches results so it can skip the root, TLD, and authoritative servers |
| **Authoritative name servers** | Some (not all) cache too, to avoid further requests |

Each layer lets the request skip the layers beyond it, so most lookups never reach the root servers.

## 5. Hardware-Level Caching

If you have a computer science background, this is familiar: L1, L2, L3 cache, main memory (RAM), and disk.

```
CPU cores
  ├─ L1 cache   (smallest, fastest, per core)
  ├─ L2 cache
  └─ L3 cache   (shared between cores)
        │
      RAM (main memory / primary storage)
        │
  Secondary storage (hard disk / SSD / network storage)
```

The CPU keeps L1, L2, and L3 caches to hold frequently used data or repeated computations. L3 is shared among CPU units.

**Example: arrays.** Arrays are good for sequential access. When you start traversing `1 2 3 4 5`, the CPU uses **predictive algorithms** to pull the next chunk of memory into a CPU cache. That's why sequential access of array elements is very fast. It's just one example of hardware caching.

### 5.1 Why RAM Is Fast (and Why It Can't Replace Disk)

The part that matters for backend work is **RAM (main memory / primary storage)**, because tools like Redis and Memcached are built on it.

- **Hard disks** are mechanical: a head physically moves around the disk to find the data.
- **RAM** has no moving parts. It uses capacitors and electrical signals, and any memory address can be accessed directly with a single signal. It's called *Random* Access Memory because it doesn't matter from which direction or in what order you access data: the access time is almost constant.

**The trade-offs.** RAM is fast but:

- **limited capacity** (and more expensive per GB), and
- **volatile**: when the power goes off, everything is wiped.

So hardware designers traded **non-volatility and capacity for speed**. That's why RAM can't replace disk:

| | Primary storage (RAM) | Secondary storage (disk) |
|---|---|---|
| Access speed | Very fast | Slower |
| Persistence | Volatile: lost on power-off | Persistent: data is physically written |
| Capacity | Limited | Large |
| Cost | Higher | Cheaper |

Each has its own use: RAM for fast access, disk for safe, permanent storage.

## 6. Software-Level Caching: In-Memory Databases

Redis and Memcached (and, on the cloud, **AWS ElastiCache**) are in-memory key-value NoSQL databases. They keep their data in **RAM**, and for persistence they use secondary storage behind the scenes. When the program starts, it reloads data from disk into memory. Reads and modifications happen against RAM, which is why they're fast. Implementing persistence is the tool's responsibility, not yours.

The three words in "in-memory key-value NoSQL" each mean something:

1. **In-memory**: data is stored in RAM, not on disk like PostgreSQL or MySQL. This is why they're very fast.
2. **Key-value**: no strict schema, no tables and rows like a relational database. You have a **key**, and you store anything as its value: a string, a number, a list, JSON. Different tools offer different data types (look into them yourself).
3. **NoSQL**: no SQL queries, no joins or aggregation, and none of the strictness of relational databases.

**Using them is easy.** You install the client library for your language (Node.js has `node-redis`, Python has `redis-py`, etc.), give a key and a value to store, and give a key to retrieve. The thing worth learning is how they work internally, because that helps you make good decisions.

For getting started: **Redis**, or its open-source alternative **Valkey** (a fork of Redis), plus a client library. Then compare the experience with retrieving from a relational database.

```python
import redis
r = redis.Redis()

r.set("greeting", "hello")        # store
print(r.get("greeting"))          # b"hello"
```

## 7. Caching Strategies

### 7.1 Lazy Caching (Cache-Aside)

Data is cached **only when someone actually requests it**. You don't proactively predict and pre-load.

1. Request comes in. Check the cache.
2. **Hit:** return it.
3. **Miss:** fetch from the primary storage, **store it in the cache**, then return it.
4. Next time, from this or another client, it's a hit.

```python
import json

def get_product(product_id):
    key = f"product:{product_id}"
    cached = r.get(key)
    if cached:                                   # cache hit
        return json.loads(cached)

    product = db.query_product(product_id)       # cache miss → primary storage
    r.set(key, json.dumps(product), ex=3600)     # store with 1-hour TTL
    return product
```

It's called "lazy" because caching happens on demand. It's very common across backend development.

### 7.2 Write-Through Caching

This is an **update strategy**. Every time data changes (a create/update/patch call), you update **both the database and the cache in the same operation**.

```python
def update_product(product_id, fields):
    product = db.update_product(product_id, fields)      # primary storage
    r.set(f"product:{product_id}", json.dumps(product))  # cache, same flow
    return product
```

| Pro | Con |
|---|---|
| The cache is **always fresh**; you never serve stale data | Every write has **extra overhead**: two systems to update at once |

## 8. Eviction Policies

RAM is limited, so a cache eventually fills up (and managed services like ElastiCache have explicit storage limits). The cache is only a **subset** of the data, so when it's full you must remove some data to make room for newer, more important data. An **eviction policy** decides what goes.

| Policy | How it chooses the victim |
|---|---|
| **No eviction** | No policy is configured. When memory is full, new writes fail with an error. |
| **LRU (Least Recently Used)** | Evicts the key that was **accessed longest ago**. |
| **LFU (Least Frequently Used)** | Evicts the key with the **fewest total accesses**. |
| **TTL-based** | Evicts the key that is **closest to expiring** (lowest remaining TTL). |

**LRU example:** the cache holds keys 1 to 4 and is full. Keys 1, 2, and 3 were accessed today; key 4 was accessed yesterday. Key 5 arrives. LRU evicts **key 4**.

**LFU example:** key 1 has been accessed 5 times, key 2 ten times, key 3 six times, key 4 twenty-three times. Key 5 arrives. LFU evicts **key 1**, which has the lowest access count.

**TTL example:** Redis lets you set a TTL per key, so keys expire automatically. When key 5 arrives, the policy evicts whichever key will expire soonest.

(In Redis these are configured as `noeviction`, `allkeys-lru`, `allkeys-lfu`, and `volatile-ttl`, among others.)

## 9. Real-World Backend Use Cases

### 9.1 Database Query Caching

Imagine an SQL query that joins many tables over millions of rows, does heavy aggregation, and returns a few rows. It's compute-intensive. Monitoring shows the API that calls it is hit very often (say it's on the landing page or dashboard) and is loading the database.

**Fix:** cache the result with a TTL, say one hour. On the next request, check the cache first. If it's a miss, run the query once and store the result. When the underlying data changes, update or delete the cache entry. This saves compute and resources and reduces the API's latency.

**Real-world examples:**

- **Amazon** caches product details, prices, and inventory data. During a MacBook sale, millions of users view the same product page. Without caching, every view (images, descriptions) would hit the database for data that rarely changes. Caching spares the database for the important work.
- **Twitter and Facebook** cache **user profile data**. Profiles change a couple of times a year. A celebrity's profile might be fetched thousands of times a day, or a million times with a movie coming up. You can invalidate the cache when the user edits their profile.

**The pattern:** it's a read-heavy operation where writes are infrequent. That's the ideal candidate for caching.

### 9.2 Session Storage

In a typical authentication flow, a **session token** is generated after login and stored somewhere. On every API call, the server must fetch the session information. Storing sessions in Redis instead of the main database means every request avoids a slower database read and puts no extra load on the database. Fetching from RAM is much faster than from a database.

### 9.3 External API Caching

Say your backend calls an external weather API and computes on the result to serve your front end. Without caching, every request from your front end triggers another call to the weather API. With many users, you'd make thousands of calls to the external service, and external APIs typically have **rate limits** or **per-call pricing**, so you'd hit the limits or inflate your bill.

Weather data doesn't change by the second, so it's safe to cache. Fetch once, cache with a **TTL of an hour**, serve all requests from the cache for that hour, then let it expire and fetch fresh data on the next request.

```python
def get_weather(city):
    key = f"weather:{city}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    data = weather_api.fetch(city)               # costs money / counts toward rate limit
    r.set(key, json.dumps(data), ex=3600)        # TTL: 1 hour
    return data
```

Whenever you integrate with an external API, think about caching to reduce billing and avoid rate limits.

### 9.4 Rate Limiting

Rate limiting is usually implemented as **middleware**: code that sits in front of your routes or controllers, between the client and your application logic.

**How it works:**

1. The middleware reads the **`X-Forwarded-For`** header, which holds the client's public IP address. It's usually added by a reverse proxy such as Nginx.
2. It uses the IP as a key in a key-value store and keeps a **counter**.
3. Suppose the rule is **50 requests per minute** per client. At the start of the minute, the first request sets the counter to 1, and each subsequent request increments it.
4. If the counter **exceeds 50 within the minute**, the middleware blocks the request and returns **`429 Too Many Requests`**.

Rate limiting protects compute-intensive APIs and helps against bots.

```python
def rate_limit(client_ip, limit=50, window_seconds=60):
    key = f"ratelimit:{client_ip}"
    count = r.incr(key)                  # atomic increment; creates key at 1
    if count == 1:
        r.expire(key, window_seconds)    # start the window on the first request
    return count <= limit                # False → respond with 429
```

**Why Redis and not a relational database?** You could store the counters in PostgreSQL or MySQL, but:

1. **Latency:** every request would need a database round trip. Even 20 to 30 ms extra matters for API latency.
2. **Database load:** with, say, 1,000 users each making 100 requests per minute, the database would be flooded with rate-limit bookkeeping alone.

An in-memory store makes it as fast as possible and keeps the load off your main database.

## 10. Summary Cheat Sheet

**What and why**
- Caching = keep a **subset** of data somewhere faster/easier to reach.
- Use it to avoid **repeated heavy computation** or **sending large data to many users**.
- Hit = found in the cache. Miss = not found, go to the source and (usually) store the result. TTL = how long an entry lives.

**Where you meet it**

| Level | Examples | Idea |
|---|---|---|
| Network | CDN (edge servers, PoP, origin, TTL) | Serve content from near the user |
| Network | DNS (OS, browser, resolver, authoritative) | Skip the recursive lookup |
| Hardware | L1/L2/L3, RAM, disk | Speed vs capacity/persistence trade-off |
| Software | Redis, Valkey, Memcached, ElastiCache | In-memory, key-value, NoSQL |

**Strategies and eviction**
- **Cache-aside (lazy):** cache on first request. **Write-through:** update cache and DB together (fresh cache, slower writes).
- **No eviction / LRU / LFU / TTL**: choose what to throw away when memory is full.

**Use cases**
- Expensive or frequent DB queries, product and profile data (read-heavy, rarely changing)
- Session storage
- External API responses (save money, avoid rate limits)
- Rate-limiting counters (low latency, no DB load)

**Rule of thumb:** cache data that is read often, changes rarely, and is expensive to produce or send. Don't cache everything, because cache memory is costly and limited.

They don't have the IP of `example.com`, but they know the addresses of the **top-level domain (TLD) servers** (`.com`, `.org`, `.in`, ...). They return a referral to the `.com` TLD server.
4. The **TLD server** doesn't have the IP either, but it returns the address of the **authoritative name server** for `example.com`.
5. The **authoritative name server** has the actual IP and returns it.
6. The resolver is called "recursive" because it keeps going deeper through different servers until it finds the answer.

**Where caching happens (several layers):**

| Layer | What it does |
|---|---|
| **Operating system** (Windows, macOS, Linux) | Keeps a local DNS cache and checks it **first**, before ever contacting the resolver |
| **Browser** (Chrome, Firefox, ...) | Keeps its own DNS cache, the next level after the OS |
| **Recursive resolver** (ISP, Google, Cloudflare) | Caches results so it can skip the root, TLD, and authoritative servers |
| **Authoritative name servers** | Some (not all) cache too, to avoid further requests |

Each layer lets the request skip the layers beyond it, so most lookups never reach the root servers.

## 5. Hardware-Level Caching

If you have a computer science background, this is familiar: L1, L2, L3 cache, main memory (RAM), and disk.

```
CPU cores
  ├─ L1 cache   (smallest, fastest, per core)
  ├─ L2 cache
  └─ L3 cache   (shared between cores)
        │
      RAM (main memory / primary storage)
        │
  Secondary storage (hard disk / SSD / network storage)
```

The CPU keeps L1, L2, and L3 caches to hold frequently used data or repeated computations. L3 is shared among CPU units.

**Example: arrays.** Arrays are good for sequential access. When you start traversing `1 2 3 4 5`, the CPU uses **predictive algorithms** to pull the next chunk of memory into a CPU cache. That's why sequential access of array elements is very fast. It's just one example of hardware caching.

### 5.1 Why RAM Is Fast (and Why It Can't Replace Disk)

The part that matters for backend work is **RAM (main memory / primary storage)**, because tools like Redis and Memcached are built on it.

- **Hard disks** are mechanical: a head physically moves around the disk to find the data.
- **RAM** has no moving parts. It uses capacitors and electrical signals, and any memory address can be accessed directly with a single signal. It's called *Random* Access Memory because it doesn't matter from which direction or in what order you access data: the access time is almost constant.

**The trade-offs.** RAM is fast but:

- **limited capacity** (and more expensive per GB), and
- **volatile**: when the power goes off, everything is wiped.

So hardware designers traded **non-volatility and capacity for speed**. That's why RAM can't replace disk:

| | Primary storage (RAM) | Secondary storage (disk) |
|---|---|---|
| Access speed | Very fast | Slower |
| Persistence | Volatile: lost on power-off | Persistent: data is physically written |
| Capacity | Limited | Large |
| Cost | Higher | Cheaper |

Each has its own use: RAM for fast access, disk for safe, permanent storage.

## 6. Software-Level Caching: In-Memory Databases

Redis and Memcached (and, on the cloud, **AWS ElastiCache**) are in-memory key-value NoSQL databases. They keep their data in **RAM**, and for persistence they use secondary storage behind the scenes. When the program starts, it reloads data from disk into memory. Reads and modifications happen against RAM, which is why they're fast. Implementing persistence is the tool's responsibility, not yours.

The three words in "in-memory key-value NoSQL" each mean something:

1. **In-memory**: data is stored in RAM, not on disk like PostgreSQL or MySQL. This is why they're very fast.
2. **Key-value**: no strict schema, no tables and rows like a relational database. You have a **key**, and you store anything as its value: a string, a number, a list, JSON. Different tools offer different data types (look into them yourself).
3. **NoSQL**: no SQL queries, no joins or aggregation, and none of the strictness of relational databases.

**Using them is easy.** You install the client library for your language (Node.js has `node-redis`, Python has `redis-py`, etc.), give a key and a value to store, and give a key to retrieve. The thing worth learning is how they work internally, because that helps you make good decisions.

For getting started: **Redis**, or its open-source alternative **Valkey** (a fork of Redis), plus a client library. Then compare the experience with retrieving from a relational database.

```python
import redis
r = redis.Redis()

r.set("greeting", "hello")        # store
print(r.get("greeting"))          # b"hello"
```

## 7. Caching Strategies

### 7.1 Lazy Caching (Cache-Aside)

Data is cached **only when someone actually requests it**. You don't proactively predict and pre-load.

1. Request comes in. Check the cache.
2. **Hit:** return it.
3. **Miss:** fetch from the primary storage, **store it in the cache**, then return it.
4. Next time, from this or another client, it's a hit.

```python
import json

def get_product(product_id):
    key = f"product:{product_id}"
    cached = r.get(key)
    if cached:                                   # cache hit
        return json.loads(cached)

    product = db.query_product(product_id)       # cache miss → primary storage
    r.set(key, json.dumps(product), ex=3600)     # store with 1-hour TTL
    return product
```

It's called "lazy" because caching happens on demand. It's very common across backend development.

### 7.2 Write-Through Caching

This is an **update strategy**. Every time data changes (a create/update/patch call), you update **both the database and the cache in the same operation**.

```python
def update_product(product_id, fields):
    product = db.update_product(product_id, fields)      # primary storage
    r.set(f"product:{product_id}", json.dumps(product))  # cache, same flow
    return product
```

| Pro | Con |
|---|---|
| The cache is **always fresh**; you never serve stale data | Every write has **extra overhead**: two systems to update at once |

## 8. Eviction Policies

RAM is limited, so a cache eventually fills up (and managed services like ElastiCache have explicit storage limits). The cache is only a **subset** of the data, so when it's full you must remove some data to make room for newer, more important data. An **eviction policy** decides what goes.

| Policy | How it chooses the victim |
|---|---|
| **No eviction** | No policy is configured. When memory is full, new writes fail with an error. |
| **LRU (Least Recently Used)** | Evicts the key that was **accessed longest ago**. |
| **LFU (Least Frequently Used)** | Evicts the key with the **fewest total accesses**. |
| **TTL-based** | Evicts the key that is **closest to expiring** (lowest remaining TTL). |

**LRU example:** the cache holds keys 1 to 4 and is full. Keys 1, 2, and 3 were accessed today; key 4 was accessed yesterday. Key 5 arrives. LRU evicts **key 4**.

**LFU example:** key 1 has been accessed 5 times, key 2 ten times, key 3 six times, key 4 twenty-three times. Key 5 arrives. LFU evicts **key 1**, which has the lowest access count.

**TTL example:** Redis lets you set a TTL per key, so keys expire automatically. When key 5 arrives, the policy evicts whichever key will expire soonest.

(In Redis these are configured as `noeviction`, `allkeys-lru`, `allkeys-lfu`, and `volatile-ttl`, among others.)

## 9. Real-World Backend Use Cases

### 9.1 Database Query Caching

Imagine an SQL query that joins many tables over millions of rows, does heavy aggregation, and returns a few rows. It's compute-intensive. Monitoring shows the API that calls it is hit very often (say it's on the landing page or dashboard) and is loading the database.

**Fix:** cache the result with a TTL, say one hour. On the next request, check the cache first. If it's a miss, run the query once and store the result. When the underlying data changes, update or delete the cache entry. This saves compute and resources and reduces the API's latency.

**Real-world examples:**

- **Amazon** caches product details, prices, and inventory data. During a MacBook sale, millions of users view the same product page. Without caching, every view (images, descriptions) would hit the database for data that rarely changes. Caching spares the database for the important work.
- **Twitter and Facebook** cache **user profile data**. Profiles change a couple of times a year. A celebrity's profile might be fetched thousands of times a day, or a million times with a movie coming up. You can invalidate the cache when the user edits their profile.

**The pattern:** it's a read-heavy operation where writes are infrequent. That's the ideal candidate for caching.

### 9.2 Session Storage

In a typical authentication flow, a **session token** is generated after login and stored somewhere. On every API call, the server must fetch the session information. Storing sessions in Redis instead of the main database means every request avoids a slower database read and puts no extra load on the database. Fetching from RAM is much faster than from a database.

### 9.3 External API Caching

Say your backend calls an external weather API and computes on the result to serve your front end. Without caching, every request from your front end triggers another call to the weather API. With many users, you'd make thousands of calls to the external service, and external APIs typically have **rate limits** or **per-call pricing**, so you'd hit the limits or inflate your bill.

Weather data doesn't change by the second, so it's safe to cache. Fetch once, cache with a **TTL of an hour**, serve all requests from the cache for that hour, then let it expire and fetch fresh data on the next request.

```python
def get_weather(city):
    key = f"weather:{city}"
    cached = r.get(key)
    if cached:
        return json.loads(cached)
    data = weather_api.fetch(city)               # costs money / counts toward rate limit
    r.set(key, json.dumps(data), ex=3600)        # TTL: 1 hour
    return data
```

Whenever you integrate with an external API, think about caching to reduce billing and avoid rate limits.

### 9.4 Rate Limiting

Rate limiting is usually implemented as **middleware**: code that sits in front of your routes or controllers, between the client and your application logic.

**How it works:**

1. The middleware reads the **`X-Forwarded-For`** header, which holds the client's public IP address. It's usually added by a reverse proxy such as Nginx.
2. It uses the IP as a key in a key-value store and keeps a **counter**.
3. Suppose the rule is **50 requests per minute** per client. At the start of the minute, the first request sets the counter to 1, and each subsequent request increments it.
4. If the counter **exceeds 50 within the minute**, the middleware blocks the request and returns **`429 Too Many Requests`**.

Rate limiting protects compute-intensive APIs and helps against bots.

```python
def rate_limit(client_ip, limit=50, window_seconds=60):
    key = f"ratelimit:{client_ip}"
    count = r.incr(key)                  # atomic increment; creates key at 1
    if count == 1:
        r.expire(key, window_seconds)    # start the window on the first request
    return count <= limit                # False → respond with 429
```

**Why Redis and not a relational database?** You could store the counters in PostgreSQL or MySQL, but:

1. **Latency:** every request would need a database round trip. Even 20 to 30 ms extra matters for API latency.
2. **Database load:** with, say, 1,000 users each making 100 requests per minute, the database would be flooded with rate-limit bookkeeping alone.

An in-memory store makes it as fast as possible and keeps the load off your main database.

## 10. Summary Cheat Sheet

**What and why**
- Caching = keep a **subset** of data somewhere faster/easier to reach.
- Use it to avoid **repeated heavy computation** or **sending large data to many users**.
- Hit = found in the cache. Miss = not found, go to the source and (usually) store the result. TTL = how long an entry lives.

**Where you meet it**

| Level | Examples | Idea |
|---|---|---|
| Network | CDN (edge servers, PoP, origin, TTL) | Serve content from near the user |
| Network | DNS (OS, browser, resolver, authoritative) | Skip the recursive lookup |
| Hardware | L1/L2/L3, RAM, disk | Speed vs capacity/persistence trade-off |
| Software | Redis, Valkey, Memcached, ElastiCache | In-memory, key-value, NoSQL |

**Strategies and eviction**
- **Cache-aside (lazy):** cache on first request. **Write-through:** update cache and DB together (fresh cache, slower writes).
- **No eviction / LRU / LFU / TTL**: choose what to throw away when memory is full.

**Use cases**
- Expensive or frequent DB queries, product and profile data (read-heavy, rarely changing)
- Session storage
- External API responses (save money, avoid rate limits)
- Rate-limiting counters (low latency, no DB load)

**Rule of thumb:** cache data that is read often, changes rarely, and is expensive to produce or send. Don't cache everything, because cache memory is costly and limited.
