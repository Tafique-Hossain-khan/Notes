# Command Design Pattern in Python

Welcome back to the LLD series. Today we're learning a new design pattern called the **Command Design Pattern**. This pattern is very useful — in many scenarios it's used directly, and just based on this pattern alone you can build a small application. It's important to understand, and just as important as it is, it's also **easy**. Once you understand it, you'll find it very intuitive — you'll realize "oh, I've been using something like this for a long time" in various applications on your computer.

---

## 1. Setting Up the Core Idea

Consider: you have an object — call it the **Source**. And another object — call it the **Receiver**.

I want to send a **message** from the Source to the Receiver — a **request**, or a **command**. You can call it anything: request, command, or action. Basically, I want to tell the Receiver to **do something**.

How do I do that? I call a method on it — say `run`, `talk`, `walk` — any method. As soon as I call a method on the Receiver, it gives me back that method's output.

### The Key Idea: Treat the Request as an Object

If I want to send a "do this" request from Source to Receiver, what if I **treat this request itself as an object**?

So now we'll have **three objects**:
1. **Source**
2. **Command**
3. **Receiver** (which already existed)

Now: the Source won't talk directly to the Receiver. Instead, the Source tells the **Command**: "go get something done for me." The Command tells the Receiver. The Receiver returns the result to the Command, and the Command returns it back to the Source.

### Why Introduce This "Command" Object?

Are we going to turn **everything** into an object in OOP? No — there's a very important purpose here. By doing this, the **Source** and the **Receiver** become **loosely coupled**.

To understand this properly, we'll use a **classic example** — the one used everywhere to teach the Command Design Pattern.

## 2. The Classic Example — Smart Home Automation System

Suppose you're building an application. This application has many **buttons**, and pressing these buttons lets you control your home's **smart devices**.

- Press **this** button → a **light bulb** turns on.
- Press **this** button → a **fan** turns on/off.
- Press **this** button → an **AC** turns on/off.
- Another button → light on/off again.

So different buttons can turn different smart home appliances on or off. We need to build this application. The device we have here can be called a **remote**.

---

## 3. The Naive Approach (Without Command Pattern)

If you don't use the Command Design Pattern and just apply whatever knowledge you currently have, you'd create a **Remote** class.

### Blueprint

A `Remote` class. Inside it, we have appliances — say a **Light** and a **Fan**.

- We'd take an object of `Light` — `light`. `Light` itself would be a class, with two methods: `on` and `off`. Calling `light.on()` turns the light on; `light.off()` turns it off. The `Light` class internally knows how turning "on" draws current through the filament, etc. — we don't worry about that. We just know: call the light's "on" — light turns on. That's it.

- In `Remote`, we'd pass an object of `Light`. The button would be a method — say `press_light_button`. Whenever this is pressed, we call `light.on()`.

To make it nicer, we could build arrays/vectors of buttons across the remote, with different indexing, since there are multiple buttons. But the **logic** is clear: we'd be **tightly coupling** this remote with `Fan`, `AC`, and `Light` directly.

### Why This Is Wrong

Suppose I want this remote to be **dynamic**. Today, a particular button controls the **light**. But tomorrow, that same button should control a **fan**, or maybe we bought a new smart device — a **smart heater** — and now this button should control the heater.

To change this button's logic, I'd have to **re-open the `Remote` class** and change the logic inside it. Which design principle does this break? The **Open-Closed Principle**, from SOLID principles.

### What Command Pattern Says

The `Remote` should **not** be directly linked to these appliances (AC, Fan, Light). Instead, it should be linked to a **Command**. The Remote tells the Command: "go get something done for me." The Command knows which appliance to ask to do that work.

## 4. UML Design — Step by Step

### Step 1: The Remote Class

We create a class **`Remote`**.

### Step 2: The Command Interface

Inside `Remote`, we'll have **commands**. So first, let's define what a "command" is.

This is going to be an **interface** — a pure abstract class. Following our naming convention: **`ICommand`**. We can write "Abstract" on top of it.

`ICommand` has **one method**: **`execute`**. Since it's an interface, we don't define it here — just declare it. Whenever you call `execute` on a command, the command will "do something" for you. We don't know exactly what, but it'll do something.

### Step 3: The Appliance — Light

Since `ICommand` is abstract, we need many **concrete commands**, and each concrete command will be **linked to an appliance**. Let's go with the example of a **Light**.

We create a `Light` class with two methods: **`on`** and **`off`**. Calling `light.on()` turns the light on; `light.off()` turns it off.

### Step 4: Connecting Command to Light — LightCommand

We create a **concrete command**: **`LightCommand`**.

- `LightCommand` deals only with `Light` — it has a reference to `Light` (a **has-a** relationship). Let's call this reference `light`.
- Since `LightCommand` overrides `ICommand`, it also overrides `execute`.
- Logically, inside `execute`: it calls `light.on()`.

We can build multiple such concrete commands the same way — e.g., **`FanCommand`**, **`ACCommand`** — each linked with its own concrete receiver (e.g., `FanCommand` ↔ `Fan`).

### Step 5: Remote Has-A ICommand

`Remote` **has-a `ICommand`** — let's call this reference `command`.

For now, assume the `Remote` has just **one button** — a method called **`press_button`**.

### How `press_button` Works

When `press_button` is called, the code inside it simply calls `command.execute()`.

- `command.execute()` is called.
- Whatever command is referenced (say a `LightCommand` assigned to `light` with "living room light"), its `execute` runs → calls `light.on()`.

So logically: pressing this remote's button turned the light on. But the **Remote itself never knew** what exactly this button does. The Remote only knows: "when the user presses this button, I call this command's `execute` method." It **delegated** its request. The Command knows: "when my `execute` is called, I'll call the Light's `on` method." And the Light knows: "when my `on` is called, I turn on the bulb."

### Changing What a Button Controls

Suppose tomorrow, instead of `LightCommand`, this button should control a `Fan`. Very simple — we add a method **`set_command`**:

- `set_command` takes a `command` and assigns it.
- If we want this button to control a fan, we call `set_command` and pass it a `FanCommand`.

We'd create another class `FanCommand` linked with a `Fan` (which also has `on`/`off` methods).

`set_command` takes a **new reference** to `FanCommand` and assigns it. Now, when the button is pressed, `execute` is called on this new command, which turns the fan on.

So logically: I don't need to change **anything** inside `Remote`. I just call `press_button`, and whatever command is referenced there, I call its `execute`. The command knows what it needs to deal with.

```python
from abc import ABC, abstractmethod

class ICommand(ABC):
    @abstractmethod
    def execute(self):
        pass

class Light:
    def on(self):
        print("Light is ON")

    def off(self):
        print("Light is OFF")

class Fan:
    def on(self):
        print("Fan is ON")

    def off(self):
        print("Fan is OFF")

class LightCommand(ICommand):
    def __init__(self, light: Light):
        self.light = light

    def execute(self):
        self.light.on()

class FanCommand(ICommand):
    def __init__(self, fan: Fan):
        self.fan = fan

    def execute(self):
        self.fan.on()

class Remote:
    def __init__(self):
        self.command = None

    def set_command(self, command: ICommand):
        self.command = command

    def press_button(self):
        self.command.execute()
```

## 5. Multiple Buttons on the Remote

I said the remote can have **multiple buttons** — not just one. That's also very simple.

Suppose we have a remote with **multiple buttons** — say **3 buttons**.

- Instead of holding **one** `command`, the `Remote` holds a **vector/array of commands**. This `has-a` relationship becomes a **one-to-many** relationship.
- `press_button` now takes a **parameter**: an **index** — which button is being pressed.
- `set_command` similarly takes a **command** AND an **index** — which index/slot we're assigning this command to.

This way, whenever we press a button, it plays/executes the command at that particular index.

## 6. Introducing the Undo Command

Now let's make a small but powerful change to the design.

### What We Add

1. We've already taken a **vector of commands** — multiple commands.
2. We add a **new method** to the `ICommand` abstract class: **`undo`**. Previously we only had `execute`. Now we add `undo` too. `undo` does **nothing special** — it does the **exact opposite** of what `execute` does.

### The Idea

For our multiple buttons: if pressing a button turns the light **on**, pressing it **again** should turn the light back **off**. This is exactly what we want in smart home automation — `Light` already has `on` and `off`.

So:
- `execute` → calls `light.on()`
- `undo` → calls `light.off()`

Now it behaves like a **proper button**: press once → light on; press again → light off. Same for every button, and every button can be dynamically assigned.

### Why We Did This

This is the **best use case** of the Command Design Pattern: any task we performed, we can **undo** it. We say: "this task happened like this, now undo it" — and the command knows exactly how to do that.

With this small change, we've made the Command Design Pattern much more powerful — now we don't just **execute** a command, we can also **un-execute** it.

### Tracking Button State

How do we know if a button is currently "on" or "off"? We add a **boolean array** — let's call it **`pressed`**. By default, all values are `False`.

- When we press a button for the first time, we set its `pressed` value from `False` → `True`.
- When we press it again, we first check: is `pressed` already `True`?
  - If `True` → this button is "on" → call **`undo`** this time, and set `pressed` back to `False`.
  - If `False` → call **`execute`**, and set `pressed` to `True`.

Now update `Remote` to support toggling:

```python
class Remote:
    def __init__(self, num_buttons=4):
        self.commands = [None] * num_buttons
        self.pressed = [False] * num_buttons

    def set_command(self, index: int, command: ICommand):
        if self.commands[index] is not None:
            del self.commands[index]
        self.commands[index] = command
        self.pressed[index] = False

    def press_button(self, index: int):
        if self.commands[index] is not None:
            if not self.pressed[index]:
                self.commands[index].execute()
            else:
                self.commands[index].undo()
            self.pressed[index] = not self.pressed[index]
        else:
            print("No command assigned at this button")
```

## 8. Doubt #1 — Why Doesn't `ICommand` Have a "Has-A" Relationship with `Light`?

A common doubt: in many UML diagrams, sometimes the **abstract** class has the "has-a" relationship, and sometimes the **concrete** class does. What's the difference? Exactly what are we trying to say?

### The Answer: Intent

The difference here is about **intent** — i.e., **what is this class's job/purpose**?

`ICommand`'s intent is **not** to have a "has-a" relationship with anything specific. It has two methods: `execute` and `undo`.

- This abstract `Command` says: "I can **execute** something. I don't know **what**, because I've only **declared** my method, not defined it."
- Similarly: "whatever I executed, I can **undo** it. But I don't know **what** I executed."

This is the job of the **concrete command**. A `LightCommand` knows: "I can execute — and what I execute is **this light**. I can call this light's `on` method. Similarly, when `undo` is called, I can call this light's `off` method." This is `LightCommand`'s job — `ICommand` has nothing to do with it.

`ICommand`'s job is just two things: `execute` and `undo`. Whoever inherits `Command` will handle **what** it executes and **what** it undoes. That's why the **has-a relationship always forms with the Command — the concrete Command**, not `ICommand`.

## 9. Doubt #2 — Why Does `LightCommand` Hold a **Concrete** `Light` (Not an Abstraction)?

Another doubt: we have `Light`, but we could also have `Fan`, `AC`, and many other appliances. Why does `LightCommand` hold a **concrete** `Light` object?

### The Tempting Alternative

Generally in OOP, we said we want to **deal in abstractions** — pass interfaces to each other, not concretions, because `LightCommand` becomes **tightly coupled** to `Light`.

**What if** we created a class `Appliance` with two methods, `on` and `off`, and made `Fan`, `AC`, `Light`, etc. all override `Appliance`? Then we wouldn't call it `LightCommand` — just `Command` (one generic concrete command), and it would hold an `Appliance` object, calling `appliance.on()` / `appliance.off()`. Then we wouldn't need a concretion of `Command` either, nor concretions of the receivers.

### Why We Did NOT Do This

This relates to the **Liskov Substitution Principle (LSP)** from SOLID — any child class should be **substitutable** for its parent.

Here, the "parent class" would be some `Appliance`, and "child classes" would be `Light`, `Fan`, etc. What methods, common to **every** appliance, would we write in `Appliance`? Generally just `on`/`off`.

But practically — is **every** appliance just "on/off"?

- **Lights** → on/off makes sense.
- **Fans** → on/off, but fans also have **speed** settings.
- **AC** → has **many** features — timer, temperature settings, etc.
- **Refrigerator**, **Heater** → each has many different unique features.

So you basically **cannot** create a single standard `Appliance` class that captures every appliance's behavior. This would **break Liskov Substitution Principle**. There are ways to work around an LSP violation, but in this case, our choice was simpler:

**We chose to build a concrete Command that deals with a concrete object / concrete receiver.** That's it. This makes our Command Design Pattern much **simpler**.

## 10. Real-World Use Cases

### 1. Undo Feature (Text Editors, Photoshop, etc.)

Any application that gives you an **undo feature** — a text editor, a text processor, Photoshop, etc. — internally executes the Command Design Pattern.

For example: you're editing a photo, something extra happens, and you press **Ctrl+Z** to undo it. Or in a text editor: you make a statement **bold**, **italic**, or change its formatting — and you can press Ctrl+Z to undo that too.

Internally, what's happening: **every action becomes a command**, and that command's job is **both** to `execute` **and** to `undo`.

So: whenever you need to implement an "undo" feature in any application, the approach is: **turn an action into a command**, and that command should be able to both execute and undo.

### 2. Keyboard Shortcuts

Another great use case: when you set up **keyboard shortcuts**.

Suppose you set up a shortcut: "whenever I press this particular key, brightness should turn on (increase)". Press it again → brightness should decrease, etc.

What happens internally: the keyboard shortcut creates a **command**, and that command knows what to do — e.g., increase or decrease brightness.

**Why does it do this (instead of directly linking the keyboard to brightness control)?** Because the keyboard shouldn't be **directly, statically linked** to "brightness" — that would be a **tight coupling**. Tomorrow, you might assign a **completely different command** to that same button.

So: keyboard buttons get **assigned a command**, and that command's job is to talk to a particular appliance/feature — e.g., increase monitor brightness, decrease brightness, minimize a task, etc.

## 11. Standard Definition

> **It encapsulates a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations.**

- "Encapsulates a request as an object" — we treated an action/command/request as an **object**.
- "Letting you parameterize clients with different requests" — the `Remote` (client) can be configured with **different** commands dynamically.
- "Queue or log requests" — for example, when you press Ctrl+Z on your computer, whatever tasks you did get undone one by one. Internally, an application maintains a **stack**: every command you perform gets **pushed** onto the stack, and as you undo, commands get **popped** off the stack. This is what "logging" or "queuing" commands means.
- "Support undoable operations" — we can undo any command.

Whenever you need to implement such features in a real-life application — supporting undoable operations — the **Command Design Pattern** should always come to mind.
