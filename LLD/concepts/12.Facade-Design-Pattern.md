# Facade Design Pattern in Python

Today we're introducing a new design pattern: the **Facade Design Pattern**. This pattern is also very simple — you'll understand it quickly, and there isn't too much to it. Let's get started.

---

## 1. What the Facade Is All About

Imagine we have a **very complex sub-system** of classes. We have a class **A**, a class **B**, a class **C**, a class **D**, a class **E** — many classes — and there are **a lot of interactions** between them.

For example:
- A depends on B
- B depends on C
- A is also dependent on C
- B depends on D
- D depends on E

...and so on. There are very complex interactions between these classes. All of these together are called a **sub-system**, and together they accomplish **some task** (for now, just assume they do *something*).

### The Client's Problem

Now suppose there's a **Client** that wants to use this sub-system — wants to get some work done — and this entire sub-system, together, performs **one overall task**. Because accomplishing that task requires many small, separate pieces of work, we've built separate classes for each piece.

This Client wants to use the sub-system. We **don't want** the Client to talk to such a complex sub-system directly — i.e., we don't want the Client to first call A, then maybe B, then C, and so on.

### The Solution: Introduce a Facade

So what do we do? We introduce a **new class** — let's call it **Facade**.

The **Facade** talks to this complex sub-system, and the **Client only talks to the Facade**.

Suppose the Client only calls **one method** on the Facade — let's call it `get_work_done`. That's it. The Client calls `get_work_done()` on the Facade, and **all the work gets done**.

The Client doesn't care **how** the Facade got this work done — which complex sub-system it called, which classes it went through. **That's the whole idea of the Facade Design Pattern.**

We'll understand this better through an example. But broadly, you now understand:

**Use Case #1**: A Client shouldn't have to talk to a complex sub-system directly — so we introduce a **gateway** in between: a Facade class that acts as a gateway. "All interactions go through me. You call me, and I'll bring you the output. You don't need to talk to this complex sub-system."

**Use Case #2**: The Facade **decouples** the Client from the complex sub-system. Since the Client isn't talking to it directly, the Client is **decoupled**. Tomorrow, if we introduce new classes into the sub-system, or add more interactions, the Client **won't be affected at all**.

There's a **third** thing the Facade helps establish: the **Principle of Least Knowledge**. We discussed this principle briefly before, but now we'll go deeper into it — it's a very important principle.

We'll cover that principle a bit later. First, let's understand the Facade Design Pattern through an example, then look at the code.

## 2. Example: Computer Boot-Up

For our example, we've taken a very simple use case where the Facade Design Pattern is actually used: when you **turn on your computer** — when you **boot up** your system/PC.

### What Happens When You Boot Up

You press a button: "Start Computer." There's probably some internal "start" command, and **a lot of things happen internally** that you have no idea about — and your computer boots up.

### What's Happening Internally (The Sub-System)

Let's understand what classes might exist internally:

1. **`CPU`** class — has a method like `initialize` (the CPU initializes itself).
2. **`Memory`** class — has some methods (e.g., self-test).
3. **`OperatingSystem`** class — the OS turns on.
4. **`BIOS`** — BIOS boots up. For BIOS to boot up, it **needs both CPU and Memory** — i.e., **first** CPU and Memory boot up, **then** BIOS boots up.

There are many complex things happening, many complex interactions — and **all of this together is a sub-system**.

We can have many more classes here too — things happening "behind your back":
- A **`HardDrive`** class — the hard disk starts **spinning** when you boot up.

And many more such classes.

### As a Client — Just One Call

As a **Client**, all we did was call a **Facade**. We have a Facade class — let's say it has **one method**: **`start_computer`**.

We called `start_computer()`, and internally, this `start_computer` talked to this entire sub-system. That's our simple example.

### Cleaner Diagram

When we call `start_computer`:
- **CPU** initializes.
- **Memory** goes through self-test.
- **Hard drive** spins up.
- **Power supply** provides power.
- **Cooling system** runs.
- **Operating system** loads.
- **BIOS** boots.

All of this happens **behind the scenes** for the Client. And what does the Client have? Just **one `ComputerFacade`** — this class has references to **all** these sub-system pieces (power supply, cooling system, CPU, memory, BIOS, etc.), and it has **one method**: `start_computer`.

### What the Client Does

The Client holds a reference to `ComputerFacade` — say `comp`. The Client calls `comp.start_computer()`.

What's inside `ComputerFacade.start_computer`? Simply: it calls each sub-system class's method, one by one, in the right order. As soon as `start_computer` is called, it interacts with this complicated sub-system and **brings back a "computer started" result** to the Client. **As simple as that.**

```python
class PowerSupply:

class CPU:

        print("Memory: self-test passed")

class HardDrive:
    def spin_up(self):
        print("Hard drive: spinning up")

class BIOS:
    def boot(self, cpu: CPU, memory: Memory):
        cpu.initialize()
        memory.self_test()
        print("BIOS: booted")

class OperatingSystem:
    def load(self):
        print("Operating System: loaded")
```

Now build the Facade:

```python
class ComputerFacade:
    def __init__(self):
        self.power_supply = PowerSupply()
        self.cooling_system = CoolingSystem()
        self.cpu = CPU()
        self.memory = Memory()
        self.hard_drive = HardDrive()
        self.bios = BIOS()
        self.os = OperatingSystem()

    def start_computer(self):
        self.power_supply.provide_power()
        self.cooling_system.start_fans()
        self.hard_drive.spin_up()
        self.bios.boot(self.cpu, self.memory)
        self.os.load()
        print("Computer booted successfully")
```

In `main`:

```python
computer = ComputerFacade()
computer.start_computer()
```

## 3. Standard UML Diagram

The standard UML diagram for the Facade pattern:

- We have a **Client**.
- The Client has a reference to a **Facade**, and calls **one method** on it — say **`execute`**.
- Inside this `execute` method, the Facade calls **its own** `execute`-type logic, which talks to the **complex sub-system**.
- The Client has **no idea** what's happening inside this sub-system. The Client only knows: "I need to talk to the Facade." **That's it.**

| Standard UML Term | Our Example |
|---|---|
| Client | `main` |
| Facade | `ComputerFacade` |
| Facade's method | `start_computer` |
| Complex sub-system | `PowerSupply`, `CoolingSystem`, `CPU`, `Memory`, `HardDrive`, `BIOS`, `OperatingSystem` |

## 4. Principle of Least Knowledge (PLK)

This is a very simple rule. Suppose you have many classes: class **A**, class **B**, and class **C**, connected like this: **A has-a B**, and **B has-a C**.

### The Rule: "Talk Only to Your Immediate Friends"

What does this mean? Class `A` should **only call methods on `B`**, because `A` is **directly linked** to `B`. `A` should **NOT** call methods on `C`.

Suppose `A` has a method `m1`, `B` has a method `m2`, and `C` has a method `m3`.

**`A` should never** call a method on `B` saying "go fetch me an object of `C`," with `B` returning a `C` object to `A`, and `A` then calling `m3` on that `C` object directly. **Don't do this**, because `A` is **not** linked to `C`. `A` does **not** "have-a" `C`. `A` has-a `B` — so `A` should not talk to `C`.

### Why So Strict?

It's simple: the **less interaction** there is between classes/components, the more **loosely coupled** our application becomes. This has been our main motive throughout this LLD series: **minimize interactions between multiple classes**, build a **loosely coupled design**.

If every class starts calling every other class's "friends," our entire loosely-coupled design **falls apart**.

So this rule, the **Principle of Least Knowledge**, says: **the less a class knows about other classes, the better your design**.

## 5. Guidelines for the Principle of Least Knowledge

To properly follow this principle, there are a few guidelines. Let's go through them one by one.

Suppose you have a class **`A`**, with methods **`m1`** and **`m2`**. You create an object of `A`: `a = A()`.

### Guideline 1: Call Methods of Your Own Object

You can call methods that **belong to this object itself**. So `a` (the object of `A`) can call `m1` and `m2` — obviously, because they belong to `A`. So far, this is what you already know.

### Guideline 2: Call Methods on Objects Passed as Parameters

You can **also** call methods on an object that was **passed in as a parameter** to a method.

For example, suppose `A` has another method, **`m3`**, which takes an argument of another class — say class **`B`**. `m3` takes a `b` (object of `B`) and does something with it.

Since `m3` takes `b` as an argument, you **can** call `b`'s methods inside `m3` — because you already have **some** information/relationship with `B` (it was given to you).

### Guideline 3: Call Methods on Objects You Create Yourself

You can **also call methods on objects you create yourself** inside a method.

For example, suppose `A` has a method **`m4`**, and inside `m4`, you create a new object of class **`D`**: `d = D()`. Since this method **itself** is creating `d`, you **can** call `d`'s methods — e.g., `d.m4()` directly inside `m4`.

### Guideline 4: Call Methods on Objects You Have a "Has-A" Relationship With

Finally — and this is very simple — you can call methods on objects that you have a **"has-a"** relationship with.

So if `A` has-a `B`, and `B` has its own methods (say `m3`, `m4`), you **can** call these methods through `A`'s object.

### Summary — The Four Rules

1. Call your own object's methods.
2. Call methods on objects passed as parameters to your method.
3. Call methods on objects you create yourself inside a method.
4. Call methods on objects you have a "has-a" relationship with.

### What This Prevents

Again — this just prevents one thing: if you have class `A`, `B`, and `C`, and your link is **only** `A → B`, you should **not** call `C`'s methods **through `B`**. This is very wrong.

If you ever need `C` to do something, you ask `B`: "do this for me," and declare that method **inside `B`**. Since `B` links to `C`, all of `C`'s interaction goes **through `B`**.

**That's the whole Principle of Least Knowledge.**

## 6. Standard Definition

> **The Facade pattern provides a simplified, unified interface to a set of complex sub-systems. It hides the complexity of the system and exposes only what is necessary to the user.**

This is exactly what we did: we hid the complexity of a very large sub-system from the Client, and provided a **Facade** — a gateway that the Client can interact with.

## 7. Facade vs Adapter — Clearing the Confusion

Many people get confused between the **Facade** pattern and the **Adapter** pattern we studied earlier. If you look at the UML diagrams, you'll understand the difference — but broadly, **both look like they're doing the same thing**: we have a Client that needs to talk to some sub-system, and we introduce a class in between — sometimes we call it a Facade, sometimes an Adapter.

But there's a **major difference**: their **intent**.

### Facade's Intent

**Hide the complexity of a sub-system** from a Client.

### Adapter's Intent

**Make two completely different interfaces talk to each other.**

### How to Decide Which to Use

If you understand the **intent** of each, you'll know which to use. Just looking at a UML diagram, you might easily say "oh, this is a Facade" or "this is an Adapter." But in **real-world applications**, when you're thinking about what to apply, sometimes **both** might seem to fit.

So you'll need to think: what is the **intent** of each pattern, and **which intent does my application follow**?

- Is it **hiding some complexity**? → Use **Facade**.
- Is it making **two completely different interfaces talk to each other** through a middle adapter? → Use **Adapter**.

## 8. Real-World Use Cases

### 1. Computer Boot-Up (Already Covered)

A very complex sub-system that we don't need to interact with directly.

### 2. Gaming Engines (e.g., Unity)

Gaming engines like **Unity** are a great example. When you load a game, you press **one button**. There's likely a Facade with **one method** — say `start_game` or `load_game`.

But **internally**, there's a **huge sub-system**, a very complex architecture of classes, doing many things:

- **Game assets** loading — many assets get loaded.
- **Memory management** — the entire game map doesn't load at once; only the area around where you currently are gets loaded. This requires memory management.
- **Physics engine** — loads the game's physics; defines whatever physics is being used in the game.
- ...and many more internal classes whose methods get called.

We, as a Client, just called `start_game`. In Unity, there's likely a Facade where we only call `start_game`, and it interacts with the **entire sub-system** to start the game for us. **A great use case** of the Facade Design Pattern.

### 3. Payment Gateway

Think of any use case where you're interacting with a sub-system — say a **payment gateway**. You just call **"make payment"**, and internally it:

- Checks if the balance is sufficient.
- Checks if the PIN is correct.
- Checks for any fraudulent transactions.
- Sends notifications, etc.

Just **one method** interacts with **multiple sub-systems**, and as a Client, we just get our payment done. **That's it.**

### General Guidance

**Any** use case where you can **hide a large sub-system** from a Client — that's where you can use a Facade.
