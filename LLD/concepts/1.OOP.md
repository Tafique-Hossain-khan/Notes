## Why OOP Exists (A Brief History Worth Knowing)

Before jumping into classes and objects, you need to understand *why* OOP was invented. This context will make every concept stick much better.

Programming languages evolved in three stages:

**Stage 1 — Machine Language.** Pure binary: `01010110 10110001`. Directly executed by the CPU. Error-prone, unreadable, impossible to scale.

**Stage 2 — Assembly Language.** Introduced mnemonics (English-like keywords). You'd write `MOV A, 61H` instead of binary. Still tightly coupled to hardware. No loops, no reusable functions, no abstraction.

**Stage 3 — Procedural Languages (like C).** Introduced functions, loops, if/else blocks. A massive leap. But it modeled code as *a list of instructions* — do this, then this, then this. Think of it like a recipe book.

**The problem?** Real-world problems aren't recipes. They're systems of interacting *things*. A ride-sharing app isn't a list of steps — it's drivers, riders, trips, payments, all interacting with each other.

Procedural code couldn't model that cleanly. So we got **Object-Oriented Programming**.

---

## The Core Ideology

> *"The way your real world works is how your programming should work."*

In the real world:
- Everything is an **object** — you, your phone, a car, a bank account.
- Objects have **characteristics** (what they are) and **behaviours** (what they do).
- Objects **interact** with each other.

OOP takes this and brings it directly into code. That's the entire idea. Every concept we'll cover — abstraction, encapsulation, inheritance, polymorphism — is just a tool to model the real world more faithfully.

## Pillar 1: Abstraction

### The Concept

When you drive a car, do you need to understand how the combustion engine works? No. You interact with the *interface*: steering wheel, accelerator, brake, gear lever.

The car *hides* the complexity and *exposes* only what you need.

That's abstraction: **hide unnecessary details from the user and expose only what's necessary.** 

A TV remote is an interface to a TV. You don't need to know how it broadcasts signals. A programming language itself is an abstraction — when you write `for i in range(10)`, you don't need to know how that compiles to machine code.

### In Python

Python uses **Abstract Base Classes (ABCs)** from the `abc` module to implement abstraction. An abstract class defines *what* methods must exist, but not *how* they work — that's left to the child class.

```python
from abc import ABC, abstractmethod

class Car(ABC):
    """
    Abstract blueprint for any car.
    This is the 'interface' — it defines what a car must be able to do,
    not how it does it.
    """

    @abstractmethod
    def start_engine(self):
        pass

    @abstractmethod
    def shift_gear(self, gear: int):
        pass

    @abstractmethod
    def accelerate(self):
        pass

    @abstractmethod
    def brake(self):
        pass

    @abstractmethod
    def stop_engine(self):
        pass


class SportsCar(Car):
    """
    A concrete implementation of Car.
    This is the actual car with real behaviour defined.
    """

    def __init__(self, brand: str, model: str):
        self.brand = brand
        self.model = model
        self.is_engine_on = False
        self.current_speed = 0
        self.current_gear = 0

    def start_engine(self):
        self.is_engine_on = True
        print(f"{self.brand} {self.model}: Engine starts with a ROAR 🔥")

    def shift_gear(self, gear: int):
        if not self.is_engine_on:
            print("Can't shift gear — engine is off.")
            return
        self.current_gear = gear
        print(f"Shifted to gear {self.current_gear}")

    def accelerate(self):
        if not self.is_engine_on:
            print("Can't accelerate — engine is off.")
            return
        self.current_speed += 20
        print(f"Accelerating... current speed: {self.current_speed} km/h")

    def brake(self):
        self.current_speed = max(0, self.current_speed - 20)
        print(f"Braking... current speed: {self.current_speed} km/h")

    def stop_engine(self):
        self.is_engine_on = False
        self.current_speed = 0
        self.current_gear = 0
        print("Engine turned off.")


# Usage — notice: you interact with the Car interface, not SportsCar's internals
my_car: Car = SportsCar("Ford", "Mustang")

my_car.start_engine()
my_car.shift_gear(1)
my_car.accelerate()
my_car.shift_gear(2)
my_car.accelerate()
my_car.brake()
my_car.stop_engine()
```

**Output:**
```
Ford Mustang: Engine starts with a ROAR 🔥
Shifted to gear 1
Accelerating... current speed: 20 km/h
Shifted to gear 2
Accelerating... current speed: 40 km/h
Braking... current speed: 20 km/h
Engine turned off.
```

Notice: you called `my_car.start_engine()` without knowing anything about *how* the engine starts. The implementation details are hidden. That's abstraction in action.

Also notice: `Car` cannot be instantiated directly. Try `Car()` — Python will raise a `TypeError`. An abstract class is a *contract*, not an object.

## Pillar 2: Encapsulation

### The Concept

Encapsulation has two ideas inside it — people often know the first and miss the second.

**Idea 1 — Bundle data and behaviour together.** A car's attributes (brand, speed, gear) and its methods (accelerate, brake) belong *together* inside one object. Not scattered as loose variables and functions. This bundling is encapsulation.

**Idea 2 — Data security.** Some data inside an object should not be directly modified from outside. Think about a car's odometer. You can't walk up to a car and set the odometer to 5 km manually (not through normal means). It only changes when you actually drive. That *restriction* is also encapsulation.

This is the key difference from abstraction:

| | Abstraction | Encapsulation |
|---|---|---|
| **Focus** | Hiding complexity | Protecting data |
| **Question** | "Do you *need* to know this?" | "Should you be *allowed* to change this?" |
| **Example** | You don't need to know how the engine works | You can't set the odometer to 0 yourself |

### In Python

Python uses a naming convention for access control:
- `public_variable` — accessible everywhere
- `_protected_variable` — convention says "don't touch this unless you're a subclass"
- `__private_variable` — name-mangled, truly restricted (use getters/setters)

```python
class SportsCar:

    def __init__(self, brand: str, model: str):
        self.brand = brand       # public — fine to access directly
        self.model = model       # public
        self.__is_engine_on = False    # private — no direct access
        self.__current_speed = 0       # private — must use getter/setter
        self.__current_gear = 0        # private
        self.__tyre_brand = "MRF"      # private with getter + setter

    # --- Getter: read-only access to private data ---
    def get_current_speed(self) -> int:
        return self.__current_speed

    # --- Getter + Setter pair for tyre (with validation) ---
    def get_tyre_brand(self) -> str:
        return self.__tyre_brand

    def set_tyre_brand(self, tyre: str):
        valid_tyres = ["MRF", "Bridgestone", "Michelin", "CEAT", "Apollo"]
        if tyre not in valid_tyres:
            print(f"Invalid tyre brand '{tyre}'. Choose from: {valid_tyres}")
            return
        self.__tyre_brand = tyre
        print(f"Tyre changed to {self.__tyre_brand}")

    # --- Behaviours ---
    def start_engine(self):
        self.__is_engine_on = True
        print(f"{self.brand} {self.model}: Engine started.")

    def accelerate(self):
        if not self.__is_engine_on:
            print("Engine is off. Start the engine first.")
            return
        self.__current_speed += 20
        print(f"Speed: {self.__current_speed} km/h")

    def brake(self):
        self.__current_speed = max(0, self.__current_speed - 20)
        print(f"Braking. Speed: {self.__current_speed} km/h")

    def stop_engine(self):
        self.__is_engine_on = False
        self.__current_speed = 0
        self.__current_gear = 0
        print("Engine off.")


my_car = SportsCar("Ford", "Mustang")

# ✅ Valid interactions
my_car.start_engine()
my_car.accelerate()
my_car.accelerate()
print(f"Current speed: {my_car.get_current_speed()} km/h")  # use getter

my_car.set_tyre_brand("Michelin")     # valid
my_car.set_tyre_brand("FakeTyre")     # rejected with message

my_car.brake()
my_car.stop_engine()

# ❌ This will raise AttributeError — you cannot touch private data directly
# my_car.__current_speed = 500   # Try it. Python will raise AttributeError.
```

**The setter matters:** Notice `set_tyre_brand()` validates the input before setting it. If the variable were public, anyone could do `my_car.tyre_brand = "RandomGarbage"` with no checks. The setter gives you *control over how data changes*.

## Pillar 3: Inheritance

### The Concept

In the real world, things share characteristics. A Sports Car and an Electric Car are both Cars. They share common traits (has a brand, has a model, can start/stop) but differ in specifics (Electric Car has a battery level; Sports Car has a turbo boost).

Inheritance lets you define a **parent class** with shared behaviour, and **child classes** that extend or override it. This directly enables reusability and scalability — the two things procedural programming struggled with.

The key principle here is the **IS-A relationship**: a `SportsCar` IS-A `Car`. A `Dog` IS-A `Animal`. If that sentence sounds natural, inheritance is the right tool.

### In Python

```python
class Vehicle:
    """Parent class — shared properties all vehicles have."""

    def __init__(self, brand: str, model: str, year: int):
        self.brand = brand
        self.model = model
        self.year = year
        self.__fuel_level = 100  # private

    def get_fuel_level(self) -> int:
        return self.__fuel_level

    def refuel(self, amount: int):
        self.__fuel_level = min(100, self.__fuel_level + amount)
        print(f"Refuelled. Fuel level: {self.__fuel_level}%")

    def get_info(self) -> str:
        return f"{self.year} {self.brand} {self.model}"

    def start(self):
        print(f"{self.get_info()}: Starting...")

    def stop(self):
        print(f"{self.get_info()}: Stopping.")


class SportsCar(Vehicle):
    """Child class — inherits from Vehicle, adds its own properties."""

    def __init__(self, brand: str, model: str, year: int, turbo: bool):
        super().__init__(brand, model, year)  # call parent constructor
        self.turbo = turbo

    def boost(self):
        if self.turbo:
            print(f"{self.get_info()}: TURBO BOOST ACTIVATED 🚀")
        else:
            print(f"{self.get_info()}: No turbo on this one.")

    # Override parent method — change how it starts
    def start(self):
        super().start()  # still call parent behaviour
        print(f"  └── Sports mode engaged.")


class ElectricCar(Vehicle):
    """Another child class — completely different internals."""

    def __init__(self, brand: str, model: str, year: int, battery_capacity_kwh: int):
        super().__init__(brand, model, year)
        self.battery_capacity = battery_capacity_kwh
        self.__battery_level = 100

    def get_battery_level(self) -> int:
        return self.__battery_level

    def charge(self, percent: int):
        self.__battery_level = min(100, self.__battery_level + percent)
        print(f"Charged. Battery: {self.__battery_level}%")

    def start(self):
        # Override — electric cars start silently
        print(f"{self.get_info()}: Starting silently... ⚡")

    def refuel(self, amount: int):
        # Override — 'refuelling' an electric car means charging
        print("Electric cars don't refuel. Use charge() instead.")


# --- Usage ---
car1 = SportsCar("Ford", "Mustang GT500", 2023, turbo=True)
car2 = ElectricCar("Tesla", "Model S", 2023, battery_capacity_kwh=100)

car1.start()          # uses overridden start
car1.boost()          # unique to SportsCar
car1.refuel(20)       # inherited from Vehicle
print(car1.get_info())

print()

car2.start()          # silently
car2.charge(30)       # unique to ElectricCar
car2.refuel(20)       # overridden — shows message
print(car2.get_info())

# isinstance() — checking the IS-A relationship
print(isinstance(car1, SportsCar))  # True
print(isinstance(car1, Vehicle))    # True — it IS-A Vehicle too
print(isinstance(car1, ElectricCar))  # False
```

**Output:**
```
2023 Ford Mustang GT500: Starting...
  └── Sports mode engaged.
2023 Ford Mustang GT500: TURBO BOOST ACTIVATED 🚀
Refuelled. Fuel level: 100%
2023 Ford Mustang GT500

2023 Tesla Model S: Starting silently... ⚡
Charged. Battery: 100%
Electric cars don't refuel. Use charge() instead.
2023 Tesla Model S

True
True
False
```

Key things to observe:
- `super().__init__()` calls the parent constructor — always do this when overriding `__init__`
- `super().start()` lets you extend parent behaviour rather than replace it entirely
- Both cars are `Vehicle` instances — that's the IS-A relationship in code

## Pillar 4: Polymorphism

### The Concept

Polymorphism means "many forms." A single interface can work with different types of objects.

The classic example: imagine you have a `Shape` class. Whether it's a `Circle`, `Rectangle`, or `Triangle`, they all have an `area()` method. You can call `.area()` on any of them without caring which specific shape it is. Same method name, different behaviour depending on the object.

There are two types:
- **Compile-time (Method Overloading)** — same method name, different parameters. Python handles this differently from Java/C++.
- **Runtime (Method Overriding)** — child class provides a different implementation of a parent method. This is the powerful one.

### In Python

```python
from abc import ABC, abstractmethod
import math

class Shape(ABC):
    """Abstract base — any shape must know its area and perimeter."""

    @abstractmethod
    def area(self) -> float:
        pass

    @abstractmethod
    def perimeter(self) -> float:
        pass

    def describe(self):
        # This method is the same for all shapes
        print(f"{self.__class__.__name__}: Area={self.area():.2f}, Perimeter={self.perimeter():.2f}")


class Circle(Shape):
    def __init__(self, radius: float):
        self.radius = radius

    def area(self) -> float:
        return math.pi * self.radius ** 2

    def perimeter(self) -> float:
        return 2 * math.pi * self.radius


class Rectangle(Shape):
    def __init__(self, width: float, height: float):
        self.width = width
        self.height = height

    def area(self) -> float:
        return self.width * self.height

    def perimeter(self) -> float:
        return 2 * (self.width + self.height)


class Triangle(Shape):
    def __init__(self, a: float, b: float, c: float):
        self.a, self.b, self.c = a, b, c

    def area(self) -> float:
        s = self.perimeter() / 2
        return math.sqrt(s * (s - self.a) * (s - self.b) * (s - self.c))

    def perimeter(self) -> float:
        return self.a + self.b + self.c


# --- Polymorphism in action ---
shapes: list[Shape] = [
    Circle(7),
    Rectangle(4, 6),
    Triangle(3, 4, 5),
]

# Same function call — different behaviour based on object type
for shape in shapes:
    shape.describe()

# --- Standalone function demonstrating polymorphism ---
def total_area(shapes: list[Shape]) -> float:
    """Works with ANY shape — doesn't care which type."""
    return sum(shape.area() for shape in shapes)

print(f"\nTotal area of all shapes: {total_area(shapes):.2f}")
```

**Output:**
```
Circle: Area=153.94, Perimeter=43.98
Rectangle: Area=24.00, Perimeter=20.00
Triangle: Area=6.00, Perimeter=12.00

Total area of all shapes: 183.94
```

**Duck Typing in Python:** Python also supports polymorphism without inheritance. If two unrelated classes both have a `.quack()` method, you can call `.quack()` on either. Python doesn't care about the type — only whether the method exists. This is called duck typing ("if it walks like a duck and quacks like a duck, it's a duck").

```python
class Dog:
    def speak(self):
        return "Woof!"

class Cat:
    def speak(self):
        return "Meow!"

class Robot:
    def speak(self):
        return "BEEP BOOP"

# These three have NO common parent class
# But polymorphism still works
for creature in [Dog(), Cat(), Robot()]:
    print(creature.speak())  # same call, different result
```

## Quick Reference: OOP in Python

```python
# Abstract class
from abc import ABC, abstractmethod

class Animal(ABC):
    @abstractmethod
    def speak(self) -> str:
        pass

# Inheritance + super()
class Dog(Animal):
    def __init__(self, name):
        self.name = name  # public

    def speak(self) -> str:
        return f"{self.name} says: Woof!"

# Access modifiers
class BankAccount:
    def __init__(self):
        self.owner = "Alice"         # public
        self._account_type = "savings"  # protected (convention)
        self.__balance = 0           # private (name-mangled)

    def get_balance(self):           # getter
        return self.__balance

# isinstance and type checking
d = Dog("Rex")
print(isinstance(d, Dog))     # True
print(isinstance(d, Animal))  # True — IS-A relationship
print(type(d))                # <class '__main__.Dog'>

# Polymorphism
animals = [Dog("Rex"), Dog("Buddy")]
for animal in animals:
    print(animal.speak())  # same call, works on any Animal
```
