# Composite Design Pattern in Python

Today we're learning a new design pattern: the **Composite Design Pattern**.

A quick note before starting: the design patterns covered so far (Strategy, Factory, Singleton, etc.) are **foundational** design patterns — meaning most generic problems can plug into one of them somewhere. The patterns we're covering now, starting with Composite, are more **use-case specific** — they solve a particular type of problem. This doesn't mean they're less important — if you're working on a real-world project, or an interview problem statement maps directly onto one of these, recognizing it is extremely valuable. Let's start with the Composite Design Pattern.

---

## 1. Similarity with Tree Data Structures

If you come from a DSA background and have studied **Trees**, you already have a good intuitive sense of the Composite Design Pattern.

**Any problem statement that can be expressed in a hierarchical / tree form**, where there are two types of nodes — **leaf nodes** and **intermediate nodes** — can be solved using the Composite Design Pattern.

### The Classic Example: Designing a File System

This is the classic example — whenever you search for the Composite Design Pattern, you'll find this example, because it feels like the pattern was **made** for this problem.

In any operating system, you have **folders**, and inside folders you have **files**. A file system has:
- **Folders**
- **Files**

Folders and files can go further into a hierarchy — a folder can contain more folders, and it can contain files. But a **file** cannot contain anything else — it's an **endpoint**, a **leaf node** — no hierarchy can form inside it.

A node that **can** have further hierarchy (like a folder) is called a **non-leaf node**, or more commonly, a **composite node**.

This connects directly to trees: in a binary tree, you have a root node, with child nodes — a child node could itself be a leaf, or it could have further children (which could again be leaves or further composites).

## 2. The Situation WITHOUT the Composite Pattern

Let's first try to solve "Designing a Folder System" **from scratch**, without any knowledge of the Composite Pattern, to see what problems arise.

### Naive Classes

**`File`** class:
- Has a **name**.
- Has a **size**.
- Has some **content**.
- Has a method **`open`** — opening gives you the file's content.

**`Folder`** class:
- Has a **name**.
- Has a list of more **folders**.
- Has a list of more **files**.

So we'd build **two separate lists**: a list called `files`, and a list called `folders`.

If we draw the relationships: **Folder can have one-to-many Files**, AND **Folder can have one-to-many Folders**. That's roughly the UML if we think about it this way.

### Implementing `ls`

`ls` = "list directory" — when you're in a directory and run `ls`, it lists everything **directly inside** that folder (files and folders, one level).

Example structure:
```
root/
├── file1.txt
├── file2.txt
├── core/
│   ├── file3.txt
│   └── file4.txt
└── file3.txt (wait — let's keep it simple, see below)
```

If `root` contains: `file1.txt`, `file2.txt`, a folder `core`, and `file3.txt` — running `ls` on `root` lists all four entries.

### Implementing `open_all`

`open_all` expands the **entire hierarchy** — recursively. If I run `open_all` on `root`, I should get `file1.txt`, `file2.txt`, and everything inside `core` too (and so on, recursively).

### The Problem: Treating Files and Folders Differently

If `File` and `Folder` are treated as **separate types**, how do we implement `open_all`? 

- For a `File`: `open_all` should just show the file's **name** (and content) — that's it, it's a leaf.
- For a `Folder`: `open_all` should **loop through** its files and folders, and recursively call `open_all` on each.

If we keep **two separate lists** (`files` and `folders`), `open_all` would first print **all files**, then **all folders** — but this **doesn't preserve the original order**! If the actual order was `file1, file2, core, file3`, but `files = [file1, file2, file3]` and `folders = [core]`, our output order would be wrong.

### The Fix Attempt: One Common List

To preserve order, we need **one common list** holding **both** files and folders (e.g., a list of pointers/references in C++, or a list of a common type in Python).

But now, when implementing `open_all`, we'd loop through this common list and need an **if/else** check for **each element**:

```python
for element in common_list:
    if element.type == "file":
        print(element.name)
    else:  # it's a folder
        element.open_all()  # recursive call
```

### Why This Gets Messy

- If the element is a **file**, `open_all` just prints its name.
- If the element is a **folder**, `open_all` recursively loops through **its own** list and calls `open_all` on each child — exactly like traversing a tree: a node tells its subtree to traverse and bring back names, then the node prints its own name plus what it got back.

This `if/else` checking ("is this a file or a folder?") has to be done **everywhere** — and gets worse as we add more methods.

### Adding a New Method: `cd` (Change Directory)

Suppose we now add a **`cd`** (change directory) command. If you're in `root` and it contains `core`, running `cd core` from `root` moves you into `core`.

But: **`cd` cannot work on a File** — you cannot "change directory" into a file. So now we have to **manage this too** — check whether something is a folder before allowing `cd`.

**All of this complexity arises from treating Files and Folders as separate, differently-behaving types.**

## 3. What the Composite Pattern Is All About

The Composite Design Pattern says: you can have **two types of elements**.

1. **Composite**
2. **Leaf**

And it says: **treat the Composite and the Leaf in the same way** — they are **not** different. "Treating them the same way" means: they should have a **common interface** — a common abstract class (call it whatever you like — interface, common abstract class, doesn't matter).

If there's a common interface/abstract class, then **both** `Composite` and `Leaf` will **override the same methods** defined in that class, and **both will respond the same way** when those methods are called.

### The Benefit

We get rid of all the `if/else` handling we saw earlier! We treat both **uniformly** — whether it's a folder or a file, **for us, both are the same thing**.

## 4. UML for the File System

### Step 1: The Common Interface — `FileSystemItem`

We create an interface/abstract class: **`FileSystemItem`**. Since its methods will be **declared but not defined**, this is an abstract class — its responsibility for defining methods falls on subclasses.

Methods on `FileSystemItem`:
1. **`ls`** — list directory — lists all folders/sub-folders directly inside.
2. **`open_all`** — expands the **entire hierarchy** down to the bottom level.
3. **`get_size`** — returns the size of this file or folder.
4. **`get_name`** — returns the item's name. (No actual name here since it's abstract — but whoever implements this will have their own name.)

### Step 2: Two Implementations — `File` and `Folder`

**`File`** class:
- Has a **name**.
- Has a **size**.
- Implements `ls`, `open_all`, `get_size`, `get_name`.

**`Folder`** class:
- Has a **name**.
- Has a **size** too — but a folder's size is the **combined size** of everything inside it (we'll compute this via looping, shown in code later).
- Implements `ls`, `open_all`, etc.
- Additionally has: **a list of `FileSystemItem`** — because `FileSystemItem` is the interface, and a folder can contain **either** files **or** folders (or both). We call this list **`children`**.

### Relationships

- **`File` is-a `FileSystemItem`**
- **`Folder` is-a `FileSystemItem`**
- **`Folder` has-a (one-to-many) `FileSystemItem`** (its `children`)

This is the **same dual relationship** (is-a + has-a) we saw in the **Decorator Design Pattern**, where a Decorator also had both an is-a and a has-a relationship with its parent class — just for memory/reference.

---

                    │   <<abstract>>           │
                    │   FileSystemItem         │
                    ├─────────────────────────┤
                    │ + ls()                   │
                    │ + open_all()             │
                    │ + get_size()             │
                    │ + get_name()             │
                    │ + cd(target)             │
                    │ + is_folder()            │
                    └───────────▲─────────────┘
                                 │
                  ┌──────────────┴───────────────┐
                  │  is-a                    is-a │
                  │                                │
        ┌─────────┴────────┐           ┌──────────┴─────────┐
        │       File        │           │       Folder        │
        ├───────────────────┤           ├──────────────────────┤
        │ - name             │           │ - name               │
        │ - size             │           │ - children: List<    │
        ├───────────────────┤           │     FileSystemItem>   │
        │ + ls()             │           ├──────────────────────┤
        │ + open_all()       │           │ + add(item)          │

## 5. Tracing `open_all` — The Polymorphism Insight

Before writing the `File` and `Folder` classes, let's trace through how `open_all` works on a hierarchy, **using only the common interface**.

### Example Hierarchy

```
root/                  (Folder)
├── file1.txt          (File)
├── file2.txt          (File)
├── core/              (Folder)
│   ├── file3.txt      (File)
│   └── file4.txt      (File)
└── user/              (Folder)
    └── file5.txt      (File)
```

### Calling `open_all` on `root`

`root` has a list (`children`) of `FileSystemItem`: `[file1, file2, core, user]`. **All four** are `FileSystemItem` — `root` doesn't care whether each one is a `File` or a `Folder`.

`root.open_all` will:
1. **Loop through** `children`.
2. For each item, call **`item.open_all()`** — directly, without checking whether it's a file or a folder.

**This is the power of polymorphism**: `root` doesn't need to know what type each child is — it just calls `open_all` on the common interface.

### What Happens for Each Type

- If `item` is a **`File`**: its `open_all` does almost nothing — it just returns/prints its own **name** (`get_name`). A file is a leaf — it has no children.
- If `item` is a **`Folder`**: its `open_all` does the **same thing** as `root`'s `open_all` — it loops through **its own** `children` and calls `open_all` on each. This is **recursive** — one node tells another node to "do something," which tells a third node to "do something," and so on.

### Recursive Call Trace (Example)

Imagine a smaller tree:

```
root
├── child1 (Folder)
│   ├── grandchild1 (File)
│   └── grandchild2 (File)
└── child2 (File)
```

Calling `root.open_all()`:
1. `root` prints its own name: `"root"`.
2. `root` loops through `children`: `[child1, child2]`.
3. `root` calls `child1.open_all()` — `child1` is a Folder:
   - `child1` prints its own name: `"child1"`.
   - `child1` loops through its `children`: `[grandchild1, grandchild2]`.
   - `child1` calls `grandchild1.open_all()` — File → returns/prints its name: `"grandchild1"`.
   - `child1` calls `grandchild2.open_all()` — File → returns/prints its name: `"grandchild2"`.
4. `root` calls `child2.open_all()` — File → returns/prints its name: `"child2"`.

This is **exactly** tree traversal: start at the root, ask each subtree to traverse itself and bring back names; print your own name plus what came back from the subtrees.

## 7. Implementing `Folder`

A `Folder` has:
- `name`
- `children` — a list of `FileSystemItem` (can hold `File`s and/or `Folder`s)
- (size is **not** stored directly — it's computed)

### Method: `add`

A method to add any `FileSystemItem` (a `File` or a `Folder`) into the `children` list.

### Method: `ls`

Loops through `children`, and for each child calls `get_name()`.

> **About the `+` prefix in printing**: in the original walkthrough, folders are printed with a `+` prefix and files without one — purely so that, visually, you can tell at a glance which entries are folders and which are files. This uses `is_folder()` to decide whether to prefix `+`. **This is cosmetic and can be ignored** — the core logic is simply: call `get_name()` on each child.

```python
def ls(self, indent=0):
    for child in self.children:
        prefix = "+ " if child.is_folder() else "  "
        print(" " * indent + prefix + child.get_name())
```

### Method: `open_all`

This is different from `ls`:
- `ls` only shows **direct children's names** — it does **not** expand further.
- `open_all` **expands everything** — recursively.

So `open_all`:
1. First, prints/returns **its own name**.
2. Then loops through `children`, and calls **`open_all`** (not `get_name`!) on each child.
   - If the child is a `File` → its `open_all` just returns its own name (leaf, recursion ends).
   - If the child is a `Folder` → its `open_all` repeats the same process (prints its own name, then loops through **its** children calling `open_all`).

This recursion continues until **leaf nodes** are hit.

```python
def open_all(self, indent=0):
    print(" " * indent + "+ " + self.name)
    for child in self.children:
        child.open_all(indent + 4)
```

### Method: `get_size`

A file's size is just `size`. A folder's size is the **combined size of everything inside it** (`children`).

```python
def get_size(self):
    total = 0
    for child in self.children:
        total += child.get_size()
    return total
```

- If `child` is a `File` → `get_size` directly returns its own `size` (leaf — recursion ends).
- If `child` is a `Folder` → `get_size` recursively loops through **its** children, sums them up, and returns the total **up** the hierarchy.

This continues recursively until all leaf nodes (files) are reached; their sizes bubble back up the hierarchy and get summed at each level.

### Method: `cd`

Recall: for a `File`, `cd` returns `None` (unsupported).

For a `Folder`:
1. Take a `target` name as an argument (the folder name we want to move into).
2. Loop through `children`.
3. For each `child`, check:
   - Is `child` a **folder** (`child.is_folder()` is `True`)?
   - AND does `child`'s name equal `target`?
4. If **both** are true → **return that child** (this is the "change directory" — we've now moved into that folder).
5. If **no match is found** after the loop → return `None` (e.g., trying to `cd` into a folder that doesn't exist).

> **This is exactly why we need `is_folder`** — without it, `cd` couldn't distinguish files from folders when searching for the target. And this is also where the `+` prefix logic in `ls` comes from — both rely on `is_folder()`.

```python
def cd(self, target_name):
    for child in self.children:
        if child.is_folder() and child.get_name() == target_name:
            return child
    return None
```

### Method: `get_name` and `is_folder`

```python
def get_name(self):
    return self.name

def is_folder(self):
    return True
```

## 9. Standard UML Diagram (General Composite Pattern)

The standard UML diagram for the Composite Design Pattern, in general terms:

- We have a **`Component`** (abstract). It has an **`operation`** method.
- `Component` can be of two types:
  - **`Leaf`**
  - **`Composite`**
- **Both `Leaf` and `Composite` have an is-a relationship with `Component`** — both **are** `Component`s.
- **`Composite` has a one-to-many relationship with `Component`** — i.e., a `Composite` holds a **list of `Component`s** (which could themselves be `Leaf`s or further `Composite`s).
- Both `Leaf` and `Composite` **override `operation`**.

### Standard UML Diagram

```
                    ┌────────────────────┐
                    │   <<abstract>>      │
                    │     Component       │
                    ├────────────────────┤
                    │ + operation()       │
                    └─────────▲──────────┘
                               │
                  ┌─────────────┴─────────────┐
                  │ is-a                  is-a │
                  │                             │
          ┌───────┴───────┐           ┌─────────┴─────────┐
          │      Leaf       │           │     Composite      │
          ├────────────────┤           ├────────────────────┤
          │ + operation()   │           │ + operation()      │
          └────────────────┘           │ - children:         │
                                         │     List<Component>│
                                         └──────────┬──────────┘
                                                     │
                                              has-a (1 to many)
                                                     │
                                                     ▼
                                               Component (children)
```

### The Key Insight

When you call `operation()` on a `Component` (say a root node), **it doesn't matter** whether that component is a `Leaf` or a `Composite`. The **caller** (e.g., a root node, or a client) just calls `operation()` — both will respond appropriately according to their own implementation. The caller doesn't need to know or care which type it is.

| Standard UML Term | Our File System Example |

| `Component` | `FileSystemItem` |

## 10. Standard Definition

> **The Composite pattern composes objects into tree-like structures, representing part-whole hierarchies. It lets the client treat individual objects and compositions of objects uniformly.**

- "Composes objects into tree-like structures" — exactly our file system: folders and files form a tree.
- "Part-whole hierarchy" — a whole `Composite` (folder) can contain further elements (parts); a `Leaf` (file) is just a part with no further breakdown.
- "Lets the client treat individual objects and compositions of objects uniformly" — whatever **client** is interacting with this sub-system (e.g., `root` calling `open_all` on its children, or `main` calling methods on `root`) doesn't care whether it's talking to a `Leaf` (file) or a `Composite` (folder) — it talks to the **common interface** (`FileSystemItem`), and that's all that matters.

## 11. Real-World Use Case — Nested Menus / Dropdowns

Any LLD problem that uses a **tree-like data structure** can be solved using the Composite Design Pattern. We've already seen the File System example.

### Another Example: Nested Dropdown Menus

Think of a **frontend dropdown list** where the list contains **further lists** inside it, which themselves contain **further lists**.

For example: a menu bar → **File** menu → **Save As** option → inside "Save As", further options like "Save as PDF", "Save as Text", and so on — potentially with even more nested options.

- The **final element** (e.g., "Save as PDF") is a **leaf node**.
- Anything that itself contains a **further dropdown list** is like our **folder** (composite).

### General Guidance

Whenever you see a problem with this kind of hierarchy — a **composite** that can contain further components, and a **leaf** that cannot — you can **directly** apply the Composite Design Pattern.

Applying it directly will get you a large part of the way to a solution — though the full problem might need additional algorithms or other design patterns layered on top. But the Composite pattern alone will solve **most of the structural problem**, because it **bifurcates** the entire problem into two components: **Composite** and **Leaf**.
