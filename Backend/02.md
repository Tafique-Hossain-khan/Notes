# API Routing in FastAPI

Same theory, now fully in FastAPI. FastAPI leans heavily on Python type hints, which actually makes several routing concepts (type-casting, validation, docs) cleaner than Flask or Express — worth calling out as we go.

```python
from fastapi import FastAPI, HTTPException, Request
from fastapi.responses import JSONResponse
from typing import Optional

app = FastAPI()
```

---

## 1. Method + Route = Identity

```python
books = [{'id': 1, 'name': 'Clean Code', 'price': 30}]

@app.get('/api/books')
def get_books():
    return {'data': books}

@app.post('/api/books')
def create_book(book: dict):
    books.append(book)
    return {'data': books}
```

Same path, two decorators (`@app.get`, `@app.post`) → two separate handlers. FastAPI matches on method + path internally, same as every other framework.

---

## 2. Static Routes

```python
@app.get('/api/books')
def list_books():
    return {'data': books}
```

Fixed string, fixed handler, always the same response shape. Nothing new here vs. the theory — FastAPI just uses `@app.get(...)` decorators instead of `app.route(..., methods=[...])`.

---

## 3. Dynamic Routes (Path Parameters)

This is where FastAPI is noticeably nicer than the others. You declare the type as a normal Python type hint, and FastAPI validates *and* casts it automatically — no `<int:...>` converter syntax needed:

```python
@app.get('/api/users/{user_id}')
def get_user(user_id: int):
    # user_id arrives as an actual Python int
    return {'userId': user_id}
```

If someone requests `/api/users/abc`, FastAPI auto-responds with a `422 Unprocessable Entity` before your function even runs — you get validation for free. This directly reinforces the theory point about path params being **identity**, not free-form data: FastAPI enforces the shape of that identity for you.

Want the raw-string behavior instead (matching what the video described as "everything comes in as a string")?

```python
@app.get('/api/users-raw/{user_id}')
def get_user_raw(user_id: str):
    return {'userId': user_id, 'type': type(user_id).__name__}
```

---

## 4. Query Parameters

In FastAPI, any function parameter that is **not** part of the path automatically becomes a query parameter:

```python
@app.get('/api/search')
def search(query: str, sort: Optional[str] = None, page: int = 1, limit: int = 20):
    return {
        'query': query,
        'sort': sort,
        'page': page,
        'limit': limit
    }
```

Called as:
```
GET /api/search?query=laptop&sort=price_asc&page=2&limit=20
```

No `request.args.get(...)` boilerplate at all — the function signature *is* the query parameter contract. Defaults (`page: int = 1`) work exactly like the theory describes: page/limit aren't required to change *which* resource you're hitting, only *how* you view it, so they get sensible fallbacks.

### Pagination example

```python
@app.get('/api/books-paginated')
def list_books_paginated(page: int = 1, limit: int = 20):
    start = (page - 1) * limit
    paged = books[start:start + limit]

    return {
        'data': paged,
        'meta': {
            'total': len(books),
            'currentPage': page,
            'totalPages': -(-len(books) // limit)  # ceiling division
        }
    }
```

Client computes the next page purely from `meta`: `GET /api/books-paginated?page=2`.

## 5. Nested Routes

```python
@app.get('/api/users')
def all_users():
    return {'data': users}

@app.get('/api/users/{user_id}')
def one_user(user_id: int):
    return {'data': find_user(user_id)}

@app.get('/api/users/{user_id}/posts')
def user_posts(user_id: int):
    return {'data': get_posts_for(user_id)}

@app.get('/api/users/{user_id}/posts/{post_id}')
def user_specific_post(user_id: int, post_id: int):
    return {'data': get_post(user_id, post_id)}
```

Reads the same way as before: `GET /users/123/posts/456` → "post 456 belonging to user 123." Each nesting level is its own independent, fully-typed route.

## 6. Route Versioning & Deprecation

FastAPI uses `APIRouter` (its equivalent of Flask Blueprints / Express Router) to group versioned routes cleanly:

```python
from fastapi import APIRouter
from fastapi.responses import JSONResponse

v1 = APIRouter(prefix='/api/v1')
v2 = APIRouter(prefix='/api/v2')

@v1.get('/products')
def products_v1():
    data = [{'id': p['id'], 'name': p['name'], 'price': p['price']} for p in products]
    response = JSONResponse(content={'data': data})
    response.headers['Deprecation'] = 'true'
    response.headers['Sunset'] = 'Wed, 31 Dec 2026 23:59:59 GMT'
    return response

@v2.get('/products')
def products_v2():
    data = [{'id': p['id'], 'title': p['name'], 'price': p['price']} for p in products]
    return {'data': data}

app.include_router(v1)
app.include_router(v2)
```

`APIRouter` is also how larger FastAPI projects organize routes across files (e.g., `routers/users.py`, `routers/products.py`) — the version prefix is just one common use of that same mechanism. The migration-window logic is identical to the theory: v1 stays alive with a deprecation notice, v2 is the new contract, and you retire v1 once clients have moved.

**Bonus — FastAPI has version-aware docs for free.** Since routers are separate, `/docs` (Swagger UI) will show `/api/v1/products` and `/api/v2/products` as distinct, separately-documented endpoints automatically.

## 7. Catch-All Routes

Two ways to do this in FastAPI, matching the two Flask approaches:

**a) Global exception handler for unmatched routes (equivalent to Flask's `@app.errorhandler(404)`):**

```python
from fastapi.exceptions import HTTPException as StarletteHTTPException
from fastapi.requests import Request

@app.exception_handler(StarletteHTTPException)
async def not_found_handler(request: Request, exc: StarletteHTTPException):
    if exc.status_code == 404:
        return JSONResponse(
            status_code=404,
            content={
                'error': 'Not Found',
                'message': f'No route matches {request.method} {request.url.path}'
            }
        )
    return JSONResponse(status_code=exc.status_code, content={'detail': exc.detail})
```

**b) Literal wildcard catch-all path (equivalent to Flask's `<path:...>`):**

```python
@app.get('/{full_path:path}')
def catch_all(full_path: str):
    return JSONResponse(
        status_code=404,
        content={'error': 'Not Found', 'message': f'/{full_path} is not a valid endpoint'}
    )
```

⚠️ Same ordering rule as before applies, even more strictly in FastAPI: this wildcard route **must be registered last**, after every real route — otherwise it will greedily match everything and your other routes will never fire.

## Cheat Sheet: Express vs Flask vs FastAPI

| Concept | Express (JS) | Flask (Python) | FastAPI (Python) |
|---|---|---|---|
| Static route | `app.get('/api/books', fn)` | `@app.route('/api/books', methods=['GET'])` | `@app.get('/api/books')` |
| Path param | `/users/:id` → string | `/users/<int:id>` → typed | `/users/{id}` + `id: int` in signature |
| Query param | `req.query.page` | `request.args.get('page', type=int)` | Just a function arg: `page: int = 1` |
| Nested route | `/users/:id/posts/:postId` | `/users/<int:id>/posts/<int:pid>` | `/users/{id}/posts/{pid}` |
| Versioning | manual prefix strings | `Blueprint(url_prefix=...)` | `APIRouter(prefix=...)` |
| Catch-all | `app.use((req,res)=>...)` last | `@app.errorhandler(404)` or `<path:...>` | `@app.exception_handler(...)` or `{path:path}` |
| Validation | manual | manual (`type=`, converters) | **automatic**, from type hints |

The one thing worth internalizing beyond the syntax: FastAPI's whole design philosophy is "the function signature *is* the contract" — path params, query params, and even request bodies are all just typed parameters, and FastAPI derives routing, validation, and auto-generated docs (`/docs`) from that single source of truth.
