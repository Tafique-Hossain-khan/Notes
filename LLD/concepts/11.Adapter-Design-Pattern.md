# Adapter Design Pattern in Python

Today we're learning a brand new design pattern: the **Adapter Design Pattern**. This is also a very easy pattern to understand, and it has a great use case whenever you develop an application. In fact, in interviews too, you can bring this up for many questions. Let's see what the Adapter Design Pattern is.

---

## 1. Real-Life Adapter — The Intuition

To understand the Adapter Design Pattern, think of a **real-life adapter**.

### Example 1: Travel Plug Adapter

Suppose you're in a hotel room that has **US-type sockets**. But your charger is an **Indian socket-based charger**. What do you do? You use an **international adapter** — your Indian charger plugs into this adapter, and the adapter itself plugs into the US socket.

### Example 2: Cable Adapter

Suppose you have a **Type-C cable** — your mobile charges via Type-C. But the adapter/port you have only accepts **Type-B**. Again, you'd need a different kind of adapter that converts Type-C to Type-B (or whatever is needed).

### The Programming Analogy

In programming, an **adapter** helps when: we have an interface, say **A**, and another interface, say **B**, and these are **completely different** interfaces.

> When I say "interface" here, it could mean either a pure contract, or an actual abstract class (like what we call an "interface" in Java) — any two classes, or two abstract classes, or two interfaces that are completely different from each other and **normally cannot talk to each other**.

We introduce an **Adapter** between these two, and this adapter helps them talk to each other. We'll see exactly how next.

## 2. Why Do We Need This Pattern?

When you write code, you typically have some **existing code** — this is your application's code.

While developing an application, you often need **third-party applications/libraries/classes** that you integrate into your application. You won't implement everything yourself — for example, you integrate a **payment gateway** (e.g., Razorpay), a **notification system** (e.g., for sending WhatsApp notifications), and many other third-party vendors/libraries.

### The Problem

A third-party library will have **different classes**, written in a **different way**, with **different methods** — completely different from your existing code.

Often, people do one of two things — or rather, they might reserve a small part of their own code that calls this third-party library's methods directly. But what does this do? It **tightly couples** your existing code with the third party.

### What Happens If You Switch Libraries?

Say you use **Library A** for your notification system. Tomorrow you switch to **Library B** — maybe because it's **cheaper**, more **cost-efficient**, or just **better**. Now where do you need to make changes? In your **existing code**. This is **wrong**.

### The Fix: Introduce an Adapter

Instead of calling the third-party library directly from your existing code, you introduce an **Adapter** in between.

The Adapter's job is exactly like a real-life adapter: it talks to your **existing code**, and it also talks to the **third-party library**. Your existing code doesn't need to know **which** third-party library you're using — it only knows: "I need to call the Adapter, and the Adapter will return something to me." The Adapter focuses on talking to the third-party library.

### The Puzzle-Piece Analogy

Imagine puzzle pieces:
- One piece is your **existing code**.
- Another piece is your **third-party library**.
- These two pieces **cannot join together directly**.

So we introduce an **Adapter** — a piece that takes a "puzzle edge" matching your existing code on one side, and a "puzzle edge" matching the third-party library on the other side. Now all three pieces fit together easily. **This is the job of the Adapter Design Pattern.**

## 3. The Example — Report Data: XML to JSON

### Setting Up the Client's Expectation

Suppose we have a **Client**. This client is part of an application where we **fetch reports** in some format. Let's say this client needs reports in **JSON format**.

What does the Client expect? It expects a class — say **`Reports`**. Since this can act as an interface, we use our naming convention: **`IReports`**.

`IReports` has one method: **`get_json_data`**. Since this is an interface, we **don't define it here** — we just declare it (it's an abstract class).

So the Client interacts with this interface: "give me JSON data" → and the Client gets JSON data. That's the simple job.

### Our Job

Our job in this software is to **implement `get_json_data`**. The Client expects us to provide JSON data for any report. We could pass some raw string data and build the JSON ourselves — **but we don't want to do this ourselves**.

### Enter the Third-Party Library

We know a **third-party library exists** that provides a report's data in **XML format**. Our job becomes: just **convert that XML data into JSON**.

Let's call this third-party library/class: **`XMLDataProvider`**. As the name suggests, this class gives us **XML data** from some raw data. It has a method: **`get_xml_data`**.

> This class could itself be abstract with concrete implementations, or it could directly provide the data. For simplicity, we assume this **is** the concrete class that gives us XML data.

### The Problem

`XMLDataProvider` gives us **XML data**. We need **JSON data**, and we don't want to convert it ourselves — we want to use this library. But these are **two different interfaces** that can't talk to each other directly (just like the puzzle-piece example): this is our **existing code** (`IReports`), and this is the **third-party library** (`XMLDataProvider`).

### The Solution: Introduce an Adapter

We create a class: **`XMLDataProviderAdapter`**.

This class's job:

1. **Override `get_json_data`** from `IReports` — because the Client expects JSON data. So first: `XMLDataProviderAdapter` will **override/inherit `IReports`**. This means: **it IS-A `IReports`** (an adapter **is-a** Report). This gives it the `get_json_data` method, which it will define.

2. **How will it provide JSON data?** Using `XMLDataProvider`. So it'll hold a **reference to `XMLDataProvider`** — i.e., **it HAS-A `XMLDataProvider`**.

So: the Adapter **is-a** `Report`, AND **has-a** `XMLDataProvider`. We hold this reference — let's call it `provider` (or `pro`).

### Terminology: "Adaptee"

Whatever the adapter is **adapting** — here, `XMLDataProvider` — is called the **Adaptee**.

### How the Client Uses It

Normally, the Client holds a reference of type `IReports` — let's call it `report`. We can pass **anything** that is an `IReports`-type object into this reference. So, instead of a "plain" `IReports`, we pass an `XMLDataProviderAdapter` — since the adapter **is-a** `IReports`, this works!

The Client just knows: "on this `report` reference, I'll call `get_json_data`, and I'll get JSON data back."

### What Happens Inside `get_json_data` (The Adapter's Implementation)

1. The adapter first calls `get_xml_data()` on its `XMLDataProvider` reference (`provider`) — getting the XML data.
2. It then **converts** this XML data **into JSON data**.
3. It returns the JSON data — and the Client gets its JSON data.

So: the adapter **behaved like a Report** (because of the **is-a** relationship and overriding `get_json_data`), and internally it **delegated** to the Adaptee (because of the **has-a** relationship) — calling the Adaptee's method first, converting the result, and returning it.

This is exactly how the Adapter let **two interfaces that couldn't talk to each other, talk to each other**.

## 4. The Client Class and Main Function

### The Client

We create a `Client` class with **one method**: `get_report`. This method takes a `report` (of type `IReports`) and `raw_data`. It calls **one method** on this report: `get_json_data`.

The Client only knows: "I have a `report`, I call `get_json_data` on it, pass `raw_data`, and I get JSON data back." The Client **doesn't care** whether internally we used a third-party library or implemented it ourselves. The Client only cares: "when I call this method, I get my JSON data."

### Main Function — Step by Step

1. Create an `XMLDataProvider` object (the **adaptee**).
2. Create an `XMLDataProviderAdapter` — a type of "adapter for `IReports`" — and pass it the `XMLDataProvider` object (the adaptee it will adapt).
3. Create a raw string: `"name:Alice,id:42"` (name = "Alice", id = "42").
4. Create the `Client`. The Client calls `get_report`, **using this adapter**.

What was the Client expecting? An `IReports`-type object. We passed it an **adapter**-type object — because the adapter **is also** an `IReports` (that's how it can be passed in / inherited).

5. We passed in the adapter, and gave it the raw data. As soon as `get_report` calls `get_json_data`:
   - The adapter's method runs.
   - It calls the **adaptee's** method (`get_xml_data`), gets XML data.
   - Converts the XML data to JSON.

### Expected Output

```
{"name": "Alice", "id": "42"}
```

## 5. Standard Definition

> **Adapter converts the interface of a class into another interface that the client expects. Adapter lets classes work together that couldn't otherwise because of incompatible interfaces.**

This is exactly what we did: the Client expected an interface (`IReports`/JSON). We converted the third-party library's interface (`XMLDataProvider`/XML) using `XMLDataProviderAdapter`, letting these classes work together.

**Why couldn't they work together otherwise?** Because their interfaces were very different — different methods, working on different things. `XMLDataProvider` gave us XML data; we needed JSON data. Very different interfaces on both sides. So we introduced an adapter to let them talk to each other. **Simple.**

## 6. Standard UML Diagram

The standard UML diagram for the Adapter Pattern:

- An interface: **`ITarget`** (the "target interface" — what the Client expects).
- Another interface: **`IAdaptee`** (the "adaptee interface").

`ITarget` and `IAdaptee` **cannot talk directly** — `ITarget` has a method called **`request`**, but `IAdaptee` has a **different** method called **`specific_request`**.

To fix this, we introduce an **Adapter**:
- **Adapter IS-A `ITarget`** (a "Report" in our example).
- **Adapter HAS-A `IAdaptee`**.

Inside `request` (the method the adapter overrides from `ITarget`), the adapter calls `specific_request` on its `IAdaptee` reference. This is exactly what we saw in our Report/XML/JSON example.

The **Client** only talks to `ITarget`.

| Standard UML Term | Our Example |
|---|---|
| `ITarget` | `IReports` |
| `ITarget.request` | `IReports.get_json_data` |
| `IAdaptee` | `XMLDataProvider` |
| `IAdaptee.specific_request` | `XMLDataProvider.get_xml_data` |
| `Adapter` | `XMLDataProviderAdapter` |

## 7. Object Adapter vs Class Adapter

Everything discussed so far — both in our example and the standard UML — is called an **Object Adapter**.

### What Is an "Object Adapter"?

It "adapts" an object — i.e., it uses **composition** (has-a relationship) with the Adaptee.

### What Is a "Class Adapter"?

There's another type of adapter called a **Class Adapter**. There's no real difference in **purpose** — an Object Adapter uses **composition**, while a Class Adapter uses **inheritance**.

### How the Diagram Changes

- We still have `ITarget` (our `Reports`-like class).
- We still have `IAdaptee`.
- Previously, the Adapter **inherited** `ITarget` (is-a) and had a **composition** (has-a) relationship with `IAdaptee`.

For a **Class Adapter**, we change this slightly: the Adapter now keeps an **inheritance** relationship with **both** `ITarget` AND `IAdaptee`. This means it uses **multiple inheritance**.

This is called a **Class Adapter**. There's no functional difference — it still has a `request` method and a `specific_request`-related method; its job is to **override `request`** and **call `specific_request`** (now inherited rather than referenced).

The only difference: one uses **inheritance**, the other uses **composition**.

### Why We Prefer Object Adapters

This is the same old debate: **inheritance vs composition** — and we always said we **prefer composition over inheritance** in real-world applications.

Additional reasons:
- **Only C++ supports multiple inheritance.** Java doesn't support multiple inheritance at all.
- Even if your language **does** support multiple inheritance (e.g., C++), we still **don't prefer** using multiple inheritance in real-world applications. We always say: **prefer composition over inheritance**.

So: we are **never** going to talk about multiple inheritance here. This was just for your knowledge — that a Class Adapter exists, and an Object Adapter exists — but **we always prefer the Object Adapter**, i.e., the composition relationship.

## 8. Real-World Use Cases

### 1. Integrating Third-Party Vendors

You've already understood this one easily: whenever you need your project to talk to / contact a **third-party vendor**, you introduce an Adapter.

- You have your **existing code**.
- You have your **vendor's code**.
- You introduce an **Adapter** in between, which **inherits** (is-a) your existing code's expected interface and has a **composition** relationship with the vendor's code, letting the two talk to each other.

Whenever your code needs to integrate a third-party library like this, recognize: **Adapter Design Pattern applies here.**

### 2. Working with Legacy Code

When developing applications, you sometimes have to work with **legacy code** — very old code.

For example: say you work in Java, and you're now using the **latest Java (22/23)**. But there's a legacy codebase written in **Java versions older than Java 8**. In that legacy code:
- Some methods are **duplicated**.
- Some methods aren't used the way they're used now.

This is your **modern application**, and this is your **legacy code**. Since you need to talk to the legacy code (because this application was already written in a very old Java/C++ version, and you **can't change it** — it's not your application, you're just **using** it), you again introduce an **Adapter** in between.

This Adapter's job: take calls from your **modern application**, and call the **legacy code's methods**. The legacy code talks to the adapter, and the adapter talks to your modern application — basically the **same** approach as integrating a third-party vendor library.

These are some real-world use cases of the Adapter Pattern. As we go through more examples in this series, you'll see more real-world use cases of the Adapter pattern too.
