# OpenAPI: Giving Remote Calls a Signature

*Why API knowledge lives in three places, how a single machine-readable contract fixes it, and how to build a whole design-first pipeline around it*

---

## 1. The Knowledge That Lives in Three Places

Take the **Tasker** task-board project built in the real-time video of this series. Its route table has about six routes. One handler, **move**, takes a JSON body with three fields: `task_id`, `to`, and `actor`. Depending on what happens downstream (in the service layer, the repository layer, or elsewhere) it answers with different status codes:

- **200** on success,
- **400** or **404** for validation or client errors,
- **500** or **502** if something goes wrong on the server side.

The React front end knows all of this. It knows it must call `/api/move`, it knows the three body fields, and it knows that a 404 means “that task does not exist”. So where does this knowledge actually live? In **three places**:

1. **The back-end handler.** It reads the body, so of course it knows.
2. **The front end’s call site** (`fetch`, Axios, or whichever library). The back end is the *handling* point, the front end is the *calling* point.
3. **A document**, if the engineer who wrote or integrated the API maintains a spec describing requirements and expectations.

Three copies of the same knowledge. The problem is keeping the three “truths” in sync.

### How it goes wrong

1. A colleague renames the field `to` to `column` because it reads better.
2. They update the back-end handler.
3. They update the front end too, because the back end validates the body and would reject the old name.
4. They **forget the document**, since a document enforces nothing. It exists only for knowledge.
5. A few weeks or sprints later, a **new engineer** who has never touched this endpoint needs to call it from another page. They find the document, which claims to be the source of truth, and ignore the real source of truth (the handler).
6. They send `to`, as the document says. The back end answers with a **validation error**.

> **Real-world picture.** Three printed copies of a restaurant menu: one taped to the kitchen wall, one on the tables, one on the website. The chef renames a dish and updates two copies. A customer orders from the third copy and the kitchen says, “we don’t make that.”

## 2. A Signature for the Remote Call

Notice when this class of problem arises: only when the call **crosses a network hop**, outside the boundary of your own codebase.

Inside one codebase, say a Go back end, a function has a **signature**: the arguments it expects and the value it returns. If someone later changes the signature (renames a struct field, changes a type from string to integer), **every call site fails to compile**. You find the break during development, not at runtime.

A remote call across the **HTTP boundary** has no such protection, because there is **no signature**. A renamed field or changed data type can only be discovered **at runtime**.

The idea of this whole article is to give the remote call the same protection:

- **freeze the signature** and document the available routes,
- the **query parameters** and **path parameters** each endpoint expects,
- the **request body fields**, down to the **data type of each field**, and
- the **various responses** you can get back.

All of it goes into one centralized document that is not prose or Markdown but a **programmatic document**, which lets us enforce the contract across the network boundary. That specification is **OpenAPI**.

An **OpenAPI description** is just a file, in **JSON or YAML** (equally supported). It describes all your API endpoints as a list, and for each endpoint every property: **inputs, outputs, and behavior**.

---

## 3. History: From Wordnik to the Linux Foundation

In **2010**, a startup called **Wordnik** had an API and about six engineers. Their customers wanted **client SDKs in many languages** (Python, PHP, JavaScript) plus documentation for each. That was the origin. **Tony Tam** started the specification, and his motivation fits in one sentence: **“we often code faster than we can document.”**

The initial idea: the server describes itself in a JSON file, and various programs read that file for various purposes.

| Year | Event |
| --- | --- |
| 2010 | Wordnik builds a JSON description of its API plus a page that renders UI from it. A designer on the team names it **Swagger**. |
| 2011 | **Swagger 1.0** is open-sourced. |
| 2014 | **Swagger 2.0**. Adoption starts to grow. |
| 2015 | **SmartBear** buys Swagger, then donates the specification to the **Linux Foundation**. Founding members include **Google, Microsoft, IBM, PayPal**, and other large companies. |
| Jan 2016 | The specification is **renamed OpenAPI** with no content change. OpenAPI 2.0 and Swagger 2.0 mean the same thing. |
| Today | The latest version is **3.2.0**, but most people still write **3.1** (the file in this article uses 3.1.1), because most tools in the market only support 3.1 so far. |

## 4. One File, Many Programs

Because the description is a structured file rather than prose, any program can parse it, search it, and format it. Plain text would make that programmatic access very hard. What can read the file?

1. **Documentation renderers.** They can be read-only, or **interactive** like **Swagger UI** and **Scalar**, where you add a sample body and a token, call the API, and inspect the response.
2. **Client library generators.** They produce off-the-shelf functions for **Python, PHP, JavaScript, Go, Rust**, any language, because the file describes the back end, not an implementation language. You don’t hand-write or hand-document each call.
3. **Server-side generators.** They produce interfaces and boilerplate you would otherwise type and keep in sync yourself.
4. **Validators.** The server can use the spec to **validate** query parameters, path parameters, and request bodies automatically, without hand-written validation code.

One file helps back end, front end, and infrastructure, and nearly every engineer on the team.

### What the official definition says

The specification describes itself with three phrases:

- **Language-agnostic.** It does not matter if your server is Go, Node.js, Python, Java, or PHP. The file describes behavior, requirements, and outputs, not the implementation language.
- **For humans and computers.** The same file produces interactive docs for people to read and test, and lets programs generate code and validation without a human involved.
- **Without source code, documentation, or traffic inspection.** You don’t read the service implementation, a possibly stale text document, or the browser network tab to learn how the API behaves. You read one file.

## 5. Four Terms That Get Confused

| Term | What it is |
| --- | --- |
| **OpenAPI Specification (OAS)** | The set of rules: which fields exist and what they mean. |
| **OpenAPI Description (OAD)** | *Your* file, usually `openapi.json` or `openapi.yaml`. It must obey every rule in the OAS. |
| **OpenAPI Initiative (OAI)** | The organization (part of the **Linux Foundation**) that publishes and maintains the specification. |
| **Swagger** | The **old name** of the specification. Today it just names tools. “The Swagger file” means the OAD (`openapi.json`/`.yaml`). “**Swagger UI**” means the tool that renders that file as interactive docs. |

JSON and YAML are interchangeable and have the same features. It depends on tool support (nearly all tools support both). Since YAML is a superset of JSON and **allows comments**, most people write YAML.

## 6. Anatomy of the Document

The smallest valid OpenAPI description has three fields:

```yaml
openapi: 3.1.1
info:
  title: Task Board API
  version: 1.0.0
paths: {}
```

- **`openapi`**: which version of the specification this file follows. Many tools still run on particular older versions, so declaring it matters.
- **`info`**: `title` and `version`. Note the two different versions: `openapi` is the **specification’s** version, while `info.version` is **your API’s** version, internal to you (recall route versioning from the routing video).
- **`paths`**: all endpoints (empty here because none are added yet).

**Root-level rules:** `openapi` and `info` are required. You also need **at least one** of `paths`, `components`, or `webhooks`. Optional: **`servers`** (where the API lives), **`security`** (authentication across all endpoints), and **`tags`** (to group endpoints).

### Servers

`servers` is a **list**, because the backend may live in several places: a local `http://localhost:8080`, a staging server, a production server. Once the base URL is written here, you only write endpoint paths, not the whole address each time.

### Paths and path items

`paths` is a **map**. Each key is an endpoint path and **must start with `/`**. The value is a **path item**: everything you can do at that address, with one entry per **HTTP method**. For example, `/api/board` has `get`, and `/api/move` has `post`. Others: `put`, `patch`, `delete`, `head`, `options`.

For a **dynamic portion** of a path, such as the ID of a task in `/api/tasks/1` (or a UUID), the client supplies the value, so you cannot document it in advance. You write it with **curly braces**: `/api/tasks/{taskId}`.

## 7. Operations

Each method under a path is an **operation**:

- **`summary`**: a one-liner.
- **`description`**: longer, with **Markdown** support (tables and formatting).
- **`tags`**: lets the rendered docs group endpoints, for example all task-related ones.
- **`operationId`**: a unique name for the operation. **Best practice: write it as a function name**, such as `getBoard`. When you use the file with a client generator, each operation becomes an **actual function** with this name, which you then call from your React or JavaScript front end without implementing the description yourself. It must be **unique across the whole file**.
- **`parameters`**, **`requestBody`**, and **`responses`**.

### Parameters

Parameters can live in four places, set by the **`in`** field:

| `in` | Where it lives |
| --- | --- |
| `path` | the URL path |
| `query` | the query string |
| `header` | HTTP headers |
| `cookie` | a cookie |

A parameter has a `name`, an `in`, a `required` flag (whether to enforce validation), and a `schema` for its value. **Path parameters must always be required**, since an optional one would turn the URL into two different URLs.

Examples from the Tasker app: the **polling endpoint** takes a `since` **query parameter** (an integer: the last sequence number the client has received). The **events** (SSE) endpoint can receive the same value in the **`Last-Event-ID` header**, which the browser sends by itself when reconnecting to the stream.

### Request body

For POST, PUT, and PATCH requests, `requestBody` is described by **`content`**: a map from **media type** (the label in the `Content-Type` header) to the body’s shape. The common ones:

- `application/json` for JSON data,
- `multipart/form-data` for **file uploads**,
- `application/x-www-form-urlencoded` for classic **HTML forms** (less common in the single-page-app era).

Under each media type you write a **schema**. For the `move` endpoint:

```yaml
/api/move:
  post:
    operationId: moveTask
    summary: Move a task to another column
    requestBody:
      required: true
      content:
        application/json:
          schema:
            type: object
            required: [task_id, to]
            properties:
              task_id: { type: string }
              to:      { type: string }
              actor:   { type: string, default: guest }
    responses:
      "200":
        description: Moved
        content:
          application/json:
            schema: { $ref: "#/components/schemas/Event" }
      "400": { description: Validation error }
      "404": { description: Task not found }
      "502": { description: Move succeeded but publishing to the message bus failed }
```

This states, without anyone reading the handler, that `task_id` and `to` are **required** (the back end throws an error otherwise), and that `actor` is **optional** and defaults to **`guest`**.

### Responses

Responses are keyed by **status code, written in quotes** (`"200"`). Codes in the 200s are success, 300s redirects, 400s client errors, and 500s server errors (covered in the HTTP video). Each response has a `description` and usually `content` (media type plus schema, shaped like the request body). The `move` operation lists **four** possible outcomes:

- **200**: returns the event data in the event schema.
- **400**: an **error response** schema (not the event schema).
- **404**: no task with that ID, also an error response.
- **502**: the move itself succeeded but could **not be published to the message bus**.

## 8. The Schema Object

The **schema object** documents data types and fields, which is what clients use most. It has a **`type`**: `string`, `number`, `integer`, `boolean`, `array`, `object`, or `null`.

- **object**: has keys (strings) and values, and each value can be any type, including another object.
- **string**: `minLength`, `maxLength`, a `pattern` it must match, or an **`enum`** of allowed values (for example `active`, `inactive`, `deleted`).
- **number/integer**: `minimum` and `maximum`.
- **array**: `items`, each with its own schema.

By composing these properties you can describe nearly any structure. There is also a section for **authentication** (what kind of token the client sends). Rather than walk every property, the rest of this article focuses on the practical workflow.

## 9. Code-First vs. Design-First

If the file is the contract between server and client, **which comes first: the file or the code?**

### Code-first

You write handlers, services, and behavior first. Then the OpenAPI file is **derived** from the code, via annotations, comments above handlers, or types. Many ecosystems have libraries for this. The file is a **by-product** of the code.

The Swagger team started code-first because they already had server code and wanted the spec derived from it. Eventually they realized **contract-first** makes more sense (a 2013 talk discusses this).

### Design-first (contract-first)

You write the **specification first**, then the back-end implementation, then the client code, mocks, and tests, based on the specification. The contract is the **source of truth**.

The speaker began with code-first on existing servers (for interactive API testing or client generation), but for **new projects has always gone contract-first**, because:

- **Front end and back end can start in parallel.** You don’t wait for the back end before writing integration, because both sides agreed on behavior up front.
- In the **agentic era** it fits naturally: you align with your agents on how an endpoint should behave, what it takes, and what it returns. Then you can start **two parallel agents**, one on the server and one on the client, and they don’t block each other.

## 10. Code-First in Practice: Tasker with ts-rest and Zod

In Tasker (from the *Production Grade Go from Scratch* playlist):

1. **Zod schemas** define the data shapes (as code objects).
2. A **ts-rest contract** attaches those schemas to paths and methods.
3. A **generator function** takes the contract and produces `openapi.json`.
4. The **Go server** serves that file for interactive documentation.

You never hand-write `openapi.json`. This is why the article doesn’t go deep into every feature of the spec: libraries like ts-rest make it so streamlined that you only need to know **the path, the inputs** (query parameters, body, path parameters, headers), **and the response** (schema and status code). Three intuitive things, written as plain JavaScript objects (JSON Schema or Zod), with nothing else to memorize.

This differs from the comment-parsing style of code-first. The speaker prefers it because you depend on **code, not comments**, which is easier to maintain and harder to get around. Python’s **FastAPI** works similarly: it parses the handler code through annotations and generates and serves `openapi.json` behind the scenes from the handler itself, not from separate comments.

## 11. The Design-First Pipeline

The real-time task-board app has **no OpenAPI description yet**. It is small and new, so it is a good candidate for design-first. The pipeline has five stages plus testing.

### Stage 1: Lint (Spectral)

Just as ESLint or a Go linter checks code, an **OpenAPI linter** checks the file. **Spectral** has the OpenAPI rules built in. It flags a missing description, an operation with no `operationId`, a response with no schema, and so on. In the demo it reports three errors (no `contact` on the info object, and two operations with no description). After fixing them it passes.

### Stage 2: Mock server (Prism)

A **mock server** reads the spec and generates a **fake server** that answers every documented request using the **examples** in the file, *before any back-end code exists*. A separate front-end team can build against the mock while the back-end team writes handlers. **Prism** is the tool. In the demo, the board returned is the example from the file, and a move request is validated against the documented schema.

### Stage 3: Client (openapi-typescript + openapi-fetch)

For a JavaScript client, **openapi-typescript** converts the spec into **TypeScript types** that know every path, endpoint, field, type, and condition. **openapi-fetch** makes the actual calls. If you misspell a field or pass the wrong data type, **the compiler catches it**.

### Stage 4: Server (oapi-codegen)

For Go, **oapi-codegen** turns the spec into **Go interfaces**. Your handler code must **satisfy the interface**, so the behavior documented in the spec is enforced as a language construct (for other languages, something equivalent). If the contract file changes and the handler doesn’t, **compilation fails**. In the demo, adding a field to the file and regenerating makes the build fail at the handler, because the implementation no longer matches the contract.

### Stage 5: Documentation

The same file renders in several ways:

- **Swagger UI**: the traditional interactive docs, with a “Try it out” button.
- **Redoc**: another UI over the same file.
- **Scalar**: the same interactivity with a more modern, clean UI, and the speaker’s personal favorite.

### Verifying the server actually matches the file

1. **Test the server against the file** with **Schemathesis**. It reads the spec, **generates valid and invalid requests** from the schemas, sends them to the real server, and checks every response against the contract, flagging anything that doesn’t match.
2. **Compare two versions of the file** (the speaker mentions this as the second way) to catch changes between versions.

### The whole pipeline, with one source of truth

```
openapi.yaml  → lint (Spectral)
              → mock server (Prism)
              → client types (openapi-typescript / openapi-fetch)
              → server interfaces (oapi-codegen)
              → docs (Swagger UI / Redoc / Scalar)
              → contract tests (Schemathesis)
```

Across every stage there is **one file**, which is the single source of truth. You can write the spec by hand, or write it in code with ts-rest and generate it, but either way you end up with `openapi.json` or `openapi.yaml`.

## 12. The Industry Standard

Beyond generating clients and docs, the same file can **validate requests in API gateways**. Big platforms such as **GitHub** and **Stripe** publish their OpenAPI files so any client can use them as documentation. GitHub’s runs to about **344,000 lines** and Stripe’s about **171,000 lines**, which makes sense for huge platforms that have existed for years. When people say OpenAPI is *the* standard for describing an API, this is what they mean: the industry decided on one format for describing back ends. A very recent use case is **AI agents**: giving an agent a tool to call.

---

## Summary

- **The problem:** inside one codebase, the compiler enforces function signatures. Across the network, nothing does, and API knowledge is copied in the handler, the client, and the docs, which drift apart.
- **The solution:** the **OpenAPI specification**, a machine-readable description of the API (paths, inputs, outputs, data types, authentication), in JSON or YAML.
- **The vocabulary:** OAS (the rules), OAD (your file), OAI (the organization under the Linux Foundation), Swagger (the old name, now a family of tools).
- **The structure:** `openapi`, `info`, `servers`, `paths` (path items with operations), `parameters` (`in`: path, query, header, cookie), `requestBody`, `responses` keyed by quoted status codes, and **schema objects** composed from types, enums, ranges, and arrays.
- **The workflow:** prefer **design-first**: write the contract, lint it, mock it, generate typed clients and server interfaces, render docs, and test the real server against it. Code-first (ts-rest with Zod, FastAPI) is a fine alternative for existing servers.
- **The payoff:** from one file you can generate client code, server interfaces, mocks, tests, docs, and validation, and a contract change breaks the build instead of surprising a user at runtime.
