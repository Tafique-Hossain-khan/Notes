# Iterator Design Pattern

## The Problem: Traversal Logic Leaking Into Business Logic

Imagine you have a `Playlist` class. It holds a list of songs. Its job is to manage songs — add a song, remove a song, get a song by name, get a song by ID.

Internally, the `Playlist` stores songs in a Python list (equivalent to a vector). So when you want to play the entire playlist, you write a loop inside `play_entire_playlist()` that iterates over that list.

Now tomorrow you decide to change the underlying data structure — instead of a list, you want to store songs in a linked list. What happens to `play_entire_playlist()`? You have to rewrite it because the traversal logic was baked in. Same for `get_song_by_name()`. Same for `get_song_by_id()`. Every method that ever loops over the songs needs to be rewritten.

This is the core problem: **traversal logic and business logic are mixed in the same class.**

The `Playlist` class should only know:
- How to add a song
- How to remove a song
- How to get a song by name or ID

It should **not** know: how to traverse its internal data structure. That is a separate responsibility.

This is a direct violation of the **Single Responsibility Principle** — a class is doing two jobs: managing songs AND knowing how to iterate over them.

What we want is for the `Playlist` to call something like:

```python
iterator = self.get_iterator()
while iterator.has_next():
    song = iterator.next()
    # do something with song
```

The `Playlist` does not need to know whether songs are stored in a list, a linked list, or a map. It just calls `has_next()` and `next()` on an iterator and gets what it needs.

When you change the underlying data structure tomorrow, you only change the **iterator**. Every other method in `Playlist` stays exactly as it is.

This is why iterators exist. In languages like C++ and Java that support them natively, the iterator is already a design pattern that enforces this separation. Today we will build our own.

---

## The Core Concept

You have two hierarchies:

**Iterator hierarchy** — knows how to traverse a data structure. Has exactly two methods:
- `has_next()` → returns `True` if a next element exists
- `next()` → returns the next element

**Iterable hierarchy** — represents any object that can be iterated over. Has exactly one method:
- `get_iterator()` → returns a concrete iterator

The iterable does not contain traversal logic. It delegates that entirely to the iterator it returns.

---

## Three Examples Together

We will build iterators for three data structures:
1. A **Linked List** (integer nodes)
2. A **Binary Tree** (in-order traversal)
3. A **Playlist** (list of songs)

All three share the same `Iterator` interface and the same `Iterable` interface.

## Python Implementation

```python
from __future__ import annotations
from abc import ABC, abstractmethod
from typing import TypeVar, Generic, Optional
from collections import deque

T = TypeVar('T')


# -----------------------------------------------------------------------
# ABSTRACT ITERATOR
# -----------------------------------------------------------------------

class Iterator(ABC, Generic[T]):
    """
    Abstract Iterator.
    Any concrete iterator must implement has_next() and next().
    The client only ever uses these two methods.
    """

    @abstractmethod
    def has_next(self) -> bool:
        """Returns True if a next element exists."""
        pass

    @abstractmethod
    def next(self) -> T:
        """Returns the next element and advances the cursor."""
        pass


# -----------------------------------------------------------------------
# ABSTRACT ITERABLE
# -----------------------------------------------------------------------

class Iterable(ABC, Generic[T]):
    """
    Abstract Iterable.
    Any object that can be iterated over must implement get_iterator().
    The traversal logic lives entirely in the Iterator, not here.
    """

    @abstractmethod
    def get_iterator(self) -> Iterator[T]:
        pass


# -----------------------------------------------------------------------
# EXAMPLE 1: LINKED LIST
# -----------------------------------------------------------------------

class LinkedListNode:
    def __init__(self, data: int):
        self.data = data
        self.next: Optional[LinkedListNode] = None


class LinkedListIterator(Iterator[int]):
    """
    Knows how to traverse a linked list.
    Traversal logic lives here — NOT in the LinkedList class.
    """

    def __init__(self, head: Optional[LinkedListNode]):
        self._current = head

    def has_next(self) -> bool:
        # Current is not None means there is still an element to visit
        return self._current is not None

    def next(self) -> int:
        value = self._current.data
        self._current = self._current.next  # advance the cursor
        return value


class LinkedList(Iterable[int]):
    """
    Linked list that is iterable.
    This class does NOT contain any traversal logic.
    It simply returns a LinkedListIterator when asked.
    """

    def __init__(self, data: int):
        self.data = data
        self.next: Optional[LinkedList] = None

    def get_iterator(self) -> Iterator[int]:
        return LinkedListIterator(head=self)


# -----------------------------------------------------------------------
# EXAMPLE 2: BINARY TREE (in-order iterator)
# -----------------------------------------------------------------------

class BinaryTreeNode:
    def __init__(self, data: int):
        self.data = data
        self.left: Optional[BinaryTreeNode] = None
        self.right: Optional[BinaryTreeNode] = None


class BinaryTreeInOrderIterator(Iterator[int]):
    """
    Iterative in-order traversal of a binary tree.
    Uses a stack internally — this logic lives here, not in BinaryTree.

    Why iterative (not recursive)?
    Because we need controlled step-by-step traversal via has_next()/next().
    A recursive approach would traverse the entire tree at once.
    """

    def __init__(self, root: Optional[BinaryTreeNode]):
        self._stack: list[BinaryTreeNode] = []
        self._current = root
        self._push_left(self._current)

    def _push_left(self, node: Optional[BinaryTreeNode]):
        """Push all left children onto the stack."""
        while node is not None:
            self._stack.append(node)
            node = node.left

    def has_next(self) -> bool:
        return len(self._stack) > 0

    def next(self) -> int:
        node = self._stack.pop()
        value = node.data
        if node.right is not None:
            self._push_left(node.right)
        return value


class BinaryTree(Iterable[int]):
    """
    Binary tree that is iterable.
    This class does NOT know how in-order traversal works.
    It delegates that entirely to BinaryTreeInOrderIterator.
    """

    def __init__(self, data: int):
        self.data = data
        self.left: Optional[BinaryTree] = None
        self.right: Optional[BinaryTree] = None

    def get_iterator(self) -> Iterator[int]:
        return BinaryTreeInOrderIterator(root=self)


# -----------------------------------------------------------------------
# EXAMPLE 3: PLAYLIST
# -----------------------------------------------------------------------

class Song:
    def __init__(self, title: str, artist: str):
        self.title = title
        self.artist = artist


class PlaylistIterator(Iterator[Song]):
    """
    Iterates over a list of songs.
    The Playlist class does not contain this logic.
    """

    def __init__(self, songs: list[Song]):
        self._songs = songs
        self._index = 0

    def has_next(self) -> bool:
        return self._index < len(self._songs)

    def next(self) -> Song:
        song = self._songs[self._index]
        self._index += 1
        return song


class Playlist(Iterable[Song]):
    """
    Manages a collection of songs.
    Business logic: add_song, remove_song, get_song_by_name.
    Traversal logic: entirely delegated to PlaylistIterator.

    If tomorrow _songs is changed from list to a linked list,
    only PlaylistIterator needs to change. Nothing else.
    """

    def __init__(self):
        self._songs: list[Song] = []

    def add_song(self, song: Song):
        self._songs.append(song)

    def remove_song(self, title: str):
        self._songs = [s for s in self._songs if s.title != title]

    def get_song_by_name(self, name: str) -> Optional[Song]:
        """
        Business logic method.
        Uses the iterator for traversal — does NOT loop directly over _songs.
        If _songs changes to a linked list tomorrow, only get_iterator() changes.
        This method stays exactly as it is.
        """
        it = self.get_iterator()
        while it.has_next():
            song = it.next()
            if song.title == name:
                return song
        return None

    def get_iterator(self) -> Iterator[Song]:
        return PlaylistIterator(songs=self._songs)


# -----------------------------------------------------------------------
# CLIENT CODE
# -----------------------------------------------------------------------

if __name__ == "__main__":

    # --- Linked List ---
    head = LinkedList(data=1)
    head.next = LinkedList(data=2)
    head.next.next = LinkedList(data=3)

    print("=== Linked List ===")
    it1 = head.get_iterator()
    while it1.has_next():
        print(it1.next(), end=" ")
    print()

    # --- Binary Tree (in-order: left -> root -> right) ---
    #       2
    #      / \
    #     1   3
    # In-order: 1, 2, 3

    root = BinaryTreeNode(data=2)
    root.left = BinaryTreeNode(data=1)
    root.right = BinaryTreeNode(data=3)

    print("\n=== Binary Tree (In-Order) ===")
    it2 = BinaryTree.__new__(BinaryTree)
    it2.data = root.data
    it2.left = root.left
    it2.right = root.right
    iterator2 = BinaryTreeInOrderIterator(root=root)
    while iterator2.has_next():
        print(iterator2.next(), end=" ")
    print()

    # --- Playlist ---
    playlist = Playlist()
    playlist.add_song(Song(title="Admiring", artist="Karan Aujla"))
    playlist.add_song(Song(title="Husn", artist="Anuv Jain"))

    print("\n=== Playlist ===")
    it3 = playlist.get_iterator()
    while it3.has_next():
        song = it3.next()
        print(f"Title: {song.title}, Artist: {song.artist}")

    # --- get_song_by_name uses iterator internally ---
    print("\n=== get_song_by_name('Husn') ===")
    found = playlist.get_song_by_name("Husn")
    if found:
        print(f"Found: {found.title} by {found.artist}")
```

**Expected Output:**

```
=== Linked List ===
1 2 3 

=== Binary Tree (In-Order) ===
1 2 3 

=== Playlist ===
Title: Admiring, Artist: Karan Aujla
Title: Husn, Artist: Anuv Jain

=== get_song_by_name('Husn') ===
Found: Husn by Anuv Jain
```

## Why the Iterative Approach for Binary Tree

You might ask: why not use recursion for in-order traversal?

Because our iterator only exposes `has_next()` and `next()`. These are **controlled, step-by-step** methods. The caller decides when to ask for the next element.

Recursive in-order traversal visits the **entire tree at once**. There is no way to pause it mid-way and ask for one element at a time.

The iterative approach using a stack gives us exactly that control. Each call to `next()` visits exactly one node. The caller is in complete control of the pace.

---

## The `get_song_by_name` Insight

Notice how `get_song_by_name` in `Playlist` uses the iterator:

```python
def get_song_by_name(self, name: str) -> Optional[Song]:
    it = self.get_iterator()
    while it.has_next():
        song = it.next()
        if song.title == name:
            return song
    return None
```

This method does not know or care that `_songs` is a Python list. If tomorrow `_songs` is changed to a linked list, `get_song_by_name` stays exactly the same. Only `PlaylistIterator` and `get_iterator()` change.

That is the payoff of the Iterator pattern: **business logic methods become immune to changes in the underlying data structure.**

## The Standard UML (Generic Form)

```
┌────────────────────────────────┐      ┌────────────────────────────────┐
│        <<abstract>>            │      │        <<abstract>>            │
│          Iterator              │      │          Iterable              │
├────────────────────────────────┤      ├────────────────────────────────┤
│ + has_next() → bool            │      │ + get_iterator() → Iterator    │
│ + next() → T                   │      └────────────────────────────────┘
└────────────────────────────────┘                   △
              △                           ┌──────────┴─────────┐
    ┌─────────┴──────────┐          ┌────────────┐     ┌────────────────┐
┌──────────┐ ┌──────────┐          │  Concrete  │     │    Concrete    │
│Concrete  │ │Concrete  │          │ Iterable A │     │  Iterable B   │
│Iterator A│ │Iterator B│          ├────────────┤     ├────────────────┤
├──────────┤ ├──────────┤          │get_iterator│────▶│ get_iterator() │
│has_next()│ │has_next()│          │() returns  │     │ returns        │
│next()    │ │next()    │          │ Iterator A │     │  Iterator B    │
└──────────┘ └──────────┘          └────────────┘     └────────────────┘
     ▲                                   │
     └───────────────────────────────────┘
     ConcreteIterable returns its own ConcreteIterator
     ConcreteIterator holds a reference to the ConcreteIterable it traverses
```

## The Standard Definition

> The Iterator pattern provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation.

An aggregate object is any object that holds a collection internally — a linked list that holds references to other nodes, a tree, a playlist that holds a list of songs. The Iterator lets you traverse all of these using the same two methods (`has_next`, `next`), without the client knowing how the traversal works internally.
