# Concurrency vs. Parallelism: A Mental Model for Backend Engineers

*Why servers wait, how operating systems and runtimes do many things at once, and how threads, event loops, async/await, and goroutines really work*

---

## Introduction: Why Concurrency Matters

Every backend system you will ever build shares one requirement: it must **handle multiple things at once**. Picture an HTTP server that can process only one request at a time. If a thousand users send requests together, 999 of them either wait or get a “server busy” error. In production, with thousands of users, that is simply impossible.

This article is not a bag of tips you can copy-paste. Its goal is a **mental model** of how your backend processes requests and performs many tasks at once, across operating systems and runtimes such as Node.js, Python, Rust, Go, and Java. That model helps you debug problems, structure applications, and make larger architectural decisions.

Most of us learn keywords like `async`/`await` and “use threads to parallelize” from language docs. They work, and you can go far without knowing why. Understanding the mechanics puts you a step ahead. So we will build the picture from the ground up.

> **Real-world picture.** Think of a restaurant. A kitchen that cooks one order from start to finish before even *looking* at the next ticket would starve its customers. Real kitchens work on many orders at once. The rest of this article is about how software kitchens do it.

---

## 1. The Cost of Not Using Concurrency

Start with a single request. A user’s Chrome browser calls our backend server. The request passes through routing, service, handler, and repository layers, and eventually needs a **database query**. The server sends the query and *waits* while the database does its own work.

How long is that wait?

| Setup | Typical wait for a simple query |
| --- | --- |
| Local machine (localhost) | about 1 to 2 ms |
| Database in a different availability zone | about 20 to 30 ms |
| Database in a far-away region | about 90 to 100 ms |

Now the key question: **what is the server doing during that wait?**

If the server is naive and processes one request at a time, line by line, the answer is *nothing*. The CPU sits idle, waiting for network packets from the database.

### Putting numbers on the waste

A modern CPU executes roughly **3 billion instructions per second**, which is **3 million instructions per millisecond**. If the server idles for 100 ms waiting on the database, it could have executed about **300 million instructions**. By handling one request at a time, it executed **zero**.

Now take a realistic API call. A medium-to-complex endpoint might involve:

- 3 to 5 database queries,
- possibly a call to an external service (such as sending an email), and
- Redis reads or writes for caching.

Say that is **5 network operations at about 50 ms each, so about 250 ms of waiting**. The actual CPU work (validation, JSON parsing, filtering, serialization) might total only **10 ms**. That means the CPU and memory are idle roughly **95% of the time**. In typical backend applications, more than 70% of request time is spent waiting on I/O.

> **Real-world picture.** A chef who puts a pot on to boil and then stands staring at it for ten minutes is wasting nearly all of their working time. A good chef starts the sauce, chops vegetables while the water heats, and returns to the pot when it is ready. Concurrency is that habit applied to CPUs.

**Concurrency**, loosely “doing multiple things at once”, lets the CPU and memory work on other tasks while one task waits for the network.

---

## 2. I/O-Bound vs. CPU-Bound Work

To see where concurrency helps, separate work into two kinds.

**I/O-bound** work spends its time waiting on something outside the CPU:

- database queries,
- network calls (HTTP, TCP) and external APIs such as an email provider or Redis,
- file reads and writes (uploads, downloads, temp files),
- logging to standard output, and standard input.

Everything here follows the pattern “send a request, wait for the response”. The CPU has no power over the waiting.

**CPU-bound** work is actual computation using CPU cycles: parsing JSON bytes, validating and comparing values, adding numbers, transforming data. Most of it is trivial: validation or JSON deserialization finishes in a millisecond or two. Heavier CPU-bound work includes:

- **image and video processing** (matrix multiplication, heavy computation),
- **encryption**, such as verifying a JWT in an authentication middleware,
- machine learning calculations.

Most backend applications, in particular typical SaaS backends, are overwhelmingly **I/O-bound**. Whether you have 1 CPU core or 8, the bottleneck is I/O. This is why concurrency is *mandatory* for backends: a server handling one request at a time wastes about 95% of its resources.

---

## 3. Concurrency vs. Parallelism

These two terms are often confused, for good reasons.

**Parallelism** means executing multiple instructions at the **same moment**. It needs **hardware support**: at least two CPU cores, because one core can only execute one instruction at one moment.

**Concurrency** is about **structuring** a program so that multiple tasks can be started, paused, and resumed, making it *feel* (and be, in terms of progress) simultaneous, even on **one CPU core**. At any single instant only one instruction runs, but several tasks are “in progress”.

Short version: **parallelism is about *doing* many things at once; concurrency is about *dealing with* many things at once.**

> **Real-world picture.** One barista in a café takes your order, starts the espresso machine, and while the shot brews, takes the next customer’s order and steams milk. That is concurrency: one person, many drinks in progress. Two baristas, each making a drink at the same moment, is parallelism. Both are “multiple orders in progress”, but only the second has two pairs of hands moving at the same time.

### A timeline with one CPU core

Two requests, **A** and **B**, arrive at the same time. We have **one core**. Times are approximate.

| Time | What happens |
| --- | --- |
| 0 to 5 ms | Request A uses the CPU: routing, validation, JSON parsing. B waits for its turn. |
| 5 ms | A sends a database query and now only waits on I/O. It no longer needs the CPU, so the scheduler (OS or language runtime) gives the CPU to B. |
| 5 to about 20 ms | B uses the CPU (validation, parsing, maybe a loop), then sends its own database query and waits on I/O. |
| about 40 ms | The database answers A. A is ready, but the CPU may not be handed over instantly; scheduling logic decides when. |
| about 50 ms | A gets the CPU back, filters values, and responds to the client. |
| shortly after | B’s database response arrives, B gets the CPU, processes, and responds. |

The CPU was never idle while there was work to do. Both requests are **in progress** from the client’s perspective. But if you zoom into any one slice of time, **only one request is running on the CPU**. That is precisely concurrency.

In a real server, requests are not alone: the process is also logging (I/O), sending telemetry (external API calls), and running background jobs. The CPU hops between all of them, and any task that starts waiting on I/O gives up the CPU to another.

### The same example with two cores (parallelism)

With two cores, when B arrives it gets its **own core** immediately. In the same time window both A and B are actually executing instructions. That is parallelism.

### Which one do you need?

- **I/O-bound workloads → concurrency.** Handle many database connections, external calls, file operations, logging, and background jobs at once.
- **CPU-bound workloads → parallelism.** Use multiple cores to finish computation as fast as possible.

Real backends need both, but lean heavily toward concurrency, since they are mostly I/O-bound (unless you do niche work like video encoding or heavy encryption).

## 4. Two Ways Computers Do Many Things at Once

Every concurrency feature you meet is built on **two** mechanisms:

1. **Threads**
2. **Event loops**

Go’s goroutines, JavaScript/Node.js `async`/`await`, and Java’s virtual threads all sit on top of one of these (or a layer built over them).

---

## 5. Threads in Depth

A **thread** is an independent unit of execution provided by the **operating system**. When a thread is created, the OS gives it:

- a **stack**, used to track function calls (if `main` calls `getUsers`, those frames are pushed on the stack) and to hold local variables (a variable like `let a = 3` inside a function lives on the stack);
- an **instruction pointer**, which records where execution currently is in the code, so the thread can resume at the right place after being paused.

### The scheduler and preemptive scheduling

With several threads, an OS **scheduler** decides which thread runs, stops, blocks, and resumes. It gives each thread a **time slice**, perhaps a couple of milliseconds. After that slice the scheduler pauses the thread, saves its state (which instruction it was on), and switches to another. This is called **preemptive scheduling**: threads are stopped *before they finish*, whether they like it or not. The scheduler is controlled by the OS, not the thread. (Scheduling algorithms are a deep topic. A popular book on the subject is *Operating Systems: Three Easy Pieces*.)

### Blocking operations

When a thread performs a **blocking operation** (any I/O where the CPU is useless: a network call, a database query, logging, a device read), it tells the OS it cannot progress. The OS marks it **blocked** and switches to another thread. When the I/O completes (for example the database replies), the thread becomes **runnable** again and the scheduler picks it up when its turn comes.

### Processes vs. threads, and shared memory

Every running program is a **process**. Threads from *different* processes are isolated from each other (for security and to prevent memory corruption); they cannot see each other’s memory. Threads in the *same* process **share memory**: the heap, global variables, and anything allocated dynamically. If thread 1 allocates an object or struct, thread 2 can reach it through its address.

This is powerful. Threads can communicate simply by reading and writing the same map or variable, with no copying and no serialization, so it is fast. It is also **dangerous** (see the section on race conditions).

With multiple cores, multiple threads can truly run in **parallel**. With four cores, four threads can run at the same moment. That speeds up CPU-bound work.

### The cost of threads

Threads are heavy. There are three overheads:

**1. Memory.** Each thread gets its own stack. On Linux the default stack can be about 8 MB of *virtual* memory. Physical memory is assigned only as needed, but you still pay real memory per thread. If a framework created one thread per request and you receive 10,000 requests in a spike, at roughly 500 KB to 1 MB each that is about **8 to 9 GB** just for request handling, and your server may run out of memory and crash.

**2. Creation.** Creating a thread requires a **system call** to the OS kernel. The kernel sets up the stack, internal bookkeeping structures, the instruction pointer, and registers the thread with the scheduler. This takes from a few microseconds to a few milliseconds, which is small to a human but significant for a hot path.

**3. Context switching.** This is usually the biggest cost. To switch from thread 1 to thread 2, the scheduler must:

1. save the current thread’s CPU registers,
2. update bookkeeping to track state,
3. pick the next thread to run, and
4. load that thread’s saved registers and state.

On modern hardware this takes about **1 to 10 microseconds** per switch, depending on factors such as whether data is in the CPU cache. With 4 cores and 100 threads, the scheduler is constantly juggling. With thousands of threads, total switching time grows to many milliseconds. It is pure maintenance work, none of it productive, which is one reason the “one thread per request” model has always struggled with high concurrency.

> **Real-world picture.** Imagine a warehouse where every worker needs their own large workbench (stack memory), takes a long time to hire and set up (creation), and a foreman (scheduler) constantly stops workers mid-task, writes down exactly where each stopped, and sends another worker in. If the foreman spends half the day on paperwork, nothing gets built.

## 6. The Event Loop in Depth

The event loop uses a different idea: **one thread** and a loop that juggles tasks. The cardinal rule is: **never block the event loop**.

Here is how it works. When a task such as request A needs a database result, it does **not** block. Instead it tells the event loop (using language primitives, mostly `async` syntax): “I want the result of this query. When it arrives, resume me. Until then I am handing back control so you can run other things.” The task is parked, and the event loop keeps track of all tasks waiting on I/O.

The operating system must help. On **Linux** this is provided by **epoll**, on **macOS** by **kqueue** (Windows has its own equivalent). Using them the loop can watch thousands of connections at once. On each iteration the loop:

1. checks which I/O operations have completed,
2. puts the corresponding tasks back in the queue (by priority), and
3. runs their callbacks, then returns to the loop.

### Why it is efficient for I/O

For CPU-bound work, more threads means faster. For I/O-bound work, the number of threads does not matter. In fact, more threads means more context switching and *slower* programs. The event loop has:

- **no context switches** between threads (there is only one),
- **no big per-task stack memory** from the OS,
- very **lightweight** pause/resume (callbacks instead of OS data structures).

So for I/O-bound concurrency, an event loop is more efficient than the threading model.

### The trade-off: you can never block it

If a callback does CPU-heavy work for 100 ms or more, **the whole loop stops** for that time. No other request progresses. Callbacks must therefore be fast. In typical SaaS backends this is rarely an issue, since latency is mostly I/O. It becomes a problem for image or video work, animation, or ML workloads. Any language with an event loop (JavaScript, for example) offers callbacks, promises, and `async`/`await` mainly so you naturally avoid blocking operations and give up control at each I/O point.

> **Real-world picture.** One very organized waiter serving a whole floor. They take an order, hand it to the kitchen, and immediately move on to the next table. When the kitchen rings the bell, they return to deliver. This works wonderfully as long as the waiter never decides to stand still for five minutes and polish all the cutlery (a long CPU-bound task), because then every table is stuck.

## 7. Walkthrough: Threaded Request Handling

Two requests: A (`SELECT * FROM users`) and B (`SELECT * FROM orders`), handled on separate threads.

1. Request A arrives. The server **parses** the JSON body and query parameters (CPU work).
2. It runs the database query. First it obtains a connection (a new TCP connection, or one from a **connection pool**), converts the SQL to bytes, and sends it.
3. It calls `read` on the database socket to wait for the reply. This is a **blocking I/O** call, so thread 1 tells the OS scheduler it is blocked.
4. The OS switches to another thread. Request B arrives and runs the same steps on thread 2, and also blocks on its own socket read.
5. If a third thread exists it gets the CPU. If not, the CPU simply waits until some I/O completes.
6. When the network card receives the database’s response, the OS wakes thread 1. It reads the bytes, deserializes them into native structures (an array of objects in JavaScript, a dictionary in Python, a struct in Go), serializes the result to JSON, sends the HTTP response, and returns to the thread pool.

In code, it looks perfectly sequential:

```python
def handle_request(user_id):
    user = db.query("SELECT * FROM users WHERE id = %s", user_id)  # thread blocks here
    return json.dumps(user)
```

When you read this you see line-by-line execution. You do not see the blocking and thread switching, but it happens behind the scenes.

## 8. Walkthrough: Event Loop Request Handling

The sequence of operations is similar. The difference lies in **how pausing and resuming works**.

1. Request A arrives and is parsed. We start the database query (TCP connection, bytes sent) and **register a callback**: “when this result returns, run this function.” Then we return control to the event loop. (This is not returning an HTTP response, just yielding.)
2. The loop picks up request B, parses it, starts its own query, registers another callback, and yields.
3. The loop keeps iterating, doing other work like logging or sending emails, and each iteration checks via epoll/kqueue which sockets have become readable.
4. Say B’s socket becomes readable first. The loop runs B’s callback: it loads the data, serializes JSON, and responds. Then A’s socket becomes readable and A’s callback runs.

The threading model resumes work using **OS-level data structures and instruction pointers**. The event loop resumes work using **callbacks**, which is far lighter.

### Callbacks, then async/await

Before ES6, JavaScript looked like this:

```javascript
db.query("SELECT * FROM users WHERE id = ?", [userId], function (err, user) {
  if (err) return handleError(err);
  sendResponse(user);
});
```

The third argument is the **callback**: logic given to the event loop in advance, to run when the I/O completes. Errors arrive as the first parameter and the result as the second.

The problem arises with more async steps. After this query you need another query, then an API call, and each requires another callback nested inside the previous one. With five or six I/O steps the code becomes deeply nested, often called callback hell. Modern JavaScript solved this with `async`/`await`:

```javascript
async function getUser(userId) {
  const user = await db.query("SELECT * FROM users WHERE id = ?", [userId]);
  const orders = await db.query("SELECT * FROM orders WHERE user_id = ?", [userId]);
  return { user, orders };
}
```

`async`/`await` is **syntactic sugar over callbacks**. Writing `await` means: “give control back to the event loop. When this I/O is complete, continue from here.” Everything after the `await` (up to the end of that function) behaves as if it were passed as a callback to the I/O operation. The result is flat, readable code, with the same single thread, no context switching, and no OS stack allocation.

## 9. Go’s Model: Goroutines (Virtual Threads)

Go uses a third approach, neither pure OS threads nor a single event loop. Conceptually it is a **virtual thread**, though Go calls it a **goroutine**. Unlike an OS thread, a goroutine is managed by the **Go runtime**, not the operating system. A goroutine starts a new concurrent task with the `go` keyword:

```go
go handleSomething()
```

In Go’s standard HTTP library, the server’s `Serve` function accepts connections and **starts a new goroutine for every incoming request**, running your handler in it. Earlier we said one OS thread per request can exhaust memory. Go can afford to do it because goroutines are so lightweight.

### How the Go scheduler works

There are two layers:

1. **OS threads** (often called **M**): the heavy layer we already know. Go creates a limited number of them, typically one per CPU core, configurable with `GOMAXPROCS`. With 4 cores you get M1 to M4.
2. **Goroutines** (**G**): the lightweight layer. Each new goroutine is placed on a queue attached to one of the OS threads by the **Go runtime scheduler**, which is *not* the OS scheduler.

When a goroutine (say G1, handling request A) hits a blocking I/O call such as `db.Query(...)`, the Go runtime pauses G1, and the OS thread M1 immediately runs another goroutine (G2, another request, or a logging task). When G1’s I/O finishes, it becomes runnable again and continues. A switch between goroutines is usually just a **pointer switch** inside the runtime, which is cheap. You can therefore run thousands or even millions of goroutines (until memory runs out), about 100 times more than OS threads.

```go
func handler(w http.ResponseWriter, r *http.Request) {
    row := db.QueryRow("SELECT * FROM users WHERE id = $1", userID) // goroutine pauses here
    // ...runs again when the response arrives
}
```

This is essentially the threading model with another layer of abstraction: the Go scheduler instead of the OS scheduler, goroutines instead of OS threads. That is why Go does well at both I/O-bound and CPU-bound work, even though it uses no event loop. (Java’s modern **virtual threads** follow a similar idea.)

> **Real-world picture.** A company has only 4 real conference rooms (OS threads) but thousands of meetings (goroutines). A smart office manager (Go scheduler) moves a meeting out of the room the moment it pauses to wait for someone’s reply, and puts another meeting in. Rooms are never idle, and nobody builds a new room per meeting.

## 10. How async/await Works Under the Hood: State Machines

Confusion around `async`/`await` is common, in Python, JavaScript, Rust, and others. Take this function:

```javascript
async function fetchUserData(userId) {
  const user = await db.getUser(userId);
  const orders = await db.getOrders(userId);
  return { user, orders };
}
```

You can picture the runtime converting it into a **state machine** that interacts with the event loop:

```javascript
function fetchUserData(userId) {
  let state = 0, user, orders;
  function step() {
    switch (state) {
      case 0:
        state = 1;
        db.getUser(userId).then(r => { user = r; step(); });
        return;
      case 1:
        state = 2;
        db.getOrders(userId).then(r => { orders = r; step(); });
        return;
      case 2:
        return { user, orders };
    }
  }
  return step();
}
```

Each `await` is a state transition. In state 0 we start the first I/O and register “when done, continue.” While we wait, the event loop is free to run other code. When the result arrives we move to state 1, start the second I/O, and so on until the final state returns.

This explains two things:

- **Why `await` works only inside `async` functions.** The `async` marker tells the compiler or runtime to transform the function into a state machine. A normal function cannot be paused and resumed this way.
- **Why blocking the event loop is so bad.** If something blocks the loop, the state machines cannot advance from state 0 to 1 to 2. Every request in flight freezes.

You do not have to memorize this, but it helps to know what your runtime is really doing.

## 11. The Dark Side: Shared State and Race Conditions

Concurrency brings its own problems. Almost all of them trace back to one cause: **shared state (shared memory)**.

### Example 1: Two threads incrementing a counter

Two threads both increment a shared `counter` that starts at 0. Incrementing is not one step, it is three:

1. read the counter into a CPU register,
2. add 1 to the register,
3. write the register back to the counter.

Now see what happens when those steps interleave:

| Time | Thread A | Thread B | Counter value |
| --- | --- | --- | --- |
| 1 ms | reads 0 |  | 0 |
| 2 ms |  | reads 0 | 0 |
| 3 ms | adds 1 (register = 1) |  | 0 |
| 4 ms |  | adds 1 (register = 1) | 0 |
| 5 ms | writes 1 |  | 1 |
| 6 ms |  | writes 1 | **1** |

Two increments ran, so we expect **2**, yet the result is **1**. One update was lost. This is a **lost update**, and the bug class is called a **race condition**.

> **Real-world picture.** Two clerks both look at the same paper ledger showing “stock: 10”. Each sells one item and writes “9”. Two items left the shop, but the ledger says 9, not 8.

### Example 2: “But JavaScript is single-threaded!”

You might think a single-threaded, `async`/`await` language is immune. It is not. Consider:

```javascript
let balance = 100;

async function withdraw(amount) {
  if (balance >= amount) {          // check
    await processWithdrawal(amount); // I/O: control goes back to the event loop
    balance -= amount;               // use
  }
}
```

Suppose `withdraw(100)` is called twice around the same time:

1. Call 1 checks `100 >= 100`, true. It reaches `await` and yields to the event loop.
2. Call 2 runs, checks `100 >= 100` (balance is still 100), true. It also reaches `await` and yields.
3. Call 1 resumes and does `balance -= 100`, so balance is **0**.
4. Call 2 resumes and does `balance -= 100`, so balance becomes **-100**, an invalid state.

The check and the update were separated by an `await`, so another task slipped in between. A single thread does not remove race conditions. Any point where you give up control can interleave tasks.

> **Real-world picture.** Two people check a shared bank account balance at the same moment, each sees 100 and withdraws 100 at two different ATMs. The bank only deducts after each machine finishes counting out cash, and the account ends up overdrawn.

## 12. Preventing Race Conditions

This topic runs deep, and operating-systems books cover it fully. Two common tools:

### Locks (mutexes)

A **lock** enforces **mutual exclusion**: only one thread may be inside the protected section at a time. Others wait until the lock is released.

```python
import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    with lock:           # only one thread at a time in here
        counter += 1
```

This avoids the lost update for the counter. The same principle protects the withdrawal check-and-update: make the check and the deduction one protected unit.

### Channels (message passing)

Go offers **channels** as a primitive. Instead of many goroutines mutating one shared variable, goroutines **send messages**, and **only one goroutine** owns and updates the variable. Sharing data by communicating, rather than communicating by sharing data, removes a whole class of races.

> **Real-world picture.** A lock is a single key to a shared bathroom: whoever holds the key goes in, everyone else waits. A channel is a single cashier at a counter: customers hand over their requests in a queue, and only the cashier touches the till.

This article is not mainly about the techniques for each of these problems. Its main goal is to get one concept clear: **what is I/O-bound and what is CPU-bound**.

## Summary and Key Takeaways

| Concept | What to remember |
| --- | --- |
| **Why concurrency** | Backends are mostly waiting (I/O). Without concurrency, about 95% of CPU time can be wasted. |
| **I/O-bound** | Waiting on databases, networks, files, logging. Most backend work. Best served by concurrency. |
| **CPU-bound** | Real computation: image/video work, encryption, number crunching. Best served by parallelism (many cores). |
| **Concurrency** | Dealing with many things at once. Possible on one core by pausing and resuming tasks. |
| **Parallelism** | Doing many things at the same moment. Needs multiple cores. |
| **Threads** | OS-managed, preemptively scheduled, share memory within a process. Heavy: stack memory, creation cost, context switching. |
| **Event loop** | One thread, callbacks, epoll/kqueue. Very efficient for I/O. Never block the loop. |
| **async/await** | Syntactic sugar over callbacks, compiled to state machines. `await` yields control to the event loop. |
| **Goroutines / virtual threads** | Lightweight threads managed by a language runtime scheduler on top of a few OS threads. Cheap enough for one per request. |
| **Race conditions** | Caused by shared state. Happen with threads *and* with async/await. |
| **Solutions** | Locks/mutexes for mutual exclusion; channels and message passing so one owner updates the data. |

**Rules of thumb:**

- For **I/O-bound, highly concurrent** workloads (web servers, API gateways, services that call other services), use event-loop style primitives (`async`/`await`) or lightweight virtual threads (goroutines, Java virtual threads). They are more efficient than one OS thread per task.
- For **CPU-bound** workloads (number crunching, string, image, or video manipulation), use threads and parallelism across cores, which beat an event loop.
- Concurrency keeps your program productive instead of wasting CPU cycles while it waits for I/O. Parallelism uses multiple cores to do several things at the same instant. Most backend work leans toward concurrency, but if you understand the difference, you can pick the right tool for each job.
