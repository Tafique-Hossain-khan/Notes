# Strategy Pattern — Cheat Sheet

1. **Problem:** Inheritance causes class explosion when behaviors (walk, talk, fly, payment, sorting, etc.) vary independently.

2. **Solution:** Extract each changing behavior into its own class (called a Strategy) and let the main object delegate work to it.

3. **Structure:** Context **HAS-A** Strategy → Context forwards calls → Concrete Strategy performs the actual work.

4. **Key Benefit:** Behaviors can be swapped at runtime without modifying existing code (**Open/Closed Principle**).

5. **Golden Rule:** **Favor Composition over Inheritance** — when behavior changes, create a new strategy instead of creating more subclasses.

# Factory Design Pattern — Interview Cheat Sheet

1. **Intent:** Encapsulate object creation logic in a dedicated place so business logic doesn't directly instantiate concrete classes.

2. **Problem Solved:** Prevents object creation (`if/else`, constructors, configuration logic) from being scattered across the codebase.

3. **Core Idea:** Client asks a Factory for an object instead of creating the object itself.

4. **Simple Factory:** One factory class decides which concrete product to create based on input (e.g., `BurgerFactory -> BasicBurger / PremiumBurger`).

5. **Factory Method:** Creation is delegated to subclasses; an abstract factory defines the creation contract, and concrete factories decide which product to instantiate.

6. **Abstract Factory:** Creates **families of related objects** (e.g., `Button + Checkbox`, `Burger + GarlicBread`) while ensuring consistency between products.

7. **Hierarchy Progression:**
   ```text
   Simple Factory
        ↓
   Factory Method
        ↓
   Abstract Factory
   ```

8. **Factory vs Strategy:**
   - **Factory:** Decides *which object gets created*.
   - **Strategy:** Decides *which behavior/algorithm gets executed*.

9. **Common Structure:**
   ```text
   Client
      ↓
   Factory
      ↓
   Concrete Product
   ```
   Client depends on abstractions, not concrete implementations.

10. **Key Benefits:** Centralized creation logic, loose coupling, easier maintenance, supports Open/Closed Principle, and allows adding new products/families with minimal impact on existing code.

## One-Line Definitions

### Simple Factory
> A single class responsible for creating different concrete objects based on input.

### Factory Method
> Define an interface for object creation, but let subclasses decide which concrete object to instantiate.

### Abstract Factory
> Provide an interface for creating families of related objects without specifying their concrete classes.

```text
Strategy  = Which behavior should run?

Simple Factory   = One factory → Many products
Factory Method   = Many factories → One product family
Abstract Factory = Many factories → Multiple related product families
```
