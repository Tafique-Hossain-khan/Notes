## L — Liskov Substitution Principle (Deep Dive)

The rule is simple to state: *a child class should be substitutable for its parent class without the client noticing.* But LSP is the most-broken principle because violations are often subtle. Here are the concrete guidelines that, if followed, guarantee you never break LSP.

LSP guidelines fall into three categories:

1. [**Signature Rule**](#signature-rule)
2. [**Property Rule**](#property-rule)
3. [**Method Rule**](#method-rule)

---

### Signature Rule

A method's *signature* = its name + its arguments + its return type.

#### 1. Method Argument Rule

When a child class overrides a method, the argument types must be the same as the parent's — or *broader* (a parent type of the original argument). Never narrower.

**Why?** The client only knows the parent's contract. If the child demands a more specific argument type, the client's valid call will break.

```python
# Broad = parent class / ancestor
# Narrow = child class / descendant

class Animal:
    pass

class Dog(Animal):
    pass

class Parent:
    def solve(self, s: str) -> None:   # takes str
        print(f"Parent solving: {s}")

class Child(Parent):
    def solve(self, s: str) -> None:   # ✅ same type — fine
        print(f"Child solving: {s}")

# ❌ This would break LSP (Python won't stop you, but the contract is broken)
class BadChild(Parent):
    def solve(self, n: int) -> None:   # narrower / completely different type
        print(f"BadChild solving: {n}")

# Client code
def client(obj: Parent):
    obj.solve("hello")   # client always passes str

client(Child())     # ✅ works
client(BadChild())  # ❌ TypeError at runtime
```

> **Note:** Python doesn't enforce argument types at compile time — that's exactly why you must enforce this discipline yourself (use type hints + mypy).

---

#### 2. Return Type Rule (Covariance)

When overriding, the return type must be the *same* or *narrower* (a subtype of the parent's return type). Never broader.

```python
class Animal:
    pass

class Dog(Animal):
    pass

class Parent:
    def get_animal(self) -> Animal:      # returns Animal
        return Animal()

class Child(Parent):
    def get_animal(self) -> Dog:         # ✅ Dog IS-A Animal — narrower, fine
        return Dog()

# ❌ Would break LSP
class Organism:
    pass

class BadChild(Parent):
    def get_animal(self) -> Organism:    # broader — Organism is Animal's parent
        return Organism()

# Client code
def client(obj: Parent):
    a: Animal = obj.get_animal()         # client expects Animal
    # If BadChild returned Organism, this assignment breaks the contract

client(Child())     # ✅
```

This is called **covariance** — the return type can vary, but only in the *same direction* as the inheritance hierarchy (downward / narrower).

---

#### 3. Exception Rule

When overriding, a method can throw the *same* exception as the parent or a *narrower* (child) exception. Never a broader one.

```python
# Exception hierarchy (simplified):
# Exception
#   ├── ValueError (like LogicError)
#   │     └── CustomValueError
#   └── RuntimeError

class Parent:
    def get_value(self):
        # Contract: throws ValueError
        raise ValueError("parent error")

class Child(Parent):
    def get_value(self):
        # ✅ narrower — CustomValueError IS-A ValueError
        raise ValueError("child out-of-range error")   # same or subtype — fine

class BadChild(Parent):
    def get_value(self):
        # ❌ RuntimeError is NOT a subtype of ValueError
        raise RuntimeError("completely different error")

# Client code
def client(obj: Parent):
    try:
        obj.get_value()
    except ValueError as e:              # client only knows to catch ValueError
        print(f"Handled: {e}")

client(Child())     # ✅ caught correctly
client(BadChild())  # ❌ RuntimeError is uncaught — program crashes
```

### Property Rule

#### 1. Class Invariant

An *invariant* is a rule that must always be true for a class. Any child class must respect (or strengthen) that invariant — never weaken it.

```python
class BankAccount:
    """Invariant: balance can never be negative."""
    
    def __init__(self, balance: float):
        if balance < 0:
            raise ValueError("Balance can't be negative")
        self.balance = balance
    
    def withdraw(self, amount: float):
        if self.balance - amount < 0:
            raise RuntimeError("Insufficient funds")
        self.balance -= amount
        print(f"Withdrawn {amount}. Remaining: {self.balance}")

class CheatAccount(BankAccount):
    """❌ Breaks the invariant — allows negative balance."""
    # An invariant is a rule or condition that must always remain true.
    # It represents a business constraint that protects the correctness of the system.
    # If an invariant is violated, the business logic becomes invalid and the system
    # may enter an inconsistent or incorrect state.
    def withdraw(self, amount: float):
        self.balance -= amount   # no check — balance can go negative
        print(f"Withdrawn {amount}. Remaining: {self.balance}")

# Client code
def process_withdrawal(account: BankAccount, amount: float):
    account.withdraw(amount)

acc = BankAccount(100)
process_withdrawal(acc, 150)   # ✅ raises RuntimeError — expected

cheat = CheatAccount(100)
process_withdrawal(cheat, 150) # ❌ balance becomes -50 — invariant broken
```

#### 2. History Constraint

A history constraint says: *a state that the parent declared as always-allowed should not be blocked by the child.*

```python
class BankAccount:
 class BankAccount:
    """
    History Constraint:
    A BankAccount promises that withdrawal is a valid operation.
    Any subclass should preserve this behavior.
    """

    def __init__(self, balance: float):
        self.balance = balance

    def withdraw(self, amount: float):
        if self.balance - amount < 0:
            raise RuntimeError("Insufficient funds")
        self.balance -= amount


class FixedDepositAccount(BankAccount):
    """
    ❌ LSP Violation (History Constraint)

    The parent class allows withdrawals whenever sufficient balance exists.

    A client working with BankAccount learns from its history/behavior
    that calling withdraw() is a valid operation.

    This subclass changes that historical behavior by completely
    blocking withdrawals, even when there is enough balance.

    Therefore, it violates the History Constraint and breaks LSP.
    """

    def withdraw(self, amount: float):
        # ❌ Parent says withdrawal is an allowed operation.
        # ❌ Child changes that rule and makes withdrawal impossible.
        # ❌ A previously valid state transition is now forbidden.
        # ❌ History Constraint is violated here.
        raise RuntimeError("Withdrawal not allowed on fixed deposit")


# Client code
def client_withdraw(account: BankAccount, amount: float):
    # Client relies on the BankAccount contract:
    # "withdraw() is a supported operation"
    account.withdraw(amount)


acc = BankAccount(500)
client_withdraw(acc, 100)  # ✅ Works as expected


fd = FixedDepositAccount(500)

# ❌ Client expects BankAccount behavior.
# ❌ FixedDepositAccount breaks that expectation.
# ❌ Subclass cannot be substituted for parent.
# ❌ LSP violation caused by breaking the History Constraint.
client_withdraw(fd, 100)
```

> **Bonus fact:** If a parent class has an immutable attribute (e.g., set via `__slots__` or a `@property` with no setter), a child class that makes it mutable also breaks the history constraint.

### Method Rule

#### 1. Pre-condition Rule

A pre-condition is a condition that must be true *before* a method runs. Child classes can make pre-conditions **weaker** (more permissive), but never **stricter**.

```python
class User:
    """
    Parent Contract (Pre-condition):

    The caller is allowed to provide any password whose length is >= 8.

    This becomes part of the public contract that all subclasses
    must honor.

    LSP Rule:
    Child classes may accept MORE inputs than the parent
    (weaker pre-condition), but must not accept fewer inputs
    (stricter pre-condition).
    """

    def set_password(self, password: str):
        # Pre-condition:
        # Password must contain at least 8 characters.
        if len(password) < 8:
            raise ValueError("Password must be at least 8 characters")

        self._password = password
        print("Password set")


class AdminUser(User):
    """
    ✅ LSP Compliant

    Parent accepts passwords with length >= 8.

    AdminUser accepts passwords with length >= 6.

    This is a weaker pre-condition because it allows
    everything the parent allows PLUS additional inputs.

    Parent accepts:
        8, 9, 10, 11, ...

    Child accepts:
        6, 7, 8, 9, 10, ...

    Therefore any valid User password is also valid
    for AdminUser.
    """

    def set_password(self, password: str):
        # Weaker pre-condition:
        # Accepts more inputs than the parent.
        if len(password) < 6:
            raise ValueError("Admin password must be at least 6 characters")

        self._password = password
        print("Admin password set")


class StrictUser(User):
    """
    ❌ LSP Violation

    Parent contract says:
        Any password with length >= 8 is valid.

    StrictUser changes the contract to:
        Password length must be >= 12.

    This is a stricter pre-condition because the child
    accepts fewer inputs than the parent.

    Parent accepts:
        8, 9, 10, 11, 12, ...

    Child accepts:
        12, 13, 14, ...

    A password that is perfectly valid for User
    may be rejected by StrictUser.

    Therefore StrictUser cannot safely replace User.
    """

    def set_password(self, password: str):

        # ❌ Stricter pre-condition introduced here.
        #
        # Parent promised:
        #     length >= 8 is valid
        #
        # Child changes the rule:
        #     length >= 12 is required
        #
        # Client code relying on the parent's contract
        # will unexpectedly fail.
        if len(password) < 12:
            raise ValueError("Password must be at least 12 characters")

        self._password = password


# Client code
def client_set_password(user: User, pwd: str):
    """
    The client only knows the User contract.

    According to User:
        Any password with length >= 8 should work.

    The client should not need to know whether it is
    dealing with User, AdminUser, or StrictUser.
    """

    user.set_password(pwd)


# "hello123" has length 8

# ✅ Parent contract says length >= 8 is valid.
# ✅ AdminUser accepts it because its pre-condition is weaker.
client_set_password(AdminUser(), "hello123")


# ❌ Parent contract says length >= 8 is valid.
# ❌ StrictUser rejects it because it introduced a stricter rule.
# ❌ Client behavior changes unexpectedly.
# ❌ LSP violation caused by breaking the Pre-condition Rule.
client_set_password(StrictUser(), "hello123")

# Pre-condition Rule:
#
# Parent class defines what inputs are valid.
#
# Child classes may weaken the pre-condition
# (accept more inputs).
#
# Child classes must not strengthen the pre-condition
# (accept fewer inputs).
#
# Otherwise code that works with the parent may fail
# when a child object is substituted, violating LSP.

```

#### 2. Post-condition Rule

A post-condition is a condition that must be true *after* a method runs. Child classes can make post-conditions **stricter** (add guarantees), but never **weaker**.

```python
class Car:
    """
    Parent Contract (Post-condition):

    After brake() completes successfully:

        speed_after < speed_before

    In other words, braking must reduce the car's speed.

    This guarantee becomes part of the public contract that
    all subclasses must preserve.

    LSP Rule:
    Child classes may provide additional guarantees
    (stricter post-conditions), but they must not remove
    guarantees made by the parent.
    """

    def __init__(self, speed: int):
        self.speed = speed

    def brake(self):
        """
        Post-condition:
            speed must decrease after braking.
        """

        self.speed -= 20

        # Parent guarantee:
        # speed_after < speed_before
        print(f"Car braking. Speed: {self.speed}")


class HybridCar(Car):
    """
    ✅ LSP Compliant

    Parent guarantees:
        1. Speed decreases after braking.

    HybridCar guarantees:
        1. Speed decreases after braking.
        2. Battery charge increases.

    The child preserves all parent guarantees
    and adds an extra one.

    This is a stricter post-condition,
    which is allowed by LSP.
    """

    def __init__(self, speed: int, charge: int):
        super().__init__(speed)
        self.charge = charge

    def brake(self):

        # Parent post-condition still satisfied.
        self.speed -= 20

        # Additional guarantee.
        self.charge += 10

        print(
            f"Hybrid braking. "
            f"Speed: {self.speed}, Charge: {self.charge}"
        )


class BrokenCar(Car):
    """
    ❌ LSP Violation

    Parent contract guarantees:

        speed_after < speed_before

    Clients rely on this behavior.

    BrokenCar removes that guarantee completely.

    After brake() executes:
        speed remains unchanged

    The parent's post-condition is no longer true.

    Therefore BrokenCar cannot safely replace Car.
    """

    def brake(self):

        # ❌ Parent promised:
        #       speed will decrease
        #
        # ❌ Child removes that guarantee.
        #
        # speed_after == speed_before
        #
        # This weakens the post-condition and
        # violates LSP.
        print("Brakes applied but speed unchanged")


# Client code
def apply_brakes(car: Car):
    """
    The client only knows the Car contract.

    It expects:

        speed_after < speed_before

    regardless of which subclass is passed.

    The client should not need to know whether
    it is working with Car, HybridCar, or BrokenCar.
    """

    before = car.speed

    car.brake()

    # Client verifies the parent's guarantee.
    assert (
        car.speed < before
    ), "Speed must decrease after braking!"


# ✅ Works

# Parent guarantee preserved:
# speed decreases

# Additional guarantee:
# battery charge increases

apply_brakes(HybridCar(100, 50))


# ❌ Fails

# Parent promised:
# speed decreases

# BrokenCar does not satisfy that promise.

# Client behavior changes unexpectedly.

# ❌ LSP violation caused by breaking
# the Post-condition Rule.

apply_brakes(BrokenCar(100))


# Post-condition Rule:
#
# Parent class defines what guarantees must be true
# after a method completes.
#
# Child classes may strengthen those guarantees
# (provide more guarantees).
#
# Child classes must not weaken or remove guarantees
# made by the parent.
#
# Otherwise client code that relies on the parent's
# contract can break when a child object is substituted,
# violating LSP.
```

## I — Interface Segregation Principle (ISP)

> *Many client-specific interfaces are better than one general-purpose interface.*
> *Clients should not be forced to implement methods they don't need.*

```python
from abc import ABC, abstractmethod


# ❌ Violates ISP — Fat Interface
class Shape(ABC):
    """
    Interface Segregation Principle (ISP):

    Clients should not be forced to depend on methods
    they do not need.

    Problem:

    This interface assumes every shape has BOTH:

        1. area()
        2. volume()

    But that assumption is incorrect.

    Examples:

        Square      -> has area, no volume
        Rectangle   -> has area, no volume
        Cube        -> has area and volume

    As a result, 2D shapes are forced to implement
    volume() even though the operation makes no sense.

    This is a classic ISP violation.
    """

    @abstractmethod
    def area(self) -> float:
        pass

    @abstractmethod
    def volume(self) -> float:
        pass


class Square(Shape):
    """
    Square only needs area().

    However, because of the fat Shape interface,
    it is forced to implement volume().

    The class is depending on functionality
    that it does not actually need.
    """

    def __init__(self, side: float):
        self.side = side

    def area(self) -> float:
        return self.side ** 2

    def volume(self) -> float:

        # ❌ ISP Violation

        # Square is a 2D shape.

        # Volume has no meaning for a square.

        # Yet the interface forces us to provide
        # an implementation.

        # We end up writing fake code just to satisfy
        # the interface contract.

        raise NotImplementedError(
            "Volume not applicable to 2D shapes"
        )


class Rectangle(Shape):
    """
    Same problem as Square.

    Rectangle only requires area().

    volume() is irrelevant but still mandatory.
    """

    def __init__(self, l: float, w: float):
        self.l = l
        self.w = w

    def area(self) -> float:
        return self.l * self.w

    def volume(self) -> float:

        # ❌ ISP Violation

        # Rectangle is being forced to implement
        # behavior it does not support.

        raise NotImplementedError(
            "Volume not applicable to 2D shapes"
        )


class Cube(Shape):
    """
    Cube is a 3D shape.

    Both area() and volume() are meaningful.

    Therefore Cube fits this interface naturally.
    """

    def __init__(self, side: float):
        self.side = side

    def area(self) -> float:
        return 6 * self.side ** 2

    def volume(self) -> float:
        return self.side ** 3
```

```python
# ✅ Follows ISP — segregated interfaces

class TwoDShape(ABC):
    @abstractmethod
    def area(self) -> float: ...

class ThreeDShape(ABC):
    @abstractmethod
    def area(self) -> float: ...
    
    @abstractmethod
    def volume(self) -> float: ...

class Square(TwoDShape):
    def __init__(self, side: float):
        self.side = side
    
    def area(self) -> float:
        return self.side ** 2

class Rectangle(TwoDShape):
    def __init__(self, l: float, w: float):
        self.l, self.w = l, w
    
    def area(self) -> float:
        return self.l * self.w

class Cube(ThreeDShape):
    def __init__(self, side: float):
        self.side = side
    
    def area(self) -> float:
        return 6 * self.side ** 2
    
    def volume(self) -> float:
        return self.side ** 3

# Now Square and Rectangle only implement what they need.
# Cube implements everything it needs.
# No class is forced to define a method it can't meaningfully implement.
```

## D — Dependency Inversion Principle (DIP)

> *High-level modules should not depend on low-level modules. Both should depend on abstractions.*

- **High-level module** = business logic (e.g., `UserService`)
- **Low-level module** = infrastructure code (e.g., `MySQLDatabase`, `MongoDB`)
- **Abstraction** = the interface/abstract class between them

```python
# ❌ Violates DIP — high-level tightly coupled to low-level

class MySQLDatabase:
    def save_to_mysql(self, user: str):
        print(f"Saving {user} to MySQL")

class MongoDB:
    def save_to_mongo(self, user: str):
        print(f"Saving {user} to MongoDB")

class UserService:
    def __init__(self):
        self.mysql_db = MySQLDatabase()   # tightly coupled
        self.mongo_db = MongoDB()         # tightly coupled
    
    def store_user_to_mysql(self, user: str):
        self.mysql_db.save_to_mysql(user)
    
    def store_user_to_mongo(self, user: str):
        self.mongo_db.save_to_mongo(user)

# Problem: if we swap MongoDB for CassandraDB,
# we must open UserService and modify it — breaking Open/Closed Principle.
```

```python
# ✅ Follows DIP — introduce an abstraction layer

from abc import ABC, abstractmethod

class Database(ABC):
    """Abstraction — both high-level and low-level depend on this."""
    
    @abstractmethod
    def save(self, user: str): ...

class MySQLDatabase(Database):
    def save(self, user: str):
        print(f"Saving {user} to MySQL")

class MongoDB(Database):
    def save(self, user: str):
        print(f"Saving {user} to MongoDB")

class CassandraDB(Database):          # new DB — no changes to UserService needed
    def save(self, user: str):
        print(f"Saving {user} to Cassandra")

class UserService:
    def __init__(self, db: Database):  # dependency injected via abstraction
        self.db = db
    
    def store_user(self, user: str):
        self.db.save(user)             # doesn't care which DB it is

# Usage
service = UserService(MySQLDatabase())
service.store_user("Alice")            # Saving Alice to MySQL

service = UserService(CassandraDB())
service.store_user("Alice")            # Saving Alice to Cassandra
# UserService was never touched.
```

> **DIP in one line:** If Open/Closed Principle is the *goal*, Dependency Inversion Principle is the *mechanism to achieve it*.

> **Real-world analogy:** A CEO doesn't call developers directly. The Manager (abstraction) sits in between. If developers change, the CEO doesn't need to know or care.
