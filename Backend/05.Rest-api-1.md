# REST API Design Fundamentals: History, Principles, and a Practical FastAPI Implementation

API design is one of the things a backend engineer spends the most time on. This post covers the theory and practice of designing REST APIs end to end: where REST came from, what the name means, how to design URLs and resources, what idempotency is and how it guides your choice of HTTP method, and how to design and implement list and create endpoints with pagination. All code is in **FastAPI (Python)**.

We focus on REST only. RPC and GraphQL are other ways to build APIs, but REST is one of the most widely used standards.

---

## 1. Why API Design Still Confuses People

Even with years of research and developer experience behind the REST standard, beginners (and often experienced engineers) still get stuck on questions like:

- Should a URI path segment be **plural or singular**?
- When updating a resource, should I use **PATCH or PUT**?
- What do I do for a **non-CRUD operation**, like "send an email", which is not a fetch, create, update, or delete? Is it an update (PATCH/PUT) or a create (POST)?
- Which **HTTP status code** should I return in each scenario?

The confusion exists because these standards were written when the web looked very different from today. Back then we mostly built **MPAs (multi-page applications)**, where the server returned a new HTML page for each navigation. Today we mostly build **SPAs (single-page applications)**. On the first request, the browser downloads all the JavaScript, and routing happens on the client using the browser's path and URL. These are client-heavy applications.

**The goal of this post is not to invent new standards.** It is to extract a set of rules and guidelines from the existing standards, so that you:

- follow one consistent style for designing APIs, payloads, and documentation,
- stop re-debating the same questions on every project,
- spend your time on business logic instead of worrying whether the API is "RESTful enough".

We'll cover resources, routes, success responses, error responses, status codes, and accepted input.

## 2. A Short History: From WWW to REST

### 2.1 Tim Berners-Lee and the World Wide Web (1990)

In 1990, Tim Berners-Lee started the **World Wide Web** project to share knowledge globally. Within about a year he invented:

1. **URI** (Uniform Resource Identifier)
2. **HTTP**, the protocol clients and servers use to communicate
3. **HTML**, the markup language that forms the skeleton of a web page
4. The first **web server**
5. The first **web browser**
6. The first **WYSIWYG HTML editor**, built into the browser

We still use advanced versions of all of these: URIs, HTTP (1.1, then 2.0, then 3.0), HTML, many kinds of web servers and browsers, and in-browser editing.

### 2.2 The Scalability Crisis

The web's user base grew exponentially in a very short time. Berners-Lee had not planned for that scale, and the web was heading toward a breakdown. New techniques, standards, and components were needed.

### 2.3 Roy Fielding's Constraints (~1993)

**Roy Fielding**, co-founder of the Apache HTTP Server project, became concerned about web scalability and proposed a set of **constraints** to solve it:

| # | Constraint | Meaning |
|---|---|---|
| 1 | **Client–Server** | Separation of concerns. The client handles UI/UX; the server handles data storage and business logic (frontend vs. backend). Each can evolve independently, which improves scalability. |
| 2 | **Uniform Interface** | A standardized way for components to communicate. It has four sub-constraints: resource identification, resource manipulation through representations, self-descriptive messages, and hypermedia as the engine of application state (HATEOAS). |
| 3 | **Layered System** | The architecture is composed of hierarchical layers; each layer only sees the layer immediately below it. This enables load balancers, proxies, and similar intermediaries without affecting core functionality. |
| 4 | **Cache** | Responses must be explicitly labeled **cacheable or non-cacheable**. Clients can cache, which reduces server load, improves network efficiency, and gives faster responses. |
| 5 | **Stateless** | Each request must contain **all the information needed** to understand and process it. The server stores no client context between requests. This improves reliability, scalability, and visibility, because *any* server can handle *any* request. |
| 6 | **Code on Demand** (optional) | Servers can temporarily extend client functionality by sending executable code (e.g., JavaScript). Optional, and not heavily used in REST. |

Fielding then worked with Berners-Lee to standardize the designs, and together they wrote the specification for **HTTP/1.1**, the first major standard version of the protocol. In **2000**, once the crisis had passed, Fielding named and described the web's architectural style in his PhD dissertation: **REST: Representational State Transfer**. Searching "Roy Fielding REST dissertation" will find it, and it is worth reading for a backend engineer.

### 2.4 Seeing the Constraints in FastAPI

Here are a few practical illustrations of the constraints.

**Stateless: every request carries everything the server needs.**

```python
from fastapi import Depends, FastAPI, Header, HTTPException

app = FastAPI()

def current_user(authorization: str = Header(...)) -> str:
    # No server-side session. The token on EVERY request identifies the caller.
    if not authorization.startswith("Bearer "):
        raise HTTPException(status_code=401, detail="Missing or invalid token")
    token = authorization.removeprefix("Bearer ")
    return decode_and_verify(token)  # e.g., verify a JWT, return user id

@app.get("/v1/me")
def me(user_id: str = Depends(current_user)):
    return {"user_id": user_id}
```

Because the server remembers nothing between requests, you can put three instances of this app behind a load balancer doing round-robin, and any instance can serve any request from the same client.

**Cache: label responses as cacheable or not.**

```python
from fastapi import Response

@app.get("/v1/countries")
def countries(response: Response):
    response.headers["Cache-Control"] = "public, max-age=3600"   # cacheable for 1 hour
    return ["IN", "US", "DE"]

@app.get("/v1/me/balance")
def balance(response: Response):
    response.headers["Cache-Control"] = "no-store"              # never cache
    return {"balance": 120}
```

## 3. Why Is It Called "REST"? Representational State Transfer

The name has three parts.

### 3.1 Representational

Resources on the web (data or objects) are exposed in a specific **representation**. The same resource can have different representations depending on the client:

- **JSON**: the most popular format; typical for server-to-server and API clients
- **XML**
- **HTML**: typical when the client is a web browser

Take a `user` resource in a database with `id`, `name`, and `created_at`. For an API client it might be JSON; for a browser it might be an HTML page.

Here is that idea in FastAPI, serving the same resource in two representations via the `Accept` header:

```python
from fastapi import FastAPI, Request
from fastapi.responses import HTMLResponse, JSONResponse

app = FastAPI()

USERS = {"1": {"id": "1", "name": "Ada", "created_at": "2025-01-01T10:00:00Z"}}

@app.get("/v1/users/{user_id}")
def get_user(user_id: str, request: Request):
    user = USERS[user_id]
    accept = request.headers.get("accept", "application/json")
    if "text/html" in accept:
        return HTMLResponse(f"<h1>{user['name']}</h1><p>Joined {user['created_at']}</p>")
    return JSONResponse(user)
```

```bash
curl -H "Accept: application/json" localhost:8000/v1/users/1   # JSON representation
curl -H "Accept: text/html"        localhost:8000/v1/users/1   # HTML representation
```

### 3.2 State

**State** is the current condition or attributes of a resource. Take an e-commerce shopping cart: its state includes the items, their quantities, and the total price. That state is what moves between client and server with each API call.

### 3.3 Transfer

**Transfer** is the movement of resource representations between client and server using HTTP methods (`GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `OPTIONS`, `HEAD`, ...). When you `GET` a web page, you are transferring a representation from server to client.

### 3.4 Putting It Together

A RESTful architecture means:

1. Resources have representations in different formats (JSON, HTML, XML).
2. The **state** of those resources is transferred between client and server.
3. Clients and servers communicate by exchanging these representations.
4. The whole system follows the constraints above to stay scalable.

## 4. URL Anatomy and URL Design Rules

### 4.1 Anatomy of a URL

```
https://sly.xyz/books/harry-potter?limit=10&page=2#reviews
└─┬──┘   └──┬──┘└────────┬───────┘└──────┬───────┘└──┬──┘
scheme   authority      path           query     fragment
```

- **Scheme**: `http` or `https` (the secure, encrypted version).
- **Authority/domain**: may include a subdomain.
- **Path (resource)**: the resource being accessed. The `/` expresses a **hierarchical relationship** between resources.
- **Query parameters**: key-value pairs, usually on `GET` requests, for filters and other parameters.
- **Fragment**: scrolls the browser to a section of the page. (It is a client-side concept: browsers do not send the fragment to the server, so it is irrelevant for API design.)

### 4.2 Anatomy of an API URL

By industry convention (a best practice, not a hard rule):

```
https://api.example.com/v1/books
└─┬──┘ └──────┬──────┘└┬┘└──┬──┘
scheme   subdomain   version resource
```

- Use the **`api` subdomain**.
- Add **versioning** in the route (`/v1`, `/v2`).
- Then the **resource**.

Imagine a Goodreads-like API (books, authors, reviews):

| Action | Route |
|---|---|
| List all books | `GET https://api.example.com/v1/books` |
| Fetch a single book | `GET https://api.example.com/v1/books/{id}` |

### 4.3 The Rules

**Rule 1: Resource names in the path are always plural nouns, even when fetching a single item.**

Many people write `/book/42` when fetching one book. Don't. The *resource collection* is `books`, and `/books/42` means "the item with ID 42 inside the `books` collection". This is consistent with rule 5 below, the hierarchy rule.

**Rule 2: Use lowercase.** URLs travel across servers, clients, and operating systems, and you don't want case-mismatch problems.

**Rule 3: No spaces and no underscores in URLs.** This applies to slugs, IDs, and any path part. Use hyphens.

**Rule 4: Use slugs for human-readable identifiers.** A slug is a human-readable representation of some property of a resource, suitable for URLs. To turn "Harry Potter" into a slug, lowercase it, then replace every space with a hyphen: `harry-potter`. The route becomes `/books/harry-potter`.

**Rule 5: A `/` means hierarchy.** `/books` is the collection (level 1); `/books/harry-potter` is one item from that collection (level 2).

### 4.4 FastAPI Implementation

```python
import re
import unicodedata
from fastapi import APIRouter, FastAPI, HTTPException

def slugify(text: str) -> str:
    """'Harry Potter' -> 'harry-potter'"""
    text = unicodedata.normalize("NFKD", text).encode("ascii", "ignore").decode()
    text = text.lower().strip()
    text = re.sub(r"[^a-z0-9]+", "-", text)   # spaces/underscores/symbols -> hyphen
    return text.strip("-")

BOOKS = {
    "harry-potter": {"id": 1, "title": "Harry Potter", "slug": "harry-potter"},
    "the-hobbit":   {"id": 2, "title": "The Hobbit",   "slug": "the-hobbit"},
}

v1 = APIRouter(prefix="/v1")           # versioning in the route

@v1.get("/books")                      # plural collection
def list_books():
    return list(BOOKS.values())

@v1.get("/books/{slug}")               # still plural, even for ONE book
def get_book(slug: str):
    book = BOOKS.get(slug)
    if not book:
        raise HTTPException(status_code=404, detail="Book not found")
    return book

app = FastAPI()
app.include_router(v1)
```

```bash
curl localhost:8000/v1/books
curl localhost:8000/v1/books/harry-potter
```

## 5. Idempotency: The Concept That Decides Your HTTP Method

**Idempotency** means performing the same action multiple times has the same effect as performing it once.

For REST, this is about the **side effect on the server**. It does not matter whether you call an endpoint once or a thousand times: the resulting server state caused by *your request* must be the same.

### 5.1 The Five Major Methods

`GET`, `POST`, `PUT`, `PATCH`, `DELETE`. (`HEAD` fetches headers only; `OPTIONS` is used in the CORS flow to find out whether an origin is allowed.)

### 5.2 `GET`: Idempotent

A `GET` only retrieves data and causes no change on the server. Someone else might create a new book between your calls and change the response, but that is not *your* side effect. Idempotency is about what your call changes, and `GET` changes nothing.

### 5.3 `PUT` and `PATCH`: Idempotent

Both update data:

- **`PATCH`**: partial update. Send only the fields you want to change (e.g., just `name`).
- **`PUT`**: full replacement. Send the complete representation, and the server replaces the stored one with your payload.

In practice people use them interchangeably, and that is tolerable for an internal API. For a **public API**, stick to the semantics: other engineers will assume you follow the standard, and violating it creates wrong assumptions and confusion. **Partial update means PATCH; full replacement means PUT.**

Why they're idempotent: change a user's name from `A` to `B`. The first call produces `A → B`. The second call, with the same payload, produces `B → B`. A million calls later the state is still `B`. No new side effect appears.

```python
from datetime import datetime, timezone
from pydantic import BaseModel

class UserReplace(BaseModel):          # PUT: ALL client-controlled fields required
    name: str
    email: str

class UserPatch(BaseModel):            # PATCH: every field optional
    name: str | None = None
    email: str | None = None

USERS = {"1": {"id": "1", "name": "A", "email": "a@x.com", "created_at": "2025-01-01T00:00:00Z"}}

@v1.put("/users/{user_id}")
def replace_user(user_id: str, body: UserReplace):
    existing = USERS.get(user_id)
    if not existing:
        raise HTTPException(404, "User not found")
    # Full replacement of the representation; id/created_at are server-owned
    USERS[user_id] = {**body.model_dump(), "id": user_id, "created_at": existing["created_at"]}
    return USERS[user_id]

@v1.patch("/users/{user_id}")
def update_user(user_id: str, body: UserPatch):
    existing = USERS.get(user_id)
    if not existing:
        raise HTTPException(404, "User not found")
    existing.update(body.model_dump(exclude_unset=True))   # only the fields that were sent
    return existing
```

`exclude_unset=True` is the key detail that makes `PATCH` partial: only fields the client actually sent are applied.

Repeat the same request and the state stays the same:

```bash
curl -X PATCH localhost:8000/v1/users/1 -H "Content-Type: application/json" -d '{"name":"B"}'
curl -X PATCH localhost:8000/v1/users/1 -H "Content-Type: application/json" -d '{"name":"B"}'  # same final state
```

### 5.4 `DELETE`: Idempotent (Subtle!)

Delete user `1`. The first call deletes it. The second call finds nothing, so the server returns **404**. Did the second call cause a side effect? No. The first call changed the state; every later call just checks, finds the user missing, and returns an error. Calling it a million times yields the same error a million times with no state change, so `DELETE` is idempotent. (The *response* differs between the first and second calls, but idempotency concerns **server state**, not the response.)

```python
@v1.delete("/users/{user_id}", status_code=204)
def delete_user(user_id: str):
    if user_id not in USERS:
        raise HTTPException(404, "User not found")   # 2nd, 3rd, ... call lands here
    del USERS[user_id]                               # only the 1st call changes state
```

### 5.5 `POST`: NOT Idempotent

`POST` is the only non-idempotent method. Create a book with a name, description, weight, and dimensions. The server inserts a row with a database-generated ID (UUID or serial). Replay the exact same request (say you re-run the same cURL) and the server inserts *another* book with the same properties but a **different ID**. (If you enforce a unique name, you'd get an error instead, but in the real world books can share names; we tell them apart by ID.) Call it 1,000 times and you get 1,000 books. The side effect changes with every call, so it's non-idempotent.

```python
import uuid

BOOKS_DB: dict[str, dict] = {}

class BookCreate(BaseModel):
    title: str
    description: str | None = None

@v1.post("/books", status_code=201)
def create_book(body: BookCreate):
    book_id = str(uuid.uuid4())                # new ID on EVERY call -> new side effect
    BOOKS_DB[book_id] = {"id": book_id, **body.model_dump()}
    return BOOKS_DB[book_id]
```

### 5.6 Summary Table

| Method | Typical use | Idempotent? |
|---|---|---|
| GET | Fetch | Yes |
| PUT | Full replace | Yes |
| PATCH | Partial update | Yes |
| DELETE | Delete | Yes |
| POST | Create / custom actions | **No** |

### 5.7 Custom (Non-CRUD) Actions: Use `POST`

What if the operation isn't fetch, create, update, or delete? For example, **"send email"**: you tell the server to perform an action, with the payload `{"target": "someone@example.com"}`. The REST spec deliberately made `POST` **open-ended**: whenever an action doesn't fit any other method, use `POST`.

```python
from pydantic import BaseModel, EmailStr   # pip install "pydantic[email]"

class SendEmail(BaseModel):
    target: EmailStr

@v1.post("/emails/send")
def send_email(body: SendEmail):
    # ... call your mail provider here ...
    return {"status": "sent", "target": body.target}
```

## 6. Where to Start When Designing an API

Before writing any business logic, **design the interface first**. A good interface is intuitive, delightful to use, and not vague. It follows REST standards to eliminate confusion, assumptions, and human error.

### 6.1 Why Standards Matter

Suppose you ignore the standards: `POST` for fetching, `DELETE` for reading, and so on. A consumer then has only two ways to learn your API's behavior (success cases, error cases, payload shapes, methods): **read your code** (only possible if it's open source or inside your organization) or **trial and error**. That leaves a lot of room for mistakes.

If you follow standards, even ~80% of the way, consumers can guess most behavior correctly. Integration time drops, there are fewer bugs, fewer confusing sync calls, and, together with good documentation and an interactive API playground, almost no guesswork.

### 6.2 The Workflow

1. **Start from the UI design** (Figma or another wireframing tool, plus product requirements). The wireframes show how end users will interact with data. You can see how the first level of consumption (users) relates to the lowest level (the database), skipping the middlemen (the frontend and the platform).
2. **Identify the resources: the nouns.** From wireframes and conversations with product people and clients, list the nouns. (It's an oversimplification, but a good rule of thumb.)
3. **Design the database schema.** (Covered in a separate video; here we do it quickly.)
4. **List the actions** clients need to perform. Start from CRUD: list, get one, create, update, delete.
5. **Design the API interface**, using an API client such as Insomnia (a lighter alternative to Postman). We are designing the *interface* (what clients see), not the *execution* (language, business logic, database calls).

### 6.3 Example: A Project Management SaaS (Jira/Linear-like)

Nouns found in the requirements: **projects, users, organizations, tasks, tags**.

For this walkthrough, our schema has three tables:

- `organizations`: all organizations on the platform
- `projects`: projects within an organization
- `tasks`: tasks created inside a project

We'll design the API for **organizations** in detail (the same pattern applies to projects and tasks), with these actions: create, list all, get one, update, delete.

## 7. Implementing the Organization API in FastAPI

### 7.1 The Domain Model

The organization has `id`, `name`, `status`, `description`, `created_at`, `updated_at`. Three of those, **`id`, `created_at`, and `updated_at`, are handled by the server**, so they are *excluded* from the create payload. The client sends only `name`, `status`, and `description`.

```python
# main.py
from __future__ import annotations

import math
import uuid
from datetime import datetime, timezone
from enum import Enum
from typing import Generic, TypeVar

from fastapi import APIRouter, FastAPI, HTTPException, Query, Response
from pydantic import BaseModel, Field


class OrgStatus(str, Enum):
    active = "active"
    inactive = "inactive"


# ---------- Request schemas (what the CLIENT may send) ----------
class OrganizationCreate(BaseModel):
    name: str = Field(min_length=1, max_length=120)
    status: OrgStatus = OrgStatus.active
    description: str | None = None


class OrganizationReplace(OrganizationCreate):
    """PUT body: the complete client-controlled representation."""


class OrganizationPatch(BaseModel):
    """PATCH body: any subset of fields."""
    name: str | None = Field(default=None, min_length=1, max_length=120)
    status: OrgStatus | None = None
    description: str | None = None


# ---------- Response schemas (what the SERVER returns) ----------
class Organization(BaseModel):
    id: str
    name: str
    status: OrgStatus
    description: str | None
    created_at: datetime
    updated_at: datetime


T = TypeVar("T")


class Page(BaseModel, Generic[T]):
    data: list[T]
    total: int          # total rows in the DB, independent of this page
    page: int           # which page this response represents
    total_pages: int    # how many pages exist for the given limit
```

Separating request schemas from response schemas is what stops clients from setting `id` or `created_at`. Pydantic simply ignores or rejects fields that aren't declared.

### 7.2 The Router and an In-Memory Store

We use a dictionary instead of a real database to keep the example runnable; swap it for SQLAlchemy or any ORM later without changing the interface.

```python
router = APIRouter(prefix="/organizations", tags=["organizations"])  # plural resource

ORGS: dict[str, dict] = {}


def now() -> datetime:
    return datetime.now(timezone.utc)
```

### 7.3 Create Organization: `POST /organizations` → 201

The server differentiates `GET /organizations` and `POST /organizations` by **HTTP method**, even though the URL is identical: `POST` goes to the create handler, `GET` to the list handler.

On success we return **`201 Created`** and the newly created entity as-is in the body (so the client immediately receives the server-generated `id` and `created_at`).

```python
@router.post("", response_model=Organization, status_code=201)
def create_organization(body: OrganizationCreate):
    ts = now()
    org = {
        "id": str(uuid.uuid4()),      # server-generated
        "created_at": ts,             # server-generated
        "updated_at": ts,             # server-generated
        **body.model_dump(),
    }
    ORGS[org["id"]] = org
    return org
```

Try it:

```bash
curl -i -X POST localhost:8000/organizations \
  -H "Content-Type: application/json" \
  -d '{"name":"Org 1","status":"active","description":"Some description"}'
```

```
HTTP/1.1 201 Created
{
  "id": "5b0e...",
  "name": "Org 1",
  "status": "active",
  "description": "Some description",
  "created_at": "2025-01-01T10:00:00Z",
  "updated_at": "2025-01-01T10:00:00Z"
}
```

### 7.4 Pagination: Theory

Before writing the list endpoint, consider why we need pagination.

A list endpoint returns many records. Without pagination:

1. **Serialization cost**: serializing 1,000 organizations into a JSON payload is a resource-heavy operation on the server and adds latency.
2. **Perceived delay for the user**: if the response takes 3–4 seconds because the client fetched 1,000 organizations, the end user notices, even though on first view they'd only see 10–20 of them. They'd need to scroll to see more.
3. **Network overhead**: you ship data nobody looks at yet.

**Pagination** returns only a portion of the data per request, usually sorted by some field such as `created_at` (latest first). When the user clicks "page 2" (or scrolls, for infinite scroll), the client makes another call asking for the next portion. Server, network, and client all perform better, and users aren't overwhelmed.

**The paginated response shape:**

| Field | Meaning | Use |
|---|---|---|
| `data` | The portion of records for this page | Render the list |
| `total` | Total count of records in the database (independent of the page) | Show "10 of 50" |
| `page` | The page this response represents | Show the current page |
| `total_pages` | How many pages exist at this limit | Pagination UI; for infinite scroll, stop fetching when `page == total_pages` |

**Query parameters** (it's a `GET`, so input goes in the query string):

- `limit`: how many items per page
- `page`: which page to return

If the client sends neither, the **server must apply defaults**: `page=1` and `limit=10` (or 20).

### 7.5 List Organizations: `GET /organizations` → 200

Success for a fetch is `200 OK`.

```python
@router.get("", response_model=Page[Organization])
def list_organizations(
    page: int = Query(1, ge=1, description="Page number, starting at 1"),
    limit: int = Query(10, ge=1, le=100, description="Items per page"),
):
    # Sort by created_at, latest first
    ordered = sorted(ORGS.values(), key=lambda o: o["created_at"], reverse=True)

    total = len(ordered)
    total_pages = math.ceil(total / limit) if total else 0

    start = (page - 1) * limit
    end = start + limit

    return Page[Organization](
        data=ordered[start:end],
        total=total,
        page=page,
        total_pages=total_pages,
    )
```

The slice `[(page-1)*limit : page*limit]` is the heart of pagination. The `ge`/`le` validators make FastAPI return `422` for nonsense values like `page=0` or `limit=100000`, which also protects your server from abuse.

### 7.6 Pagination Walkthrough with 5 Organizations

Create five organizations (`Org 1` … `Org 5`) and list them with no parameters. The defaults (`page=1`, `limit=10`) return all five. Now apply `limit=2`:

```bash
curl "localhost:8000/organizations?limit=2&page=1"
```

```json
{
  "data": [ {"name": "Org 5", "...": "..."}, {"name": "Org 4", "...": "..."} ],
  "total": 5,
  "page": 1,
  "total_pages": 3
}
```

- `data` has **Org 5 and Org 4**: sorted by `created_at`, latest first.
- `total` is **5**: the whole table, even though only two rows are returned.
- `page` is **1** and `total_pages` is **3**, because 5 items at 2 per page is 2 + 2 + 1.

| Request | `data` | `total` | `page` | `total_pages` |
|---|---|---|---|---|
| `?limit=2&page=1` | Org 5, Org 4 | 5 | 1 | 3 |
| `?limit=2&page=2` | Org 3, Org 2 | 5 | 2 | 3 |
| `?limit=2&page=3` | Org 1 | 5 | 3 | 3 |

Visually, with the full ordered list `[5, 4 | 3, 2 | 1]`, each page is one slice of it. On the last page there's a single entry, and `page == total_pages` tells the client that nothing more remains.

If you remove both parameters, the server falls back to the defaults and returns all five (because the default limit of 10 exceeds 5). **Always set defaults on the server.**

### 7.7 Get One, Update, and Delete

These complete the five actions identified earlier. Note again that the resource segment stays plural (`/organizations/{id}`).

```python
def _get_or_404(org_id: str) -> dict:
    org = ORGS.get(org_id)
    if org is None:
        raise HTTPException(status_code=404, detail="Organization not found")
    return org


@router.get("/{org_id}", response_model=Organization)
def get_organization(org_id: str):
    return _get_or_404(org_id)


@router.put("/{org_id}", response_model=Organization)
def replace_organization(org_id: str, body: OrganizationReplace):
    """Full replacement of the representation (idempotent)."""
    org = _get_or_404(org_id)
    org.update(body.model_dump())           # every client-controlled field is overwritten
    org["updated_at"] = now()
    return org


@router.patch("/{org_id}", response_model=Organization)
def update_organization(org_id: str, body: OrganizationPatch):
    """Partial update (idempotent)."""
    org = _get_or_404(org_id)
    org.update(body.model_dump(exclude_unset=True))   # only fields actually sent
    org["updated_at"] = now()
    return org


@router.delete("/{org_id}", status_code=204)
def delete_organization(org_id: str):
    """Idempotent in effect: 1st call deletes, later calls 404 with no state change."""
    _get_or_404(org_id)
    del ORGS[org_id]
    return Response(status_code=204)


# ---------- App wiring with versioning ----------
app = FastAPI(title="Project Management API")
app.include_router(router)                      # local demo: no version prefix
# In production, mount under a version: app.include_router(router, prefix="/v1")
```

## 8. A Quick Test Script (Verifying Idempotency Yourself)

Here's a small script that demonstrates the idempotency table with real calls:

```python
# check_idempotency.py  (pip install httpx)
import httpx

c = httpx.Client(base_url="http://localhost:3000")

# POST is NOT idempotent: two identical calls -> two resources
payload = {"name": "Acme", "status": "active", "description": "demo"}
a = c.post("/organizations", json=payload).json()
b = c.post("/organizations", json=payload).json()
print("POST ids differ:", a["id"] != b["id"])                       # True

# PATCH IS idempotent: repeating it leaves the same state
r1 = c.patch(f"/organizations/{a['id']}", json={"name": "B"}).json()
r2 = c.patch(f"/organizations/{a['id']}", json={"name": "B"}).json()
print("PATCH same state:", r1["name"] == r2["name"] == "B")         # True

# DELETE: first 204, then 404, but the server state doesn't change after the first
print(c.delete(f"/organizations/{a['id']}").status_code)            # 204
print(c.delete(f"/organizations/{a['id']}").status_code)            # 404
```

## 9. Cheat Sheet: The Rules in One Place

**URL design**
- Subdomain `api.`, versioning like `/v1`, then the resource.
- Resource names are **plural nouns**, even when addressing a single item (`/books/42`).
- **Lowercase** only; **no spaces, no underscores**; use hyphens in slugs (`harry-potter`).
- `/` means hierarchy: collection → item.

**Methods**
- `GET` fetches (idempotent).
- `POST` creates and is the home for custom actions (non-idempotent).
- `PUT` fully replaces (idempotent).
- `PATCH` partially updates (idempotent).
- `DELETE` removes (idempotent).

**Responses**
- Creation returns **201** with the created entity, including server-generated `id` and timestamps.
- Successful fetches return **200**.
- Missing entity returns **404**.
- List endpoints are **paginated** (`data`, `total`, `page`, `total_pages`), with `page` and `limit` query parameters and server-side defaults.

**Workflow**
1. Wireframes and requirements
2. Identify resource nouns
3. DB schema
4. List the CRUD (and custom) actions
5. Design the interface, then implement the business logic
