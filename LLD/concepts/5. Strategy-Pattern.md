# Strategy Design Pattern in Python

## What Are Design Patterns, and Why Should You Care?

When you're building applications, you'll keep running into the same kinds of problems. Here's the thing — you're not the first one. Thousands of developers faced these exact same problems before you, and the smart ones wrote down their solutions. Those documented solutions are **design patterns**.

Every design pattern is essentially saying one thing in different ways:

> Some parts of your code will change constantly. Other parts won't. Separate them.

Keep the changing parts isolated from the stable parts. That way, when your application evolves — and it always will — adding a new feature touches only the part that's supposed to change, leaving everything else untouched. Minimal code changes, minimal risk.

There are officially 23 design patterns. Today we're covering one of the most important and commonly used ones: the **Strategy Pattern**.

## The Problem: A Robot Simulator

Let's say we're building an application that simulates different kinds of robots. Each robot can:

- **Walk**
- **Talk**
- **Be displayed** (its visual projection — what it looks like on screen)

The natural first instinct is to model this with a class hierarchy using inheritance.

```python
from abc import ABC, abstractmethod

class Robot(ABC):
    def walk(self):
        print("Walking normally")

    def talk(self):
        print("Talking normally")

    @abstractmethod
    def projection(self):
        pass
```

We have two robot types to start with:

```python
class CompanionRobot(Robot):
    def projection(self):
        print("Displaying CompanionRobot")

class WorkerRobot(Robot):
    def projection(self):
        print("Displaying WorkerRobot")
```

Clean. Simple. No problems yet.

## When Inheritance Starts Breaking Down

Now a new robot arrives — the `SparrowRobot`. It can walk, talk, *and fly*. Easy enough:

```python
class SparrowRobot(Robot):
    def fly(self):
        print("Flying with wings")

    def projection(self):
        print("Displaying SparrowRobot")
```

Then a `CrowRobot` arrives. It also flies — with the same wing-based flying logic:

```python
class CrowRobot(Robot):
    def fly(self):
        print("Flying with wings")  # exact same code as SparrowRobot

    def projection(self):
        print("Displaying CrowRobot")
```

You've just copy-pasted the `fly` method. This breaks the **DRY principle** — Don't Repeat Yourself. The same logic now lives in two places. Change one, forget the other, and you have a bug.

Your first fix: move `fly` up to the parent `Robot` class. But now *every* robot can fly, including `CompanionRobot` and `WorkerRobot`, which definitely shouldn't.

Your second fix: add an intermediate class.

```python
class FlyableRobot(Robot):
    def fly(self):
        print("Flying with wings")

class SparrowRobot(FlyableRobot):
    def projection(self):
        print("Displaying SparrowRobot")

class CrowRobot(FlyableRobot):
    def projection(self):
        print("Displaying CrowRobot")
```

Now a `JetRobot` shows up. It flies — but with a jet engine, not wings. It needs its own `fly` logic, so you override it:

```python
class JetRobot(FlyableRobot):
    def fly(self):
        print("Flying with jet engine")  # override

    def projection(self):
        print("Displaying JetRobot")
```

Then `JetRobot2`, `JetRobot3`... all with the same jet flying code. DRY violation again. So you split further:

```python
class FlyWithWings(FlyableRobot): ...
class FlyWithJet(FlyableRobot): ...
```

And it keeps going. Some robots can't walk. Some can't talk. Now you need `WalkableRobot`, `NonWalkableRobot`, `TalkableRobot`, `NonTalkableRobot` — and every combination of these. The hierarchy explodes into a combinatorial mess.

There's a famous line that captures this perfectly:

> **The solution to inheritance is not more inheritance.**

## The Strategy Pattern: Extract What Changes

Here's what the Strategy Pattern says:

> **Define a family of algorithms, put each one in a separate class, so they can be swapped at runtime.**

The key insight: `walk`, `talk`, and `fly` are the parts that *change*. `projection` is the part that *doesn't* — each robot displays itself differently, and that's always handled by the subclass. So we extract the changing parts.

**Step 1: Create an interface (abstract class) for each behavior.**

```python
from abc import ABC, abstractmethod

class Walkable(ABC):
    @abstractmethod
    def walk(self):
        pass

class Talkable(ABC):
    @abstractmethod
    def talk(self):
        pass

class Flyable(ABC):
    @abstractmethod
    def fly(self):
        pass
```

**Step 2: Create concrete implementations of each behavior.**

```python
# Walking behaviors
class NormalWalk(Walkable):
    def walk(self):
        print("Walking normally")

class NoWalk(Walkable):
    def walk(self):
        print("Cannot walk")

# Talking behaviors
class NormalTalk(Talkable):
    def talk(self):
        print("Talking normally")

class NoTalk(Talkable):
    def talk(self):
        print("Cannot talk")

# Flying behaviors
class NormalFly(Flyable):
    def fly(self):
        print("Flying with wings")

class NoFly(Flyable):
    def fly(self):
        print("Cannot fly")

class JetFly(Flyable):
    def fly(self):
        print("Flying with jet engine")
```

**Step 3: The Robot class uses composition, not inheritance, for these behaviors.**

```python
from abc import ABC, abstractmethod

class Robot(ABC):
    def __init__(self, walk_behavior: Walkable, talk_behavior: Talkable, fly_behavior: Flyable):
        self._walk_behavior = walk_behavior
        self._talk_behavior = talk_behavior
        self._fly_behavior = fly_behavior

    def walk(self):
        self._walk_behavior.walk()

    def talk(self):
        self._talk_behavior.talk()

    def fly(self):
        self._fly_behavior.fly()

    @abstractmethod
    def projection(self):
        pass
```

The `Robot` class doesn't *know* how to walk, talk, or fly. It delegates — hands the request off to whoever holds that responsibility. The robot itself is a dumb object: it owns references to the behavior objects and just forwards calls to them.

**Step 4: Create robot types.**

```python
class CompanionRobot(Robot):
    def projection(self):
        print("Displaying CompanionRobot")

class WorkerRobot(Robot):
    def projection(self):
        print("Displaying WorkerRobot")
```

**Step 5: Compose robots at runtime.**

```python
companion = CompanionRobot(
    walk_behavior=NormalWalk(),
    talk_behavior=NormalTalk(),
    fly_behavior=NoFly()
)

worker = WorkerRobot(
    walk_behavior=NormalWalk(),
    talk_behavior=NoTalk(),
    fly_behavior=NormalFly()
)

companion.walk()   # Walking normally
companion.talk()   # Talking normally
companion.fly()    # Cannot fly

worker.walk()      # Walking normally
worker.talk()      # Cannot talk
worker.fly()       # Flying with wings
```

Now if a jet-flying robot appears, you add one class — `JetFly` — and pass it in. The `Robot` class doesn't change. The existing robots don't change. You've extended behavior without modifying existing code. That's the Open-Closed Principle in action.

## Eliminating Inheritance Entirely

You might have noticed: `CompanionRobot` and `WorkerRobot` still inherit from `Robot`. If `projection` is also a changing behavior, we can extract it too:

```python
class Projectable(ABC):
    @abstractmethod
    def project(self):
        pass

class CompanionProjection(Projectable):
    def project(self):
        print("Displaying CompanionRobot")

class WorkerProjection(Projectable):
    def project(self):
        print("Displaying WorkerRobot")
```

Now `Robot` becomes a fully concrete class:

```python
class Robot:
    def __init__(
        self,
        walk_behavior: Walkable,
        talk_behavior: Talkable,
        fly_behavior: Flyable,
        projection_behavior: Projectable
    ):
        self._walk_behavior = walk_behavior
        self._talk_behavior = talk_behavior
        self._fly_behavior = fly_behavior
        self._projection_behavior = projection_behavior

    def walk(self):
        self._walk_behavior.walk()

    def talk(self):
        self._talk_behavior.talk()

    def fly(self):
        self._fly_behavior.fly()

    def projection(self):
        self._projection_behavior.project()
```

Build any robot purely through composition:

```python
companion = Robot(
    walk_behavior=NormalWalk(),
    talk_behavior=NormalTalk(),
    fly_behavior=NoFly(),
    projection_behavior=CompanionProjection()
)
```

No subclasses. No inheritance hierarchy. Pure composition.

> **The Strategy Pattern's core message: Favor composition over inheritance.**

## The Standard Structure

In Strategy Pattern terminology:

- The **Context** (`Robot`) holds a reference to a strategy and delegates to it.
- The **Strategy** (`Walkable`, `Talkable`, `Flyable`) is the abstract interface.
- The **Concrete Strategies** (`NormalWalk`, `NoWalk`, `JetFly`, etc.) are the actual implementations.

```
Context
  ├── has-a → Strategy (abstract)
                  ├── ConcreteStrategy1
                  ├── ConcreteStrategy2
                  └── ConcreteStrategy3
```

The context calls one method on the strategy (`walk()`, `fly()`, etc.). The concrete strategy decides exactly what that means.

## Real-World Examples

**Payment System**

```python
class PaymentStrategy(ABC):
    @abstractmethod
    def pay(self, amount: float):
        pass

class UPIPayment(PaymentStrategy):
    def pay(self, amount: float):
        print(f"Paying ₹{amount} via UPI")

class CreditCardPayment(PaymentStrategy):
    def pay(self, amount: float):
        print(f"Paying ₹{amount} via Credit Card")

class NetBankingPayment(PaymentStrategy):
    def pay(self, amount: float):
        print(f"Paying ₹{amount} via Net Banking")

class PaymentProcessor:
    def __init__(self, strategy: PaymentStrategy):
        self._strategy = strategy

    def process(self, amount: float):
        self._strategy.pay(amount)
```

**Sorting System**

```python
class SortStrategy(ABC):
    @abstractmethod
    def sort(self, data: list) -> list:
        pass

class QuickSort(SortStrategy):
    def sort(self, data: list) -> list:
        # quicksort implementation
        return sorted(data)  # placeholder

class MergeSort(SortStrategy):
    def sort(self, data: list) -> list:
        # mergesort implementation
        return sorted(data)  # placeholder

class Sorter:
    def __init__(self, strategy: SortStrategy):
        self._strategy = strategy

    def sort(self, data: list) -> list:
        return self._strategy.sort(data)
```

Same structural idea: swap the algorithm without touching the context.

## Summary

| Problem with Inheritance | How Strategy Pattern Solves It |
|---|---|
| Code duplication across subclasses | Each behavior lives in exactly one class |
| Hierarchy explodes with new combinations | Compose behaviors freely, no new hierarchy needed |
| Changing behavior requires changing base class | Add a new concrete strategy class, touch nothing else |
| Violates Open-Closed Principle | Open for extension (new strategy), closed for modification |

The one-line takeaway: **favor composition over inheritance**. When behavior varies, extract it into a strategy. Let the context own a reference to it and delegate. Your application becomes something you can extend without fear.
