## 0. Setup: Shared Code for Part 2

Part 2's code makes two changes to Part 1's models, based on rules from this half of the video:

1. **JSON fields are camelCase** (`createdAt`, `totalPages`, `organizationId`). Part 1 used snake_case, which is idiomatic Python but not the JSON convention. Section 7 explains why; here we fix it once with a base model.
2. **Organization status is `active` / `archived`**, which is the pair the demo uses.

```python
# main.py
import math
import uuid
from datetime import datetime, timezone
from enum import Enum
from typing import Any, Generic, TypeVar

from fastapi import APIRouter, BackgroundTasks, FastAPI, HTTPException, Query, Response
from pydantic import BaseModel, ConfigDict, Field
from pydantic.alias_generators import to_camel


class CamelModel(BaseModel):
    """Python code uses snake_case; the JSON on the wire is camelCase."""
    model_config = ConfigDict(alias_generator=to_camel, populate_by_name=True)


# ---------- Enums ----------
class OrgStatus(str, Enum):
    active = "active"
    archived = "archived"


class ProjectStatus(str, Enum):          # values are an assumption for the demo
    planned = "planned"
    active = "active"
    completed = "completed"
    archived = "archived"


class SortOrder(str, Enum):
    ascending = "ascending"
    descending = "descending"


# ---------- Organization schemas ----------
class OrganizationCreate(CamelModel):
    name: str = Field(min_length=1, max_length=120)
    status: OrgStatus = OrgStatus.active          # sane default (see section 8)
    description: str | None = None


class OrganizationPatch(CamelModel):              # every field optional
    name: str | None = Field(default=None, min_length=1, max_length=120)
    status: OrgStatus | None = None
    description: str | None = None


class Organization(CamelModel):
    id: str
    name: str
    status: OrgStatus
    description: str | None
    created_at: datetime
    updated_at: datetime


# ---------- Project schemas ----------
class ProjectCreate(CamelModel):
    name: str = Field(min_length=1, max_length=120)
    organization_id: str
    status: ProjectStatus = ProjectStatus.planned
    description: str | None = None


class ProjectPatch(CamelModel):
    name: str | None = Field(default=None, min_length=1, max_length=120)
    status: ProjectStatus | None = None
    description: str | None = None


class ProjectCloneOverrides(CamelModel):          # optional body for the clone action
    name: str | None = None
    description: str | None = None
    status: ProjectStatus | None = None


class Project(CamelModel):
    id: str
    name: str
    organization_id: str
    status: ProjectStatus
    description: str | None
    created_at: datetime
    updated_at: datetime


# ---------- Paginated envelope ----------
T = TypeVar("T")


class Page(CamelModel, Generic[T]):
    data: list[T]
    total: int           # all matching rows, independent of this page
    page: int
    total_pages: int


# ---------- Storage (swap for a real DB later) ----------
ORGS: dict[str, dict] = {}
PROJECTS: dict[str, dict] = {}


def now() -> datetime:
    return datetime.now(timezone.utc)


# ---------- One list pipeline shared by every list endpoint ----------
def build_page(
    items: list[dict],
    *,
    filters: dict[str, Any],
    sort_key: str,
    sort_order: SortOrder,
    page: int,
    limit: int,
) -> dict:
    # 1. filter
    for field, wanted in filters.items():
        if wanted is not None:
            items = [i for i in items if i[field] == wanted]
    # 2. sort (explicit, because a DB gives no ordering guarantee)
    items = sorted(items, key=lambda i: i[sort_key], reverse=sort_order is SortOrder.descending)
    # 3. paginate
    total = len(items)
    start = (page - 1) * limit
    return {
        "data": items[start:start + limit],
        "total": total,
        "page": page,
        "total_pages": math.ceil(total / limit) if total else 0,
    }
```

`build_page` is deliberately shared. Every list endpoint (organizations, projects, and later tasks) goes through the same filter → sort → paginate pipeline, so they behave identically. That is the consistency principle from section 7 applied in code.

## 1. Recap: Defaults Carry the Pagination Design

When the client sends no `page` or `limit`, the server still responds, with `page=1` and a default `limit` of 10 (or 20). It does not return a validation error saying "you're missing the page parameter". Sending `limit=2&page=1/2/3` over five organizations returns slices of 2 + 2 + 1. This was already built in Part 1; the next sections extend the same list endpoint with sorting and filtering.

## 2. Sorting in a List API

A list API should support sorting through **two query parameters**:

| Parameter | Meaning | Default |
|---|---|---|
| `sortBy` | The resource field to sort on (`name`, `status`, `createdAt`, ...) | `createdAt` |
| `sortOrder` | `ascending` or `descending` | `descending` |

### 2.1 Why a Default Sort Is Mandatory

The principle is that **the server should supply defaults for everything obvious** and never make the client send it. Sorting is a prime example:

- A database does **not store rows in any guaranteed sequence**. If you don't sort explicitly, the same request can return rows in a different order between calls.
- So every list endpoint must have a default sort even when the client sends nothing.
- The natural default is **`createdAt` descending**: the latest entries first. It is the obvious expectation for "list everything".

The default also applies per parameter. If the client sends `sortBy=name` but no `sortOrder`, the server still applies `descending`. That's why, in the demo, `sortBy=name` alone returned Org 5, 4, 3, 2, 1, and adding `sortOrder=ascending` flipped it to 1, 2, 3, 4, 5.

### 2.2 Implementation

Public sort values are camelCase (the wire format); we map them to internal keys:

```python
class OrgSortBy(str, Enum):
    name = "name"
    status = "status"
    createdAt = "createdAt"
    updatedAt = "updatedAt"


ORG_SORT_KEYS = {
    "name": "name",
    "status": "status",
    "createdAt": "created_at",
    "updatedAt": "updated_at",
}
```

Using an `Enum` means a nonsense `sortBy=banana` gets a `422` from FastAPI automatically, and the allowed values show up in the Swagger docs.

## 3. Filtering in a List API

Filtering lets the client narrow the list, for example a UI toggle that shows only active or only archived organizations. The convention is simple: **the parameter name is the field name**, and the value is what to match.

```
GET /organizations?status=archived      → only archived organizations
GET /organizations?status=active        → only active organizations
GET /organizations?name=Org 4           → the one organization named "Org 4"
```

You can combine filters with sorting and pagination in one request.

### 3.1 The Complete List Endpoint

```python
orgs = APIRouter(prefix="/organizations", tags=["organizations"])


@orgs.get(
    "",
    response_model=Page[Organization],
    summary="List organizations (paginated, sortable, filterable)",
)
def list_organizations(
    # pagination
    page: int = Query(1, ge=1, description="Page number, starting at 1"),
    limit: int = Query(10, ge=1, le=100, description="Items per page"),
    # sorting
    sort_by: OrgSortBy = Query(OrgSortBy.createdAt, alias="sortBy"),
    sort_order: SortOrder = Query(SortOrder.descending, alias="sortOrder"),
    # filtering
    status: str | None = Query(None, description="Filter by status"),
    name: str | None = Query(None, description="Filter by exact name"),
):
    return build_page(
        list(ORGS.values()),
        filters={"status": status, "name": name},
        sort_key=ORG_SORT_KEYS[sort_by.value],
        sort_order=sort_order,
        page=page,
        limit=limit,
    )
```

Note that `status` is typed as `str`, not `OrgStatus`. This matches the demo's behavior: filtering by a value that matches nothing returns an empty list rather than an error (see section 5). If you'd prefer strictness, type it as `OrgStatus` and invalid values will return `422` instead. Both are defensible; just be consistent.

### 3.2 Try It

Create an organization with `status: "archived"` (the demo calls it "Org 6" and gets a `201`), then:

```bash
# default: createdAt desc, so the archived org (newest) comes first
curl "localhost:3000/organizations"

# sortBy=name, sortOrder omitted → still descending
curl "localhost:3000/organizations?sortBy=name"

# ascending
curl "localhost:3000/organizations?sortBy=name&sortOrder=ascending"

# only archived
curl "localhost:3000/organizations?status=archived"

# only active
curl "localhost:3000/organizations?status=active"

# combined filters
curl "localhost:3000/organizations?status=active&name=Org%204"
```

The last request returns exactly one row, because only one organization is named "Org 4".

**Pagination, sorting, and filtering are the three features every list API should have.**

## 4. Single-Resource Endpoints: Get, Update, Delete

### 4.1 PATCH Over PUT for Updates

The instructor says he rarely uses `PUT` for updates, and the reasoning is historical:

- In the **multi-page application** era, replacing a whole entity from a form post was common.
- In **single-page applications**, data is JSON-heavy and clients usually send only the fields that changed. Nothing ever needs to replace the entire entity.

So `PATCH` is what you'll mostly see, and it's the better semantic fit for partial updates. Developers often use `PUT` and `PATCH` interchangeably; try to stick to the standard anyway. **Partial update → `PATCH`.**

### 4.2 The Routes Look the Same on Purpose

Get one, update one, and delete one all share the same URL shape, and **only the HTTP method differs**:

```
GET     /organizations/{id}   → fetch one
PATCH   /organizations/{id}   → partially update one
DELETE  /organizations/{id}   → delete one
```

The same applies to the collection pair: `POST /organizations` (create) and `GET /organizations` (list) share a URL and differ by method. The server routes by method: `POST` goes to the create handler, `GET` to the list handler.

The `{id}` is a **dynamic path parameter** (a string the client fills in), and it makes the path hierarchical: collection → one item.

### 4.3 Implementation

```python
def get_org_or_404(org_id: str) -> dict:
    org = ORGS.get(org_id)
    if org is None:
        raise HTTPException(status_code=404, detail="Organization not found")
    return org


@orgs.post("", response_model=Organization, status_code=201)
def create_organization(body: OrganizationCreate):
    ts = now()
    org = {
        "id": str(uuid.uuid4()),
        "created_at": ts,
        "updated_at": ts,
        **body.model_dump(),
    }
    ORGS[org["id"]] = org
    return org


@orgs.get("/{org_id}", response_model=Organization)
def get_organization(org_id: str):
    return get_org_or_404(org_id)                       # 200


@orgs.patch("/{org_id}", response_model=Organization)
def update_organization(org_id: str, body: OrganizationPatch):
    org = get_org_or_404(org_id)
    org.update(body.model_dump(exclude_unset=True))     # only fields the client sent
    org["updated_at"] = now()
    return org                                          # 200 + the updated entity


@orgs.delete("/{org_id}", status_code=204, response_class=Response)
def delete_organization(org_id: str):
    get_org_or_404(org_id)
    del ORGS[org_id]
    # 204: success, nothing to send back
```

### 4.4 Walkthrough and Status Codes

**Update** (flip Org 6 from `archived` to `active`):

```bash
curl -i -X PATCH localhost:3000/organizations/<ID> \
  -H "Content-Type: application/json" -d '{"status":"active"}'
```

- Status **`200 OK`**. Nothing was created, so it is not `201`; the call just succeeded.
- The body is the **full updated entity**, so the client can immediately render the new state.
- Listing again shows Org 6 as `active`.

**Get one:**

```bash
curl -i localhost:3000/organizations/<ID>      # 200 + the organization
```

**Delete:**

```bash
curl -i -X DELETE localhost:3000/organizations/<ID>
```

- Status **`204 No Content`**, with an empty body.
- Meaning: the operation succeeded (it's in the `2xx` family), but there's nothing to send back. You deleted the thing, so there is no information about it to return. This is the standard response to a successful delete.

**After the delete:**

- `GET /organizations` no longer includes Org 6 (the list now ends at Org 5).
- `GET /organizations/<ID>` returns **`404`** with an error message ("Organization not found").

## 5. 404 vs. Empty List: An Important Distinction

Both cases look like "no data", but they mean different things.

| Situation | Response |
|---|---|
| Client asks for **one specific resource** that doesn't exist (`GET /organizations/<deleted-id>`) | **`404 Not Found`** |
| Client asks for a **list** and nothing matches (empty table, or a filter that matches nothing) | **`200 OK`** with an empty array |

A 404 means "the particular entity you named doesn't exist". A list request doesn't name a particular entity; it asks for *whatever matches*, and "nothing" is a valid answer.

```bash
curl -i "localhost:3000/organizations?status=banana"
```

```
HTTP/1.1 200 OK
{ "data": [], "total": 0, "page": 1, "totalPages": 0 }
```

**Rule of thumb:** list endpoint with no data → empty array and `200`. `404` only when the client requests a specific entity that does not exist.

That covers **CRUD**: **C**reate (`POST`), **R**ead (both list and get-one), **U**pdate (`PATCH`), **D**elete (`DELETE`).

## 6. Custom Actions

### 6.1 Why `archive` Is Not Just a `PATCH`

Suppose the client wants to archive Org 5. It looks like an update, since `status` goes from `active` to `archived`. So why not `PATCH {"status": "archived"}`?

Because archiving is a **business operation**, not a field edit. Archiving an organization may require the server to:

- archive or remove all projects inside the organization,
- remove or archive all tasks inside those projects,
- notify the organization's users by email.

Updating the `status` field alone doesn't do any of that. If a client could `PATCH` the status to `archived` directly, you'd get archived organizations whose projects and users were never handled, and every client would need to know the cascade rules. So we model it as an explicit **custom action** and keep the logic on the server.

### 6.2 Custom Actions Use `POST`

Anything that isn't create, read, update, or delete goes to `POST`, the open-ended method (Part 1, section 5.7). The URL pattern:

```
POST /organizations/{id}/archive
      └──────┬──────┘ └─┬┘ └──┬──┘
        collection    one    action
```

It reads as a clean hierarchy: *all organizations → this particular organization → perform this action on it.* The action name is a verb at the end of the path. That's the one place a verb is acceptable, since there's no noun-based CRUD method that fits.

### 6.3 Implementation

```python
def notify_org_members(org_id: str) -> None:
    # stand-in for sending emails / notifications
    print(f"[email] Organization {org_id} was archived")


@orgs.post("/{org_id}/archive", response_model=Organization)
def archive_organization(org_id: str, background: BackgroundTasks):
    org = get_org_or_404(org_id)

    org["status"] = OrgStatus.archived
    org["updated_at"] = now()

    # Side effects that a plain PATCH of "status" would never perform:
    for project in PROJECTS.values():
        if project["organization_id"] == org_id:
            project["status"] = ProjectStatus.archived
            project["updated_at"] = now()
            # ...also archive/remove this project's tasks here...
    background.add_task(notify_org_members, org_id)    # run after the response is sent

    return org                                         # 200
```

Result: the response is the organization with `"status": "archived"`.

### 6.4 `POST` Does Not Always Mean `201`

The archive call returns **`200`**, not `201`, because nothing was created. Don't assume "POST → 201":

- `POST /organizations` creates → `201`
- `POST /organizations/{id}/archive` performs an action and creates nothing → `200`

**Match the status code to what happened, not to the HTTP method.** (The clone action below shows the opposite case: a custom action that does create something, so it returns `201`.)

## 7. Applying the Same Patterns to Projects

The video repeats the whole exercise for a second resource so the patterns become second nature. The lesson is that **the patterns don't change; only the resource does.** Task endpoints would look the same.

### 7.1 Endpoint Map

| Action | Method & route | Success |
|---|---|---|
| Create project | `POST /projects` | `201` + entity |
| List projects | `GET /projects` | `200` + page |
| Get one | `GET /projects/{id}` | `200` |
| Update | `PATCH /projects/{id}` | `200` + updated entity |
| Delete | `DELETE /projects/{id}` | `204` |
| Clone (custom action) | `POST /projects/{id}/clone` | `201` + new entity |

### 7.2 The Create Payload and JSON Casing

The create body accepts `name`, `organizationId`, `status`, and `description`. `id`, `createdAt`, and `updatedAt` are server-handled, so they are **not** accepted from the client. Remember `ProjectStatus.planned` is the server default, so the client may omit `status`.

```json
{
  "name": "Project 1",
  "organizationId": "5b0e...",
  "status": "planned",
  "description": "Some description"
}
```

**JSON payloads, requests *and* responses, use camelCase.** This is the near-universal JSON convention (`organizationId`, not `organization_id` or `OrganizationID`). Because it's an established pattern, clients don't have to guess. In our code, `CamelModel` handles this automatically: Python stays snake_case and the wire format is camelCase.

### 7.3 Implementation

```python
projects = APIRouter(prefix="/projects", tags=["projects"])   # plural, lowercase

PROJECT_SORT_KEYS = {
    "name": "name",
    "status": "status",
    "createdAt": "created_at",
    "updatedAt": "updated_at",
}


class ProjectSortBy(str, Enum):
    name = "name"
    status = "status"
    createdAt = "createdAt"
    updatedAt = "updatedAt"


def get_project_or_404(project_id: str) -> dict:
    project = PROJECTS.get(project_id)
    if project is None:
        raise HTTPException(status_code=404, detail="Project not found")
    return project


@projects.post("", response_model=Project, status_code=201)
def create_project(body: ProjectCreate):
    # Production note: verify organization_id exists before inserting.
    # The demo uses an arbitrary ID to keep the focus on the interface.
    ts = now()
    project = {"id": str(uuid.uuid4()), "created_at": ts, "updated_at": ts, **body.model_dump()}
    PROJECTS[project["id"]] = project
    return project


@projects.get("", response_model=Page[Project])
def list_projects(
    page: int = Query(1, ge=1),
    limit: int = Query(10, ge=1, le=100),
    sort_by: ProjectSortBy = Query(ProjectSortBy.createdAt, alias="sortBy"),
    sort_order: SortOrder = Query(SortOrder.descending, alias="sortOrder"),
    status: str | None = Query(None),
    name: str | None = Query(None),
    organization_id: str | None = Query(None, alias="organizationId"),
):
    return build_page(
        list(PROJECTS.values()),
        filters={"status": status, "name": name, "organization_id": organization_id},
        sort_key=PROJECT_SORT_KEYS[sort_by.value],
        sort_order=sort_order,
        page=page,
        limit=limit,
    )


@projects.get("/{project_id}", response_model=Project)
def get_project(project_id: str):
    return get_project_or_404(project_id)


@projects.patch("/{project_id}", response_model=Project)
def update_project(project_id: str, body: ProjectPatch):
    project = get_project_or_404(project_id)
    project.update(body.model_dump(exclude_unset=True))
    project["updated_at"] = now()
    return project


@projects.delete("/{project_id}", status_code=204, response_class=Response)
def delete_project(project_id: str):
    get_project_or_404(project_id)
    del PROJECTS[project_id]
```

### 7.4 Walkthrough (as in the demo)

1. Create Project 1, 2, 3 → each returns `201`.
2. `GET /projects?limit=1` → one project (the newest, Project 3).
3. `GET /projects?limit=1&page=2` → Project 2 (the next slice).
4. `PATCH /projects/<id>` with `{"description": "new description"}` → `200` and the updated entity.
5. `DELETE /projects/<id>` → `204`, empty body.

Sorting and filtering work exactly as they did for organizations, because they share `build_page`.

### 7.5 The Custom Action: `clone`

Cloning a project could be simulated by the client: fetch the project, then `POST` its fields to `/projects`. But we don't know what "clone" means on the server. It may also need to:

- clone every task inside the project,
- email the project owner that their project was cloned,
- do other work the client doesn't know about.

A client calling plain create can't trigger any of that, so cloning is an explicit custom action:

```
POST /projects/{id}/clone
```

```python
def notify_project_owner(project_id: str) -> None:
    print(f"[email] Project {project_id} was cloned")


@projects.post("/{project_id}/clone", response_model=Project, status_code=201)
def clone_project(
    project_id: str,
    background: BackgroundTasks,
    overrides: ProjectCloneOverrides | None = None,    # optional body
):
    source = get_project_or_404(project_id)            # 404 if missing/deleted
    ts = now()

    clone = {
        **source,
        "id": str(uuid.uuid4()),                       # new identity
        "name": f"{source['name']} clone",
        "created_at": ts,
        "updated_at": ts,
    }
    if overrides:                                      # client may override fields
        clone.update(overrides.model_dump(exclude_unset=True, exclude_none=True))

    PROJECTS[clone["id"]] = clone
    # ...also clone the project's tasks here...
    background.add_task(notify_project_owner, source["id"])
    return clone
```

Behaviors worth noticing:

- **Cloning a deleted project returns `404 Project not found`**, because the entity doesn't exist.
- **Cloning an existing project returns `201 Created`.** This custom action *does* create a new resource, so it returns `201`, in contrast to `archive`, which returned `200`. You can't derive the status code from "it's a POST" or "it's a custom action"; it depends on what happened on the server.
- The body is optional. A clone request can be sent with no payload, or with fields the client wants to override.
- The response is the newly created project (e.g., "Project 2 clone") with all other fields copied from the source.

## 8. Principles for a Great API

The first set of principles is about **the experience of whoever integrates your API**. The consumer knows only what your interface shows them, and the second half of the video makes these points.

### 8.1 Consistency Above All

Within one platform, across all resources, keep your routes, query parameters, JSON payloads, and responses in one style:

- If `create organization` accepts a `description` field, `create project` must also call it `description`, not `desc`, `descr`, or `details`.
- If organizations use a plural route (`/organizations`), projects must use `/projects`, not `/project`.

Why this matters: a frontend engineer integrates one endpoint, then **makes assumptions** about the rest ("the project also has a name and a description, so the payload must look like this"). If your API behaves consistently, those assumptions come true and integration takes minutes. If not, they hit validation errors, then have to read docs, and then re-check every endpoint for surprises. The instructor calls consistency of style across API design one of the most important characteristics of a good backend engineer. If you can't follow the global REST standard for some reason, **follow *something* and stick to it**, and never change styles between endpoints or resources.

You can even enforce this in code. Shared `build_page`, `CamelModel`, `SortOrder`, and a shared error shape are what keep every list endpoint identical.

### 8.2 Interactive Documentation (Swagger / OpenAPI)

Plan interactive docs from the start. A Swagger/OpenAPI playground works as both a **testing tool** and **living documentation** for whoever integrates the API. How consistently you create, maintain, and update your OpenAPI documentation is one of the things that sets you apart as a backend engineer.

FastAPI generates OpenAPI automatically, so the job is making it good:

```python
app = FastAPI(
    title="Project Management API",
    version="1.0.0",
    description="Organizations, projects and tasks.",
)

app.include_router(orgs)
app.include_router(projects)
# Production: app.include_router(orgs, prefix="/v1") ...
```

Add `summary`, query-parameter `description`, `tags`, and explicit error responses so the docs describe behavior:

```python
@orgs.get(
    "/{org_id}",
    response_model=Organization,
    summary="Get one organization",
    responses={404: {"description": "Organization not found"}},
)
def get_organization(org_id: str): ...
```

Open **`/docs`** (Swagger UI) or **`/redoc`**.

### 8.3 Sane Defaults

- **On `GET`/list calls:** `page=1`, `limit=10`, `sortBy=createdAt`, `sortOrder=descending`, so the client never has to send obvious values.
- **On `POST` calls:** require only the information that is *absolutely necessary* and default everything else. An organization's `status` could be `active` or `archived`, but a newly created organization is obviously `active`. So if the client omits `status`, the server sets `active`. That's why `OrganizationCreate.status` defaults to `OrgStatus.active`, and a client can create an organization with just a `name`:

```bash
curl -i -X POST localhost:3000/organizations \
  -H "Content-Type: application/json" -d '{"name":"Minimal Org"}'
# 201, "status": "active"
```

(`description` is optional too, so only `name` is required.) Choose the default that makes the most sense for your business logic, and only when it's a safe assumption.

### 8.4 No Abbreviations

Don't name a field `desc`, `qty`, or `addr`. You know what you meant when you designed the interface, but the people integrating your API have less context and can't be expected to decode shorthand. Keep payload fields and query parameters **readable and intuitive**: `description`, not `dsc`.

### 8.5 Design the Interface Before Writing Code

A REST API is **designed first, coded second.** The initial phase is a series of design decisions (resources, routes, payloads, status codes), and it deserves its own session, separate from programming and independent of language or framework (Go, Node, Python). Starting from an OpenAPI/Swagger spec or an API client (Insomnia, Postman) shows you how consumers will actually use the API, and that makes the final design more intuitive.

A practical FastAPI version of this: write the Pydantic schemas and route signatures first, open `/docs`, and *review the interface as a consumer* before implementing the business logic behind it.

## 9. Verifying Everything with Tests

A runnable pytest file that exercises each behavior from this part (`pip install pytest httpx`):

```python
# test_api.py
import pytest
from fastapi.testclient import TestClient

from main import ORGS, PROJECTS, app

client = TestClient(app)


@pytest.fixture(autouse=True)
def reset_store():
    ORGS.clear()
    PROJECTS.clear()
    yield


def make_org(name, status=None):
    body = {"name": name}
    if status:
        body["status"] = status
    r = client.post("/organizations", json=body)
    assert r.status_code == 201
    return r.json()


def test_create_defaults_status_to_active():
    org = make_org("Minimal")
    assert org["status"] == "active"
    assert "createdAt" in org and "updatedAt" in org          # camelCase


def test_list_defaults_and_pagination():
    for i in range(1, 6):
        make_org(f"Org {i}")
    body = client.get("/organizations", params={"limit": 2, "page": 3}).json()
    assert [o["name"] for o in body["data"]] == ["Org 1"]
    assert (body["total"], body["page"], body["totalPages"]) == (5, 3, 3)


def test_default_sort_is_created_at_desc():
    for i in range(1, 4):
        make_org(f"Org {i}")
    names = [o["name"] for o in client.get("/organizations").json()["data"]]
    assert names == ["Org 3", "Org 2", "Org 1"]


def test_sort_by_name_default_desc_then_ascending():
    for i in range(1, 4):
        make_org(f"Org {i}")
    desc = client.get("/organizations", params={"sortBy": "name"}).json()["data"]
    asc = client.get("/organizations", params={"sortBy": "name", "sortOrder": "ascending"}).json()["data"]
    assert [o["name"] for o in desc] == ["Org 3", "Org 2", "Org 1"]
    assert [o["name"] for o in asc] == ["Org 1", "Org 2", "Org 3"]


def test_filter_by_status_and_name():
    make_org("Org 1")
    make_org("Org 6", status="archived")
    r = client.get("/organizations", params={"status": "archived"}).json()
    assert [o["name"] for o in r["data"]] == ["Org 6"]
    r = client.get("/organizations", params={"name": "Org 1"}).json()
    assert r["total"] == 1


def test_empty_list_is_200_not_404():
    r = client.get("/organizations", params={"status": "banana"})
    assert r.status_code == 200
    assert r.json() == {"data": [], "total": 0, "page": 1, "totalPages": 0}


def test_patch_returns_200_and_updated_entity():
    org = make_org("Org 6", status="archived")
    r = client.patch(f"/organizations/{org['id']}", json={"status": "active"})
    assert r.status_code == 200
    assert r.json()["status"] == "active"
    assert r.json()["name"] == "Org 6"                         # untouched field


def test_delete_returns_204_then_get_is_404():
    org = make_org("Org 6")
    r = client.delete(f"/organizations/{org['id']}")
    assert r.status_code == 204 and r.content == b""
    assert client.get(f"/organizations/{org['id']}").status_code == 404
    assert client.delete(f"/organizations/{org['id']}").status_code == 404   # idempotent state


def test_archive_custom_action_returns_200():
    org = make_org("Org 5")
    r = client.post(f"/organizations/{org['id']}/archive")
    assert r.status_code == 200                                # POST, but nothing created
    assert r.json()["status"] == "archived"


def test_project_crud_and_clone_returns_201():
    org = make_org("Org A")
    r = client.post("/projects", json={"name": "Project 2", "organizationId": org["id"]})
    assert r.status_code == 201 and r.json()["status"] == "planned"
    pid = r.json()["id"]

    clone = client.post(f"/projects/{pid}/clone")
    assert clone.status_code == 201                            # custom action that creates
    assert clone.json()["name"] == "Project 2 clone"
    assert clone.json()["id"] != pid

    assert client.delete(f"/projects/{pid}").status_code == 204
    assert client.post(f"/projects/{pid}/clone").status_code == 404   # deleted → 404
```

Run with `pytest -q`.

## 10. Cheat Sheet for Part 2

**List endpoints (`GET /resources`)**

| Query param | Default | Notes |
|---|---|---|
| `page` | `1` | |
| `limit` | `10` (or 20) | cap the maximum |
| `sortBy` | `createdAt` | field name from the resource |
| `sortOrder` | `descending` | `ascending` / `descending` |
| `<field>` | none | filter parameter = field name |

- Always sort by default (databases don't guarantee order).
- Response envelope: `data`, `total`, `page`, `totalPages`.
- Nothing matched → `200` with `data: []`, `total: 0`, `totalPages: 0`. **Never `404`.**

**Single-resource endpoints (same URL, different method)**

| Action | Method | Success | Missing resource |
|---|---|---|---|
| Get one | `GET /resources/{id}` | `200` | `404` |
| Partial update | `PATCH /resources/{id}` | `200` + updated entity | `404` |
| Delete | `DELETE /resources/{id}` | `204`, empty body | `404` |
| Create | `POST /resources` | `201` + created entity | n/a |

**Custom actions:** `POST /resources/{id}/{action}` for anything that isn't CRUD (`archive`, `clone`). Use them when the operation has business side effects the client shouldn't have to replicate. The status code reflects what happened: `200` if nothing was created, `201` if something was.

**Principles**
1. Be **consistent** across routes, payloads, query params, and responses.
2. JSON fields are **camelCase**.
3. Provide **interactive docs** (OpenAPI/Swagger) and keep them up to date.
4. Provide **sane defaults**; require only what's essential on `POST`.
5. **No abbreviations.**
6. **Design the interface first** (language-agnostic), then code it.

## 11. Wrapping Up

Across both parts, the whole design reduces to a small set of repeatable patterns: plural lowercase resource nouns, hierarchy through `/`, the right method for the right operation (reasoned from idempotency), accurate status codes (`200`, `201`, `204`, `404`), paginated/sorted/filtered lists with server-side defaults, custom actions on `POST`, and strict consistency. Once you've internalized these, designing the API for the next resource, such as `tasks`, takes minutes rather than debates, and you can spend your time on the business logic.
