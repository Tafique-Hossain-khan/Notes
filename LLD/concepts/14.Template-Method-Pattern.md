# Template Method Design Pattern

## The Problem: Pipelines and Order of Execution

Imagine you are a data scientist working with different machine learning algorithms — Neural Networks, Decision Trees, Random Forests, SVMs, and so on. No matter which algorithm you work with, you follow the same pipeline — a fixed list of steps, always in the same order:

1. **Load Data**
2. **Pre-process Data**
3. **Train Model**
4. **Evaluate Results**
5. **Save Model**

These steps must never be reordered. You cannot train a model before pre-processing it. You cannot save a model before training it. The sequence is non-negotiable.

Now here is the problem: if you just hand this off to other developers and say "go implement a Neural Network class and a Decision Tree class," nothing stops them from calling these steps in the wrong order. Someone might train before pre-processing. Someone might save before evaluating.

You want to give every developer a **template** — a pre-defined structure that says: *this is the order, and you cannot change it.* That is exactly what the Template Method Pattern solves.

---

## Core Idea

The Template Method Pattern defines a **skeleton of an algorithm** inside a method, and **defers some steps to subclasses**. The subclasses can redefine certain steps of the algorithm without changing the algorithm's structure.

The order of execution — the pipeline — always stays the same. Only the *implementation* of individual steps changes depending on which model or algorithm is being used.

## UML Diagram

```
┌─────────────────────────────────────────────┐
│           <<abstract>>                      │
│            ModelTrainer                     │
├─────────────────────────────────────────────┤
│ + train_pipeline(path)   ← template method  │
│   (defined here, NOT overridable)           │
│                                             │
│ + load_data(path)        ← defined here     │
│ + pre_process()          ← defined here     │
│ + train_model()          ← abstract         │
│ + evaluate_model()       ← abstract         │
│ + save_model()           ← defined here     │
└─────────────────────────────────────────────┘
                    △
                    │  (inherits)
         ┌──────────┴──────────┐
         │                     │
┌────────────────┐   ┌──────────────────────┐
│ NeuralNetwork  │   │   DecisionTree       │
│    Trainer     │   │     Trainer          │
├────────────────┤   ├──────────────────────┤
│ train_model()  │   │ train_model()        │
│ evaluate_model │   │ evaluate_model()     │
│ save_model()   │   │ (uses default save)  │
└────────────────┘   └──────────────────────┘

         Used by:
┌──────────────────────────────┐
│           Client             │
├──────────────────────────────┤
│ has-a → ModelTrainer (ref)   │
│ calls → train_pipeline()     │
└──────────────────────────────┘
```

**Key points from the UML:**

- `ModelTrainer` is an abstract class — it is not purely abstract because some methods are defined here and some are left abstract.
- `train_pipeline()` is the **template method**. It is defined in the parent and **cannot be overridden** by subclasses.
- `train_model()` and `evaluate_model()` are abstract — subclasses **must** override them.
- `load_data()`, `pre_process()`, and `save_model()` are defined in the parent — subclasses **may** override them if needed, but they don't have to.
- The `Client` holds a reference to `ModelTrainer` (could be any subclass), and calls only `train_pipeline()`. It does not care which concrete model it is talking to.

## Python Implementation

```python
from abc import ABC, abstractmethod


class ModelTrainer(ABC):
    """
    Abstract base class. Defines the template method (train_pipeline)
    and the fixed order of execution. Subclasses override individual steps.
    """

    # -------------------------------------------------------------------
    # TEMPLATE METHOD — defines the pipeline. Final: do not override this.
    # -------------------------------------------------------------------
    def train_pipeline(self, path: str):
        self.load_data(path)
        self.pre_process()
        self.train_model()
        self.evaluate_model()
        self.save_model()

    # -------------------------------------------------------------------
    # Concrete methods — defined here, shared across all subclasses.
    # Subclasses CAN override these if they need different behaviour.
    # -------------------------------------------------------------------
    def load_data(self, path: str):
        print(f"[Common] Loading dataset from: {path}")

    def pre_process(self):
        print("[Common] Splitting into train/test sets and normalising data")

    def save_model(self):
        print("[Common] Saving model to disk in default format")

    # -------------------------------------------------------------------
    # Abstract methods — subclasses MUST override these.
    # -------------------------------------------------------------------
    @abstractmethod
    def train_model(self):
        pass

    @abstractmethod
    def evaluate_model(self):
        pass


# -----------------------------------------------------------------------
# Concrete subclass 1: Neural Network
# Overrides train_model, evaluate_model, AND save_model (optional override)
# -----------------------------------------------------------------------
class NeuralNetworkTrainer(ModelTrainer):

    def train_model(self):
        print("[NeuralNetwork] Training neural network using 100 epochs, Adam optimiser")

    def evaluate_model(self):
        print("[NeuralNetwork] Evaluating accuracy and loss on validation set")

    def save_model(self):
        # Overrides the default save — stores in a specific neural net format
        print("[NeuralNetwork] Saving model in .h5 format to /models/nn/")


# -----------------------------------------------------------------------
# Concrete subclass 2: Decision Tree
# Only overrides train_model and evaluate_model — uses default save
# -----------------------------------------------------------------------
class DecisionTreeTrainer(ModelTrainer):

    def train_model(self):
        print("[DecisionTree] Training decision tree with max_depth=10")

    def evaluate_model(self):
        print("[DecisionTree] Evaluating using precision, recall, and F1-score")

    # Does NOT override save_model — uses the common implementation from parent


# -----------------------------------------------------------------------
# Client
# Has-a relationship with ModelTrainer. Calls train_pipeline only.
# Does not care which concrete trainer is passed.
# -----------------------------------------------------------------------
class Client:

    def __init__(self, trainer: ModelTrainer):
        self.trainer = trainer

    def run(self, path: str):
        self.trainer.train_pipeline(path)


# -----------------------------------------------------------------------
# Usage
# -----------------------------------------------------------------------
if __name__ == "__main__":
    print("=" * 50)
    print("Starting Neural Network Training")
    print("=" * 50)
    nn_client = Client(NeuralNetworkTrainer())
    nn_client.run("/data/images/dataset.csv")

    print()

    print("=" * 50)
    print("Starting Decision Tree Training")
    print("=" * 50)
    dt_client = Client(DecisionTreeTrainer())
    dt_client.run("/data/tabular/dataset.csv")
```

**Expected Output:**

```
==================================================
Starting Neural Network Training
==================================================
[Common] Loading dataset from: /data/images/dataset.csv
[Common] Splitting into train/test sets and normalising data
[NeuralNetwork] Training neural network using 100 epochs, Adam optimiser
[NeuralNetwork] Evaluating accuracy and loss on validation set
[NeuralNetwork] Saving model in .h5 format to /models/nn/

==================================================
Starting Decision Tree Training
==================================================
[Common] Loading dataset from: /data/tabular/dataset.csv
[Common] Splitting into train/test sets and normalising data
[DecisionTree] Training decision tree with max_depth=10
[DecisionTree] Evaluating using precision, recall, and F1-score
[Common] Saving model to disk in default format
```

Notice what is happening:

- Both trainers follow the **exact same order**: load → pre-process → train → evaluate → save.
- Neural Network overrides `save_model()` so it saves in its own format. Decision Tree does not — it uses the parent's default.
- The Client does not change at all. It just calls `train_pipeline()` and the correct behaviour flows through automatically.
- No matter in what order the developer writes the method overrides inside the subclass, the execution order is always controlled by `train_pipeline()` in the parent.

## What Makes This Work

The trick is the **template method** (`train_pipeline`) in the parent class:

```python
def train_pipeline(self, path: str):
    self.load_data(path)    # Step 1 — always first
    self.pre_process()      # Step 2 — always second
    self.train_model()      # Step 3 — always third
    self.evaluate_model()   # Step 4 — always fourth
    self.save_model()       # Step 5 — always last
```

This method is defined in the parent and controls the sequence. In Python, you enforce "do not override this" through convention and documentation (unlike C++ `const` or Java `final`). The standard practice is to name it clearly and document it.

When `self.train_model()` is called here — Python's method resolution order (MRO) ensures that if a subclass has overridden `train_model()`, the subclass's version runs. That is how the template method calls the correct implementation without knowing which subclass it is dealing with.

## Real-World Analogy: UPI Payment Flow

Consider a payment system. No matter whether it is UPI, Credit Card, or Debit Card — the pipeline is always:

1. Validate (check if Account A has sufficient funds)
2. Debit (deduct from Account A)
3. Credit (add to Account B)
4. Confirm (verify the transaction completed)
5. Close (finalise and record)

You cannot credit before debiting. You cannot debit before validating. The order is fixed. But how UPI validates is different from how a Credit Card validates — they implement these steps differently.

This is exactly where Template Method Pattern fits. The pipeline is defined once in the parent. Each payment method overrides the steps in its own way.

---

## Standard Definition

> The Template Method Pattern defines the **skeleton of an algorithm** in an operation, deferring some steps to subclasses. Template Method lets subclasses **redefine certain steps of an algorithm without changing the algorithm's structure**.

Two key things:

1. The algorithm's **structure** (the pipeline, the order) never changes.
2. The **implementation** of individual steps can vary per subclass.

---

## When to Use This Pattern

Use the Template Method Pattern whenever you know the **order of execution** must stay fixed, but the **implementation** of individual steps will vary. Concretely:

- Any ML training pipeline (as shown above)
- Payment processing flows (validate → debit → credit → confirm)
- Any multi-step workflow where step order is non-negotiable
- Report generation pipelines (fetch data → format → render → export)

If you find yourself thinking "the flow must always be A → B → C, but A, B, C look different for different cases" — that is your signal to use this pattern.
