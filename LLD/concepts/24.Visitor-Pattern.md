# Visitor Design Pattern in Python — A Complete Hands-On Guide

---

## The Problem: A Class That Never Stops Growing

Imagine you have a class `A`. It has two methods: `m1` and `m2`. Everything is working fine.

Then a new requirement arrives — you need to add `m3`. You add it inside class `A`. Then another requirement comes for `m4`. You add that too. Then `m5`... and the pattern continues.

```
Class A
  ├── m1()
  ├── m2()
  ├── m3()   ← new requirement
  ├── m4()   ← another new requirement
  └── ...    ← keeps growing
```

Every time a new requirement comes in, you open the same class and modify it.

**What SOLID principles are being violated here?**

**1. Open-Closed Principle (OCP):**
> A class should be *open for extension* but *closed for modification.*

But here, you are forced to open and modify the same class every time a new requirement arrives. That is a direct violation of OCP.

**2. Single Responsibility Principle (SRP):**
> A class should have only one reason to change.

When you keep adding methods for different concerns inside one class, the class ends up having multiple reasons to change. SRP is broken.

**Other consequences:**
- The class becomes increasingly **complex**.
- **Unit testing** becomes harder — testing each method in isolation becomes a nightmare as the class grows.

The fundamental rule from design patterns says:

> **Encapsulate what varies.**

Whatever changes frequently, pull it out of the class. What doesn't change should stay stable.

---

## The Example: A Document Management System

Let's take a concrete example. Imagine you have an application that handles multiple types of documents:
- **Text File**
- **Image**
- **Video**

You create a parent class `DocumentElement` and have each document type extend it.

```
DocumentElement  (abstract/parent)
  ├── TextFile
  ├── Image
  └── Video
```

Now new requirements start coming in:

1. **Calculate Size** — every document needs to calculate its own size.
2. **Compress** — every document needs to compress itself (text files, images, videos each have their own compression algorithm).
3. **Scan for Virus** — every document needs to be scanned for viruses.

The naive approach: add an abstract method in `DocumentElement` for each operation, and override it in every subclass.

```
DocumentElement
  ├── calculate_size()   ← abstract
  ├── compress()         ← abstract
  └── scan_for_virus()   ← abstract

TextFile(DocumentElement)
  ├── calculate_size()   ← overrides
  ├── compress()         ← overrides
  └── scan_for_virus()   ← overrides

Image(DocumentElement)
  ├── calculate_size()   ← overrides
  ├── compress()         ← overrides
  └── scan_for_virus()   ← overrides

Video(DocumentElement)
  ├── calculate_size()   ← overrides
  ├── compress()         ← overrides
  └── scan_for_virus()   ← overrides
```

Every time a new operation arrives, you modify `DocumentElement` and all its subclasses. OCP and SRP both get violated. The classes grow endlessly.

---

## The Key Assumption Before Introducing the Visitor Pattern

Before introducing the Visitor Pattern, take note of this important assumption:

> **The types of documents (TextFile, Image, Video) are fixed. They will NOT change frequently.**

New document types like `PDF` are NOT going to be added often — that is a rare/unlikely change.

**What DOES change frequently?** The **number of operations** — calculate size, compress, scan for virus, and more operations will keep coming in as new requirements arrive.

This is the exact distinction that drives the Visitor Pattern:

- **Frequently changing:** operations on the elements
- **Less frequently changing:** the element types themselves

So the rule applies: **extract and encapsulate what varies.** Pull the operations OUT of the element classes.

---

## Introducing the Visitor Pattern

**Step 1: Strip the element classes of all operations.**

Remove `calculate_size`, `compress`, `scan_for_virus` from `DocumentElement`, `TextFile`, `Image`, and `Video`. The element classes become clean.

**Step 2: Create a Visitor hierarchy.**

Create an abstract class `IVisitor`. For every document type, add one `visit` method — using **method overloading** (same method name, different parameter type):

```
IVisitor  (abstract)
  ├── visit(TextFile t)
  ├── visit(Image img)
  └── visit(Video vid)
```

**Step 3: Create concrete Visitors — one per operation.**

Each operation becomes its own concrete Visitor class that extends `IVisitor` and overrides all three `visit` methods:

```
SizeCalculatorVisitor(IVisitor)
  ├── visit(TextFile t)   → calculate size of text file
  ├── visit(Image img)    → calculate size of image
  └── visit(Video vid)    → calculate size of video

CompressVisitor(IVisitor)
  ├── visit(TextFile t)   → compress text file
  ├── visit(Image img)    → compress image
  └── visit(Video vid)    → compress video

ScanVirusVisitor(IVisitor)
  ├── visit(TextFile t)   → scan text file for virus
  ├── visit(Image img)    → scan image for virus
  └── visit(Video vid)    → scan video for virus
```

The logic that was previously inside `TextFile.compress()` is now inside `CompressVisitor.visit(TextFile t)`. The logic is the same — it has just moved to a dedicated class.

**Step 4: Add a single `accept` method to each element.**

Each document class gets exactly **one** method: `accept(IVisitor v)`. That's it. The element classes are now stable and will never need to change again.

```
DocumentElement  (abstract)
  └── accept(IVisitor v)  ← abstract, single method

TextFile(DocumentElement)
  └── accept(IVisitor v)  → v.visit(self)

Image(DocumentElement)
  └── accept(IVisitor v)  → v.visit(self)

Video(DocumentElement)
  └── accept(IVisitor v)  → v.visit(self)
```

Inside each `accept`, there is only one line: `v.visit(self)`. Pass `self` (the current object) to the visitor's `visit` method. Because `self` is of type `TextFile`, Python resolves to the `visit(TextFile)` overload. Because `self` is of type `Image`, it resolves to `visit(Image)`. And so on.

## How the Client Uses This

```python
# Create a document
file_one = TextFile("document.txt")

# Run size calculation on it
file_one.accept(SizeCalculatorVisitor())

# Run compression on it
file_one.accept(CompressVisitor())

# Run virus scan on it
file_one.accept(ScanVirusVisitor())
```

Each call to `accept` passes a different visitor. The element class (`TextFile`) never changes. New operations = new Visitor subclass. That's all.

## Python Implementation

> **Note on method overloading in Python:** Python does not support traditional method overloading (same method name, different parameter types) the way Java does. We handle this using `singledispatchmethod` from the `functools` module, or by using `isinstance` checks, or by using separate method names per type. The cleanest Pythonic approach is shown below using `singledispatchmethod`.

```python
from abc import ABC, abstractmethod
from functools import singledispatchmethod


# ─────────────────────────────────────────────
# Element Hierarchy
# ─────────────────────────────────────────────

class DocumentElement(ABC):
    def __init__(self, name: str):
        self.name = name

    def get_name(self) -> str:
        return self.name

    @abstractmethod
    def accept(self, visitor: "IVisitor") -> None:
        pass


class TextFile(DocumentElement):
    def __init__(self, name: str):
        super().__init__(name)
        self.content = "This is text content."

    def get_content(self) -> str:
        return self.content

    def accept(self, visitor: "IVisitor") -> None:
        visitor.visit(self)


class Image(DocumentElement):
    def __init__(self, name: str):
        super().__init__(name)

    def accept(self, visitor: "IVisitor") -> None:
        visitor.visit(self)


class Video(DocumentElement):
    def __init__(self, name: str):
        super().__init__(name)

    def accept(self, visitor: "IVisitor") -> None:
        visitor.visit(self)


# ─────────────────────────────────────────────
# Visitor Hierarchy
# ─────────────────────────────────────────────

class IVisitor(ABC):

    @singledispatchmethod
    def visit(self, element) -> None:
        raise NotImplementedError(f"No visit method for {type(element)}")

    @visit.register(TextFile)
    @abstractmethod
    def _(self, t: TextFile) -> None:
        pass

    @visit.register(Image)
    @abstractmethod
    def _(self, img: Image) -> None:
        pass

    @visit.register(Video)
    @abstractmethod
    def _(self, vid: Video) -> None:
        pass


class SizeCalculatorVisitor(IVisitor):

    @IVisitor.visit.register(TextFile)
    def _(self, t: TextFile) -> None:
        print(f"Calculating the size of the text file: {t.get_name()}")

    @IVisitor.visit.register(Image)
    def _(self, img: Image) -> None:
        print(f"Calculating the size of the image: {img.get_name()}")

    @IVisitor.visit.register(Video)
    def _(self, vid: Video) -> None:
        print(f"Calculating the size of the video: {vid.get_name()}")


class CompressVisitor(IVisitor):

    @IVisitor.visit.register(TextFile)
    def _(self, t: TextFile) -> None:
        print(f"Compressing text file: {t.get_name()}")

    @IVisitor.visit.register(Image)
    def _(self, img: Image) -> None:
        print(f"Compressing image: {img.get_name()}")

    @IVisitor.visit.register(Video)
    def _(self, vid: Video) -> None:
        print(f"Compressing video: {vid.get_name()}")


class ScanVirusVisitor(IVisitor):

    @IVisitor.visit.register(TextFile)
    def _(self, t: TextFile) -> None:
        print(f"Scanning text file for virus: {t.get_name()}")

    @IVisitor.visit.register(Image)
    def _(self, img: Image) -> None:
        print(f"Scanning image for virus: {img.get_name()}")

    @IVisitor.visit.register(Video)
    def _(self, vid: Video) -> None:
        print(f"Scanning video for virus: {vid.get_name()}")


# ─────────────────────────────────────────────
# Client / Main
# ─────────────────────────────────────────────

if __name__ == "__main__":
    image_one: DocumentElement = Image("sample.jpg")
    image_one.accept(SizeCalculatorVisitor())
    image_one.accept(CompressVisitor())
    image_one.accept(ScanVirusVisitor())

    print()

    video_one: DocumentElement = Video("clip.mp4")
    video_one.accept(CompressVisitor())
```

**Expected Output:**
```
Calculating the size of the image: sample.jpg
Compressing image: sample.jpg
Scanning image for virus: sample.jpg

Compressing video: clip.mp4
```

> **Simpler alternative for Python (without singledispatchmethod):** Since Python resolves types at runtime, many implementations use `isinstance` checks inside the visitor or use separate method names (`visit_text_file`, `visit_image`, `visit_video`). Both are valid. The `singledispatchmethod` approach mirrors the Java method overloading behaviour most closely.

## Double Dispatch

When you study the Visitor Pattern, you will always see the term **double dispatch**. It sounds complicated but it is extremely simple.

**Double dispatch means: two references together decide which method gets called.**

Let's trace through the execution:

```python
file_one = TextFile("doc.txt")
file_one.accept(SizeCalculatorVisitor())
```

**Reference 1:** `file_one.accept(...)` — this tells you *which `accept` method* to call. Since `file_one` is a `TextFile`, `TextFile.accept` is called.

**Reference 2:** Inside `TextFile.accept`, the code is `v.visit(self)`. Here `self` is the `TextFile` instance. This `self` reference tells you *which `visit` method* to call inside the visitor.

So:
- Reference 1 (`file_one`) → decides which `accept` executes → lands in `TextFile.accept`
- Reference 2 (`self` inside `accept`) → decides which `visit` executes → lands in `visit(TextFile)`

Two references. Two decisions. That is double dispatch.

**Single dispatch** (what you normally use): one reference decides which method runs. Example: `obj.some_method()` — the type of `obj` alone decides.

**Double dispatch** (what Visitor uses): two references together decide. First reference selects the visitor (which operation). Second reference (`self`) selects the correct overload (which element type).

```
file_one.accept(SizeCalculatorVisitor())
    │                    │
    │                    └── Reference 1: selects SizeCalculatorVisitor
    │
    └── leads to TextFile.accept(v)
                    │
                    └── v.visit(self)
                              │
                              └── Reference 2: self is TextFile
                                  → calls visit(TextFile) overload
```

## Visitor Pattern vs. Strategy Pattern

This is one of the most common points of confusion. Both patterns involve creating a hierarchy of classes. Both involve passing objects around. But they solve **fundamentally different problems**.

### Strategy Pattern — Recap

In the Strategy Pattern, we had a `Robot` class. The robot could `fly`, `talk`, and `walk`. These **three behaviours are fixed** — the robot always has exactly these three behaviours.

What changes? **How** the robot performs each behaviour. There can be multiple ways to fly:
- `FlyWithWings`
- `FlyWithJet`
- `NoFly`

The number of flying styles can grow. But the number of behaviours (`fly`, `talk`, `walk`) stays constant.

```
IFlyBehaviour  (abstract)
  ├── FlyWithWings
  ├── FlyWithJet
  └── NoFly

ITalkBehaviour  (abstract)
  └── ...

IWalkBehaviour  (abstract)
  └── ...

Robot
  ├── fly_behaviour: IFlyBehaviour
  ├── talk_behaviour: ITalkBehaviour
  └── walk_behaviour: IWalkBehaviour
```

The Robot class holds references to its strategy objects. The **number of strategies (behaviours) is constant**. What varies is the implementation of each behaviour.

### Visitor Pattern — The Contrast

In the Visitor Pattern applied to the Robot scenario, the robot only has **one way** of flying (or talking, or walking) — no multiple implementations for each behaviour.

What changes? **New operations keep getting added.** The robot now needs to `fly`, then `swim`, then `study`, then more and more operations — the number of operations keeps growing.

```
Robot
  └── accept(v: IVisitor)  ← the only method; never changes

IVisitor  (abstract)
  └── visit(r: Robot)

FlyVisitor(IVisitor)     → handles flying for Robot
WalkVisitor(IVisitor)    → handles walking for Robot
TalkVisitor(IVisitor)    → handles talking for Robot
SwimVisitor(IVisitor)    → handles swimming for Robot
```

Every new operation = one new Visitor subclass. The `Robot` class never changes.

### Side-by-Side Comparison

| | Strategy Pattern | Visitor Pattern |
|---|---|---|
| **What is fixed?** | Number of operations/behaviours | Element types |
| **What varies?** | How each behaviour is implemented | Number of operations |
| **New requirement type** | New way to perform an existing behaviour | Entirely new operation on elements |
| **Example** | New way to fly (gliding, rocket, etc.) | New operation on files (encrypt, backup, etc.) |
| **When to use** | Behaviours are known; implementations differ | Operations keep growing on stable element types |
| **Complexity** | Simpler | Slightly more complex |

### The Honest Trade-off

What if both behaviours **and** their implementations are changing? Then you face a decision:

- **Strategy** is simpler to understand and maintain. You accept a slight OCP violation when new behaviours are added (you would need to add a new strategy reference to the class).
- **Visitor** handles the growing-operations case perfectly but is more complex to set up.

In practice, if both dimensions are changing and you want to handle it fully, you can **combine both patterns** — Visitor for new operations, Strategy for multiple implementations of each operation. Together they solve the full tightly-coupled mess.

## Standard Definition

> **Visitor Pattern:** Allows adding new operations to existing classes without changing their structure. It separates the operation from the object it operates on.

Breaking that down:

- "Adding new operations to existing classes without changing their structure" — every new operation is a new Visitor subclass. The element classes (`TextFile`, `Image`, `Video`) never change.
- "Separates the operation from the object it operates on" — `compress` logic no longer lives inside `TextFile`. It lives in `CompressVisitor`. The object (`TextFile`) and the operation (`compress`) are decoupled.

## Real-World Use Cases

**1. Game Rendering Engines**

In a game engine, there are many game objects (enemies, terrain, UI elements). Operations on them grow over time: render, update physics, detect collision, play audio, serialize to save file. Each new operation would be a new Visitor. The game object classes never change.

**2. Compilers (Abstract Syntax Trees)**

When a compiler parses your code, it builds a tree structure called an AST (Abstract Syntax Tree). Each node in the tree represents a keyword, expression, or statement. Operations on the tree include: type checking, code generation, optimization, pretty-printing. Each operation is a Visitor that traverses the tree. The AST node classes stay fixed.

**3. Document Processing (as shown above)**

Any application that processes a fixed set of document types (text, image, video, audio) but adds new operations over time (compress, encrypt, backup, index, thumbnail) is a natural fit for Visitor.

## Quick Reference — When to Use Visitor

Use the Visitor Pattern when:

- You have a **stable set of element types** (rarely or never adds new types).
- You have **operations that keep growing** — new requirements keep adding new operations.
- Each operation needs to do something **different for each element type**.
- You want to keep element classes **clean and stable** — they should only know how to `accept` a visitor, nothing else.

Do NOT use Visitor when:

- New element types are added frequently — every new element type requires updating **every existing Visitor** with a new `visit` method. This is the known trade-off of the Visitor Pattern.
- The operations are few and unlikely to grow — the extra structure adds complexity without benefit.
