# Authentication & Authorization — Complete Notes

## 1. Core Definitions

- **Authentication** = answering *"Who are you?"* — the process of assigning/verifying an identity for a subject in a given context (a platform, an OS, a device).
- **Authorization** = answering *"What can you do?"* — the process of determining a subject's permissions/capabilities within that context.

These are two distinct problems and most of the historical evolution below is really the story of people inventing better answers to each question separately.

---

## 2. Historical Evolution of Authentication

Understanding *why* each mechanism exists makes the technical details easier to retain.

| Era | Mechanism | Underlying Principle |
|---|---|---|
| Pre-industrial societies | A trusted person (e.g., a village elder) vouches for you; deals sealed with a handshake | Human contextual trust — doesn't scale beyond a small community |
| Medieval period | Wax seals on documents/letters | **Something you have** (possession) — first widely-adopted "authentication token"; vulnerable to forgery (first authentication bypass attacks), which led to watermarks and encrypted codes |
| Industrial Revolution | Telegraph operators used pre-agreed static passphrases | **Something you know** — first shared secrets |
| 1961 (MIT Project MAC / CTSS) | First multi-user computer passwords | Digital authentication begins. Passwords were stored in **plain text** — a printed password file leaked, triggering the shift to secure password storage (hashing) |
| 1970s | Diffie–Hellman key exchange → asymmetric cryptography; Kerberos (ticket-based auth) | Basis for modern PKI (Public Key Infrastructure) and a precursor to token-based authentication |
| 1990s | Multi-Factor Authentication (MFA); biometrics | Combines **something you know + something you have + something you are**. Biometrics bring new problems: false positives/negatives, template security |
| 21st century | OAuth, JWT, Zero Trust Architecture, passwordless (WebAuthn) | Cloud, mobile, and API-based architectures demand scalable, stateless-friendly authentication |
| Emerging/future | Decentralized identity (blockchain-based), behavioral biometrics, post-quantum cryptography | Post-quantum cryptography specifically exists because quantum computers are expected to eventually break current asymmetric algorithms (RSA, etc.) |

**Why this matters practically:** every "modern" mechanism you'll implement (hashing, tokens, MFA) exists to solve a specific failure of the mechanism before it. Keep that cause → effect chain in mind and the whole field stops feeling arbitrary.

## 3. Three Building Blocks You'll See Everywhere

### 3.1 Sessions

- HTTP is **stateless by design** — each request is isolated, with no memory of previous ones. Fine for static content, but broken for anything needing continuity (shopping carts, "stay logged in").
- A **session** creates temporary server-side memory for a user:
  1. On login, server generates a unique **session ID**, stores it + user data in a persistent store (database or in-memory store like Redis/Memcached).
  2. Session ID is sent to the client as a **cookie**.
  3. Every subsequent request automatically includes that cookie; server uses the ID to look up the user's data.
  4. Sessions are short-lived (expire after N minutes) — after expiry, a fresh login/session is required.
- Storage evolution: file-based sessions (didn't scale) → database-backed sessions (survive server restarts) → distributed in-memory stores (Redis/Memcached — fast, works across regions).

### 3.2 JWT (JSON Web Tokens)

- Formalized in 2015 to solve the scaling problems of server-side sessions: storage cost across millions of users, and replication/consistency issues when synchronizing session data across globally distributed servers.
- **Self-contained and stateless**: the token itself carries the claims (user data), so no server-side lookup is needed to verify identity.
- Structure (base64-encoded, dot-separated): `header.payload.signature`
  - **Header** — metadata, e.g. the signing algorithm.
  - **Payload** — the claims. Common fields:
    - `sub` — subject (user ID)
    - `iat` — issued-at timestamp
    - custom fields — name, role, etc.
  - **Signature** — created with a secret key; used to verify the token hasn't been tampered with.
- **Advantages**: statelessness (no server storage), scalability (any server holding the shared secret can verify independently — ideal for microservices), portability (compact, URL-safe, easy to pass around).
- **Disadvantages**:
  - **Theft risk**: whoever holds the token can impersonate the user until it expires.
  - **Revocation is hard**: there's no built-in way to invalidate a single token before expiry (short of rotating the server's secret, which logs *everyone* out).
- **Hybrid approach**: keep JWT's stateless verification, but maintain a **blacklist** of revoked tokens in a persistent store, checked only when you need to explicitly revoke access. This reintroduces a storage lookup, so it's a deliberate trade-off, not "true" statelessness.
- **Practical advice**: for production, in a medium-to-large system, prefer a dedicated auth provider (Auth0, Clerk, etc.) unless you specifically need to understand/control the internals — but understanding the internals (which this document covers) is valuable for learning backend engineering.

### 3.3 Cookies

- A cookie is a small piece of data a **server stores in the client's browser**.
- Security property: a cookie set by one server is only sent back to that same server (not readable by others).
- Typical authentication flow:
  1. Client sends credentials.
  2. On success, server sets a cookie containing the auth token (JWT or session ID).
  3. Browser automatically attaches that cookie on every subsequent request to that server.
- Use **`HttpOnly`** cookies for auth tokens — this prevents JavaScript from reading the cookie value, which mitigates XSS-based token theft.

## 4. Types of Authentication

### 4.1 Stateful Authentication

**Flow:**
1. Client sends username/password.
2. Server validates credentials.
3. Server generates a session ID, bundles it with user data, stores it in Redis/DB.
4. Server sends the session ID back in an `HttpOnly` cookie.
5. Every subsequent request includes the cookie; server looks up the session ID in the store to identify/authorize the user.

**Pros:** centralized control, real-time visibility into active sessions, easy to revoke access immediately (just delete the session).
**Cons:** limited scalability, more operational complexity in distributed systems (latency from synchronizing session stores across regions).
**Best for:** most traditional web apps / SaaS platforms where session revocation and control matter.

### 4.2 Stateless Authentication (JWT-based)

**Flow:**
1. Client sends username/password.
2. Server validates credentials.
3. Server creates and signs a JWT containing user ID, role, etc., using its secret key.
4. Server returns the JWT to the client.
5. Client sends the JWT back on every request (typically in the `Authorization: Bearer <token>` header).
6. Server verifies the signature using its secret key — no storage lookup needed.

**Pros:** scalable, no session-store dependency, ideal for distributed/microservice architectures and mobile apps.
**Cons:** revocation is hard/complex (see JWT disadvantages above).
**Best for:** APIs, distributed systems, mobile clients.

**Common hybrid strategy:** use stateful (cookie/session) auth for your main web app, and stateless (JWT) auth for mobile apps / third-party API integrations — combining the strengths of both.

### 4.3 API Key–Based Authentication

- User/developer generates a cryptographically random API key from a platform UI.
- That key is then used to authenticate **programmatic** requests to the platform's servers — bypassing the UI entirely.
- **Ideal use case: machine-to-machine (M2M) communication** — one server calling another server's API with no human/browser involved (as opposed to client-to-server interactions driven by a human typing into a login form).
- Advantages: trivially easy to generate, no complex handshake needed, can be scoped with specific permissions and expiry.
- Typical usage: store the key in an environment variable / secret manager, send it on every request (commonly in a header).

### 4.4 OAuth 2.0 and OpenID Connect (OIDC)

**The problem OAuth solves — delegation:** one platform needing to access another platform's resources on a user's behalf (e.g., a travel app reading your Gmail for flight tickets, a social app importing your contacts). Before OAuth, the only "solution" was **sharing your password directly** with the third party — disastrous, because:
- It grants *full* access with no way to limit scope.
- Revocation requires changing your password *everywhere* that password is used.

**OAuth 1.0 (2007):** replaced password-sharing with **token-sharing** — tokens carry limited, specific permissions instead of full account access.

Key roles:
| Role | Description | Example |
|---|---|---|
| Resource Owner | The user who owns the data | You |
| Client | The app requesting access | A travel/social app |
| Resource Server | Where the data actually lives | Your Google account |
| Authorization Server | Issues the token after you approve | Google's auth server |

Flow: client redirects user to the authorization server → user authenticates and grants permission → authorization server sends a token to the client → client uses the token to access the resource server on the user's behalf.

**OAuth 2.0 (~2010):** evolved from 1.0 to fix two pain points — implementation complexity and error-prone cryptographic signing. Introduced:
- **Bearer tokens** (simpler, though more vulnerable if leaked — must always be sent over HTTPS).
- Multiple **flows** depending on client type:
  - **Authorization Code flow** — server-side web apps.
  - **Implicit flow** — browser-based apps (now discouraged for security reasons).
  - **Client Credentials flow** — machine-to-machine communication.
  - **Device Code flow** — input-constrained devices (e.g., smart TVs).

**Important gap:** OAuth 2.0 solves *authorization* (delegated access) but not *authentication* (proving identity).

**OpenID Connect (OIDC, ~2014):** built on top of OAuth 2.0 to add the missing authentication layer, via an **ID Token** (a JWT) containing the user's identity (user ID, issued-at time, issuing authority, name, email, etc.). This is exactly what powers "Sign in with Google / Facebook / Discord" buttons.

OIDC flow:
1. User clicks "Sign in with Google" on a client app.
2. Client redirects to the authorization server (Google).
3. User logs in and grants requested permissions.
4. Authorization server returns an **authorization code** (and sometimes an ID token) to the client.
5. Client exchanges the authorization code for an **access token** (and ID token if not already received).
6. Client uses the access token to act on the user's behalf against the resource server, and the ID token to know who the user is.

### 4.5 Choosing a Type — Rule of Thumb

| Type | Best for |
|---|---|
| Stateful | Traditional web apps needing centralized session control/revocation |
| Stateless (JWT) | APIs, distributed/scalable systems, mobile clients |
| OAuth2 / OIDC | Third-party delegated access, "Sign in with X" |
| API Key | Server-to-server / machine-to-machine, single-purpose API access |

## 5. Authorization: Role-Based Access Control (RBAC)

- Not every authenticated user should have the same capabilities. Ad-hoc solutions (e.g., a secret "god-mode" string passed in requests) are insecure and unmaintainable — if intercepted, it grants full uncontrolled access, and adding more privileged users means creating and managing more such strings.
- **RBAC** solves this properly: define **roles** (e.g., `user`, `admin`, `moderator`), and assign each role a specific set of **permissions** on specific resources. You can go as granular as needed — different permissions per resource, not just per role globally.

**Typical flow:**
1. On signup, the server assigns a role to the user (stored in the DB).
2. On each request, the server determines the caller's role — either by decoding it from the token (JWT) or by looking it up in the DB (session-based).
3. That role is attached to the request context and checked before permitting access to a given operation.
4. If the role lacks permission, the server responds with **HTTP 403 Forbidden**.

## 6. Security Practices Every Backend Engineer Should Know

### 6.1 Generic Error Messages

During authentication, never return specific error messages like `"user not found"` or `"incorrect password"`. These leak information to attackers:
- `"user not found"` tells an attacker the username doesn't exist — they'll move to the next target.
- `"incorrect password"` confirms the username *is* valid — the attacker now focuses effort on brute-forcing just the password.

**Always return a single generic message** (e.g., `"Authentication failed"`) regardless of which check failed. (This rule is specific to authentication — normal validation errors elsewhere can still be user-friendly.)

### 6.2 Timing Attacks

A typical login flow does, in order: (1) look up the username, (2) check if the account is locked, (3) hash the provided password and compare it to the stored hash. Step 3 (hashing) takes measurably longer than steps 1–2. This creates a timing side-channel:
- If the username doesn't exist, the server fails fast (fails at step 1).
- If the username exists but the password is wrong, the server takes longer (it reached the hashing step).

An attacker can measure response time differences to infer whether a username is valid — even though the response *message* is generic.

**Mitigations:**
- Use **constant-time comparison functions** for password hashes (never a plain `==` on hash strings).
- **Simulate a fixed delay** for all authentication attempts so failing early vs. late is indistinguishable.

### 7.1 Password Hashing (never store plain text)

```python
from passlib.context import CryptContext

pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def hash_password(plain_password: str) -> str:
    return pwd_context.hash(plain_password)

def verify_password(plain_password: str, hashed_password: str) -> bool:
    # passlib's verify() is a constant-time comparison internally —
    # this directly addresses the timing-attack concern from section 6.2
    return pwd_context.verify(plain_password, hashed_password)
```

### 7.2 Stateless Authentication with JWT

```python
from datetime import datetime, timedelta, timezone
from jose import jwt, JWTError
from fastapi import FastAPI, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm

app = FastAPI()

SECRET_KEY = "CHANGE_ME_TO_A_LONG_RANDOM_SECRET"   # keep this out of source control
ALGORITHM = "HS256"
ACCESS_TOKEN_EXPIRE_MINUTES = 30

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="token")

# fake "database"
fake_users_db = {
    "alice": {"username": "alice", "hashed_password": hash_password("secret123"), "role": "admin"}
}

def create_access_token(data: dict, expires_delta: timedelta = None):
    to_encode = data.copy()
    expire = datetime.now(timezone.utc) + (expires_delta or timedelta(minutes=15))
    to_encode.update({"exp": expire, "iat": datetime.now(timezone.utc)})
    return jwt.encode(to_encode, SECRET_KEY, algorithm=ALGORITHM)

@app.post("/token")
def login(form_data: OAuth2PasswordRequestForm = Depends()):
    user = fake_users_db.get(form_data.username)
    # Generic error message regardless of WHICH check fails (section 6.1)
    generic_error = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Authentication failed",
        headers={"WWW-Authenticate": "Bearer"},
    )
    if not user or not verify_password(form_data.password, user["hashed_password"]):
        raise generic_error

    access_token = create_access_token(
        data={"sub": user["username"], "role": user["role"]},
        expires_delta=timedelta(minutes=ACCESS_TOKEN_EXPIRE_MINUTES),
    )
    return {"access_token": access_token, "token_type": "bearer"}

def get_current_user(token: str = Depends(oauth2_scheme)):
    credentials_exception = HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail="Authentication failed",
        headers={"WWW-Authenticate": "Bearer"},
    )
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM])
        username: str = payload.get("sub")
        role: str = payload.get("role")
        if username is None:
            raise credentials_exception
    except JWTError:
        raise credentials_exception
    return {"username": username, "role": role}

@app.get("/me")
def read_current_user(current_user: dict = Depends(get_current_user)):
    return current_user
```

Try it: `POST /token` with form fields `username=alice&password=secret123`, then call `GET /me` with header `Authorization: Bearer <token>`.

### 7.3 Stateful Authentication with Sessions (Redis + Cookies)

```python
import uuid
import redis
from fastapi import FastAPI, Response, Request, HTTPException, Depends

app = FastAPI()
r = redis.Redis(host="localhost", port=6379, db=0, decode_responses=True)

SESSION_COOKIE_NAME = "session_id"
SESSION_TTL_SECONDS = 900  # 15 minutes

@app.post("/login")
def login(username: str, password: str, response: Response):
    user = fake_users_db.get(username)
    if not user or not verify_password(password, user["hashed_password"]):
        raise HTTPException(status_code=401, detail="Authentication failed")

    session_id = str(uuid.uuid4())
    r.hset(f"session:{session_id}", mapping={"username": username, "role": user["role"]})
    r.expire(f"session:{session_id}", SESSION_TTL_SECONDS)

    response.set_cookie(
        key=SESSION_COOKIE_NAME,
        value=session_id,
        httponly=True,     # JavaScript cannot read this cookie
        secure=True,        # only sent over HTTPS
        samesite="lax",
        max_age=SESSION_TTL_SECONDS,
    )
    return {"message": "logged in"}

def get_session_user(request: Request):
    session_id = request.cookies.get(SESSION_COOKIE_NAME)
    if not session_id or not r.exists(f"session:{session_id}"):
        raise HTTPException(status_code=401, detail="Authentication failed")
    data = r.hgetall(f"session:{session_id}")
    return data

@app.get("/dashboard")
def dashboard(user: dict = Depends(get_session_user)):
    return {"welcome": user["username"], "role": user["role"]}

@app.post("/logout")
def logout(request: Request, response: Response):
    session_id = request.cookies.get(SESSION_COOKIE_NAME)
    if session_id:
        r.delete(f"session:{session_id}")   # instant revocation — the key advantage of stateful auth
    response.delete_cookie(SESSION_COOKIE_NAME)
    return {"message": "logged out"}
```

### 7.4 JWT Revocation via Blacklist (Hybrid Approach)

```python
# Reuses the JWT setup from 7.2, plus a Redis-backed blacklist

def blacklist_token(token: str, expires_in_seconds: int):
    r.setex(f"blacklist:{token}", expires_in_seconds, "true")

def is_token_blacklisted(token: str) -> bool:
    return r.exists(f"blacklist:{token}") == 1

@app.post("/logout-jwt")
def logout_jwt(token: str = Depends(oauth2_scheme)):
    # Blacklist for the remaining lifetime of the token
    blacklist_token(token, ACCESS_TOKEN_EXPIRE_MINUTES * 60)
    return {"message": "token revoked"}

def get_current_user_checked(token: str = Depends(oauth2_scheme)):
    if is_token_blacklisted(token):
        raise HTTPException(status_code=401, detail="Authentication failed")
    return get_current_user(token)
```

### 7.5 API Key Authentication (Machine-to-Machine)

```python
from fastapi import Security
from fastapi.security.api_key import APIKeyHeader

API_KEY_NAME = "X-API-Key"
api_key_header = APIKeyHeader(name=API_KEY_NAME, auto_error=False)

# In a real system: store keys with owner, scopes and expiry in a database
valid_api_keys = {
    "sk_live_29fj2039fj2039fj203": {"owner": "partner-service-1", "scopes": ["read:notes"]}
}

def get_api_key(api_key: str = Security(api_key_header)):
    if api_key not in valid_api_keys:
        raise HTTPException(status_code=401, detail="Authentication failed")
    return valid_api_keys[api_key]

@app.get("/api/notes")
def get_notes_via_api_key(client: dict = Depends(get_api_key)):
    if "read:notes" not in client["scopes"]:
        raise HTTPException(status_code=403, detail="Forbidden")
    return {"data": ["note1", "note2"], "accessed_by": client["owner"]}
```

### 7.6 OAuth2 / OIDC — "Sign in with Google" (Authorization Code Flow)

```python
# pip install authlib httpx
from authlib.integrations.starlette_client import OAuth
from starlette.config import Config
from starlette.requests import Request
from fastapi.responses import RedirectResponse

config = Config(environ={
    "GOOGLE_CLIENT_ID": "your-client-id.apps.googleusercontent.com",
    "GOOGLE_CLIENT_SECRET": "your-client-secret",

oauth = OAuth(config)
oauth.register(
    name="google",
    server_metadata_url="https://accounts.google.com/.well-known/openid-configuration",
    client_kwargs={"scope": "openid email profile"},
)

@app.get("/login/google")
async def login_google(request: Request):
    redirect_uri = request.url_for("auth_google_callback")
    return await oauth.google.authorize_redirect(request, redirect_uri)

@app.get("/auth/google/callback")
async def auth_google_callback(request: Request):
    token = await oauth.google.authorize_access_token(request)
    # token contains an access_token AND an id_token (the OIDC identity layer)
    user_info = token.get("userinfo")  # decoded ID token claims: sub, email, name, picture...
    # Look up or create a local user record keyed on user_info["sub"], then
    # issue your OWN session/JWT for subsequent requests (don't rely on Google's token long-term).
    return {"email": user_info["email"], "name": user_info["name"]}
```

### 7.7 Role-Based Access Control (RBAC) as a Dependency

```python
from fastapi import Depends, HTTPException, status

def require_role(required_role: str):
    def role_checker(current_user: dict = Depends(get_current_user)):
        if current_user["role"] != required_role:
            raise HTTPException(status_code=status.HTTP_403_FORBIDDEN, detail="Forbidden")
        return current_user
    return role_checker

@app.get("/admin/dead-zone-notes")
def get_dead_zone_notes(user: dict = Depends(require_role("admin"))):
    return {"deleted_notes": ["old_note_1", "old_note_2"]}

@app.get("/notes")
def get_notes(user: dict = Depends(get_current_user)):
    # any authenticated user, regardless of role
    return {"notes": ["note_1", "note_2"]}
```

### 7.8 Mitigating Timing Attacks

```python
import asyncio
import time

FAKE_HASH_FOR_TIMING = hash_password("dummy-password-for-timing-consistency")

@app.post("/login-timing-safe")
async def login_timing_safe(username: str, password: str):
    start = time.monotonic()
    user = fake_users_db.get(username)

    if user:
        password_ok = verify_password(password, user["hashed_password"])
    else:
        # Always run a hash comparison, even for a nonexistent user,
        # so failing at "user not found" takes the same time as failing at "wrong password"
        verify_password(password, FAKE_HASH_FOR_TIMING)
        password_ok = False

    if not user or not password_ok:
        # Pad remaining time up to a fixed minimum so total response time is constant
        elapsed = time.monotonic() - start
        min_response_time = 0.3  # seconds
        if elapsed < min_response_time:
            await asyncio.sleep(min_response_time - elapsed)
        raise HTTPException(status_code=401, detail="Authentication failed")

    return {"message": "login successful"}
```

## 8. Summary Cheat Sheet

| Concept | Key Idea | When to Use |
|---|---|---|
| Session (stateful) | Server stores state, client holds a reference (session ID) | Web apps needing central control/revocation |
| JWT (stateless) | Client holds all state in a signed token | APIs, distributed systems, mobile |
| Cookie | Server-set, browser-managed storage; use `HttpOnly` | Transport mechanism for session IDs or JWTs in browsers |
| API Key | Long-lived credential for programmatic access | Machine-to-machine / server-to-server |
| OAuth 2.0 | Delegated authorization via scoped tokens | Third-party resource access |
| OIDC | Identity layer on top of OAuth 2.0 (ID Token) | "Sign in with X" |
| RBAC | Roles → permissions → resources | Any system with differentiated user capabilities |
| Generic errors | Never reveal *which* auth check failed | Always, in every auth flow |
| Constant-time checks / delay padding | Prevent timing side-channels | Always, in every auth flow |
