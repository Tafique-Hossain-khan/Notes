# Webhooks for Backend Engineers: Receiving, Securing, and Building Them

Every video in this series so far assumed one thing: **the client always starts the connection** and the server answers. The real-time video bent that rule (the server can push data later), but the client still had to open the connection first.

This article covers a different kind of communication: **service-to-service, backend-to-backend**, with no browser and no human involved. It has three parts:

1. **Receiving webhooks:** the mechanics and the security model.
2. **Sending webhooks:** building your own provider.
3. **Knowing when a webhook is the wrong tool.**

The video's own code is in Go. The snippets below are short, framework-free Python written to illustrate the ideas, so treat them as sketches.

---

## 1. The Problem: Knowing What Happened in Someone Else's System

Take the running example, a **task board app with a paid plan**. Payments go through a provider like **Stripe**. When a user pays, the money moves **in Stripe's system, not yours**. So how does your backend learn that the payment succeeded, so it can unlock the plan?

### 1.1 Why not just let the browser tell you?

It's tempting to have the user's browser carry the "payment succeeded" signal. Two reasons that fails:

| Reason | Explanation |
|---|---|
| **Reliability** | The user's network can drop, they can close the tab by mistake, or their machine can crash. The signal gets lost. |
| **Security** | Client-side data can be modified. You cannot trust the client for something as critical as "this payment was approved". |

**Your server must be the source of truth** for signals like this. The signal has to reach your server directly from the provider's server.

### 1.2 First attempt: polling

The brute-force idea: after sending the payment to Stripe, **poll** their API every second ("is it done yet?"). If it's still pending, keep polling. When Stripe decides success or failure, the next response says so, you update your database, and you tell the browser.

Problems (the same ones from the real-time systems video):

- **Delay:** polling every second gives an average delay of **half a second**.
- **Waste:** every "still pending" response is a wasted request.
- **Load on the provider:** say the provider has **10,000 merchants**, each polling once per second. That is **10,000 requests per second** hitting their API.
- **Rate limiting:** to protect themselves, providers aggressively rate-limit. You can no longer poll every second. If you're pushed to a **60-second interval**, your average delay becomes **30 seconds**.

### 1.3 The fix: flip the direction

Instead of you asking the provider repeatedly, **trust the provider to tell you** when the event happens. That is a **webhook**.

> A webhook is just a plain **HTTP `POST` request** that a service sends to a **URL you gave them**, to tell you an event happened.

It's like a **reverse API call**. Normally you call a service's API when *you* need something. With a webhook, **they call your API** when *they* have something to tell you.

### 1.4 A bit of history

- **2007:** **Jeff Lindsay** proposed that web architecture needed something like the **Unix pipe**: a primitive for one service to push its output to another when an event happens. He called these **webhooks**, described as **user-defined callbacks** done over HTTP `POST`. The pipe comparison is because it resembles redirecting standard output in a terminal.
- **2009:** Engineers at Google built a protocol on the same idea for blog feeds, called **PubSubHubbub**.

## 2. Vocabulary

Every provider words things a little differently, but these terms are common:

| Term | Meaning |
|---|---|
| **Provider / sender** | The system where the event actually happens (Stripe, GitHub) |
| **Consumer / receiver** | Your service |
| **Endpoint** | The URL on **your** side that the provider will `POST` to |
| **Event** | Anything predefined: "payment succeeded", "task moved to another board" |
| **Delivery** | **One attempt** to send an event to your endpoint |
| **Subscription** | Your registration with the provider: "here's my URL, and these are the event types I want" |

> **Key point:** one event can have **multiple deliveries**. Build your receiver assuming the same event can arrive more than once. Section 6 explains why.

## 3. One Delivery, End to End (the Receiver)

### 3.1 The demo receiver

The video builds a small receiver with three parts:

- `main`: sets up **one route**, `POST /hooks/github`.
- `inbox`: the **handler**. It reads the complete body, **verifies the signature**, **stores the delivery ID**, and responds.
- `verify`: the signature-check package.

It's the typical shape of a webhook handler.

### 3.2 Reaching your laptop: tunnels

The receiver runs on a laptop with **no public address**. A webhook is an **inbound request from the internet**, and:

- Home routers **don't forward** unsolicited internet traffic to your devices.
- `localhost` means nothing to a server on the internet. They work with domain names and IP addresses.

So during development you use a **tunnel** such as **ngrok** or **Cloudflare Tunnel**. It gives a local port (say `8081`) a **public HTTPS address** and securely forwards requests to it.

In the demo, a webhook is added to a GitHub repository with the tunnel URL, a JSON content type, a **secret**, and only the **push** event. GitHub sends a ping. When the author pushes a commit, the receiver logs one `POST` with the event name in a header, a delivery ID, a signature, and the response it returned (**`202`**). GitHub also keeps its own copy of every attempt under **Recent deliveries** (headers, payload, and your response).

### 3.3 Anatomy of a delivery

| Part | Example (GitHub) | Purpose |
|---|---|---|
| Method and URL | `POST /hooks/github` | The endpoint you exposed |
| `Content-Type` | `application/json` | Body format |
| Event type header | `X-GitHub-Event` | Which kind of event |
| Delivery ID header | `X-GitHub-Delivery` | Unique ID for this event |
| Signature header | `X-Hub-Signature-256` | Proof of origin (section 5) |
| Body | Full event data as JSON | The payload |

### 3.4 How the provider decides success

Like any HTTP client, the provider relies on **status codes and time**:

- **Any `2xx`** (200, 202, ...) is a success. It doesn't matter which one.
- **Anything else** (3xx, 4xx, 5xx) is a **failure**.
- You must respond **within a time limit**, or it counts as a failure:

| Provider | Time limit |
|---|---|
| GitHub | **10 seconds** |
| Shopify | **5 seconds** |
| Slack | **3 seconds** |
| Microsoft Graph (Outlook APIs) | **3 seconds** |

**Always read each provider's documentation** for their limit and their retry behavior.

### 3.5 Registration: one URL per provider

A registration form usually asks for a **URL, a secret, and a list of event types**.

> **Advice:** give **each provider its own URL**: `/hooks/github`, `/hooks/stripe`. Never a generic `/hooks/callback`.

Each provider has its own headers, signature style, and retry behavior. Your handler has to account for all of that, so keep endpoints and handlers **separate per provider**.

### 3.6 Handshakes

Some providers add a **handshake** before sending real events: they send a request to your new URL and wait for a **specific answer**.

| Provider | Handshake |
|---|---|
| **Microsoft Graph** | Sends a **validation token**; you return it in **plain text** |
| **Discord** | Sends a **ping**; you reply **pong** |
| **Amazon SNS** | Sends a **subscription confirmation** message with a URL you must visit |

**Why?** A webhook system calls whatever URL it's given. Without a handshake, a malicious person could register a **victim's address** for every event type of a big provider (AWS, Stripe, GitHub) and make the provider flood the victim. That is a **DDoS attack** using the provider as a weapon. The handshake proves you control the URL.

## 4. The Threat: Anyone Can POST to a Public URL

Your endpoint is a **public URL**, and the data it receives can **unlock a user's paid plan**.

Webhook URLs follow predictable patterns (`/webhooks`, `/hooks`, `/callback`). So anyone who guesses yours can `POST` `{"payment": "succeeded", "user": 42}` and get a free plan. That's a serious security problem.

> **HTTPS doesn't solve this.** HTTPS stops people from reading or tampering with bytes **in transit**. It says nothing about **who wrote** the data.

You need a guaranteed way to know the request **really came from the provider**.

## 5. Five Ways to Prove a Delivery Is Genuine

| # | Method | How it works | Verdict |
|---|---|---|---|
| 1 | **Secret token in the URL** | A basic-auth-like secret in the URL itself | **Weakest.** URLs get logged in many places (local logs, CloudWatch, Elasticsearch), so the secret leaks into logs everywhere. |
| 2 | **IP allowlist** | Providers publish the IPs they send from (GitHub, Stripe, Polar, ...). Your firewall or cloud config allows **only those IPs**. | Better, but **not complete on its own** |
| 3 | **Mutual TLS** | The provider gives you a **client certificate** to use | Strong, less common |
| 4 | **HMAC signature (shared secret)** | A signature over the body, using a secret **only you and the provider know** | **The most common.** Roughly **65 to 80%** of providers use it. |
| 5 | **Public-key signature** | The provider signs with a **private key**; you verify with their **public key** | Used by **Discord** |

The rest of the video uses method 4.

### 5.1 HMAC explained

**HMAC** = **H**ash-based **M**essage **A**uthentication **C**ode.

Recall hashing: a function that turns any bytes into a **fixed-length fingerprint**, where **changing even one byte changes the whole fingerprint**.

**The flow:**

1. The provider computes `HMAC-SHA256(body, shared_secret)` and puts the result **in a header**.
2. You receive the request and compute the **same HMAC** over the **same body** with the **same secret**.
3. You **compare** the two. If they match, you know the sender had the secret, so it's your provider and the body wasn't altered.

```python
import hmac, hashlib

def verify_signature(secret: bytes, raw_body: bytes, header_sig: str) -> bool:
    expected = "sha256=" + hmac.new(secret, raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header_sig)   # constant-time (see 5.4)
```

The video looks at Stripe's Go SDK verification code. Stripe's header contains `t=<unix timestamp>` and one or more `v1=<signature>` values, and the SDK compares with `hmac.Equal`.

### 5.2 Exactly what gets signed differs by provider

Check each provider's docs for this:

| Provider / scheme | What is signed | Why |
|---|---|---|
| **GitHub** | The **body** only | Simple |
| **Stripe** | `timestamp + "." + body` | The timestamp is protected, which defends against **replays** (section 5.3) |
| **Standard Webhooks** | `delivery_id + "." + timestamp + "." + body` | The **ID** is protected too |
| **Twilio** | The **full endpoint URL plus form fields in sorted order**, with **SHA-1** | Ensures the exact URL also matches |

### 5.3 The raw-body trap

The signature is over **exact bytes**. Suppose your framework parses the JSON for you (for example `express.json` in Node.js), and you **re-encode** the object to a string and then compute the HMAC. If the provider wrote JSON with **no spaces** and your encoder adds a **space after every colon**, the bytes differ, so the HMAC differs, and **every verification fails**.

> **Rule: read the body as raw bytes → verify the bytes → only then parse.**

The video demonstrates three runs:

1. Correct secret, verify raw bytes → **`202`**.
2. Secret changed on GitHub's side, then redeliver → the signature no longer matches → receiver returns **`401`**, and GitHub records the 401.
3. Correct secret, but the receiver **parses and re-encodes before verifying** → verification **fails again**.

```python
def handle(request):
    raw = request.read_body()                       # bytes, untouched
    if not verify_signature(SECRET, raw, request.headers["X-Hub-Signature-256"]):
        return 401
    event = json.loads(raw)                         # parse AFTER verifying
    ...
```

### 5.4 Replay attacks

The HMAC proves *who* sent a delivery. A new problem is *when*.

Suppose an attacker (via a man-in-the-middle) captures **one real delivery** with valid headers and body. An hour later, or 1,000 times, they **send it again**. The signature is genuine (it's a copy), so your handler accepts it. That is a **replay attack**.

**Defense:** include a **timestamp inside the signed string**. It can't be changed without breaking the signature. Stripe does exactly this, and its library **rejects anything older than five minutes**.

### 5.5 Constant-time comparison

When comparing your computed signature to the header's, **don't use the language's ordinary equality**. A normal string comparison **stops at the first differing byte**, so it returns slightly faster when the mismatch comes early. An attacker who can measure that tiny timing difference across thousands or millions of requests could **derive the signature byte by byte**.

Use a **constant-time comparison**, which takes the same time regardless of how different the strings are:

| Language | Function |
|---|---|
| Go | `hmac.Equal` |
| Node.js | `crypto.timingSafeEqual` |
| Python | `hmac.compare_digest` |

## 6. Provider-Side Danger: SSRF

There's another security issue, this time for **the provider** (Stripe, GitHub) and also for **you** when you build your own (section 9).

A provider **calls whatever URL the customer types in**, from the **provider's own network**. An attacker could register a URL like `http://169.254.169.254/...`, which on most cloud platforms is the **metadata service**, which can hand out **credentials** or reveal **internal admin services**. The provider's dispatcher dutifully `POST`s there. This is **Server-Side Request Forgery (SSRF)**.

**Just checking the URL at registration isn't enough**, because:

- The attacker's domain can resolve to a **public IP at registration**, then be switched to a **private IP** later.
- A public address can **redirect** to a private one.

**Proper defense:**

1. **Resolve the hostname yourself** and check the resulting address against a fixed list of **private ranges**.
2. **Never follow redirects.** Normally HTTP clients follow `301/302`; for webhooks that is a threat. Treat anything that isn't a `2xx` as a failure, which is why providers consider a `3xx` a failed delivery.
3. If you can, send webhooks from a **separate network through an egress proxy**. Stripe has an open-source one called **Smokescreen**.

```python
import ipaddress, socket

def safe_to_call(host: str) -> bool:
    for info in socket.getaddrinfo(host, None):
        ip = ipaddress.ip_address(info[4][0])
        if ip.is_private or ip.is_loopback or ip.is_link_local or ip.is_reserved:
            return False
    return True
# Then connect to that resolved IP, and set the HTTP client to NOT follow redirects.
```

## 7. "At Least Once": Idempotency and Ordering

Suppose the signature is fine. Now a different problem.

### 7.1 Duplicates

1. The provider `POST`s an event.
2. Your handler does its work (writes the database row) and answers **`200`**.
3. That `200` is **lost in the network** (a dropped connection, a restarted load balancer).
4. The provider never saw it, so as far as it knows the delivery **failed**, and it **retries** with the same payload.

So you receive the **same event again**, maybe seconds or minutes later, **in an unpredictable order**. That is why providers promise **at least once** delivery: the event **will** reach you and **won't be lost**, but it can arrive **more than once**. It is **never "exactly once"**.

### 7.2 The solution: idempotent receivers

Your receiver must be safe to call **many times with the same event**, producing the side effects **only once**. (This is the idempotency idea from the REST series.)

Every provider gives each event a **delivery/event ID that stays the same across retries**:

| Provider | Where the ID is |
|---|---|
| GitHub | `X-GitHub-Delivery` header |
| Stripe | The event `id` in the body |
| Standard Webhooks | `webhook-id` |

**Technique:**

- Keep a table of processed deliveries with the delivery ID as a **unique constraint**.
- **Insert the delivery ID in the same database transaction as the real work.**

**Why the same transaction matters:**

| Order | What can go wrong |
|---|---|
| Do the work, **then** store the ID | A crash between the two means the work is done but the ID wasn't saved. The retry looks new, so the work is done **twice**. |
| Store the ID, **then** do the work | If the work fails, the retry sees the ID and skips it, so the work **never happens**. |
| **Both in one transaction** | Either **both** happen or **neither**. |

```sql
BEGIN;
INSERT INTO processed_deliveries (delivery_id) VALUES ($1);   -- UNIQUE; fails on duplicate
UPDATE users SET plan = 'paid' WHERE id = $2;                 -- the actual work
COMMIT;
-- On unique-violation for delivery_id: the event was already handled → just return 200.
```

### 7.3 Ordering is not guaranteed

Retries also scramble order. An engineer who worked on Stripe's API wrote this up in **2017**. Example: one object produces two events, **created** then **deleted**.

- The `created` delivery fails once (say your server was deploying) and is retried **5 minutes later**.
- The `deleted` delivery is sent a second later and succeeds.

You receive **deleted first, then created**. If your handler trusts events at face value, you end up with a row for an object that **no longer exists**. Stripe's docs say events aren't delivered in order, and timestamps are in **seconds**, so two events within the same second can share a timestamp.

**Three solutions:**

1. **Treat the event as a signal only.** On receipt, **fetch the object's current state** from the provider's API and act on that. Order no longer matters, but it costs **one extra API call**.
2. **Version check.** Put a **version or `updated_at`** on your copy and **apply an event only if it's newer**, inside one transaction.
3. **Buffer.** Hold events for an object until the earlier ones arrive. This can cause trouble because arrival isn't predictable.

Some providers offer **strict ordering as a (paid) feature**.

## 8. Retries, and Surviving Load

### 8.1 Retry schedules differ per provider

When your endpoint fails, times out, or returns a non-2xx, providers retry. **The schedule is provider-specific**, so read the docs before integrating.

| Provider | Retry behavior |
|---|---|
| **Stripe** | **Exponential backoff for up to 3 days.** If still failing, it **disables your endpoint** and **emails you**. |
| **Svix** (a popular "webhooks as a service" provider, used so companies don't have to build all this) | Retries **immediately**, then after **5 s, 5 min, 30 min, 2 h, 5 h, 10 h**, and so on |
| **GitHub** | **Zero retries.** If your server was down, that delivery is gone. You must press **Redeliver** manually, or write a script that **lists failed deliveries through GitHub's API and redelivers them**. |
| Shopify, Slack, Polar, ... | Each has its own schedule |

(Svix exists because a full webhook system is a lot of engineering: security, retries, edge cases.)

### 8.2 Your own slowness becomes more load

Combine the timeouts (10 s, 5 s, 3 s) with the retries:

- Every delivery you fail to acknowledge in time becomes a **retry**, which **adds to your normal user traffic**.
- **Bursts** are common: a billing provider renews all subscriptions **on the 1st of the month**; a marketing tool emailing **half a million people** sends a delivery receipt per recipient.

If your handler does **everything inside the request** (verify, update two or three tables, call other APIs, respond), it will likely **miss the deadline**, and each miss creates another retry, which creates more load.

### 8.3 The thin receiver

Make the receiver do a **fixed, tiny set of steps**:

1. **Read** the body.
2. **Verify** the signature.
3. **Store** the delivery in a table.
4. **Respond `2xx` immediately.**
5. **Stop.**

Then a **background worker** (ideally fed by a **queue**, see the task-queue article) does the real processing asynchronously.

```
Provider ──POST──▶ [Receiver: read → verify → store delivery → 202]
                              │
                              ▼
                     Queue / deliveries table ──▶ Worker (idempotent processing)
```

## 9. Building Your Own Webhooks (the Sender)

Everything so far was **receiving**. Now you're the provider.

**Scenario:** in the task board app, every time a task moves, an event `task.moved` happens (with a sequence number, the task, who moved it, and when). A customer wants a signal whenever a task moves to **done**, so they can post it to a chat or run their own logic. They give you a **URL**, and you give them a **secret** (the way Stripe and GitHub gave you one).

### 9.1 The naive version and its three bugs

In the move handler, after saving the move, call `http.Post(customerURL, ...)`. This causes three problems:

| # | Problem |
|---|---|
| 1 | **Latency:** if the customer's endpoint is slow or down, **your** move handler waits on it, so their slowness becomes part of **your** response time to your own front end |
| 2 | **Lost event:** the move is saved, then your container **crashes or redeploys** before the `POST`. The move happened but **the customer was never told** |
| 3 | **False event:** you `POST` first, then your database write **fails** or your backend crashes. You told the customer a move happened that **never happened** in your database |

### 9.2 The solution: the Outbox pattern

An **outbox** is just **a normal table in your database** (the same database that holds everything else).

1. In the move handler, open **one transaction**: **update the task** *and* **insert an outbox row** containing the full event. Commit.
2. Because both are in **one transaction**, **either both happen or neither does**. That kills problems 2 and 3.
3. A **separate background process (the dispatcher)** reads outbox rows and does the actual delivery **asynchronously**. That kills problem 1: the move handler responds as fast as before.

This is the **write-ahead log** idea from the databases video, applied to events: **write your intention to somewhere durable first, then let another process carry it out.**

```sql
BEGIN;
UPDATE tasks SET status = 'done' WHERE id = $1;
INSERT INTO outbox (event_type, payload) VALUES ('task.moved', $2);
COMMIT;
```

### 9.3 The three tables

| Table | Holds |
|---|---|
| **endpoints** | The customer's URL and secret |
| **outbox** | The events waiting to be delivered |
| **deliveries** | **One row per attempt** |

### 9.4 What the dispatcher does for each delivery

1. **Sign** the body with the endpoint's secret, in the **Standard Webhooks** format (`id.timestamp.body`).
2. **`POST`** with a **10-second timeout**. There's no hard rule; choose per your service and promises, but 10 s is the common standard.
3. **Record the attempt:** status code, the **first 2 KB of the response**, and the time taken.
4. **`2xx` →** mark **delivered**. No more retries.
5. **Anything else →** compute the next retry using **exponential backoff plus jitter**, and respect any **`Retry-After`**.
6. After the **last attempt**, mark the event **exhausted**.
7. After **ten consecutive failures**, **disable the endpoint** and **email the owner**.
8. Use **one queue per endpoint**, so one customer's dead URL **doesn't stall everyone else's** deliveries.
9. Run the **SSRF guard** (resolve and check the address) **before every send**, not just at registration. A hostname that was public when registered can be repointed later.

### 9.5 Backoff and jitter

- **Exponential backoff:** instead of a fixed gap, the gap grows each attempt: e.g. 5 seconds, then 5 minutes, then 15 minutes, then 1 hour.
- **Jitter:** add a **random** amount to the computed delay. A retry planned for 5 minutes might fire at 5 min 42 s. With a thousand retries scheduled together, jitter **spreads them out** so they don't all hit at the same instant.
- **`Retry-After`:** if the receiver sends it ("I'm having trouble, try again in an hour or six"), honor it instead of your own schedule.

```python
import random

def next_delay(attempt: int, retry_after: int | None = None) -> float:
    if retry_after:
        return retry_after                              # the receiver asked for this
    base = min(5 * (3 ** attempt), 6 * 3600)            # 5s, 15s, 45s, ... capped at 6h
    return base + random.uniform(0, base * 0.2)         # jitter
```

### 9.6 The demo results

- Move a task → the **outbox row exists before anything is sent**.
- The customer's endpoint answers **500** → attempt 1 fails, and the deliveries table already shows **when the next attempt is due**. The delays **grow** with each attempt (backoff plus jitter).
- Fix the customer's endpoint → the next attempt gets **`200`** → marked **delivered**, no more retries.
- Try registering the app's **own admin route on the loopback address** as a webhook URL → **refused, with a reason**. A hostname that resolves to a **private address** is refused the same way, and the check runs **on every send**.

## 10. When a Webhook Is the Wrong Tool

A webhook is fundamentally a **notification**: "this thing happened, here's its data".

**Webhooks are the right tool when used as notifications:**

- When this event happens, **post to a chat or channel**.
- When this event happens, **start a CI/CD pipeline** (for example a GitHub Actions build).
- When a payment succeeds, **unlock this plan for this user**.

### 10.1 The wrong use: syncing a copy of the provider's data

The notorious case (from the author's own experience) is **Clerk**, an authentication and authorization provider. Instead of building email/password, "Sign in with Google/GitHub", email flows, session lists, and device sign-out yourself, you use Clerk's SDKs. The catch: **your users, organizations, roles, and permissions live in Clerk's database**.

For speed you want a **copy in your own database** (a users table, an organizations table, a roles/permissions table). Reading from your own database in the same region might take **50 to 60 ms**, while repeated calls to Clerk's API add up to **500 to 600 ms**.

The common solution is to sync that copy with **webhooks**: subscribe to `user.created/updated/deleted`, `organization.*`, `role.*`, and write to your tables.

**That's fine in principle. The way it's usually done is the problem.** You immediately inherit every webhook edge case: **timeouts, replays, duplicates, out-of-order events**. Your copy only stays valid if you solve all of them.

### 10.2 The robust approach: use the provider's event log

Providers (Clerk included) keep a **log of events**, available through an API (something like a `/events` endpoint) and a dashboard. That log is **guaranteed to be ordered**, because it's written inside the provider's own infrastructure. The ordering problem only appears with distributed network calls.

**Strategy 1: poll the log (when slightly stale data is OK).**

- Every **5 minutes**, a background worker fetches events from the provider's events API.
- It applies the inserts, updates, and deletes to your copy.
- It **stores the last processed event ID**, so the next run starts from where it left off instead of redoing everything.

**Strategy 2: webhook as a nudge (when you need near-real-time).**

- Subscribe to a webhook that fires **whenever the provider adds an entry to its event log**.
- When it arrives, **start a background process immediately**. Starting from your stored **last event ID**, fetch **all events since then**, in order, and apply them.
- Example: a user changes their name in the front end through Clerk's SDK (your backend never sees it). Clerk updates the name and appends an event to its log in one transaction. Because you subscribed, it also pings your webhook. Your worker fetches the new `user name updated` event and updates your database. Within milliseconds to seconds, both copies are in sync.

The webhook is only a **"go look at the log" signal**, not the data source. You no longer depend on its order, its uniqueness, or its delivery guarantees, because the ordered log is the source of truth.

## 11. Cheat Sheet

**Why webhooks:** polling wastes requests, adds delay, and overloads providers. Webhooks flip it: the provider `POST`s to your URL when something happens.

**Receiver checklist**

| Step | Rule |
|---|---|
| Endpoint | **One URL per provider** (`/hooks/github`, `/hooks/stripe`) |
| Body | Read **raw bytes** first; **verify, then parse** |
| Verify | **HMAC** with the shared secret; **constant-time compare** |
| Replay defense | **Timestamp inside the signed string**; reject old ones (Stripe: > 5 min) |
| Respond | **`2xx` fast** (GitHub 10 s, Shopify 5 s, Slack/MS Graph 3 s) |
| Duplicates | Store the **delivery ID** (unique) **in the same transaction** as the work |
| Ordering | Fetch **current state**, or compare **version/`updated_at`** |
| Heavy work | **Queue it** to a background worker |
| Local dev | Use a **tunnel** (ngrok, Cloudflare Tunnel) |

**Five proof-of-origin methods:** secret in URL (weakest), IP allowlist, mutual TLS, **HMAC (most common)**, public-key signature (Discord).

**Delivery guarantee:** **at least once**, never exactly once, and unordered.

**Sender checklist**

| Concern | Solution |
|---|---|
| Slow customer endpoint | **Outbox** plus a background dispatcher |
| Crash between save and send | Outbox row in the **same transaction** |
| Retries | Exponential backoff **plus jitter**, honor `Retry-After`, disable after repeated failures |
| One bad endpoint | **Queue per endpoint** |
| SSRF | Resolve, check private ranges, **no redirects**, **check on every send**, consider an egress proxy |
| Signing | **Standard Webhooks** format: `id.timestamp.body` |

**Rule of thumb:** webhooks are **notifications**. To keep a **copy** of someone's data in sync, use the **event log** and use webhooks only as the nudge.
