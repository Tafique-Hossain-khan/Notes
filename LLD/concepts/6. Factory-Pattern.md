# Factory Design Pattern: A Hands-On Python Guide

---

## Why Factory Pattern?

When learning the Strategy Pattern, we extracted varying behavior into separate strategy classes:

```text
NotificationStrategy
├── EmailNotification
├── SMSNotification
└── SlackNotification
```

The `NotificationService` no longer needed `if/else` statements to decide *how* to send a notification. It simply delegated the work to whichever strategy it was given.

However, a new question appears:

> Who creates the strategy object?

Without a Factory, the creation logic is usually scattered throughout the application:

```python
if provider == "openai":
    strategy = OpenAIProvider()
elif provider == "gemini":
    strategy = GeminiProvider()
elif provider == "claude":
    strategy = ClaudeProvider()

ai_service = AIService(strategy)
```

Notice that the Strategy Pattern solved the problem of **behavior selection**, but we still have the problem of **object creation**.

The Factory Design Pattern addresses this second concern.

A Factory centralizes all object creation logic into a dedicated class:

```python
provider = AIProviderFactory.create("openai")
ai_service = AIService(provider)
```

Now the client code doesn't know:

- Which concrete class is being instantiated
- How the object is configured
- What dependencies are required to create it

It simply asks for an object and receives one.

### The Real Goal

The Factory Pattern is **not about eliminating `if/else` statements**. In fact, a simple factory often contains those conditionals internally.

The goal is to move object creation decisions into a single location instead of scattering them across the codebase.

Without Factory:

```text
Business Logic
    ├── creates OpenAIProvider
    ├── creates GeminiProvider
    └── creates ClaudeProvider
```

With Factory:

```text
Business Logic
        │
        ▼
   Factory
        │
        ▼
Concrete Object
```

This separation gives us two independent responsibilities:

### Strategy Pattern

Responsible for:

```text
How should the work be performed?
```

Examples:

- Email vs SMS notifications
- OpenAI vs Gemini responses
- Percentage vs Flat discounts

### Factory Pattern

Responsible for:

```text
Which concrete object should be created?
```

Examples:

- Create `OpenAIProvider`
- Create `GeminiProvider`
- Create `EmailNotification`
- Create `SMSNotification`

### Strategy + Factory Together

In real applications these patterns are commonly used together:

```text
Configuration/User Input
            │
            ▼
         Factory
            │
            ▼
Creates Strategy
            │
            ▼
         Context
            │
            ▼
     Executes Behavior
```

Example:

```text
"gemini"
    │
    ▼
AIProviderFactory
    │
    ▼
GeminiProvider()
    │
    ▼
AIService
    │
    ▼
generate_response()
```

The Strategy Pattern decouples behavior.

The Factory Pattern decouples object creation.

Both patterns exist for the same overarching reason:

> Separate responsibilities so that changes in one part of the system have minimal impact on the rest of the codebase.

There are three forms of this pattern, each an extension of the previous:

1. Simple Factory
2. Factory Method
3. Abstract Factory

## 1. Simple Factory

### The Idea

A single class contains the object-creation logic. It receives a *type* parameter and returns the appropriate concrete object.

### Example: Burger Shop

Say a burger shop sells three kinds of burgers: Basic, Standard, and Premium. Each burger knows how to prepare itself.

```python
from abc import ABC, abstractmethod

# Abstract Product
class Burger(ABC):
    @abstractmethod
    def prepare(self):
        pass

# Concrete Products
class BasicBurger(Burger):
    def prepare(self):
        print("Preparing Basic Burger with one patty and ketchup")

class StandardBurger(Burger):
    def prepare(self):
        print("Preparing Standard Burger with one patty, cheese, and lettuce")

class PremiumBurger(Burger):
    def prepare(self):
        print("Preparing Premium Burger with gourmet bun and wagyu patty")
```

Now the factory:

```python
# Simple Factory
class BurgerFactory:
    def create_burger(self, burger_type: str) -> Burger:
        if burger_type == "basic":
            return BasicBurger()
        elif burger_type == "standard":
            return StandardBurger()
        elif burger_type == "premium":
            return PremiumBurger()
        else:
            raise ValueError(f"Invalid burger type: {burger_type}")
```

Client code:

```python
factory = BurgerFactory()
burger = factory.create_burger("standard")
burger.prepare()
# Preparing Standard Burger with one patty, cheese, and lettuce
```

The client has no `new`/constructor calls. It just asks the factory and gets back a `Burger`.

### Definition

> A factory class that decides which concrete class to instantiate, depending on a given type.

> **Note:** Simple Factory is not formally a design pattern — it's a design principle. Factory Method and Abstract Factory are the proper patterns.

## 2. Factory Method

### The Idea

Simple Factory uses one concrete factory for all products. Factory Method asks: what if the *factory itself* should be abstract?

Make the factory an abstract class with a `create_*` method that subclasses override. Each subclass (concrete factory) decides which specific product to create.

This gives you the same abstraction layer on the factory side that you already have on the product side.

### Example: Two Burger Franchises

The same burger shop now has two franchises:

- **SinghBurger** — makes normal burgers (Basic, Standard, Premium)
- **KingBurger** — makes wheat-based burgers (Basic Wheat, Standard Wheat, Premium Wheat)

```python
from abc import ABC, abstractmethod

# Abstract Product
class Burger(ABC):
    @abstractmethod
    def prepare(self):
        pass

# Concrete Products — Normal
class BasicBurger(Burger):
    def prepare(self):
        print("Preparing Basic Burger with one patty and ketchup")

class StandardBurger(Burger):
    def prepare(self):
        print("Preparing Standard Burger with one patty, cheese, and lettuce")

class PremiumBurger(Burger):
    def prepare(self):
        print("Preparing Premium Burger with gourmet bun and wagyu patty")

# Concrete Products — Wheat
class BasicWheatBurger(Burger):
    def prepare(self):
        print("Preparing Basic Wheat Burger with bun, patty, and ketchup")

class StandardWheatBurger(Burger):
    def prepare(self):
        print("Preparing Standard Wheat Burger with cheese and veggies")

class PremiumWheatBurger(Burger):
    def prepare(self):
        print("Preparing Premium Wheat Burger with gourmet wheat bun")
```

Abstract factory and its concrete subclasses:

```python
# Abstract Factory
class BurgerFactory(ABC):
    @abstractmethod
    def create_burger(self, burger_type: str) -> Burger:
        pass

# Concrete Factory 1
class SinghBurger(BurgerFactory):
    def create_burger(self, burger_type: str) -> Burger:
        if burger_type == "basic":
            return BasicBurger()
        elif burger_type == "standard":
            return StandardBurger()
        elif burger_type == "premium":
            return PremiumBurger()
        else:
            raise ValueError(f"Invalid type: {burger_type}")

# Concrete Factory 2
class KingBurger(BurgerFactory):
    def create_burger(self, burger_type: str) -> Burger:
        if burger_type == "basic":
            return BasicWheatBurger()
        elif burger_type == "standard":
            return StandardWheatBurger()
        elif burger_type == "premium":
            return PremiumWheatBurger()
        else:
            raise ValueError(f"Invalid type: {burger_type}")
```

Client code:

```python
factory: BurgerFactory = KingBurger()
burger = factory.create_burger("basic")
burger.prepare()
# Preparing Basic Wheat Burger with bun, patty, and ketchup

factory = SinghBurger()
burger = factory.create_burger("basic")
burger.prepare()
# Preparing Basic Burger with one patty and ketchup
```

The client only interacts with `BurgerFactory`. Swapping `KingBurger` for `SinghBurger` changes the entire product family without touching anything else.

### Definition

> Define an interface for creating an object, but let subclasses decide which class to instantiate.

## 3. Abstract Factory

### The Idea

Factory Method handles one product family. Abstract Factory extends this: a single factory is responsible for creating *multiple related products*.

If each franchise now makes both burgers *and* garlic bread, the factory needs two creation methods. One concrete factory produces a consistent family: e.g., KingBurger makes wheat burgers *and* wheat garlic bread.

### Example: Franchise Makes Two Products

```python
from abc import ABC, abstractmethod

# Product Family 1: Burger (same as before, abbreviated)
class Burger(ABC):
    @abstractmethod
    def prepare(self): pass

class BasicBurger(Burger):
    def prepare(self): print("Preparing Basic Burger")

class BasicWheatBurger(Burger):
    def prepare(self): print("Preparing Basic Wheat Burger")

# Product Family 2: Garlic Bread
class GarlicBread(ABC):
    @abstractmethod
    def prepare(self): pass

class BasicGarlicBread(GarlicBread):
    def prepare(self): print("Preparing Basic Garlic Bread")

class CheeseGarlicBread(GarlicBread):
    def prepare(self): print("Preparing Cheese Garlic Bread with extra cheese")

class BasicWheatGarlicBread(GarlicBread):
    def prepare(self): print("Preparing Basic Wheat Garlic Bread")

class CheeseWheatGarlicBread(GarlicBread):
    def prepare(self): print("Preparing Cheese Wheat Garlic Bread with extra cheese")
```

Abstract factory now declares methods for *both* products:

```python
# Abstract Factory
class MealFactory(ABC):
    @abstractmethod
    def create_burger(self, burger_type: str) -> Burger:
        pass

    @abstractmethod
    def create_garlic_bread(self, bread_type: str) -> GarlicBread:
        pass

# Concrete Factory 1 — Normal products
class SinghBurger(MealFactory):
    def create_burger(self, burger_type: str) -> Burger:
        if burger_type == "basic":
            return BasicBurger()
        raise ValueError(f"Invalid type: {burger_type}")

    def create_garlic_bread(self, bread_type: str) -> GarlicBread:
        if bread_type == "basic":
            return BasicGarlicBread()
        elif bread_type == "cheese":
            return CheeseGarlicBread()
        raise ValueError(f"Invalid type: {bread_type}")

# Concrete Factory 2 — Wheat products
class KingBurger(MealFactory):
    def create_burger(self, burger_type: str) -> Burger:
        if burger_type == "basic":
            return BasicWheatBurger()
        raise ValueError(f"Invalid type: {burger_type}")

    def create_garlic_bread(self, bread_type: str) -> GarlicBread:
        if bread_type == "basic":
            return BasicWheatGarlicBread()
        elif bread_type == "cheese":
            return CheeseWheatGarlicBread()
        raise ValueError(f"Invalid type: {bread_type}")
```

Client code:

```python
factory: MealFactory = KingBurger()

burger = factory.create_burger("basic")
bread = factory.create_garlic_bread("cheese")

burger.prepare()
# Preparing Basic Wheat Burger

bread.prepare()
# Preparing Cheese Wheat Garlic Bread with extra cheese
```

Switch to `SinghBurger()` and both products switch to their normal variants — zero other changes.

### Definition

> Provides an interface for creating families of related objects without specifying their concrete classes.

## Factory vs Strategy — When to Use Which

Both patterns can sometimes solve the same problem (a notification system, for instance, can be built with either). The distinction is in *intent*:

Use **Strategy** when you want to vary an algorithm at runtime. You assume the objects already exist and you're choosing between behaviors.

Use **Factory** when you want to separate object creation logic from business logic. You're deciding *how and when* objects get built, not just which behavior to invoke.

Neither is universally correct. In an interview, the stronger answer is demonstrating you understand both and can articulate the trade-off for your specific scenario.
