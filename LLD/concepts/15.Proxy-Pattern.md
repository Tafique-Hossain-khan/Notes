# Proxy Design Pattern

## What is the Proxy Pattern?

Imagine you have a **User** and a **Resource**. The User wants to send a request to the Resource and get a reply. Simple.

Now, what if we do not want the User to talk directly to the Resource? We introduce a third object in between — the **Proxy**. The Proxy is the representative of the Resource.

Here is what the flow looks like:

```
User  →  request  →  Proxy  →  request  →  Resource
User  ←  reply   ←  Proxy  ←  reply   ←  Resource
```

The User never talks to the Resource directly. Every request goes through the Proxy first. The Proxy then validates or processes the request in some way, and forwards it to the Resource.

The critical point: **the User cannot differentiate between talking to a Proxy and talking to the real Resource.** The Proxy behaves exactly like the Resource. The User just sends a request expecting a reply — it does not need to know or care whether it is talking to a Proxy or the real object.

Why do we introduce a Proxy in between? There are several reasons:

- The Resource may hold **critical data** — the Proxy first authenticates the User before allowing access to the Resource. If the User is not authenticated, the Proxy rejects the request right there without ever touching the Resource.
- The Proxy may apply **additional validations** before forwarding the request — checking for false data, malformed input, and so on.
- The Resource may **exist on a remote server** over the internet — the local application cannot call it directly. The Proxy is a local object that establishes the internet connection to the remote server, makes the call, and returns the reply. The User just thinks it called a local object.

---

## Types of Proxy

There are three types of proxies:

1. **Virtual Proxy** — protects an expensive resource from being created until it is actually needed
2. **Protection Proxy** — protects a critical resource by authenticating/authorising the caller first
3. **Remote Proxy** — acts as a local representative for a resource that exists on a remote server

The core concept is identical in all three. A Proxy has:
- An **is-a** relationship with the interface/abstract class (so it behaves like the real object)
- A **has-a** relationship with the real resource (so it can delegate calls to it)

The UML diagram is the same for all three. Only the **intent** differs.

## The Standard UML Diagram

```
┌──────────────────────────────────────────────┐
│           <<interface / abstract>>           │
│                 ISubject                     │
├──────────────────────────────────────────────┤
│ + operation()                                │
└──────────────────────────────────────────────┘
              △                  △
              │ (inherits)       │ (inherits)
              │                  │
┌─────────────────────┐  ┌───────────────────────────┐
│     RealSubject     │  │         Proxy             │
├─────────────────────┤  ├───────────────────────────┤
│ + operation()       │  │ - real: RealSubject        │
└─────────────────────┘  ├───────────────────────────┤
                         │ + operation()              │
                         │   (validates, then calls   │
                         │    real.operation())        │
                         └───────────────────────────┘

┌──────────────────────────────────────────────┐
│                  Client                      │
├──────────────────────────────────────────────┤
│ - ref: ISubject   ← always pass Proxy here   │
│ + calls ref.operation()                      │
└──────────────────────────────────────────────┘
```

- `Client` holds a reference to `ISubject`.
- We always pass a `Proxy` instance into that reference — never the `RealSubject` directly.
- `Proxy` inherits from `ISubject` (is-a) AND holds a reference to `RealSubject` (has-a).
- When `Client` calls `operation()`, it calls `Proxy.operation()`, which decides how/when to call `RealSubject.operation()`.

## Type 1: Virtual Proxy

### The Problem

You have an `ImageDisplayer` class. When you create an instance of it, the constructor performs a series of **expensive operations**:

1. Load the image from disk
2. Apply a compression algorithm (image might be large)
3. Apply filters

This is done in the constructor so that when you call `display()` later, the image shows up instantly. That sounds smart — but here is the problem.

What if the client creates an `ImageDisplayer` object but **never calls `display()`**? All those expensive operations happened for nothing. Memory was used, CPU was spent, and the image was never shown.

In a large application where you create many such objects, this wastes a significant amount of resources.

You cannot just move the expensive work into `display()` either, because you may not have access to the third-party `ImageDisplayer` class — it is a library you cannot modify.

**Solution: introduce a Virtual Proxy.**

### UML for Virtual Proxy

```
┌──────────────────────────────────────────────┐
│           <<abstract>>                       │
│              IDisplay                        │
├──────────────────────────────────────────────┤
│ + display()                                  │
└──────────────────────────────────────────────┘
         △                        △
         │ (inherits)             │ (inherits)
         │                        │
┌─────────────────────┐  ┌─────────────────────────────┐
│   ImageDisplayer    │  │       ImageProxy             │
├─────────────────────┤  ├─────────────────────────────┤
│ - path: str         │  │ - _real: ImageDisplayer|None │
│                     │  │ - _path: str                 │
│ Constructor:        │  │                              │
│  loads image        │  │ Constructor:                 │
│  compresses image   │  │  sets _real = None (cheap!)  │
│  applies filters    │  │                              │
│  (expensive!)       │  │ + display():                 │
│                     │  │   if _real is None:          │
│ + display()         │  │     _real = ImageDisplayer() │
│   (shows image)     │  │   _real.display()            │
└─────────────────────┘  └─────────────────────────────┘

┌─────────────────────────────────────────────┐
│                  Client                     │
├─────────────────────────────────────────────┤
│ - ref: IDisplay  ← always pass ImageProxy  │
│ + ref.display()                             │
└─────────────────────────────────────────────┘
```

### How It Works

- `ImageProxy` constructor does **nothing expensive** — it just sets `_real = None`.
- The expensive operation (creating the real `ImageDisplayer`) is **deferred** until someone actually calls `display()`.
- This is called **lazy loading** — postpone the heavy work for as long as possible.
- Once the real object is created (on first `display()` call), subsequent calls to `display()` use the already-created object. The expensive work only happens once.

The trade-off: the first call to `display()` will be a little slower. But you save resources for all the cases where `display()` is never called at all.

### Python Implementation

```python
from abc import ABC, abstractmethod


class IDisplay(ABC):
    @abstractmethod
    def display(self):
        pass


class ImageDisplayer(IDisplay):
    """The real, expensive object."""

    def __init__(self, path: str):
        self._path = path
        # Expensive operations happen here in the constructor
        self._load_image()
        self._compress_image()
        self._apply_filters()

    def _load_image(self):
        print(f"[Expensive] Loading image from disk: {self._path}")

    def _compress_image(self):
        print(f"[Expensive] Applying compression algorithm to: {self._path}")

    def _apply_filters(self):
        print(f"[Expensive] Applying filters to: {self._path}")

    def display(self):
        print(f"[ImageDisplayer] Displaying image: {self._path}")


class ImageProxy(IDisplay):
    """
    Virtual Proxy for ImageDisplayer.
    Defers the expensive constructor call until display() is actually called.
    """

    def __init__(self, path: str):
        self._path = path
        self._real: ImageDisplayer | None = None  # No expensive work yet
        print(f"[ImageProxy] Proxy created for: {self._path} (no loading yet)")

    def display(self):
        # Lazy loading: create the real object only when needed
        if self._real is None:
            print("[ImageProxy] First display() call — creating real object now")
            self._real = ImageDisplayer(self._path)
        self._real.display()


# Client
class Client:
    def __init__(self, displayer: IDisplay):
        self._displayer = displayer

    def show(self):
        self._displayer.display()


if __name__ == "__main__":
    print("=== Creating proxy (no expensive work yet) ===")
    proxy = ImageProxy("photo.jpg")

    print()
    print("=== Client calls display() for the first time ===")
    client = Client(proxy)
    client.show()

    print()
    print("=== Client calls display() again (real object already exists) ===")
    client.show()

    print()
    print("=== Proxy created but display() never called ===")
    unused_proxy = ImageProxy("unused_photo.jpg")
    print("(No expensive operations happened — memory saved)")
```

**Expected Output:**

```
=== Creating proxy (no expensive work yet) ===
[ImageProxy] Proxy created for: photo.jpg (no loading yet)

=== Client calls display() for the first time ===
[ImageProxy] First display() call — creating real object now
[Expensive] Loading image from disk: photo.jpg
[Expensive] Applying compression algorithm to: photo.jpg
[Expensive] Applying filters to: photo.jpg
[ImageDisplayer] Displaying image: photo.jpg

=== Client calls display() again (real object already exists) ===
[ImageDisplayer] Displaying image: photo.jpg

=== Proxy created but display() never called ===
[ImageProxy] Proxy created for: unused_photo.jpg (no loading yet)
(No expensive operations happened — memory saved)
```

**Summary of Virtual Proxy:** Protects an expensive resource by not creating it until a method on it is actually called. The proxy holds `None` until that moment.

## Type 2: Protection Proxy

### The Problem

You have a `RealDocumentReader` class with a method `unlock_pdf(file_path, password)`. It connects to a file, takes a password, and unlocks the PDF.

Now you have a premium feature: only users who have paid (premium users) should be able to unlock PDFs. You need to protect access to `RealDocumentReader` so that non-premium users are blocked.

You also have a `User` class with a `name` and a boolean `is_premium`.

**Solution: introduce a Protection Proxy.**

The proxy holds a reference to the real reader AND a reference to the current `User`. When `unlock_pdf()` is called on the proxy, it first checks `user.is_premium`. If true, it forwards the call to the real reader. If false, it blocks the request.

### UML for Protection Proxy

```
┌────────────────────────────────────────────────────┐
│              <<abstract>>                          │
│             IDocumentReader                        │
├────────────────────────────────────────────────────┤
│ + unlock_pdf(file_path: str, password: str)        │
└────────────────────────────────────────────────────┘
           △                          △
           │ (inherits)               │ (inherits)
           │                          │
┌──────────────────────┐   ┌────────────────────────────────────┐
│  RealDocumentReader  │   │     DocumentReaderProxy            │
├──────────────────────┤   ├────────────────────────────────────┤
│ + unlock_pdf(        │   │ - _real: RealDocumentReader        │
│     file_path,       │   │ - _user: User                      │
│     password)        │   ├────────────────────────────────────┤
└──────────────────────┘   │ + unlock_pdf(file_path, password): │
                           │   if user.is_premium:              │
                           │     real.unlock_pdf(...)           │
                           │   else:                            │
                           │     raise PermissionError          │
                           └────────────────────────────────────┘

┌──────────────────────────────────────┐
│               User                   │
├──────────────────────────────────────┤
│ - name: str                          │
│ - is_premium: bool                   │
└──────────────────────────────────────┘

┌──────────────────────────────────────────────────────┐
│                     Client                           │
├──────────────────────────────────────────────────────┤
│ - reader: IDocumentReader  ← always pass Proxy here  │
│ - user: User                                         │
│ + reader.unlock_pdf(file, password)                  │
└──────────────────────────────────────────────────────┘
```

### Python Implementation

```python
from abc import ABC, abstractmethod


class User:
    def __init__(self, name: str, is_premium: bool):
        self.name = name
        self.is_premium = is_premium


class IDocumentReader(ABC):
    @abstractmethod
    def unlock_pdf(self, file_path: str, password: str):
        pass


class RealDocumentReader(IDocumentReader):
    """The real resource — unlocks the PDF."""

    def unlock_pdf(self, file_path: str, password: str):
        print(f"[RealDocumentReader] Unlocking '{file_path}' with provided password")
        print(f"[RealDocumentReader] PDF unlocked successfully!")


class DocumentReaderProxy(IDocumentReader):
    """
    Protection Proxy for RealDocumentReader.
    Only allows premium users to unlock PDFs.
    """

    def __init__(self, user: User):
        self._user = user
        self._real = RealDocumentReader()

    def unlock_pdf(self, file_path: str, password: str):
        if self._user.is_premium:
            print(f"[Proxy] User '{self._user.name}' is premium — allowing access")
            self._real.unlock_pdf(file_path, password)
        else:
            raise PermissionError(
                f"[Proxy] Access denied for '{self._user.name}' — "
                f"this feature is for premium users only"
            )


# Client
class Client:
    def __init__(self, reader: IDocumentReader):
        self._reader = reader

    def open_pdf(self, file_path: str, password: str):
        self._reader.unlock_pdf(file_path, password)


if __name__ == "__main__":
    premium_user = User(name="Alice", is_premium=True)
    free_user = User(name="Bob", is_premium=False)

    print("=== Premium user tries to unlock PDF ===")
    proxy = DocumentReaderProxy(user=premium_user)
    client = Client(proxy)
    client.open_pdf("report.pdf", "secret123")

    print()
    print("=== Free user tries to unlock PDF ===")
    proxy2 = DocumentReaderProxy(user=free_user)
    client2 = Client(proxy2)
    try:
        client2.open_pdf("report.pdf", "secret123")
    except PermissionError as e:
        print(e)
```

**Expected Output:**

```
=== Premium user tries to unlock PDF ===
[Proxy] User 'Alice' is premium — allowing access
[RealDocumentReader] Unlocking 'report.pdf' with provided password
[RealDocumentReader] PDF unlocked successfully!

=== Free user tries to unlock PDF ===
[Proxy] Access denied for 'Bob' — this feature is for premium users only
```

**Summary of Protection Proxy:** Protects a critical resource by checking authorisation before forwarding any call to the real object.

## Type 3: Remote Proxy

### The Problem

You have a `DataService` class that fetches data from a database. But this `DataService` lives on a **remote server** — it does not exist locally in your application. To call it, you must:

1. Establish a network connection to the remote server
2. Send the request over the internet
3. Receive the reply

The Client should not have to know any of this. The Client just wants to call `fetch_data()` and get data back. It should not care about IP addresses, connection setup, or network calls.

**Solution: introduce a Remote Proxy.**

The Remote Proxy is a local object. When `fetch_data()` is called on it, it establishes the connection, makes the remote call, and returns the result. The Client thinks it is calling a local object.

You can also apply **lazy loading** here: establish the connection only when `fetch_data()` is first called, not in the constructor.

### UML for Remote Proxy

```
┌──────────────────────────────────────────────────┐
│               <<abstract>>                       │
│              IDataService                        │
├──────────────────────────────────────────────────┤
│ + fetch_data() -> str                            │
└──────────────────────────────────────────────────┘
           △                          △
           │ (inherits)               │ (inherits)
           │                          │
┌─────────────────────┐   ┌──────────────────────────────────────────┐
│    DataService      │   │          DataServiceProxy                 │
│  (on remote server) │   │          (local object)                  │
├─────────────────────┤   ├──────────────────────────────────────────┤
│ - db_connection     │   │ - _remote: DataService | None            │
│ + fetch_data()      │   │ - _server_ip: str                        │
└─────────────────────┘   ├──────────────────────────────────────────┤
                          │ + fetch_data():                           │
                          │   if _remote is None:                    │
                          │     establish connection to server        │
                          │     _remote = DataService(connection)    │
                          │   return _remote.fetch_data()            │
                          └──────────────────────────────────────────┘

┌──────────────────────────────────────────────────┐
│                   Client                         │
├──────────────────────────────────────────────────┤
│ - svc: IDataService  ← always pass Proxy here    │
│ + svc.fetch_data()                               │
└──────────────────────────────────────────────────┘

Real-world microservice picture:

  ┌─────────────────────────────────┐      ┌───────────────────────┐
  │         Server 1                │      │      Server 2          │
  │  ┌──────────┐  ┌────────────┐   │      │  ┌─────────────────┐  │
  │  │   Cart   │→ │  User      │ ──┼──────┼→ │  UserService    │  │
  │  │  Service │  │  Proxy     │   │ net  │  │  (real)         │  │
  │  └──────────┘  └────────────┘   │      │  └─────────────────┘  │
  └─────────────────────────────────┘      └───────────────────────┘
```

### Python Implementation

```python
from abc import ABC, abstractmethod
import time  # simulating network delay


class IDataService(ABC):
    @abstractmethod
    def fetch_data(self) -> str:
        pass


class DataService(IDataService):
    """
    The real service — lives on a remote server.
    Requires a connection to be established before use.
    """

    def __init__(self, server_ip: str):
        # This simulates the expensive network connection setup
        print(f"[DataService] Connecting to database at {server_ip}...")
        time.sleep(0.5)  # simulate connection time
        self._server_ip = server_ip
        print(f"[DataService] Connection established to {server_ip}")

    def fetch_data(self) -> str:
        print(f"[DataService] Fetching data from remote database at {self._server_ip}")
        return "{'user': 'Alice', 'orders': 42}"


class DataServiceProxy(IDataService):
    """
    Remote Proxy for DataService.
    Lazy loads the real DataService — connection established only on first fetch_data() call.
    Client does not need to know about server IPs or connection setup.
    """

    def __init__(self, server_ip: str):
        self._server_ip = server_ip
        self._remote: DataService | None = None
        print(f"[DataServiceProxy] Proxy created. No connection yet.")

    def fetch_data(self) -> str:
        # Lazy connection: only establish when actually needed
        if self._remote is None:
            print("[DataServiceProxy] First call — establishing connection now")
            self._remote = DataService(self._server_ip)
        return self._remote.fetch_data()


# Client
class Client:
    def __init__(self, service: IDataService):
        self._service = service

    def run(self):
        print("[Client] Requesting data...")
        result = self._service.fetch_data()
        print(f"[Client] Received: {result}")


if __name__ == "__main__":
    print("=== Proxy created (no connection yet) ===")
    proxy = DataServiceProxy(server_ip="192.168.1.10")

    print()
    print("=== First fetch_data() call ===")
    client = Client(proxy)
    client.run()

    print()
    print("=== Second fetch_data() call (connection already exists) ===")
    client.run()
```

**Expected Output:**

```
=== Proxy created (no connection yet) ===
[DataServiceProxy] Proxy created. No connection yet.

=== First fetch_data() call ===
[Client] Requesting data...
[DataServiceProxy] First call — establishing connection now
[DataService] Connecting to database at 192.168.1.10...
[DataService] Connection established to 192.168.1.10
[DataService] Fetching data from remote database at 192.168.1.10
[Client] Received: {'user': 'Alice', 'orders': 42}

=== Second fetch_data() call (connection already exists) ===
[Client] Requesting data...
[DataService] Fetching data from remote database at 192.168.1.10
[Client] Received: {'user': 'Alice', 'orders': 42}
```

**Summary of Remote Proxy:** Acts as a local representative for an object that exists on a remote server. Hides all connection and networking complexity from the Client.

## The Standard Definition

> The Proxy Pattern provides a **surrogate or placeholder** for another object to **control access** to it.

The job of the Proxy is simply to be the representative of the real object. Any request from any client that would go to the real object goes through the Proxy first. The Proxy then:
- Applies validations or authentication (Protection Proxy)
- Defers expensive creation (Virtual Proxy)
- Handles remote connection and communication (Remote Proxy)
- Or any combination of the above (a hybrid)

In all three cases, the Client cannot tell whether it is talking to the Proxy or the real object — and it does not need to.

---

## Real-World Use Cases

Any time you need to control access to an object, the Proxy pattern fits. Concretely:

- **Login / premium features** — a user must be logged in or have a paid subscription to access a feature → Protection Proxy
- **Microservice architecture** — `CartService` on Server 1 needs to call `UserService` on Server 2. `CartService` talks to a local `UserServiceProxy` which handles the network call transparently → Remote Proxy
- **Any heavy object** (image loaders, video players, document parsers) that should not be created until it is actually used → Virtual Proxy

If you see a requirement that says: "before calling this method, first check X" or "this object lives somewhere else on the network" or "don't create this object until someone actually needs it" — that is your signal to use the Proxy Pattern.
