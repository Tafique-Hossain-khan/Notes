# UML Diagrams: A Python Developer's Hands-On Guide

---

## What Are UML Diagrams?

Imagine you have an idea for an application in your head. You need to communicate that idea to another developer. You have two options: write long paragraphs describing every component, every object, every interaction — or draw a diagram.

The diagram wins. Every time.

UML (Unified Modeling Language) diagrams are exactly that — a standardized way to express your application's design visually. You show which components exist, what objects or entities are involved, and how they interact and connect with each other.

There are 14 UML diagrams in total, split into two categories:

**Structural (Static) Diagrams** — Show the structure of your application: which classes exist and how they are connected to each other.

**Behavioral (Dynamic) Diagrams** — Show how the components of your application interact: how objects send messages to each other and call each other's methods.

You only need to master two of these to handle virtually all LLD (Low Level Design) interviews and real-world design work:

1. **Class Diagram** — from the Structural category
2. **Sequence Diagram** — from the Behavioral category

The remaining 12 are highly use-case specific and rarely come up. Let's build both from the ground up.

---

## Part 1: Class Diagrams

A class diagram tells you two things:

- Which classes exist in your application
- How those classes are connected to each other

That's it. Master these two and you've mastered class diagrams.

---

### Representing a Class in UML

Every class is drawn as a rectangle divided into three sections:

```
┌─────────────────┐
│   ClassName     │  ← Section 1: Class name
├─────────────────┤
│  variable: type │  ← Section 2: Attributes (variables)
│  variable: type │
├─────────────────┤
│  method(): type │  ← Section 3: Methods (behaviors)
│  method(): type │
└─────────────────┘
```

If the class is **abstract**, you write `«abstract»` above the class name.

Let's take a `Car` class as an example. In Python it would look like:

```python
class Car:
    def __init__(self):
        self.brand: str = ""
        self.model: str = ""
        self.engine_cc: int = 0

    def start_engine(self) -> None:
        pass

    def stop_engine(self) -> None:
        pass

    def accelerate(self) -> None:
        pass

    def brake(self) -> None:
        pass
```

In UML, this becomes:

```
┌──────────────────────┐
│         Car          │
├──────────────────────┤
│ + brand   : str      │
│ + model   : str      │
│ + engine_cc: int     │
├──────────────────────┤
│ + start_engine(): void│
│ + stop_engine(): void │
│ + accelerate(): void  │
│ + brake(): void       │
└──────────────────────┘
```

Notice the symbols before each variable and method. These represent **access modifiers**:

| Symbol | Access Modifier | Accessible From |
|--------|----------------|-----------------|
| `+` | Public | Anywhere |
| `#` | Protected | Within class + child classes |
| `-` | Private | Within class only |

In Python, the convention maps as:

```python
class Car:
    def __init__(self):
        self.brand = ""        # + public
        self._model = ""       # # protected
        self.__engine_cc = 0   # - private
```

### Representing Associations Between Classes

When two classes are connected, that connection is called an **association**. There are two top-level types:

- **Class Association** → Inheritance
- **Object Association** → Composition (includes Simple Association, Aggregation, and Composition proper)

Let's go through each.

---

### Inheritance — The "Is-A" Relationship

Inheritance represents an "is-a" relationship. A child class inherits from a parent class.

- `Cow` **is an** `Animal`
- `Tiger` **is an** `Animal`
- `ManualCar` **is a** `Car`
- `ElectricCar` **is a** `Car`

In Python:

```python
class Animal:
    def eat(self) -> None:
        pass

class Cow(Animal):
    def moo(self) -> None:
        pass

class Tiger(Animal):
    def roar(self) -> None:
        pass
```

In UML, inheritance is shown with a **closed arrowhead** pointing from child to parent:

```
    Animal
      ▲
      │  (closed arrow = inheritance)
     Cow
```

The arrow always points toward the parent class.

### Composition — The "Has-A" Relationship

All three types below (Simple Association, Aggregation, Composition) represent a **"has-a" relationship**. They differ only in the strength of that relationship.

---

#### Simple Association

The **weakest** form. Two objects are related by a simple link, nothing more complex.

Example: Arjun lives in a house.
- `Arjun` **has a** `House` (or lives in one)
- If the House disappears, Arjun still exists. If Arjun leaves, the House still exists.

```python
class House:
    def __init__(self):
        self.address: str = ""

class Arjun:
    def __init__(self, house: House):
        self.house = house  # simple reference
```

In UML: drawn with an **open arrowhead**:

```
Arjun ──────────────> House
       (open arrow)
```

---

#### Aggregation

**Stronger** than simple association. One object acts as a **container** for other objects — but those contained objects can exist independently.

Example: A `Room` has a `Sofa`, `Bed`, and `Chair`.
- The sofa, bed, and chair are **part of** the room.
- But a `Chair` object can exist without a `Room` — it's independent.

```python
class Chair:
    pass

class Sofa:
    pass

class Bed:
    pass

class Room:
    def __init__(self, chair: Chair, sofa: Sofa, bed: Bed):
        self.chair = chair
        self.sofa = sofa
        self.bed = bed
```

In UML: drawn with an **open diamond** on the container side:

```
Chair ◇──────── Room
Sofa  ◇────────╱
Bed   ◇────────
```

The diamond sits at the "whole" (Room), arrows point from "parts" to "whole."

---

#### Composition (Proper)

The **strongest** form. The parts **cannot exist independently** of the whole.

Example: A `Chair` is composed of `Wheels`, `Arms`, and `Seat`.
- `Wheels`, `Arms`, `Seat` are **part of** the chair.
- They **cannot exist without** the chair — a detached chair arm is not a standalone object in any meaningful sense.

```python
class Wheels:
    pass

class Arms:
    pass

class Seat:
    pass

class Chair:
    def __init__(self):
        self.wheels = Wheels()   # created inside — cannot exist independently
        self.arms = Arms()
        self.seat = Seat()
```

In UML: drawn with a **filled (solid) diamond**:

```
Wheels ◆──────── Chair
Arms   ◆────────╱
Seat   ◆────────
```

---

### The Key Distinction

| Type | Relationship | Parts Independent? | UML Symbol |
|------|-------------|-------------------|------------|
| Simple Association | `Arjun` lives in `House` | Yes, completely | Open arrow `──>` |
| Aggregation | `Room` contains `Chair` | Yes | Open diamond `◇──` |
| Composition | `Chair` made of `Wheels` | No | Filled diamond `◆──` |
| Inheritance | `Cow` is an `Animal` | N/A (is-a) | Closed arrow `──▷` |

Programmatically in Python, all three "has-a" types look the same — you store a reference to another object inside a class. The distinction is conceptual, reflecting how you think about the real-world relationship.

```python
# All three look like this in code:
class B:
    def __init__(self):
        self.a = A()   # or passed in via __init__ parameter

    def do_something(self):
        self.a.method_one()   # calling A's method through the reference
```

## Part 2: Sequence Diagrams

While class diagrams show **structure**, sequence diagrams show **behavior** — specifically how objects communicate with each other over time.

A sequence diagram answers: "When object A calls object B, what exactly happens, in what order?"

---

### Components of a Sequence Diagram

**1. Objects/Actors**

Represented as labeled boxes at the top:

```
┌──────┐   ┌──────┐   ┌──────┐
│  A   │   │  B   │   │  C   │
└──────┘   └──────┘   └──────┘
```

Unlike class diagrams, you don't show attributes or methods here — just the object's name.

---

**2. Lifeline**

A dashed vertical line below each object showing how long that object exists during the application's runtime:

```
┌──────┐   ┌──────┐
│  A   │   │  B   │
└──┬───┘   └──┬───┘
   │           │
   │           │       ← lifelines (dashed vertical lines)
   │           │
```

If object C is created mid-flow (not at start), its lifeline starts later:

```
┌──────┐
│  A   │
└──┬───┘
   │
   │          ┌──────┐
   │          │  C   │   ← created mid-flow
   │          └──┬───┘
   │             │
```

---

**3. Activation Bar**

A solid rectangle on the lifeline showing when an object is **actively processing** (can send or receive messages):

```
   │           │
   ║           │        ← A is active (solid bar)
   ║           ║        ← both active
   │           ║
   │           │
```

When an object has no activation bar, it exists but is idle — it cannot send or receive messages.

---

**4. Messages**

Two types:

**Synchronous** — sender waits for a response before continuing. Drawn with a **closed arrowhead**. The response comes back as a **dashed line**:

```
   ║─────────────────>║   message()
   ║<- - - - - - - - -║   response
```

**Asynchronous** — sender fires and doesn't wait. Drawn with an **open arrowhead**. No response line needed:

```
   ║ - - - - - - - - >║   message()
   ║ - - - - - - - - >║   another_message()
```

---

**5. Create and Destroy Messages**

**Create** — one object spawns a new object mid-flow:

```
   ║──── create ──────>┌──────┐
                       │  New │
                       └──┬───┘
                          │
```

**Destroy** — an object's lifeline ends (marked with an X):

```
                          ║
   ║──── destroy ─────────X   ← object terminated
```

---

**6. Lost and Found Messages**

**Lost message** — sent but never received (shown with a dot/circle at the end):

```
   ║──── message ────── •   ← message lost, no receiver
```

**Found message** — received but the sender is unknown or no longer active:

```
   • ──── message ─────>║   ← source unknown or gone
```

---

### How to Draw a Sequence Diagram

Follow these three steps every time:

**Step 1 — Define the use case.** What specific flow are you modeling? (One diagram = one flow.)

**Step 2 — Identify the objects involved** in that flow.

**Step 3 — Draw the diagram**, adding lifelines, activation bars, and messages in order.

### ATM Withdrawal — Full Example

**Use Case:** User goes to ATM, enters account number and amount, gets cash.

**Objects involved:** `User`, `ATM`, `Transaction`, `Account`, `CashDispenser`

**Flow:**

1. `User` sends `withdraw(account_no, amount)` to `ATM`
2. `ATM` creates a new `Transaction` object
3. `Transaction` sends `check_amount(amount)` to `Account`
4. `Account` returns `True` (sufficient funds)
5. `Transaction` is destroyed (its job is done)
6. `ATM` sends `withdraw_cash(amount)` to `CashDispenser`
7. `CashDispenser` returns cash to `ATM`
8. `ATM` returns cash to `User`

Here is the sequence in Python-style pseudocode to see the actual calling structure:

```python
# This is what the sequence diagram represents as code

class Account:
    def check_amount(self, amount: float) -> bool:
        return self.balance >= amount

class Transaction:
    def __init__(self, account: Account):
        self.account = account

    def verify(self, amount: float) -> bool:
        return self.account.check_amount(amount)

class CashDispenser:
    def withdraw_cash(self, amount: float) -> float:
        # dispense cash
        return amount

class ATM:
    def __init__(self, account: Account, dispenser: CashDispenser):
        self.account = account
        self.dispenser = dispenser

    def withdraw(self, account_no: str, amount: float):
        # Step 2: Create transaction (CREATE message)
        txn = Transaction(self.account)

        # Step 3-4: Verify funds (synchronous message + response)
        if txn.verify(amount):
            # Transaction destroyed after this — job done

            # Step 6-7: Dispense cash (synchronous message)
            cash = self.dispenser.withdraw_cash(amount)

            # Step 8: Return to user
            return cash

        return None

# User interaction
user_account = Account()
dispenser = CashDispenser()
atm = ATM(user_account, dispenser)

cash = atm.withdraw("ACC123", 5000)  # User sends the initial message
```

**Diagram (text form):**

```
User        ATM         Transaction     Account     CashDispenser
 |           |               |              |              |
 |─withdraw─>|               |              |              |
 |           |──[create]────>|              |              |
 |           |               |──check_amt──>|              |
 |           |               |<─── True ────|              |
 |           |               X (destroyed)  |              |
 |           |──────────── withdraw_cash ──────────────────>|
 |           |<──────────── cash ──────────────────────────|
 |<─ cash ───|               |              |              |
```

---

### Additional Sequence Diagram Constructs

These appear less frequently but are good to know:

- **`alt`** — represents an `if/else` block. You show both the true branch and false branch within an `alt` frame.
- **`opt`** — represents a single `if` condition (no else).
- **`loop`** — represents a `for` or `while` loop, showing repeated interaction.

## Quick Reference

```
CLASS DIAGRAM SYMBOLS
─────────────────────────────────────────────
+ (plus)         →  public
# (hash)         →  protected
- (minus)        →  private

──▷  closed arrow     →  Inheritance (is-a)
──>  open arrow       →  Simple Association (has-a, weak)
◇──  open diamond     →  Aggregation (has-a, parts independent)
◆──  filled diamond   →  Composition (has-a, parts not independent)

SEQUENCE DIAGRAM SYMBOLS
─────────────────────────────────────────────
│         dashed vertical line  →  Lifeline
║         solid bar on lifeline →  Activation Bar
──>       closed arrow          →  Synchronous message
- ->      open arrow            →  Asynchronous message
<- - -    dashed return         →  Response
──>┌──┐   box creation          →  Create message
   X      X at end of lifeline  →  Destroy message
──>•      dot at end            →  Lost message
•──>      dot at start          →  Found message
```
